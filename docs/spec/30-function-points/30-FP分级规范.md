## 1. 目的与原则

功能点（FP）分级描述**"产品能做什么、每种情况会怎样"**，是回归测试与需求验收的对照源。

三条硬原则：

1. **黑盒视角、纯业务分类** —— 分类维度是用户可感知的业务域（窗口 / 文件树 / 对话 / 任务 / 错误处理 / 配置…），**与运行时模块无关**。不允许按 gui/server/gateway 这类组件维度切分。
2. **场景可穿透到代码分支** —— 每个场景须给出**穿透点**（代码文件 : 行、消息主题、分支条件），使黑盒用例可定位到实现，便于缺陷归因与回归定位。
3. **可测性显式声明** —— 每个功能点/场景标注可否自动验证、如何验证；不可测须说明理由与替代验证方式。

---

## 2. 三级结构

```text
分类 Category  ── 业务域（一级，扁平，见 §3）
  └─ 功能点 Function Point ── 域内一项可交付能力（二级）
       └─ 场景 Scenario ── 该功能点在某种具体情况下的行为（三级）
```

- **分类** = 名词（"文件树"），数量稳定，不随功能增减。
- **功能点** = 能力陈述（"拖拽移动文件/目录"），可勾选式验收。
- **场景** = 带条件的用例（"目标为文件时，移动到该文件所在目录"）。

## 4. ID 规范

| 层级 | 格式 | 示例 |
|------|------|------|
| 功能点 | `<分类码>-<3位序号>` | `FT-004`、`CHAT-012` |
| 场景 | `<功能点ID>-S<2位序号>` | `FT-004-S03` |
| 用例（测试侧） | `TC-<功能点ID>-<2位>` | `TC-FT-004-03` |

规则：

- 序号单调递增、**永不复用**；删除的功能点保留 ID 并标 🗄。
- 功能点 ID 一经分配即稳定，重命名只改"名称"不改 ID。
- 场景序号在同一功能点内连续；新增场景追加，不重排。

---

## 5. 功能点条目字段

每个功能点用如下结构描述（写入对应分类文档）：

| 字段 | 必填 | 说明 |
|------|:---:|------|
| **ID** | ✅ | 见 §4 |
| **名称** | ✅ | 能力陈述，动宾结构 |
| **说明** | ✅ | 一句话界定范围与边界（做什么、不做什么） |
| **入口 / 前置** | ✅ | 从哪触发、依赖什么状态 |
| **关联消息** | ○ | 涉及的 `域-动作` 主题（引用 61-消息一览） |
| **关联模块** | ○ | 反向引用模块篇（[20-modules/*](../20-modules/)），便于定位实现 |
| **状态** | ✅ | ✅ / ⚠️ / 🔵 / ⏳ / 🗄 |
| **可测性** | ✅ | 自动 / 半自动 / 手动 / 不可测（附理由） |

## 6. 场景条目字段

| 字段 | 必填 | 说明 |
|------|:---:|------|
| **ID** | ✅ | 见 §4 |
| **场景名** | ✅ | 描述"什么情况下会怎样" |
| **类型** | ✅ | 见 §7 情况清单 |
| **前置条件** | ✅ | 系统状态、配置、已有数据 |
| **操作步骤** | ✅ | 可复现的最短路径 |
| **预期结果** | ✅ | 可观测、可断言 |
| **异常/分支** | ○ | 非主路径的处理 |
| **穿透点** | ✅ | 代码文件:行 / 消息主题 / 分支条件（黑盒→白盒的桥） |
| **可测性 / 测试** | ✅ | 是否有自动化用例，编号 `TC-*` |

## 7. 情况清单（"各种情况"的系统枚举维度）

设计场景时按下列维度逐条自检，避免遗漏：

| 维度 | 典型情况 |
|------|---------|
| 正常路径 | 标准输入、标准前置下的预期行为 |
| 状态前置 | 无项目 / 无会话 / 未选 LLM / 空数据 / 初始化中 |
| 输入边界 | 空值、超长、特殊字符、非法路径、大小写改名 |
| 并发 | 多任务并行、多工具同轮、多窗口/多开、批量任务 |
| 取消与中断 | 用户取消、级联取消、停止按钮、删除运行中会话 |
| 失败与重试 | 工具失败、LLM 错误、可恢复/不可恢复、手动重试 |
| 恢复 | 应用重启、断链续写、崩溃后状态重建、遗留"运行中"清理 |
| 超时 | 响应超时、流式超时、ask_user 前端超时、工具超时 |
| 权限与安全 | 信任目录外、路径越界、沙箱拦截 |
| 展示态 | 主题 / 语言切换、面板显隐、尺寸越界归一 |

> 一个功能点通常覆盖多个维度；不必每维度都建场景，但**跳过须有理由**。

## 8. 与消息面、测试的映射

- **消息映射**：功能点"关联消息"字段引用 [61-消息一览](../60-reference/61-消息一览.md) 的 topic；改动消息主题/payload = 冻结变更，须用户确认。
- **测试映射**：[50-testing/51-FP与测试映射.md](../50-testing/51-FP与测试映射.md) 维护 `FP/场景 ↔ TC 用例 ↔ 测试脚本` 三方对照；FP 变更须同步该表。
- **不可测例外**：确不可自动化的（如系统托盘、多显示器物理行为）标"手动"，须写明人工步骤。

---

## 9. 维护流程

1. 新增能力 → 在对应分类文档追加功能点（分配新 ID）+ 至少一条场景。
2. 行为变更 → 更新场景"预期结果/穿透点"，并在映射表标注受影响用例。
3. 删除能力 → 功能点与场景标 🗄，保留 ID 与历史行，不物理删除。
4. 每篇 FP 文档头部维护"日期 / 状态 / 关联测试脚本"。
