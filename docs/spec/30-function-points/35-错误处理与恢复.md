## 3. 恢复动作定义

> （本节为 2026-09-10 原设计稿整体迁入，语义与现行代码一致；原文件路径与旧常量已按现行 `src/lib/llm/server` 表述改写。）

恢复机制由两个正交维度定义：**触发方式**（谁做）× **动作方法**（做什么）。附录 A 每个场景的「自动重试（runner 内）/ 自动续写（后端）/ 手动重试方式」三列即对应下表组合。

### 3.1 动作方法（做什么）

1. **重发上下文（方式 A）**：把**同一份 messages 上下文**再次调用 LLM（runner 内每次 attempt 复用 `messages`，复用历史 messages，**不二次落库**用户消息）。用于**首字（首字节）前失败**——还没收到任何内容，重发不会重复。tokens 不省，但失败不污染历史。**重试前先做网络连接预检（ERR-002）。**
2. **加「继续」（方式 B）**：在已有内容后追加 `user:"继续"` 让 LLM 续写。用于**已收到部分内容**——重发整个上下文会导致重复输出。进程内断链恢复即此方式的同 turn 变体（落库部分文本后追加「继续」）。「继续」的使用与落库策略：
   - **只在最后是不完整回复时使用**（length 截断 / 断链 / 错误后已有部分内容）——触发 LLM 接着生成。
   - **tool_result / 重新运行 tool_call 后不发表「继续」**——工具结果是下一轮 LLM 调用的天然输入（迭代循环自动继续），发「继续」是多余指令。
   - **「继续」落库为一条「类似 user 消息」**（特殊标记，前端按「续写」样式展示）——历史保持连贯（`assistant 半截 → user"继续" → assistant 续写`），LLM 上下文与历史一致，重启后恢复自然衔接。
   - **连续续写只落一条「继续」**：多次续写时后续内容直接追加合并，不重复落库（避免「继续」刷屏）。
3. **重新运行工具**：读保存的 name+args 重跑该工具（不经 LLM 重新生成参数）→ 结果回填 tool_pair → 交还 LLM 继续本 turn。仅**同步被打断/取消**（S2/S4）提供，见 ERR-007。

### 3.2 触发方式（谁做）

| 触发方式 \ 动作 | 重发上下文（A） | 加「继续」（B） | 重新运行工具 |
|---|---|---|---|
| **后端自动**（同一轮次） | ✅ 无内容失败重试（S7/S14 等 retryable） | ✅ 断链续写（S6/S8）+ 内部 `llm-start` 自动续写（length / 可重试错误，同一轮次延续） | — |
| **前端手动**（用户点按钮） | ✅ 首字前失败点「重试」 | ✅ 有内容点「继续」 | ✅ 底部「重试」按钮（S2/S4） |

- **后端自动（同一轮次）**：所有自动恢复都在后端完成，前端不参与——**无内容失败** → runner 重发上下文（方式 A，见 ERR-003）；**有内容断链** → 进程内 `resumePartial` 续写（方式 B 同 turn 变体，不重发）；**length 截断 / 可重试错误** → 后端经**内部 `llm-start`**（同一轮次）自动发起续写轮次。发起方是后端自己（`llm-start` 事件支持后端内部发布，Notify=true），前端仅显示。
- **两字段的区别**（附录 A 每场景的「自动重试（runner 内）」 vs 「自动续写（后端）」）：
  - **自动重试（runner 内）** = **同一次来回（`step`）内**、流失败（可重试错误 + **无内容**）时重发同一份上下文（方式 A）——解决「**流没读完**」。
  - **自动续写（后端）** = **同一轮内**的**续写**（后端经内部 `llm-start{continue:true}` 发起，**复用该 session 最后一轮 turn**、**不新起轮次**）（有内容→加「继续」；无内容→重发本次发送的上下文（用户消息 / tool_result）），续写上限控制——解决「**读完了但没写完**（截断/失败后接续）」。**〔原文「一轮 LLM 输出结束后…发起新轮次」与本篇 §:157/:160 的「同一轮次」及代码不符（`llm-start{continue:true}` 复用最后一轮 turn，`src/lib/llm/server/server.go:939`）〕**
- **前端手动**：用户点击按钮。LLM 级「继续/重试」按钮 → 按 `retryText()` 决定（继续 or 重发本次发送的上下文（用户消息 / tool_result））；工具级「重试」按钮 → 重新运行工具。
- **自动 → 手动回退**：后端自动**耗尽**、错误**不可自动重试**（如 API Key 401）、或**用户取消** → 前端只显示按钮，等用户手动。

## 4. 消息落库机制

- **assistant 按「段」增量落库**：流中在**内容段边界**（思维链→正文→工具调用的类型切换）与流结束时各落一次；多次落库写**同一行**（主键回填），非每 token、不产生多条消息——崩溃最多丢**当前段**，不丢已完成的段。
- **assistant 段的可重放内容 = 正文 + tool_calls**（思维链随行）；**无正文且无 tool_calls 的段不落库**（避免产生会被协议规则清空的空 assistant 行）。
- **工具发起即落 `running`（tool_pair）**：content 仅含 `call` 段（工具名 + 参数 + `tool_call_id`）；终态由结果**就地回填同一行**（不新增消息）。同一次工具调用**恒一行**。
- **流中断的迭代**：已有正文 → 落库半截 assistant + 追加「继续」续写（S6/S8）；无内容 → 不落库。
- **工具状态区分**（内部 status → 用户体验呈现）：`running`（执行中）/ `completed` / `failed`（真实失败）/ `interrupted`（abort/异常退出：S2/S3 → 呈现「已中断」）/ `cancelled`（用户操作取消：S4/S5 → 呈现「已取消」）。重试按钮按同步/转后台：同步（S2/S4）可重试，转后台（S3/S5）不提供。
- **turn 终结时补写 `FinishReason`**：`stop` / `length` / `insufficient_system_resource` / `interrupted`（见 §5.1）。

## 5. 关键机制

### 5.1 `FinishReason` 落库

turn 终结时补写 UPDATE（**非空才写**）：`stop`（正常）/ `length`（截断）/ `insufficient_system_resource`（资源不足）/ `interrupted`（turn 级失败：断链、取消、超时/错误耗尽，无终态）。

### 5.2 turn 未完成判定与恢复

自动在后端（同一轮次，内部 `llm-start`），前端只显示 + 手动入口：

- `UNFINISHED_REASONS = ['length', 'insufficient_system_resource', 'interrupted']`——只有这些才视为「未写完」。
- 后端自动续写：同一轮次内由后端自动完成（内部 `llm-start`），前端不参与；发什么按 `retryText()` 判定；有上限（`maxAutoContinue`），超限转手动按钮。
- `status=error` 且**不可自动重试**（`retryable=false`，如 API Key 错误）→ 后端不续写，直接显示「重试」按钮 = 手动重试。（**`retryable` 的取值来源= 终态事件 `session-complete`/`llm-complete` 的**可选字段** `retryable`**（错误终态携带；超时/网络/429/5xx → true，鉴权/协议与 `EMPTY_REPLY` 等 → false），前端据此判定，见 [61 §4.3](../60-reference/61-消息一览.md)；**空回复（`EMPTY_REPLY`）虽 `retryable=false` 但也走「提示 + 继续」**。）
- `retryText()`（后端续写与前端手动共用）：最后一条消息是 assistant 输出（已收到内容）→ 发「继续」（方式 B）；否则（首字前失败，无内容）→ 重发本次发送的上下文（用户消息 / tool_result）（方式 A）。
- 静态（重启后）：从 `getTurnsPaginated` 返回的 turns 取最后 turn 的 `finish_reason`：**∈ `UNFINISHED_REASONS` → 显示「继续/重试」按钮；`stop` → 不显示（正常完成）**；无记录（旧数）时兜底启发式（最后一条非空 assistant 视为完成）。

### 5.3 孤立 tool_call 处理

**tool_call 恒与其 `tool` 结果成对**：工具**发起时即落 `role=tool` 行（`running`，见 §4）→ 不会出现「assistant.tool_calls 无对应 tool 消息」的孤立态（该形态会被 OpenAI 兼容 API 以 400 拒绝）。进程异常遗留的非终态行由启动清理标 `interrupted`（此时 `result` 段为空 → 该 tool 消息正文为空串，协议允许）；重试回填后即为真实结果。

### 5.5 `llm-start` 系事件与 busy 防御

后端可自发发起 LLM 轮次（自动续写/自动重发/工具完成通知的载体）：

- `llm-start`（前端 → 后端）：启动一轮 LLM，**每 start 生成新 turn-id**；前端 send/队列出队时发。
- `llm-started`（兼容名）= **服务就绪 ack**（桥在收到 `server-starting` 时兼发；payload 仅 `{session_id, turn_id, sub, notify, instance_id}`，前两项为空串）；**每轮受理确权请用 `turn-start`**（见 [61 §6](../60-reference/61-消息一览.md)）。
- `session-complete`（后端 → 前端）：一轮终结 ack（含 turn-id/status/finish_reason）。
- **内部 `llm-start`**（Notify=true）：后端（LLM 域）自己发布——用于 **length 截断 / 可重试错误后的自动续写**、以及**后台任务完成通知自动触发 LLM 回复**；**busy 防御**：域忙时收到的 llm-start 入 pending 队列，当前轮次结束后自动续发。
- 因此「自动续写（后端）」由后端内部 `llm-start` 完成，**前端不参与发起**（只接收 turn-start/session-complete 显示，手动时由用户操作触发）。

### S6 断链：流读取中连接断开（EOF / connection reset）

| 字段 | 内容 |
|---|---|
| 判定方式 | 读流时连接断开（EOF / connection reset），断开前已收到内容（finish_reason 或部分内容）——断开前已收到非空 finish_reason → 流完整；未收到 → 部分内容断链。区分：连接前失败走 S14、chunk 间隔超时走 S8、chunk JSON 解析失败走 S13 |
| 运行中处理 | 断开前已收到 finish_reason = SSE 流完整：`stop` → 内容完整，即时 Done；`length`（截断）→ 走**断链恢复**（进程内）：落库部分文本 + 追加「继续」续写；断开前未收到 finish_reason → 同样走断链恢复（`resumePartial` 续写） |
| 运行中显示 | 部分文本 + 「继续」恢复气泡（recover notice） |
| 自动重试（runner 内） | **无「重发」**——断开时已有内容，重发会让 LLM 从头重复生成/工具重复执行（已收内容时不重发），改为**续写**（`resumePartial`）；`stop` 内容完整无失败、`length` 截断。runner 重发（方式 A）仅用于**无内容**失败（S7/S14）；重试次数只管重发，不影响续写 |
| 自动续写（后端） | 进程内已恢复 → 无；**进程内恢复失败（续写反复断/超时）或进程被 kill** → 走后端自动续写（内部 `llm-start` 加「继续」，有上限，超限转手动按钮） |
| 手动重试方式 | 后端自动续写**均耗尽**（反复断链超限 / 进程被杀重启后）→ 方式 B（加「继续」）用户手动续写（非重发） |
