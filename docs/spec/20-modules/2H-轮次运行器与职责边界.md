
## 2. 目标形态

### 2.1 分层

```
┌──────── llm/server（纯胶水：MQ ⇄ 领域事件 / data ⇄ 端口 / gateway ⇄ 工具）────────┐
│ 订阅与应答 · payload 编解码 · instance 视图 · data facade · gateway 调用           │
│ 领域事件 → 61 主题 · 端口实现（Store / Events / Tools / LLM）                      │
└───────▲──────────────────────────────┬────────────────────────────────────────────┘
        │ EventSink（session 定义，server 实现）        │ TurnStore / ToolInvoker / LLM（同上）
        │                                              ▼
┌───────┴────────── session（规则 + 状态机，零 IO；不 import chat）──────────────────┐
│ runner：turn 生命周期 · 输入队列与策略 · 帧决策 · 自动续写 · 运行态注册表          │
│ inbox ：insertable / insert↔next_turn / discarded（纯函数）                        │
│ compose：上下文组装 / 投影 / token / 压缩（现状已在此，runner 同模块直接调用）     │
└───────▲───────────────────────────────────────────────────────────────────────────┘
        │ TurnExecutor（session 端口，server 实现；唯一 import chat 的地方）
        │
   chat（无状态单例 Engine；每次 RunTurn 建局部 turn 状态）
```

### 2.2 五条职责判据

1. **session** 知道「该不该插、插不进去怎么办、这轮算不算完、下一轮谁来起」。
2. **chat** 只知道「这一轮怎么跑」（step 循环、帧执行、工具环）。
3. **server** 只知道「把 A 搬到 B」（MQ ↔ 领域事件、data ↔ 端口、gateway ↔ 工具）。
4. **router** 只知道「一次 LLM 来回」（协议适配 / 报文级重试），无业务状态。
5. **gateway** 只知道「工具怎么被调用与聚合」，持资源池，不持会话语义。

### 2.3 状态归属（一致性单位）

| 类别 | 例子 | 归属 | 同步手段 |
|---|---|---|---|
| **轮内业务状态** | 帧栈、held 回执/插话、resumeNotes、step 计数 | 随 turn（`TurnParams` → chat 的 `turn`） | 不需要锁（单 goroutine 拥有） |
| **会话运行态注册表** | `turns`（instKey(instance,turn)）、`busy`（instance+session）、`asks`、群聊调度表 | **session runner（进程内单例）** | 互斥保护；`busy` 承担同 session 串行 |
| **资源 / 配置缓存** | router specs、gateway 注册表、连接池、execPool | 进程级单例 | `RWMutex` / 原子操作 |
| **每轮语义快照** | LLM spec、model、超时、续写参数、工具白名单 | 从配置缓存拷贝进 `TurnRequest` | 锁内拷贝一次，之后不持锁 |

**判据**：配置池与资源池**不算业务状态**；「无状态」指无**业务**共享可变状态，**不等于无锁**。锁永远留在缓存、池与运行态注册表上。

## 3. 组件契约

### 3.1 `session/runner`（新子包）

依赖白名单 = 标准库 + 本模块 + `chonkpilot-agent/types`；**不 import chat / router / gateway / mq / data**。

> 注：模块根 `deps_test.go` 扫 `./...`（整模块），白名单约束对 `component` 等既有子包同样生效。

```go
// 输入：宿主投递的轮内输入（server 只做搬运，不判类型）
type Input struct {
    ID      string
    Kind    InputKind        // Insert | ToolResult | NextTurn
    Content string
    Result  *ToolResult      // 仅 ToolResult
}

// 一轮的全部入参（身份 + 快照）
type TurnRequest struct {
    InstanceID, SessionID, TurnID string
    Spec     LLMSpec          // 本轮 LLM 快照（session 自持纯数据类型）
    Config   RuntimeConfig    // MaxSteps / 自动续写 / 超时 / 白名单（同一快照）
    First    *Input           // 可空：首输入已由宿主落库时用 Kick 触发
}

// 外部能力：全部由 server 实现；Context 不设端口（runner 直接调同模块 compose）
type Hooks struct {
    Store  TurnStore      // 落库 / inbox 同事务消费（方法清单见 §3.6）
    Events EventSink      // 领域事件（server 映射为 61 主题，见 §3.7）
    Tools  ToolInvoker    // 工具派发
    Inbox  <-chan Input   // 轮内输入队列
}

// 执行端口：server 实现（唯一 import chat 的地方）
type TurnExecutor interface {
    RunTurn(ctx context.Context, req TurnRequest, h Hooks) (TurnResult, error)
}
```

**分工**：runner 决定「何时起一轮 / 何时插 / 插不进降级 / 何时继续 / 何时收口」；chat 决定「这一轮内部怎么循环」。**插入的决策在 runner，帧的执行在 chat。**

**本专题实施范围**（与 §8 批次对齐）：`runner` 只接管**轮次生命周期 + 输入策略 + 自动续写 + 终态映射**；**子轮次 / 子聊天 / 群聊调度（原 M3）不在本专题批次内**，待批次 5 稳定后单独排期（见 §10-4）。

**实际落地（2026-10-28，批次 5 本体）**：`runner` 新增三组纯决策 + 状态：
`lifecycle.go`（`Lifecycle`：创建 / `Close` 幂等 / `BeginFinish` 唯一终态 + `DecideFollowUp` 终态后续轮动作）、
`frames.go`（`Frame[T]` / `Frames[T]`：LIFO 插入帧栈 + 主帧等待集合，`Cur/Open/PendingOf/InflightOf/TakePending/ClearInflight/HasPending`）、
`autocontinue.go`（`ContinueConfig` → `DeriveAutoContinue`：usr 开关 && 非子轮次，`EngineDelay` 折正最小时长）。
主仓 `llm/server` 只剩适配：`turnCtx.life`/`turnCtx.frames` 取值 + `Close()`/`Done()` 转发，`finish` 用 `BeginFinish`/`DecideFollowUp`，
`engineRuntimeConfig` 用 `AutoContinue`；`turnCtx` 的 `once`/`done`/`finishOnce`/`inserts`/`pending`/`inflight` 字段与帧栈访问器（`curFrame`/`frameOpenLocked` 等）全部删除。

### 3.2 `session/inbox`（纯策略）

- `insertable(state)`：当前帧无在飞工具调用 → 可插；否则不可插
- 类型互转：`insert → next_turn`（轮已关 / 不可插 / 入队失败）、`next_turn → insert`（用户催「立刻插入」且相位允许）
- 状态机：`pending / consumed / discarded`；撤回优先于消费
- 输出纯决策，不写库；写库由 `TurnStore` 端口执行

**实际落地（2026-10-27，批次 4）**：新包 `chonkpilot-agent/session/src/inbox`（纯函数，零 IO）——`Phase{TurnOpen,FrameBusy}` · `Insertable/ClassifyAdd` · `CanPromote/CanDiscard/Consumable` · `Degrade/Promote` + `Kind`/状态常量；主仓 `llm/server` 的 `insertable()` / `onInboxAdd` / `onInboxPromote` / `onInboxDiscard` / `engineRouteInsert` / `consumeNextTurn` / `discardNextRunForTurn` 全部改调用该包（行为逐项不变，只换判定来源与常量）；L1 纯策略用例 = `chonkpilot-agent/session/src/inbox/inbox_test.go`。

### 3.3 `chonkpilot-agent/types`（新仓，纯数据）

**收录**（第一批）：`Message` · `ToolCall` · `ToolSpec` · `ToolResult` · `CallContext` · `Usage`

**归属说明**：`LLMSpec` / `RuntimeConfig`（§3.1 用到）属**session 自持**的纯数据类型，不进第一批；若 chat / router 也需要，二期再评估迁入。

**不收录**：

| 类型 | 原因 |
|---|---|
| router 的 `Message{Content []Part}` / `Request` / `Event` | 协议无关**块模型**，与快照文本模型不同构；router 须保持零本仓依赖 |
| chat 的 `Event` / `InboxItem` / `TurnState` | 运行语义，不是数据契约 |

**规则**：只有 struct + 常量，零方法、零接口、零 import（除 stdlib）；JSON tag 与现状**逐字节一致**（MQ / 快照 / shadow 都依赖）。

**迁移**：新仓定义 → chat / session 用 `type X = llmtypes.X` **别名过渡**（行为零变更）→ 键集断言（`chatadapter_test` / `v2contract_fixture` / `assertKeys`）全绿 → 再删别名。

**实际落地（2026-10-27，批次 2）**：① 新仓 `E:\BizWorks\chonkpilot-agent\types`（module `github.com/lsong98sh/chonkpilot-agent/types`，仅 stdlib；`types_test.go` 以搬出前 Marshal 输出作**逐字节 golden**）；② chat 6 个类型全部改别名；③ **session 不再 import chat**——`Message`/`ToolCall` 别名到 llm-types，`Context` 由 session 自定义（字段 = `SystemPrompt + Messages`，宿主 `engineTurnContext.Build` 做边界转换），`deps_test` 白名单收紧为 `stdlib + llm-types`；④ 主仓各 module 加三仓**开发期本地 replace**（与 `go-webview2` 同口径，发布版本化后删除）。

### 3.4 chat：无状态单例（B 方案）

现状 `Runtime` 持 `state` / `seq` / `resumeNotes` / `heldResults` / `heldInserts`（全部轮内状态），且 `Deps` 里混入 `InstanceID` / `SessionID`（**每轮身份**）——这是「每轮 `New`」的真正原因。

目标：

```go
type Engine struct { logger *slog.Logger; clock Clock }   // 单例，跨轮无状态

type TurnParams struct {                                   // 原 Deps + 身份（与 §3.1 TurnRequest 一一对应）
    InstanceID, SessionID, TurnID string
    Context ContextProvider; Store TurnStore; Sink EventSink
    Tools ToolInvoker; Catalog ToolCatalog; LLM LLMClient
    Config RuntimeConfig; Lifecycle Lifecycle; Inbox Inbox; Shadow *Recorder
}

func (e *Engine) RunTurn(ctx context.Context, p TurnParams) (TurnResult, error) {
    t := &turn{engine: e, p: p, state: NewTurnState(p.SessionID, p.TurnID), resumeNotes: map[string]string{}}
    return t.run(ctx)     // 全部可变状态挂在 t 上
}
```

硬要求：

1. **身份外提**：`InstanceID/SessionID` 从 `Deps` 移到 `TurnParams`（先做，A 方案也受益）
2. **状态下沉**：`state / held* / resumeNotes / seq` 全部进 `turn`；`Runtime` 不再持有
3. **并发安全**：同一 `Engine` 并发跑不同 session 的 turn，`-race` 通过；做不到就不叫无状态单例

改造面：上述字段集中在 `engine.go` 与 `engine_*_test.go`（精确处数实施时用 `rg` 实测，不在此估算）。

**实际落地（2026-10-27，批次 3）**：`chat.Deps` 删除 `InstanceID/SessionID`；新增 `chat.TurnParams` 与 `RunTurnParams`；`RunSubTurn` 继承父轮 InstanceID；宿主每轮显式传身份；过渡入口 `NewForTurn` + `RunTurn(ctx,turnID)` 保留。

**实际落地（2026-10-27，批次 6）**：`chat.Engine` 成为**无状态单例**（只持默认端口：logger/clock/lifecycle/config），轮内状态（`TurnState` / `seq` / `resumeNotes` / `heldResults` / `heldInserts`）全部收进每次 `RunTurn` 新建的局部 `Runtime`；新增 `RunTurnParamsWith(ctx, p, Deps)` —— 端口（Context/Store/Sink/Tools/Catalog/LLM/Inbox/Shadow）可按轮传入，Engine 不持轮内状态；宿主 `llm/server` 持 `Server.engine` 进程级单例，`runEngineLoop` 每轮只传端口快照。L1 `engine_concurrency_test.go`：同一 Engine 并发 8 轮（不同 session）`-race` 全绿。过渡入口 `NewForTurn` / `RunTurn(ctx,turnID)` 按批次口径保留（批次 3/5/6 不删），新代码一律走 `RunTurnParams(With)`。

### 3.5 router / gateway

| 组件 | 共享物 | 性质 | 结论 |
|---|---|---|---|
| `router.Router` | `cfg` + `specs` + `adapters`（RWMutex） | 配置缓存；`Call` 本身无请求状态 | 无业务状态；**每 Call 由调用方 `Register(spec)` 后 `Call`**（现状即如此），中途改配置不影响在飞 turn |

## 4. 一致性策略：快照 vs 活读

### 4.1 判据

- **低频写 + 强语义绑定** → **每轮快照**（LLM spec / model / 超时 / 续写 / 白名单 / 重试参数）
- **高频变化 / 大对象** → **活读 + 读时拷贝引用**（工具列表、知识库与索引列表、连接池）
- 快照只拷贝一次（锁内），之后不持锁；活读必须**一次读全**，避免「半新半旧」撕裂

### 4.2 结论

| 对象 | 策略 | 说明 |
|---|---|---|
| 基本配置（四级） | **快照** | `newTurnCtx` 内 `loadUserConfig` 一次读取共用（代码注释即「一次读取共用」），派生到 `tc.*` |
| LLM spec | **快照** | `s.chat` 先 `Register(spec)` 再 `Call`，spec 来自本轮快照 |
| **工具列表** | **活读 + RWMutex** | 不拉快照：工具集随 instance / 场景 / 白名单 / 插件启停变化，且 `[]ToolSpec` 体积随工具数增长。每 step 组装时在锁内**拷贝一次切片（共享底层字符串，不深拷贝 schema）** |
| 知识库 / 索引列表 | **活读 + RWMutex** | 同上；不跨轮保存副本 |

**接受的行为**：中途新增 MCP 工具 → 本轮后续 step 可见（每 step 重新取工具集）；删除工具后模型若调用已消失工具 → 由 gateway 返回明确错误（不静默）。

## 5. 单例（desktop）与文件锁

### 5.1 结论（2026-10-29 TOPO-1 §2.22.6 现行口径）

- **判据 = 实例 UDS socket 的独占 listen**：`%LOCALAPPDATA%\chonkpilot\instance\<数据根指纹>.sock`（指纹 = 数据根绝对路径小写化后 sha1 前 16 hex；空数据根 → `global.sock`）；入口第一件事调用 `singleinstance.Acquire(host.DesktopDataRoot())`，`ErrAlreadyRunning` → 先 `singleinstance.Send(activate)` 激活既有实例（交付成功即静默退出；失败才原生弹框 + `os.Exit(0)`）
- **作用域 = 数据根（profile）**：`<work-dir>/.chonkpilot` 决定 socket 名 → 同一数据根的第二实例不建窗、不碰数据根，只把激活命令交给既有实例（保护同一个 bbolt 库），**不同数据根可并存**（多实例 / 多工作区）
- **先 dial 再 listen（不先 Remove）**：dial 成功 = 已有实例；dial 失败 → listen 成功 = 唯一；listen 失败 → 再 dial 一次确认竞态，仍失败才判崩溃残留 → `os.Remove` 后重试一次 listen，仍失败即 fail-closed 硬错误
- **激活通道（2026-11-03）**：连接读一行 JSON `Command{Cmd,WorkDir}`（1s / 4KB；旧探针连接忽略）→ `Instance.SetHandler`（未装时缓存最新一条）→ 主仓 `host.handleActivation`：有项目主窗口则前置一个（workdir 匹配 → 前台项目 → 最近活动 → 字典序），一个都没开则执行「打开工作目录」；**不做** window class 注册/反注册
- 进程退出时 `Instance.Close` 关闭监听并移除 socket；崩溃残留由下次启动的「dial → Remove → 重试」清理（**不残留判定**）

**实际落地**：`chonkpilot-framework/host/src/singleinstance`（`Acquire` / `Send` / `Command` / `SetHandler` / `Path` / `DataRootFingerprint`）；`src/desktop/main.go` 入口第一件事调用，`ErrAlreadyRunning` 时发激活命令，弹框与退出由壳负责（framework 只返回 typed error）。〔2026-10-29 前为 Windows 命名互斥 `CreateMutexW`（`procsingleton`），该判据已整体删除〕

### 5.2 为什么不用 UDS bind 失败 / window class 作判据

| 机制 | 跨进程判重 | 说明 |
|---|---|---|
| `RegisterClassEx` | ❌ | 窗口类默认**进程本地**，两进程同名注册都成功 |
| UDS bind 失败（先 Remove 再 Listen） | ❌ | Windows 下先 `Remove` 再 `Listen` 会**顶掉**旧路径 |
| **UDS 独占 listen（不先 Remove）** | ✅ | 现行方案：`dial` 探测 → `listen` 判唯一 → stale 清理重试；Windows AF_UNIX 重复绑定失败 |
| `CreateMutexW`（已删除） | ✅ | 曾在 2026-10-27 批次 1 使用；2026-10-29 被 UDS 方案取代 |

### 5.3 删除 session 文件锁

`sessionlock_windows.go` / `sessionlock_other.go`（锁目录默认 `~/.chonkpilot/locks`，文件名为 **sanitize 后的 session id** + `.lock`）**在单例成立后删除**；进程内互斥改由 runner 运行态注册表的 `busy`（`instKey(instance, session)`）承担。

**实际落地（2026-10-27，批次 1）**：`sessionlock_{windows,other}.go` 与 `sessionlock_test.go` 已删除；`Server.locksDir`、`turnCtx.sessionLock`、`onLLMStart` 的加锁/释放、`Close` 的释放全部移除（同 session 互斥继续由 `busy` 注册表保证）；原文件内的 3 条非锁用例（跨轮快照 / 同 session 忙拒绝 / 空 instance 拒绝）已迁至 `turnlifecycle_test.go`。

〔2026-11-03〕`~/.chonkpilot/locks` 目录下的存量锁文件均为上述已删除实现与更早 per-session 锁的残留（0 字节、无读取方），可整体清理。

## 11. 异常与重启恢复（强制）

runner 接管的是**有状态**能力（`turns` / `busy` / `asks` / 帧栈），按项目规则必须逐条回答五问：

| # | 问题 | 结论 |
|---|---|---|
| 1 | 状态落在哪 | 内存 = 运行态注册表（`turns` / `busy` / `asks`）+ chat 的轮内 `turn`；持久 = `sessions` / `turns` / `messages` / `inbox_items` / `turn_events` / `messages.ask_id` |
| 2 | 输入是否受理即持久化 | **是**：`llm-start` 受理先 `EnsureSession/EnsureTurn` 落库，再应答 `accepted`；`llm-send` 先落消息再投递 |
| 3 | 非终态由谁收口 | 启动清理（`CleanupStaleTurns`）+ `data-ask-pending` 扫描 + 轮内超时（`PendingWait`）；下沉后由 **runner 发起、server 提供启动钩子**，不得因搬迁丢失 |
| 4 | 重启后重建还是收敛 | **不重建内存 turn**，统一收敛到终态（`interrupted` / ask `expired`），用户可「重试」；帧栈按 `TurnState.Version` 校验，不兼容则收敛 |
| 5 | 副作用语义 | 工具调用至少一次（结果按 `call_id` 落库幂等）；inbox 消费按 `M-INBOX-<id>` 幂等；重复回执不重复派发；未知 `ask_id` 回执明确失败、不静默 |

**迁移要求**：上述收口的**归属**在批次 5 必须逐条落位（谁发起、谁提供钩子、谁写库），并在 L1 补「异常中断 → 重启 → 恢复」用例（MQ 驱动 + MQ 断言）。
