本文描述**一条用户消息从 UI 到落库再回灌**的完整链路，并覆盖取消、异步、压缩、提问、通知等旁路。

---

## 0. 参与方与通道

| 参与方 | 角色 | 通道 |
|--------|------|------|
| 前端（Vue） | 展示态 | `POST /publish`（发）+ 事件订阅（收） |
| server（会话层） | 编排：回合 / tool_pair / tasktree | mq |
| persist（数据面） | 权威状态落库 | mq（`data-*`） |
| gateway | 工具唯一入口 | mq（`mcp-*`） |
| mcp-server（+ core-mcp-server） | 工具契约扫描与 `runtime=builtin` 进程内执行；插件 MCP server 提供其余工具 | 进程内 / 插件桥 |
| filesys | 文件变更 | mq（`filesys.*`） |
| 插件（history / codegraph / …） | 事件订阅（**compress 已内建，非插件**） | mq |

> 全部相对主题由宿主注入 `chonk.` 前缀；下文写作 `chonk.<相对主题>`——相对主题为 **kebab 单段**（如 `session-start`、`mcp-tools-call`），**不是**点分域前缀（`chonk.session.start` 为错误记法）。

## 1. 阶段一 · 启动与恢复

```text
GUI 启动
  ├─ instance-register {instance_id, work_dir, data_dir} ─▶ server 登记实例（无返回）
  ├─ 数据面初始化：三层库解析（usr / prj / prjusr）+ 一树一库 dialog（**无迁移、无 seed**）
  ├─ gateway 扫描 capability 契约 → 注册工具 → 发 mcp-gateway-changed（订阅方刷新缓存）
  ├─ data-session-active-get → 活动会话；无则前端/对话面板按需 data-session-latest 取最新
  └─ data-session-context {session_id, include_snapshot} → 重建上下文
```

- 启动清理：`data-session-cleanup-stale` 把遗留 `running` turn 标 `interrupted`。
- 实例保活：`instance-heartbeat`（30s）· 退出：`instance-exit`（注销 + 取消名下 running + 释放锁）。
  - **心跳与退出判定（编译开关 `split`）**：`heartbeatTimeout` 判定与 `plugin/instance.Sweep(timeout)` 在**单体默认构建不编入**、**分离形态（`-tags split`）编入**；编入后按心跳保活（30s 发布 / 90s 判超时 → 判定侧消费方 llm-server `Manager.Sweep(90s)` → 既有 `exitInstance`、persist 30s 扫描 → 既有 `instanceGone`（解绑 + `data.Unregister`））；单体形态实例**随进程生命周期**结束，失效只由**显式 `instance-exit`** 清理；`instance-heartbeat` 订阅保留，**仅供分离/去中心化形态保活**。见 [28-plugins §2](../20-modules/28-plugins.md) · [61 §4.1](../60-reference/61-消息一览.md)。

## 2. 阶段二 · 受理与上下文（回合开始）

```text
用户点发送
  └─ POST /publish chonk.llm-start {session, turn, llm?, think?, effort?, scenario_id?, continue?}
        ├─ server 写回 Result {accepted, session, turn}
        ├─ data-session-ensure-session {session_id}       # 幂等建会话
        ├─ data-session-ensure-turn    {turn_id, session_id}  # 幂等建轮次
        ├─ data-session-context        {session_id, exclude_turn}
        │     └─ 决策：有快照 → 快照前缀 + snapshot_turn 之后 turns（跳过 interrupted）
        │              无快照 → 从最新往回找首个有 summary 的 turn 作起点（summary → system "[历史摘要]"+summary）
        ├─ 组装 system（场景 main.agent.md）+ 历史 + 用户消息
        └─ 调 LLM（流式）
```

- 场景提示词来自场景目录（见 [02-配置层级](02-配置层级.md) §7.2）。
- LLM 返回流式广播：`chonk.session-receive {session, turn, type: reason|text|tool-call, payload}`。
- 逐条落库：`data-session-append-message {turn_id, msg:{role, kind?, content, tool_call_id?, tool_calls?}}`。**新 id 形态 = `M<yyyyMMddHHmmss><微秒6位><4位随机>`（25 字符，自带时间序）**；旧 `m-<rand>` 仅兼容读取（`src/lib/data/internal/kernel/viewdata.go NewMessageKey`）。（2026-11-04 核对）

## 3. 阶段三 · 工具调用（核心回环）

### 3.1 同步工具

```text
LLM 产出 tool-call
  └─ server 组装 tool_pair（回合产物）→ chonk.mcp-tools-call {name, arguments}（经 gateway）
        └─ gateway 路由 → Provider
              ├─ inprocess mcp-server：扫描 .tool.md → **`runtime=builtin` 进程内执行**
              │     └─ 返回统一 JSON（content + structuredContent；用户自建 executor 才走 spawn，>200KB 落临时文件仅该路径适用）
              ├─ 插件 MCP server：file 11 / web 3 / task_run / codegraph / vfts 等
              └─ 第三方 MCP：proxied / spawned http
        ◀─ gateway 写回 v.Result {resultType, content, structuredContent, isError}
  ├─ 回填 tool_pair（调用层）
  ├─ data-session-append-message（tool 结果）
  └─ chonk.llm-send {type: tool-result, content, tool_call_id} → 续轮
```

> gateway 只收「执行请求」、发「执行结果事件」，**不感知 tool_pair**（tool_pair 属会话层）。

### 3.2 异步 / 后台工具

```text
工具调用按 async 模式（契约/调用级 auto|always|never|manual；默认 auto）
  ├─ always：立即任务化并返回 {structuredContent.status: pending, task_id}
  ├─ auto  ：任务化启动（一次调用）；到 async-threshold 自动转后台（不重跑；提前完成就地交付）
  ├─ manual：任务化运行；到 timeout 发 mcp-tools-timeout{options:[detach,cancel]} 待用户裁决（**不是立即 pending**）
  └─ never ：阻塞等待（显式 always 可覆盖；配置 cancel_on_timeout > 0 时到点自动取消）
  …… 后台执行 ……
  └─ chonk.mcp-tasks-report {task_id, tool, state, result_summary,
                             instance_id, session?, turn?, tool_call_id?, top_session?, parent?}
        （通知，发送方不 await；订阅方收敛 = 仅 server）
        └─ server onGatewayTaskDone → 回填 tool_pair → 结果喂回 → 续轮（llm-send）
```

> **已订正（2026-11-04 核对）**：原文档「超 async-threshold 或声明 manual → gateway 立即返回 pending」与实现不符；字段原名 `owner_instance_id` 也不存在，实际为 `instance_id`。语义以 `chonkpilot-agent/gateway/src/mcpgateway.go`（doCall / detach）与 `port.go OnTaskReport` 为准。

- 异步结果与状态：**不再经 gateway 方法面**（`mcp-tasks-status` / `mcp-tasks-result` / `mcp-tasks-list` / `mcp-tasks-cancel` / `mcp-tools-background` 已移除）——异步结果读 **message 表**（role=tool 消息 content 的 `{call,result,async}`；`data-session-content` 的 key `tool_result:<tool_call_id>`）、状态以**任务层**为准；取消 / 转后台经**进程内 sink**（`ExecSink.CancelExec` / `DetachExec` → gateway 执行池）。见 [61 §5.1](../60-reference/61-消息一览.md) · [21 §9.3](../10-architecture/21-任务层设计方案.md)。

### 3.3 任务树（与工具调用并行落库）

| 消息 | 方向 | 作用 |
|------|------|------|
| `chonk.task-started` / `chonk.task-updated` / `chonk.task-done` | server → 客户端 | 任务树节点生命周期（**server 编排终态单源广播**，含 llm 子会话） |
| `data-tasktree-upsert` | server → persist | 任务节点落库（node_type 由 kind 推） |
| `data-tasktree-list` / `data-tasktree-tasks` | 前端 → persist | 任务区刷新 / 运行态列表 |
| `data-tasktree-delete` | 前端 → persist | 「关闭任务」级联删除子树（经 `task-deleted` 同步 server 内存） |

## 4. 阶段四 · 终态与压缩

```text
回合结束
  ├─ chonk.session-complete {session, turn, status: complete|incomplete|error|interrupted, code?, message?, text?}
  │     # 唯一终态：正常/错误/取消都收敛于此
  ├─ data-session-complete-turn {turn_id, status, finish_reason?}
  └─（压缩 = 进程内后台、无 MQ 事件；session-compress 已于 2026-10-31 退出消息面）
        └─ 内建压缩（src/lib/llm/server/compress.go）：组装后按 Usage 判阈值 → 摘要 → CAS 回写
              └─ **只写** data-snapshot-set {session_id, snapshot:{history, snapshot_turn}}
```

> **已订正（2026-11-04 核对）**：现行压缩路径**只写快照**（`SnapshotSet`）；摘要并入快照 history 的 system 消息。`data-session-set-summary` / `TurnSetSummary` 仅 persist 侧可服务，**生产代码无调用方**（仅测试引用）。**已知差异（待用户拍板）**：文档曾承诺「写 set-summary」，代码未实现——按当前实现记录，不臆造。

- finish 语义：`stop` 正常收；`length` 续写；`error`/空回复 → 前端「继续」。
- 快照读：`data-snapshot-get`（无 → null，调用方回退全量 history）。

## 5. 旁路

### 5.1 取消

```text
用户点取消（或删除运行中会话）
  └─ chonk.llm-cancel {session, turn?} → {cancelled, turn}
        ├─ 停止当前回复 + 清排队
        ├─ 级联取消：子会话及后代任务（tasktree 子树）
        └─ 广播 chonk.session-complete {status: interrupted}
```

### 5.2 ask_user（AI 提问）

> **现状（2026-11-04 核对）= 全局弹窗队列 · 单问单答**；原「chat 内联表单 + `questions[]` 一表 N 问 + 增量 `answers[]` + awaiting 跨重启」目标态**未落地**（[13-生命周期 §5](../10-architecture/13-生命周期.md) 🗑）。

```text
LLM 调用 ask_user（一个 ask = 一个问题）
  └─ chonk.session-ask {instance_id, ask_id, question, dialog_id, session, turn, expires_at,
                        options?, multi?, custom?, recommended?}
        └─ 前端（Ask 中心 / 弹窗）渲染单问卡片
  └─ ask-user-reply {instance_id, ask_id, answer, dialog_id}
        ├─ server 按 ask_id 取走等待登记 → 单值 answer 直接 FeedToolResult 回填当前 turn
        ├─ 等待登记缺失（超时摘除 / 重启）→ 回查落库行，按「普通 user 消息 = 新 turn」处理
        └─ 每条 ask 独立；turn 等待期仍为 running（无 awaiting 状态）
```

> **已订正**：原载荷 `questions:[…]` / `answers:[{id,answer,custom?}]` 与实现完全不同；以 `src/lib/llm/server/handler_ask.go` 与 61 §4.2/§4.3 为准。

### 5.3 后台任务完成通知（四段链路，已实现）

> **2026-11-04 已实现**（代码：`src/lib/llm/server/notifyqueue.go`、`finish.go`）。后台任务完成且调用方 turn 已离开时：① **落库**——通知消息写入调用方会话（`role=user`、`kind=notify`），落库主键 = 事件 `message_id`（`msg-notify-<task_id>`），重复 completion 同 id 幂等；② **挂账/轮末冲刷**——会话有运行轮次 → 只入队（不落库、不显示），该轮结束按完成顺序落库 + 广播；idle → 立即落库 + 广播；③ **text-notify 续轮**——idle 落库后起内部通知轮（`llm-start` 构造 + `llm-send{type:text-notify}`），LLM 自动继续；④ **已取走不通知**——结果已被 `tool_result` 取走（或 message 表已有终态结果行）→ 不发通知；**通知轮防循环**——通知轮内派生的后台任务完成只落库/广播，不再级联触发新的通知轮。
>
> `tool-notify` 事件载荷保持既有字段不变（`instance_id, session_id, turn_id, task_id, notice:"completion", message, message_id`），前端仍按 `message_id` 去重。

**内容范式**（`role=user`，消息 `kind=notify`，前端 🔔 样式，与普通 user 消息可区分）：

```text
🔔 异步任务已完成：{工具名}（task_id=xxx）。该任务结果尚未获取，可调用 task_status(task_id="xxx") 获取完整结果。
```
（任务失败时文案为「执行失败」。）

| 维度 | 实现规则 |
|------|------|
| 时机 | 后台任务完成且结果「未取走」时：调用方 turn 活跃 → **挂账**（暂存，**不落库、前端也不显示**），**轮末立刻冲刷**；系统 idle → **立即发送**。冲刷 = 落库 + 前端同刻显示，**同一 message_id** |
| 落库/显示 | 落调用方会话（归调用方 turn）+ 前端实时显示；**同一份消息同一 id**，前端按真实 id 去重 |
| 取消条件 | 结果已被 `task_status` 读取 → **不发通知**（内存 consumed 集合；message 表终态结果行兜底） |
| 多条并发 | 多条通知按完成顺序**依次写入**（先完成先落库，前端按序显示） |
| 触发新一轮 | idle 落库后经 `llm-send {type: text-notify}` 起内部通知轮；通知轮内派生的后台任务完成时只显示/落库，**不再级联触发**（防循环） |
| 提示条 | 与通知消息**并存**：提示条 = 即时提醒（临时，点击定位任务；会话忙碌时暂存，结束后统一弹出），通知消息 = 正式记录（进入会话历史） |

**前端待发送队列（按 LLM 分桶，useSendQueue）**：**现状只承载 `message`**；`notify` 由后端自动续轮（已实现，见上）；`ask_user` 答案走 `ask-user-reply` 直达，不再入队。原 `{type:'notify'|'message'|'tool'}` 多类型与 `notify > tool > message` 优先级**已不存在**（2026-11-04 核对）。

- 队列项：`{ id, type: 'message', payload: { sessionId, text, llm, thinkFlag, effortLevel, scenarioId } }`。
- 入队来源：LLM busy 时点【入队】按钮。
- 出队：`session-complete` 正常 → 自动逐条发送；`interrupted`/取消 → 消息写回输入框（由用户点击发送）。
- 队列项操作：**撤回** = 删除该项 + 内容写回输入框；**删除** = 仅从队列删除。
- ~~结果已取走：后端按 task_id 通知前端删除对应 notify 项~~（多类型队列作废后无对应实现）。

## 6. 时序总览（文字版）

```text
UI ──llm-start──▶ server ──ensure/append──▶ persist
                     │
                     ├──llm-send──▶ LLM ──receive(reason/text/tool-call)──▶ UI
                     │
                     ├──tools-call──▶ gateway ──▶ mcp-server(builtin)/插件 MCP
                     │        ◀──v.Result──────────────────────────────┘
                     │        （异步：mcp-tasks-report ──▶ server）
                     ├──task-started/updated/done──▶ UI
                     ├──data-tasktree-upsert──▶ persist
                     └──complete──▶ data-session-complete-turn ──▶ persist
                              └─compress（进程内）──snapshot-set──▶ persist
```

**关键点**：唯一回环（工具完成 → 回合继续）经 MQ 事件解耦；所有写操作经 persist 数据面；前端只连 server / persist / filesys，不直连 gateway。
