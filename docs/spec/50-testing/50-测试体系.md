## 1. 唯一准则

**`docs/spec/60-reference/61-消息一览.md` 是测试的唯一准则**：

- 测试过程中任何**发送的消息、接收确认的消息**，必须与 [61-消息一览](../60-reference/61-消息一览.md) 一致。
- **msg 及其 payload 不能新增 / 修改 / 删除**，除非经用户确认。
- 由此推出：**所有测试必须通过「发送 mq 消息」驱动、「监听 mq 消息」断言**；禁止直接调用组件方法、操作 Vue 实例内部状态、或模拟组件内部事件链。

## 2. 分层

| 层 | 位置 | 形态 | 覆盖对象 |
|----|------|------|---------|
| L1 模块单测 | 各模块内 `*_test.go` | 同包 Go 单测 | 内部逻辑（解析、状态机、DSL、索引、熔断…） |
| L2 黑盒单测 | `src/test/<module>/unittest/` | 独立 `go.mod` + `replace` 指向被测模块 | 经**公开包 API**（多为内存总线直驱） |
| L3 契约/执行器脚本 | `src/test/chonkpilot-mcp-server/systest/`、`src/test/chonkpilot-mcp-tools/systest/` | Python | MCP 契约、executor 命令行 |
| L4 GUI 系统测试 | `src/test/chonkpilot-gui/systest/` | Python，经 `--test-port` | 前端 + 内嵌全栈（mq 驱动） |
| L5 手工 | — | 人工 | Chrome/桌面注入、多显示器、资源管理器等 OS 集成 |

> **L1 与 L2 的分工判据**：Go 的 `go test ./...` 只发现**本模块包目录**下的 `*_test.go`；要访问**未导出**标识符，测试文件必须与被测源码**同目录且 `package` 子句一致**（内部测试包，如 `package server` / `package mq` / `package dsl`）——**"同模块"不够**，同模块的其他目录就是另一个包，同样看不到私有符号。L2 的独立 module 以普通导入方式引用被测包，只能写**外部测试包**（`package xxx_test`，仅用导出 API）。因此：
> - **要触碰包内私有状态 / 函数** → 留在 **L1**。例：`src/lib/llm/server/*_test.go`（14 文件，全为 `package server`，测内部 turn / 会话锁 / DSL 解析 / 任务树）；`src/plugins/codegraph/server/server_test.go`（用未导出 `dropWorkspace` / 全局注册表做用例间隔离）。
> - **只需对外行为** → 集中到 **L2**（可跨模块组合、统一入口、不污染生产模块）。例：`src/test/chonkpilot-data/unittest/persist/*`、`src/test/chonkpilot-filesys/unittest`、`src/test/chonkpilot-lib/unittest/{mq,paths}` 全为 `package xxx_test`。
>
> 两类并存是**刻意取舍**：把 L1 也搬进 `src/test/` 只能改成外部测试包，代价是失去白盒能力。
>
> **测试代码不进产物**：`*_test.go`（含 `export_test.go`）在 `go build` 时被**无条件排除**（按文件名后缀判定），只进入 `go test` 的测试二进制；`src/test/**` 是独立 module，主模块构建根本看不到它。⚠️ 两个反例才会混进包/产物——**非 `_test.go` 的测试辅助**（如 `testutil.go`、`internal/mock/`）与 **`go:embed` 打进产物的测试夹具**；本仓已核查为 **0**（无 `"testing"` 被非测试文件导入、无 embed 指向 `test|systest|unittest`）。

## 3. 驱动通道（`--test-port`）

`chonkpilot.exe --test-port=2345`（仅 127.0.0.1；不传则该通道不存在）。

| 端点 | 用途 |
|------|------|
| `GET /ping` | 探活 + `ready`（首次导航完成前 `/eval` 返回 503） |
| `POST /eval` | 万能：执行 JS（`window.mq.emit(...)` 驱动 / 注册 `window.mq.on(...)` 断言） |
| `POST /publish` | 直达后端（需后端订阅方处理的事件） |
| `POST /wait-event` | 等待指定 mq 事件（复用 publish 语义） |
| `POST /click` / `/input` / `/text` / `/html` / `/exists` | DOM 便捷操作与断言 |
| `POST /console` | 读/清前端 console（`window.__chonkConsole`） |
| `GET /screenshot` | 截图（PNG） |

**驱动范式**（见 [52-test-port驱动](52-test-port驱动.md) §3.4）：

- 发送 = `/eval` 执行 `window.mq.emit('<topic>', <payload>)`（与真实交互等效）；需后端处理方时用 `/publish`。
- 断言 = `/eval` 注册 `window.mq.on('<topic>', cb)` push 到 `window.__chonkEvents` 后取样。
- **断言优先级**：能通过 mq 事件 payload 断言的不依赖 DOM；DOM 断言仅验证渲染落点。
- 结果需 `unwrapString` 解包双重 JSON；textarea/input 文本读 `.value` 而非 `.textContent`。

### 5.2 L1 特例 · vfts 的 `zvec_c_api.dll` 前置（唯一入口）

`src/plugins/vfts` 的 L1（同包 `*_test.go`，见 §2）经 **CGO** 链接 `zvec_c_api`：**编译期**需头文件/导入库（`CGO_CFLAGS` / `CGO_LDFLAGS`），**运行期**需 `zvec_c_api.dll` 在可加载路径——该 DLL 由 **Windows 加载器在测试进程启动前**解析（须在启动前就位于可加载路径）；而 `build-vfts.ps1` 只把该 DLL 放在**产物 exe 同目录** → **单测环境无注入**。故两种缺参形态各有其症状：**完全无 CGO 参数** → 编译期 `fatal error: zvec/c_api.h: No such file or directory`（build failed）；**设了 CGO 参数但 DLL 不在 PATH** → 运行期 `exit status 0xc0000135`（找不到 DLL）。

**一条式前置命令（与 `build-vfts.ps1` 同款 CGO 环境 + 把 `third_party\zvec\windows_amd64` 前置到 `PATH`；无需改系统 PATH）**：

```powershell
cd <repo>\src\plugins\vfts
$z = "$PWD\third_party\zvec"
$env:GOROOT = "e:\GoDev\go1.26"
$env:Path = "e:\GoDev\go1.26\bin;e:\GoDev\msys64\ucrt64\bin;$z\windows_amd64;" + $env:Path
$env:GOPROXY = "https://goproxy.cn,direct"
$env:CGO_ENABLED = "1"
$env:CGO_CFLAGS = "-I$($z.Replace('\','/'))/include"
$env:CGO_LDFLAGS = "-L$($z.Replace('\','/'))/windows_amd64 -lzvec_c_api"
go test ./...   # → ok  github.com/chonkpilot/chonkpilot-vfts-mcp-server/server（1 例：TestIncrementalIndexSmoke）
```

> **实跑（2026-09-17）**：① 完全无 CGO 参数（干净环境）→ `fatal error: zvec/c_api.h: No such file or directory` / `FAIL … [build failed]`；② 仅设 `CGO_CFLAGS`+`CGO_LDFLAGS`、DLL 目录**不在** PATH → `exit status 0xc0000135`；③ 本节命令全量 → `ok …/server 2.837s`。

> **为何不在 `src/test/**` 侧注入**：L1 测试文件按 Go 规则**必须与被测源码同包同目录**（见 §2 分工判据），`src/test/**` 只有独立 module 的 L2，**无 L1 承载点**；且 `PATH` 由**加载器在进程启动前**读取，进程内 `TestMain`/`os.Setenv` 已太晚 → 只能由**调用方**注入，故以本节为唯一入口（"测试环境前置"统一处），不另起脚本/L1 运行器。

- **无需手工预起底座**：`run_all.py` 与各 `run_*.py` 经 `harness`（`src/test/chonkpilot-gui/systest/harness.py`）**按需拉起** mock LLM / GUI——动态端口（`free_port()`）、独立 `--data-dir` 与独立 `HOME`/`USERPROFILE`（usr 主库隔离），套件 `finally` / 进程退出（`atexit`）/ 中断（信号）**三路径回收**整棵进程树。
- **复用优先**：目标端口已有 `/ping ready` 的**外部实例** → 直接复用（`owned=False`，**不回收**）；端口空闲才自起。因此"想复用外部实例"仍可行，但**不是必需前提**。
- 详细资源规范（禁止裸 `subprocess` 起进程、禁止常驻 mock、只回收自起实例）见 [51 §6](51-FP与测试映射.md)。

### 5.3 L1 特例 · codegraph 的 gcc 前置（无外部 DLL）

`src/plugins/codegraph` 的 L1 经 **CGO** 编译（`github.com/tree-sitter/go-tree-sitter` 及各语言 binding 的 C 源码随 module 一起编译），**不加载任何外部 DLL**，但 **PATH 必须含 gcc**（同 `build-codegraph.ps1`）：

```powershell
cd <repo>\src\plugins\codegraph
$env:GOROOT = "e:\GoDev\go1.26"
$env:Path = "e:\GoDev\go1.26\bin;e:\GoDev\msys64\ucrt64\bin;" + $env:Path
$env:GOPROXY = "https://goproxy.cn,direct"
go test ./... -count=1   # → ok  github.com/chonkpilot/chonkpilot-codegraph-mcp-server/server（0.784s）
```

> **实跑（2026-09-17）**：PATH 去掉 `msys64\ucrt64\bin`（并以空 `GOCACHE` 强制重编）→ `# runtime/cgo  cgo: C compiler "gcc" not found: exec: "gcc": executable file not found in %PATH%` / `FAIL … [build failed]`；加回 gcc → `ok …/server 0.784s`（`-v` 计 83 例 PASS）。
> 与 §5.2 的区别：vfts 链接**外部** `zvec_c_api`（头/导入库/DLL 三重前置），codegraph 的 C 代码**随源码编译**，故只需 gcc；`src/plugins/plugin-{codegraph,vfts}` 均为纯 Go，**不需** gcc 或 zvec（已实跑确认）。

脚本约定：`run_case` 输出 PASS/FAIL；退出码 0 = 全过。

## 6. 已知边界与约定

1. **折叠目录下子级展开状态不持久化**：展开态只按展开目录相对路径数组（`filetree-expanded-key`）保存，重启后折叠目录下的子目录展开状态丢失（原 `filetree-data` 整树快照已于 2026-09-11 摘除，见 [42-决策记录](../40-roadmap/42-决策记录.md) F）。
2. **`tool_result` 按子 turn id 检索**取最后一条 assistant 消息，断链恢复场景会缺部分文本（回复路径不受影响）。
3. **弱断言项**：代码索引（仅调用链不报错）、转异步通知（async 仅 dbg）、部分弹窗入口（仅出现）。
4. **工具矩阵**（全工具 × 同步/异步/取消形态）由 Go 单测覆盖，非脚本层。
5. **桌面/Chrome 相关**用手工或 `dummywm` 兜底；`gui.pick-executable` 等原生对话框不可自动化（脚本覆盖等价的手工输入 + 落盘 + 重启链路）。
