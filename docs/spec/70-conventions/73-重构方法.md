## 1. 功能树：粒度与用途

### 1.1 黄金粒度：一个用户可感知的操作

- ❌ 太细：「场景名输入框」
- ✅ 刚好：「新建一个场景」（打开对话框 → 填名 → 填描述 → 保存 → 列表刷新）
- ❌ 太粗：「场景管理」（含新建 / 编辑 / 删除 / 切换四个独立操作）

### 1.2 用途 = 找茬，不是拍照留底

重构后必须能逐叶验证「这个功能还在不在」。每片叶子附**三列**：

```text
├── 4.2 Agent 管理
│   ├── 现状（as-is）：现在做了什么、怎么实现
│   ├── 问题（pain）：耦合 / 重复 / 边界不清 / 数据链断
│   └── 方案（to-be）：重构后应如何、涉及哪些文件
```

**典型问题：同构重复** —— 同一类编辑器在两个数据源各维护一份，字段几乎相同却互不同步 → 统一为一个组件 + `mode` 区分，数据层各自存。

**典型问题：新功能侵入管道** —— 新能力应只在输入端加一步（如新增转写步骤），不侵入既有执行链。

## 2. 六步流程（输入 → 怎么做 → 输出 → 完成标准）

| Step | 目标 | 关键产出 |
|------|------|---------|
| 1 功能树整理 | 前端入手反向追踪（组件 → API → Service → DB） | 功能树（每叶 as-is / pain / to-be）+ P0~P3 问题排序 |
| 2 功能决策 | 逐功能判定 **保留 / 删除 / 合并 / 新增** | 功能决策矩阵 + 废弃代码清单 + 新增需求描述 |
| 3 架构设计 | 按功能做数据 / 分层 / 接口 / 扩展设计 | 架构设计文档（数据流、模块划分、接口） |
| 4 制定规约 | 编程规范 + 安全规范 + 命名规范 | [71-编程规范](71-编程规范.md) · [72-工具开发规范](72-工具开发规范.md) |
| 5 分层分批实现 | 自底向上（模型 → 存储 → 领域 → 执行 → 宿主 → 前端） | 可编译代码 |
| 6 编译 + 测试验证 | 通过编译 + 功能无遗漏 + 安全审查 | 验证记录 |

### 2.1 Step 2 关键动作

- **删除项识别**：前端反向追踪（叶子 → API → 后端方法）；存储反查（有写无读的表 / 字段）；API 覆盖率差集（后端方法 − 前端调用）。
- **新增项评估**：加这个功能要改多少既有文件？能否只加文件不改旧代码（开闭原则）？

### 2.2 Step 3 四个维度

- **数据设计**：`[数据源] → [存储] → [加载时机] → [消费方] → [回写/失效]`；单源真理（同类数据仅一处写入口）；前后端字段对齐（JSON tag 统一）。
- **分层设计**：层间依赖单向（上层依赖下层）、无循环依赖、每层职责单一。
- **接口设计**：按领域分组；入参有类型定义（不传 `map[string]interface{}`）；返回统一结构。
- **扩展设计**：模块间依赖倒置（依赖抽象接口）；DTO 与内部 Model 不相混（防腐层）。

## 3. 问题检查维度框架（六层）

| 层 | 关注点 |
|----|--------|
| 1 代码质量 | 超长文件 / 函数、魔数、裸 `err`、命名（脚本可扫） |
| 2 数据层 | 单源真理、字段对齐、读写一致性、迁移策略 |
| 3 领域层 | 职责边界、重复逻辑、状态机完整性 |
| 4 扩展层 | 开闭原则、插件 / 接口点、配置驱动能力 |
| 5 架构层 | 分层与依赖方向、循环依赖、模块边界 |
| 6 运行层 | 可观测性、错误恢复、资源与并发 |

**应用顺序**：代码质量 → 数据层 → 领域层 → 扩展层 → 架构层 → 运行层（前两层可脚本化，后四层靠评审）。

## 4. 设计方法论（四招）

| 手法 | 抓手 |
|------|------|
| **加强边界** | 明确模块出入口；对越界访问说「不」；用类型 / 接口固化契约 |
| **降低复杂度** | 拆分超长文件 / 函数；消除隐式依赖；用常量替代魔值 |
| **解耦** | 依赖倒置；事件化（发布-订阅）替代直接调用；防腐层隔离外部模型 |
| **模块化** | 单文件单职责；可独立测试；可独立替换实现 |

> 本仓库的落地形态：组件间一律走 MQ（见 [11-MQ与消息](../10-architecture/11-MQ与消息.md)），工具执行经 gateway 唯一入口（见 [26-mcp-gateway](../20-modules/26-mcp-gateway.md)）。

## 5. 三层防护模型（工程级保障）

| 层 | 目标 | 手段 |
|----|------|------|
| 1 输入防线（Security） | 不信任外部输入 | 参数校验、路径约束（见 [14-安全域-agentbox](../10-architecture/14-安全域-agentbox.md)）、权限最小化 |
| 2 运行防线（Reliability） | 出错可恢复 | 重试 / 超时 / 熔断、错误分类与恢复（见 [35-错误处理与恢复](../30-function-points/35-错误处理与恢复.md)）、状态可恢复 |
| 3 可观测性（Observability） | 出问题能定位 | 结构化日志（见 [71-编程规范](71-编程规范.md) §5/§12）、事件可追踪、关键指标 |

**优先级**：输入防线 > 运行防线 > 可观测性（MVP 常砍掉后两层，重构时按此顺序补回）。

---

## 6. 从问题到修复方案

1. 按 **P0（数据断链）→ P1（严重质量）→ P2（扩展性）→ P3（规范）** 排序。
2. 每个 P0/P1 必须给出：现象 → 证据（文件 / 行）→ 修复方案 → 影响面。
3. 修复后回归验证；**「重构 ≠ 签名不变」**——允许为正确性改契约，但须同步文档（[61-消息一览](../60-reference/61-消息一览.md) 等）与测试（见 [50-测试体系](../50-testing/50-测试体系.md)）。
