> **交叉引用（2026-09-19，U1 跨进程入口）**：**P3-1（去中心化 MQ/自研）/ P3-5（分布式多实例）/ P3-8（per-instance gateway 实例 + cache，T-36）的落地前置 = 跨进程入口拍板** —— 方案（5 候选）与推荐（**A · HTTP + SSE/POST**，最小切片 = 先跑通「1 服务端 + 1 浏览器客户端」）见 [19 §8（§U1）](../10-architecture/19-多租户服务端形态.md)；登记 [40 I-104](40-演进计划.md)。**本表批次结论不变。**
>
> **P3-6 定调（2026-09-11）**：**`inprocess` 不是关键**；关键是**组件要对外提供这种能力**——「通过 mq 可以获取**数据 / 状态**、**操作 llm / task**」才是核心诉求。`ask_user` / `llm_run` / `tool_stop` / `tool_result` 是**工具视角**的封装，故表现为"只能进程内"；应改为**能力面暴露**，工具退化为其消费者。
>
> 已澄清的三条约束：
> 1. **编排可外置、执行归位**——`llm_run` 的每一步 LLM 均可表达为 `session-start` / `session-send` / `session-complete` + `tool-result` 回灌，故**编排器可外挂、会话仍在 server**；`ask_user` 改为**非阻塞轮末提问（推荐项）**后即无跨进程等待；`tool_stop` / `tool_result` 的**发起**可外挂、**执行**必须在归属进程（`context.CancelFunc` 不可序列化）。
> 2. **状态两份、归属分明**——任务树 = **DB 投影**（`data-tasktree-*`，任意进程可读）+ **内存句柄表** `task_id → {cancelFn, parentID}`（**每进程一张、不可序列化**；gateway 一张已有、server 一张待抽离）。取消按 `task_id` 路由到归属进程（gateway 任务 → `gc.TaskCancel`；server 侧 goroutine → server 自取消）。
> 3. **ask 需按会话标注**——ask 现为**阻塞式全局弹窗队列**（`askUserManager`），与"属于哪个 chat"矛盾；应改为**所属会话内联**并在**会话树节点**打标。数据侧其实已有：server 为每次 ask 建 `kind=ask_user` 任务节点且 reply 前恒 `running`（已落库、`full` 模式可见），缺的是前端标注（`SessionTreeNode` 的 `kindIcon`/`kindColor` 无 `ask_user` case → 落 `default` 灰色"其他工具"）。
>
> **拆分提示**：第 3 条（ask 会话树标注 + 非阻塞化）**不依赖 P3-1**，可先在单机落地；第 1/2 条依赖去中心化 MQ。
