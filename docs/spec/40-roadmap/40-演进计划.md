> **P3-6 定调（2026-09-11）**：**`inprocess` 不是关键**；关键是**组件要对外提供这种能力**——「通过 mq 可以获取**数据 / 状态**、**操作 llm / task**」才是核心诉求。`ask_user` / `llm_run` / `tool_stop` / `tool_result` 是**工具视角**的封装，故表现为"只能进程内"；应改为**能力面暴露**，工具退化为其消费者。〔历史口径：`llm_run` 与 `tool_stop` 均已删除（`tool_stop` 2026-11-04，`task_stop` 为唯一停止入口）。〕
> **〔2026-10-17 用户口径（D7）〕**：方向进一步明确 —— **所有工具调用全部移到进程外**（**server / gateway 本体不迁**；迁出的是 LLM 可调用工具与 gateway 注册工具的 handler / executor）；server 进程**对外提供 5 类原子能力**（文件变更监控 / 数据库读写 / 配置读写 / LLM 调用 / MCP 调用）；外部工具 / 插件经 **TCP/IP 或 UDS** 消费这些原子能力，进而实现任务、会话、配置、能力面、文件、记忆、LLM/simple、**GUI 控制**等动作，操控 server 与 GUI。专题稿 = [插件桥接端口设计方案](../../bridge-plugin/插件桥接端口设计方案.md)（D7 / §0.1 / §9 S10–S11）。
>
> 已澄清的三条约束：
> 1. **编排可外置、执行归位**——`llm_run` 的每一步 LLM 均可表达为 `session-start` / `session-send` / `session-complete` + `tool-result` 回灌，故**编排器可外挂、会话仍在 server**；`ask_user` 改为**非阻塞轮末提问（推荐项）**后即无跨进程等待；`tool_stop` / `tool_result` 的**发起**可外挂、**执行**必须在归属进程（`context.CancelFunc` 不可序列化）〔历史口径：`tool_stop` 已删除，2026-11-04，`task_stop` 为唯一停止入口〕。
> 2. **状态两份、归属分明**——任务树 = **DB 投影**（`data-tasktree-*`，任意进程可读）+ **内存句柄表** `task_id → {cancelFn, parentID}`（**每进程一张、不可序列化**；gateway 一张已有、server 一张待抽离）。取消按 `task_id` 路由到归属进程（gateway 任务 → `gc.TaskCancel`；server 侧 goroutine → server 自取消）。
> 3. **ask 需按会话标注**——ask 现为**阻塞式全局弹窗队列**（`askUserManager`），与"属于哪个 chat"矛盾；应改为**所属会话内联**并在**会话树节点**打标。数据侧其实已有：server 为每次 ask 建 `kind=ask_user` 任务节点且 reply 前恒 `running`（已落库、`full` 模式可见），缺的是前端标注（`SessionTreeNode` 的 `kindIcon`/`kindColor` 无 `ask_user` case → 落 `default` 灰色"其他工具"）。
>
> **拆分提示**：第 3 条（ask 会话树标注 + 非阻塞化）**不依赖 P3-1**，可先在单机落地；第 1/2 条依赖去中心化 MQ。
