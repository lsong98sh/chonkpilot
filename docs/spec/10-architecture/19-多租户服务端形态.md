## 1. 问题与目标

- **要解决的问题**：现有多形态（GUI 单体 / CLI / split 分离）中，**唯一带窗口、且只能单人单机使用**——GUI 前端上行不监听端口（虚拟源拦截），无任何用户 / 项目 / 协作概念，`work_dir` 由客户端自报。要支持「一台服务端、多用户、多项目、可邀请协作」的服务端形态，需要同时补齐**编译形态、前端运行模式、服务端作用域**三条轴。
- **目标（用户口径，可验收）**：
  1. 新增编译形态 **`-browser`**：**单体**、server **监听端口（默认 `5668`**，实测该端口空闲）。
  2. 前端含 **注册 / 登录 / 选择项目 / 新建项目**。
  3. 按**登录用户创建目录**，用户**只能选自己目录下的目录**。
  4. 可**邀请他人协作**（角色 `owner` / `manager` / `participant`），**每个参与者一份 datadir**。
- **目录映射（目标态）**：

| 目标路径 | 等价于 |
|---------|--------|
| `server-workspace/<user>/.chonkpilot` | `~/.chonkpilot` |
| `server-workspace/<user>/projects/<project-id>` | **项目目录**（= work_dir） |
| `server-workspace/<user>/projects/<project-id>.data/<user-id>` | `~/.chonkpilot/data/<prj-uuid>`（prjusr 数据根） |
| `<exeDir>/chonkpilot/`（新增） | 用户 / 项目 / 关系与**角色**的元数据库 |

- **非目标**：不改 `paths.ResolvePath` / `fileops.ValidateFilePath` 的解析语义；不改 `tools/call` 的 `_meta["chonkpilot"]` 上下文链；**61 消息面零变更**；不引入外部 IDP。
- **开放问题（待用户拍板）**：
  1. `server-workspace` **根位置**（建议 **exe 同级**，与 `<exeDir>/capability` 同构）；
  2. **认证方式**（建议**本地账号 + 服务端令牌**，无外部 IDP）；
  3. 是否**复用 `data/<prj-uuid>` 结构并加 user 层**（建议复用结构 + 加一层）；
  4. **权限落层**（建议**服务端中间件** + `filesys.withinWorkDir` **第二道**）；
  5. **用户名是否直接作目录名**（建议**清洗规则**或 uuid 目录 + `chonkpilot/` 映射表，参考 `src/lib/core/paths/paths.go:74-94 sanitizeInstance`）。

## 2. 总体方案

```text
浏览器 ──HTTP──▶ chonkpilot-browser（单体 exe，默认 :5668）
                   ├─ 静态面：/ 与 /show/（复用 fileserver 语义）
                   ├─ 上行面：/publish 等价（保留 {type,payload} 与 {ok,result,errors} 信封）
                   ├─ 下行面：SSE（事件推送，替代 GUI 的 w.Eval）
                   ├─ 认证与会话：注册/登录/令牌（全新模块）
                   ├─ 作用域裁决：用户目录白名单 → 下发 work_dir / data_dir
                   └─ 内嵌同一 lib 集：server（llm）→ persist → filesys → gateway(mcp-server)
```

**三条改动轴**：① **编译形态**（新 module + 新脚本，不污染 gui）；② **前端运行模式**（前端工程独立 `src/frontend` + 双入口，见 §3.2）；③ **服务端作用域**（work_dir 由服务端下发 + `filesys` 归属校验）。

> **口径确认**：**「browser 下，用 browser 替代 gui 层」** —— 本形态**替代 gui 层职责**：前端承载（§3.2 双入口）+ 会话托管（认证/作用域裁决/下行推送）+ `-bridge-url` 对端角色；原 gui 层的 **native 能力必须替换或禁用**（`gui.dir.*` / `console.open` / `reveal` / `capture` / `toolchain.detect` / `system.builtins`，§3.3），**不复用 `testserver` 的 `/eval`·`/click`**。连带口径：**split 下 gui 与 instance 绑定、无需分割**（`src/lib/gui/main.go:533,586,609`）——需按 instance 分离的是**服务端**，详见 [20-实例隔离与后端分离](20-实例隔离与后端分离.md) §1 D3/D4。

**关键设计取舍**：**数据层无需新机制**——`persist.Options.UsrPath` 已证明「注入 UsrPath → prjusr 根随之重定位」，e2e harness 已用独立 `--data-dir` + 独立 `HOME`/`USERPROFILE` 起多实例。

### 3.2 前端工程独立与双入口（**✅ 已实施**，实施记录见 [§8.10](#810-已实施前端工程独立--双入口)）

> **本节取代**此前「路线 A 编译时复制覆盖 / 路线 B 抽 `src/client`」两选项与「推荐折中（同工程双入口）」表述。
> **用户口径原话**：「前端，独立为一个目录 `src/frontend`。`npm build` 结果放入原来的 `frontend/dist` 目录即可 embed。双入口：`index.html` 给 browser 用；embed 使用 `embed.html`，编译后复制改名 `index.html`。」（原话笔误 `chonkpilot-fontend`，正文一律用 **`src/frontend`**。）

**决策要点**

1. **前端工程独立**：源码工程从 `src/gui/frontend` 抽出为仓库级目录 **`src/frontend`**（**唯一源码真相**）；**构建产物仍落到 `src/gui/frontend/dist`**，使 GUI 既有 `//go:embed all:frontend/dist`（`src/lib/gui/main.go:40`）**无需任何 Go 代码改动**即可继续工作。
2. **双入口、按形态分别构建**：`index.html` = **browser 形态**入口；`embed.html` = **GUI / embed 形态**入口，构建后**复制改名为 `index.html`** 再供 embed 使用。
3. **强制约束（⚠️ 不可省）：两形态产物不得落在同一目录** —— browser 的 `index.html` 与 embed 的 `embed.html→index.html` **最终文件名相同**；若共用同一 `dist` 会**互相覆盖**，导致 GUI 嵌到 browser 入口（或反之）。**要求**：两形态**各自输出到独立目录**——如 browser → `dist/browser/`（该目录内为 `index.html`）；GUI → `dist/`（`embed.html` 构建后**重命名为该目录的 `index.html`**）；**embed 只指向 GUI 那一份**。

**可行性依据（既有事实，本方案无需改 Go 代码）**

| 既有事实 | 落点 | 意义 |
|------|------|------|
| 前端 `base: './'` | `src/frontend/vite.config.js` | 产物与宿主 / 端口无关 |
| 上行只用**相对** `fetch('/publish')` | `src/frontend/src/utils/mq.js:94` | 换 HTTP 宿主无需改 API 基址 |
| GUI 在 `index.html` 上做 `instance_id` 注入 | `src/lib/gui/main.go:423-432` | **重命名后文件名仍是 `index.html` → 注入逻辑不受影响**（本方案可行的关键） |

> **现状：无 monorepo**（`package.json` 无 `workspaces`、无 `pnpm-workspace.yaml`、无 `go.work`；Go 侧每目录独立 `go.mod` + `replace`）→ `src/frontend` 为**同级独立工程**（自带 `package.json`），**不依赖 workspace 机制**。

### 3.4 安全前置（⚠️ 阻塞项）

> **本项为落地前置：不先解决，多租户下必然越权。**

- **缺口**：`src/lib/filesys` 的 `work_dir` **直接取自请求 payload**，仅校验「path 在 wd 内」、**不校验 wd 归属**（`filesys.go:74,92,144,376`）→ 多租户下**越权**（任意登录用户可指定他人目录 / 任意目录）。
- **白名单入口只有 3 处**：`filesys.withinWorkDir`（`src/lib/filesys/filesys.go:376-378`）· `fileserver.go:49-62`（allowed = `WorkDir` + `DataDirs`）· `src/lib/gui/bridge/local.go:318,341`（`openNewWindow` / `opendir-dialog`）。
- **R-11 挡不住**：[16-路径解析规范 §8](16-路径解析规范.md) 只校验**路径形态**（绝对 / `~/` / `!/`，`src/lib/core/paths/pathcheck.go:18`、`paths.go:106-135`），**不做归属校验**；且 `--work-dir` / `--data-dir` **允许相对与 `../`**（`src/lib/core/paths/paths.go:150`，规范明示「**有意行为**」）→ **单靠 `ResolveDir` 挡不住越界**。
- **修法（P3 批次）**：**`filesys` 忽略请求 `work_dir`，改由 instance 绑定**（服务端在注册/调用链上绑定用户目录），`withinWorkDir` 退为**第二道**；越权用例必须入测试。
- **交叉引用**：本条即 [20-实例隔离与后端分离 §4](20-实例隔离与后端分离.md) **缺口 6**（filesys 采信请求 `work_dir`、不校验归属），**归入本篇 P3 批次 = 强制前置**（不重复登记：缺口 6 与 [I-84](../40-roadmap/40-演进计划.md) 的 P3 为同一项，只交叉引用）。

> **安全前置口径**：**filesys 不改**（以 `workdir` 为管理单位、**维持现状**；**本形态不要求「`filesys` 忽略请求 `work_dir`、改由 instance 绑定」**）；**安全改由「instance 绑定 `work_dir`」+「agentbox 执行层限制（`security-*` = 可读 / 可写目录、递归）」承担**（agentbox 定位见 [14-安全域-agentbox](14-安全域-agentbox.md) §3.1/§4）。故上文「**修法（P3 批次）**」**不属本次实施范围**，**P3 不再作为本形态的强制前置**（§7 已同步）。

## 6. 边界与异常

- **越权（最高优先）**：未做 §3.4 前，任何登录用户可借 payload 的 `work_dir` 读写任意目录。**filesys 不改；安全由「instance 绑定 `work_dir`」+「agentbox 执行层限制」承担，P3 不属本次实施**。
- **同用户 / 同项目并发**：bbolt 同库双开会冲突（已定「**允许同用户多项目双开**（不同 data-dir）、**同项目双开拒**（lock）」）→ 服务端需给出明确错误与提示。
- **只读安装位置**：`<exeDir>/chonkpilot/` 落在只读目录（如 Program Files）时写入失败 → 需降级策略（同 [02-配置层级](../00-overview/02-配置层级.md) 口径：仅展示 + 提示，不报错）。
- **迁移**：prjusr 根加 user 维度属**数据布局变更**，旧目录需一次性迁移（`src/lib/data/persist/migrate.go`）；迁移须**幂等**。
- **用户名作目录名**：非法字符 / 保留名 / 大小写不敏感冲突 → 必须清洗或用 uuid 目录 + 映射表（参考 `paths.go:74-94 sanitizeInstance`）。
- **参与者 datadir**：每个参与者一份 → 数据不共享；**协作 ≠ 共享同一 prjusr**，语义须在 UI 明确，避免「看不到对方会话」的误解。
- **native 能力缺失**：`gui.dir.open-dialog` 等被禁用后，前端相关入口必须**隐藏或降级**（否则报错）。

### 8.1 问题定义

- **browser 形态要求「多客户端 ↔ 单服务端（内部多 instance）」**（§1 目标：一台服务端、多用户、多项目；§2 拓扑）。而**跨进程 MQ 面不存在**（事实见 8.2）→ **入口缺失 ⇒ 多客户端架构无法成立**。
- **GUI（standalone）形态天然 1 进程 1 instance**（`src/lib/gui/main.go:533` 实例 uuid · `:586` WebView2 profile · `:609` 注入桥），**不跨进程、不受本节影响**；本节只解决「服务端与前端分处不同进程」时的入口与传输。
- **不是「MQ 没做好」**——是**入端口**缺位：前端→后端的 `/publish` 现由 WebView2 虚拟源拦截提供（`src/lib/gui/main.go:408-449,698-712`），下行是宿主 `w.Eval`；二者都**只在同进程宿主内成立**（§3.1 b）。

### 8.3 候选方案（5 个）

#### 方案 A · HTTP + SSE/WS 入口（**推荐**）

- **机制**：服务端进程（`chonkpilot-server.exe` 或新 `chonkpilot-browser`）**新建 HTTP 监听**：上行 `/publish` 等价（保持 `{type,payload}` 请求与 `{ok,result,errors}` 应答信封，§3.3）；下行 **SSE**（§3.3 推荐）+ POST 上行；静态面 `/` + `/show/` 复用 fileserver 语义。前端以 **`src/frontend` 的 browser 入口**（§3.2 `index.html`）接入；事件按 instance 过滤后下发（复用 `acceptEventInstance`）。
- **需要改的模块**：新增入口/会话模块 + 静态面；前端（browser 入口，mq 客户端基本不改）；instance 注册由 HTTP 会话绑定（`instance-register` 载荷不变）；native 能力替换/禁用（§3.3 清单）。
- **与既有 instance 隔离的关系**：instance 归属改由**服务端会话/用户**决定（不再由客户端自报 `work_dir`）；同进程多 instance ⇒ 缺口 1–8 适用（**已实施 1/2/3/4/5/7/8**；6 按用户口径不纳入、9 策略性）。**不需要跨进程总线**。
- **优点**：与已定决策**完全一致**（§3.2 前端独立、§3.3 SSE+POST、[20 D4](20-实例隔离与后端分离.md)「browser 替代 gui 层」）；**MQ 消息面零变更**；不改 mq 实现；HTTP 生态成熟（鉴权/静态/长连接现成）；可增量落地。
- **风险与代价**：服务端须**新建监听**（当前 0 端口）；需**鉴权/会话/作用域**（§3.5 `server-workspace` 仍待拍板）；SSE 单向 ⇒ 上行另走 POST（§3.3 已定）；事件过滤须严格（已有实现）；**不得复用 testserver `/eval`·`/click`**（§3.3）。
- **是否新增 MQ 主题**：**否**（上行/下行沿用既有主题与信封）→ **不触发 61 冻结**。
- **对测试体系的影响**：新形态旁路，**不破坏**既有 harness（只认 `dist/desktop/chonkpilot.exe`，§3.2 e2e 影响）；新用例仍须 **mq 驱动 + mq 断言**（[50 §1](../50-testing/50-测试体系.md)）；若确需新 msg/payload，**必须先过 61**（唯一准则，禁增改删）。

#### 方案 B · 跨进程总线（把 `mq` 换成 TCP / 命名管道实现）

- **机制**：`src/lib/core/mq` 增跨进程实现（TCP / 命名管道），**保留 `Emit`/`On`/Promise/通配（`>`/`*`）/`Prefix` 语义**（`bus.go:99-117`）；客户端进程与 server 进程接入**同一总线后端**。
- **需要改的模块**：`src/lib/core/mq`（新增实现 + 传输层）；所有 `mq.New` 调用点（`src/lib/gui/main.go:537` · `src/lib/llm/main.go:46`）；心跳/桥的传输口径（`heartbeat_split.go:39`）。
- **与既有 instance 隔离的关系**：隔离逻辑本就按 instance 分桶（第一/二批），**跨进程后语义不变**；但「单进程服务多 instance」的缺口面会**真实暴露**（不再是白盒替代）→ 依赖已实施的 1/2/3/4/5/7/8。
- **优点**：**消息面语义零变更**（主题/payload 全保留）；客户端（gui/cli/前端桥）代码基本不改；与 [40 P3-1](../40-roadmap/40-演进计划.md)「去中心化 MQ（自研）」方向**一致**。
- **风险与代价**：需自研传输/序列化、断线重连、订阅生命周期、**跨进程 Promise 应答关联**（`Value.Result` 写回语义在跨进程下需应答协议）、鉴权与暴露面；**工作量最大、面最广**，且与业务迭代并行。
- **是否新增 MQ 主题**：**否**（保留既有主题；传输层内部帧不算业务主题，但须登记文档）。
- **对测试体系的影响**：L1 单测现基于进程内实现 → 新实现须**同一套语义**，建议同一用例矩阵跑两实现；e2e harness 不变。

#### 方案 C · 每 instance 一进程（服务端仅做路由/托管）

- **机制**：服务端只做**路由/托管/生命周期**；**每个 instance 起一组进程**（llm + gateway，与 D2「`llm` 按 instance 分离」衔接）；filesys/data 归服务端或随 instance（D2 合并方向）。
- **需要改的模块**：服务端进程管理（拉起/回收/端口/心跳）；persist/data 绑定；filesys 归属；编排与可观测。
- **与既有 instance 隔离的关系**：**最强隔离** —— 「进程 = instance」，缺口 1–8 天然规避（同 standalone）；但「服务端托管多 instance」本身需路由与生命周期管理。
- **优点**：崩溃/资源隔离好；回收 = 进程退出；与 D2/D3 口径一致。
- **风险与代价**：**进程数随 instance 线性增长**（内存/句柄）；仍**不解决「前端 ↔ 服务端」入口**（本方案**依赖 A 或 B**，不能单独成形态）；启动/回收时序、端口分配、stale 进程（[I-74](../40-roadmap/41-未决项登记.md) 同类问题放大）。
- **是否新增 MQ 主题**：**否**（沿用既有）；进程管理面若新增端点/主题则须过 61。
- **对测试体系的影响**：e2e 需管理多进程（类似 [I-74](../40-roadmap/41-未决项登记.md)）；用例编排更重。

#### 方案 D · browser 形态单 instance 裁剪（先做「单实例浏览器访问」）

- **机制**：browser 进程内**只承载 1 个 instance**（同 standalone 的「进程 = instance」），HTTP 暴露给浏览器；**多客户端/多租户延后**。
- **需要改的模块**：**最小** —— 复用 gui 内嵌 server（`src/lib/gui/main.go:559-577`）+ 新 HTTP 入口（SSE/POST）+ `src/frontend` browser 入口；**不做**鉴权/多用户/白名单。
- **与既有 instance 隔离的关系**：1:1，**缺口不显现**（同 standalone）。
- **优点**：**最快跑通**「1 服务端 + 1 浏览器客户端」；不碰 mq、不碰 61；为方案 A 打地基（入口面先立）。
- **风险与代价**：**多客户端/多用户/协作目标推迟**；单 instance 仍需解决「`work_dir` 从哪来」（服务端下发）与 native 能力禁用；若入口面预留不足，后续多客户端**返工**。
- **是否新增 MQ 主题**：**否**。
- **对测试体系的影响**：最小；与 standalone harness 并行；新用例须 mq 驱动。

#### 方案 E · 混合（A 入口 + C 进程托管，对齐 D2 混合方向）

- **机制**：**A 作入口/前端承载** + **C 作后端托管**：服务端接 HTTP/SSE，按 instance（或 workdir）**拉起 llm/gateway 进程**，事件经服务端回流到对应客户端；与 [20 §5 C（用户倾向）](20-实例隔离与后端分离.md) 同向。
- **需要改的模块**：A 的入口面 + C 的进程编排 + 路由/归属映射（instance ↔ 进程 ↔ 客户端）。
- **与既有 instance 隔离的关系**：进程级隔离 + 服务端路由；缺口由「进程 = instance」规避，服务端只看路由表。
- **优点**：隔离与伸缩兼顾；与 D2 / [20 §5 C](20-实例隔离与后端分离.md) / `only-stdio 可隔离`（agentbox 只约束「扫描到的 runtime」、仅 stdio 的 MCP server 可隔离，[40 P1-5](../40-roadmap/40-演进计划.md)）自洽。
- **风险与代价**：**A + C 的代价叠加**（入口 + 进程编排 + 路由）；复杂度最高；**应先立 A、再评估 C**（与 [20 §5 推进建议](20-实例隔离与后端分离.md) 同序）。
- **是否新增 MQ 主题**：**否**（沿用既有）；路由层若需新面须过 61。
- **对测试体系的影响**：入口面与进程编排分别验证，再合测。

### 8.5 推荐（1 个）：**方案 A**，以 **方案 D 为最小可交付切片**起步

**推荐理由**：① 与**已定决策完全一致**（§3.2 前端工程独立 + 双入口、§3.3「SSE + POST」、[20 D4](20-实例隔离与后端分离.md)「browser 替代 gui 层」）；② **不做跨进程总线**（B）即可满足 browser「多客户端 ↔ 单服务端」—— 前端本就走 HTTP（`fetch('/publish')` 相对路径，`mq.js:94`），无需复用 mq 内部语义；③ **MQ 消息面零变更**（§5；无需触发 61 冻结）；④ **复用 instance 隔离成果**（缺口 1/2/3/4/5/7/8 + `acceptEventInstance` 事件过滤）；⑤ 与「**only-stdio 可隔离**」自洽（入口不改 executor spawn 语义）。

**最小可交付切片（先跑通「1 服务端 + 1 浏览器客户端」）**：

1. **立入口（零业务新增）**：在既有服务端进程上新建 HTTP 监听 —— `/publish` 等价（保持信封）+ **SSE 下行** + 静态面（复用 fileserver 语义）；前端用 `src/frontend` 的 browser 入口（§3.2）。
2. **绑定单 instance**：`work_dir` / `data_dir` 改由**服务端下发**（HTTP 会话绑定）；`instance-register` 载荷保持既有字段（§3.5）。
3. **只读面跑通**：经 mq 驱动 + mq 断言（[50 §1](../50-testing/50-测试体系.md)）验证静态面 / 文件树只读 / 会话历史读取。
4. **再加第 2 个客户端**（切片 2）：事件按 instance 过滤下发（复用 `acceptEventInstance`），引入鉴权与实例上限（`DefaultMaxInstances` 已实施）。
5. **再评估 C/E**（多 instance 进程托管）：依赖 [I-74](../40-roadmap/41-未决项登记.md)（同 work-dir 并发第二实例不就绪）先有结论。

> **不推荐先说**：B 的传输层（面最大、与业务解耦性差）；C 单独成形态（**无入口则不可用**）。

| instance 过滤 | 复用桥同判据 `acceptEventInstance`：载荷 `instance_id` 非空且 ≠ 本实例 → **不投递** | `httpapi.go:forwardEvent/acceptEventInstance` |
| 不重复/不串 | 请求-应答**不回投为事件**（`publishV` 先 `markPublished` 标记自发布，`forwardEvent` 命中即跳过）→ 客户端 A 的请求不会出现在客户端 B 的事件流 | `httpapi.go:markPublished/isSelfPublished`、`publish.go:publishV` |
| 单客户端 | 与 D 切片**逐字节一致**（单客户端 = 广播表只有 1 个通道） | — |
| 未做 | 实例上限 / 多租户（后续批次；`DefaultMaxInstances` 未接入本入口） —— **〔订正（2026-10-08）：入口鉴权已落地（`withAuth`），见 [§8.8](#88-已实施d-切片http--sse-单-instance-入口) 表下订正注；多租户仍待后续。〕** | [40 I-104](../40-roadmap/40-演进计划.md) |
