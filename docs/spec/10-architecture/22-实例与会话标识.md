## 1. 总原则：客户端不自称

> **凡客户端可自称的标识（`instance_id` / `work_dir` / `user` / 形态），都不得作为作用域或身份依据。**
> payload 中这些字段的语义 = **「自述 / 提议」**；服务端**以连接层（入口绑定 / 凭证）为准并校验**。

四处同类问题：

| 场景 | 表现 | 归属 |
|------|------|------|
| filesys 请求 | 采信 payload 的 `work_dir` → 可声明任意目录（真越权） | G-21 ✅ 已实施 |
| 多实例 | `instance_id` 客户端可自称（单实例无害，多实例可跨实例越权） | 本条 |
| claim payload | `user` 由客户端携带（须以连接层为准 + 交叉校验） | G-28（2a）/ §6（2b） |
| 形态判定 | **UA 客户端可伪造** → 不可作鉴权依据，**仅可作日志诊断** | 本条 |

**统一链路**：

```text
连接层（token / cookie / 入口绑定）→ 服务端解析 → 内存实例表
   → instance（已校验上下文句柄）→ 注入各层
```

## 2. 术语与硬规则

| 术语 | 定义 |
|------|------|
| **token** | 不透明随机串 / cookie；**凭据**，由服务端签发（§6，**2b**） |
| **instance** | **已校验的上下文句柄** = `{instance_id, work_dir, data_dir}` 的绑定；**不是**「服务端进程」 |
| **instance-id** | instance 的标识；**由服务端绑定 / 生成**（客户端自述者不采信）。对前端**可见**（`window.__ck.instanceId` + payload `instance_id`），但**不构成凭据** |
| **client_type** | 客户端形态 = `desktop` / `gui` / `browser`，**由服务端按入口判定**（非客户端自报、非 UA） |
| **Authenticator** | 认证**门面**（可替换实现：本期本地库 / OS 账号 / LDAP / OIDC）；**属阶段 2b，未实施**（§6） |

**硬规则**

1. **token 与 instance-id 分离**（映射在服务端内存）→ token 泄漏不暴露 instance 结构。
2. **客户端不自称**（§1）：身份与作用域由入口绑定后注入；前端不携带、不判定。
3. **`work_dir` 必须服务端校验归属** → 校验通过后绑定 `instance → work_dir`，后续各层按 instance 查绑定、**忽略 payload**。
4. **形态不由 UA 判定**：`window.__ck.form` 由**服务端注入**（§6.6）。

## 3. 实例生命周期

### 3.1 认领：`instance-claim`（请求-响应）

前端启动即发起（2b 为登录 / 选目录之后；2a 无登录，直接发起）。

| 形态 | 请求 payload | 服务端取值 |
|------|------|------|
| **desktop** | **无参**（`user?` / `work_dir?` 均省略） | `work_dir` = **服务端启动参数** `--work-dir`（缺省 cwd）；本机单用户、**免鉴权** |
| **gui** | `{user, work_dir}` | 服务端**校验后绑定**：`user` **以连接层为准 + 交叉校验**；`work_dir` **校验归属权限** |
| **browser** | `{user, work_dir}` | 同上 |

> **三形态**（`desktop` / `gui` / `browser`；**形态名重整，语义翻转** —— 原 `standalone` → `desktop`、原 `desktop`（≡ team）→ `gui`）差异**只在客户端形态**（WebView2 ↔ 浏览器）与**令牌承载**（GUI = 桥注入 / browser = `Set-Cookie`）。旧稿的 IdentityProvider 档（其中一档把 GUI 的客户端断言直接视为可信）**已删除** —— `gui` 的 server **可运行在异地**，故 `gui` 与 `browser` **同等要求认证**，一律以连接层凭证为准（§6 · [61 §4.6](../60-reference/61-消息一览.md)）。

### 3.2 服务端行为（claim 成功后）

1. 生成 / 绑定 `instance_id`（2a 折衷见下）
2. 写**服务端内存实例表**：`{instance_id, work_dir, data_dir, lastBeat, client_type}` —— **进程重启即清**
3. **广播既有 `instance-register`**（主题与 payload **一字不改**：`{instance_id, work_dir, data_dir?, client_type?}`），供 `src/lib/data` / `src/lib/filesys` 登记 `instance → work_dir`（G-21 依赖它）
4. 应答**发起者** `{instance_id, work_dir, data_dir}`

> **⚠️ 2a 折衷**：入口（GUI 桥 / httpapi）**已在启动时自生成并注入 `instance_id`**（供 SSE 事件过滤、`/show` URL 等**首屏前**即需使用）。若 claim 另发新 id，会同进程出现**双 id 源**、会话与 filesys/data 立刻失配 → 2a 采「**入口绑定优先、缺省服务端生成 uuid v4**」。
> **2b 认证域成为唯一绑定方后须转为恒服务端生成**（消除双 id 源）。

### 3.3 心跳与回收

- **发布方 = 客户端**：GUI 形态的客户端 = **前端 SPA**（claim 成功后起定时器）；**CLI 的客户端 = 宿主**（无 SPA）。
- 周期 **30s**，payload `{instance_id}`；**语义 = 客户端续期**（「该实例仍在使用」），**非**「服务端存活证明」。
- 服务端 **90s** 未收 → **回收该实例 + 数据根绑定** → 后续请求 `instance-unauthorized`。
- **保持既有 `-tags split` 门控**：**单体默认构建不发布、不判超时**；分离形态编入后由判定侧（llm / persist / 插件）各自 sweep。见 [28-plugins §2](../20-modules/28-plugins.md)。

### 3.4 错误码（复用既有 `{ok, error}` 信封，**不新增字段**）

| 码 | 触发 | 前端动作 |
|------|------|------|
| `instance-unauthorized` | 未登录 / 令牌失效 / 90s 未续期被回收 | **跳登录**（2b）；2a 显示明确占位提示 |
| `instance-forbidden` | 已登录但**无权访问该 `work_dir`**；实例数超上限（64） | **不跳登录**，提示换目录 |

## 4. 失效与重建

```text
服务端重启 → 内存实例表清空 → 客户端带旧 token → 无法解析 → instance-unauthorized
  ├─ desktop → 直接重新 claim（服务端启动参数）
  ├─ gui      → 免登录令牌自动重登（2b）→ 重新 claim
  └─ browser  → 跳登录页（2b）
```

> ⚠️ **「未认证」必须是消息面错误码**（如 `{ok:false, error:"instance-unauthorized"}`），**不能是 HTTP 401** —— GUI 走 MQ，没有 HTTP 状态码。三形态统一由前端据此决策。

**cookie 是缓存，不是真相**：cookie 存在 ≠ instance 有效；失效即重走 §3。

## 5. 承载：前端零身份逻辑

| 形态 | 凭据 / 令牌承载 | 前端是否读 |
|------|-----------|:---:|
| browser | **`Set-Cookie`**（`/publish` / `/events` / `/show` 同源自动携带） | ❌ 不读 |
| gui（desktop / gui） | **桥在转发时注入**（进程内） | ❌ 不读 |

**为什么必须 cookie（而非 localStorage）**：`EventSource('/events')` 与 `<img src="/show/…">` **无法自定义 header**，只能靠 cookie 自动携带。

> 🆕 **命名**：**构建/部署面**已重整 —— `build-standalone-gui.ps1` → `build-desktop.ps1`（产物 `dist/desktop/`）· `build-split.ps1` → `build-gui.ps1`（产物 `dist/gui/`）；**（第二刀）形态标识亦已重整（语义翻转）**：原 `standalone` → **`desktop`**（桌面单体）、原 `desktop`（≡ team）→ **`gui`**（GUI 客户端 + 独立 server），`browser` 不变 —— 即**本文 §2 `client_type` 行 · §3 认领表 · 本表**已按新名改写（运行时语义标识 `window.__ck.form` 同步，见 [61 §4.6](../60-reference/61-消息一览.md)）。**产物名同步**：桌面单体宿主 `chonkpilot-gui.exe` → `chonkpilot.exe`；gui 形态客户端 → `chonkpilot-gui-client.exe` / `chonkpilot-cli-client.exe`，服务端 `chonkpilot-server.exe` 名不变（gui 与 browser **共用同一份 server**）。

**实测结论**（PoC `TECH-POC/webview2-cookie`，**5/5 通过**）

- GUI 虚拟源 `https://app.localhost`（无 HTTP server，`WebResourceRequested` 拦截）下，cookie **行为与标准 HTTP 源一致**：可设置、拦截器合成 `Set-Cookie` 生效、同源 `fetch`/`EventSource` 自动携带（含 HttpOnly）、跨进程重启持久。
- ⚠️ **cookie 口径（硬规则 · WebView2 实测）**：
  - **默认 = 会话 cookie（不设 `Max-Age` / `Expires`）** → **关闭浏览器即失效**。这是**期望行为**（短命凭据），不是缺陷。
  - 实测事实：不带 `Max-Age` 即**不跨进程重启持久**（一度被误判为「WebView2 不支持持久」）——该「不持久」**正是被采纳的语义**。
  - **长期凭据另立一层**：gui 形态的**免登录令牌**存 `~/chonkpilot`（**加密**、**不过期**、**须可自证**，见 §6.3），与会话 cookie 不是同一物。

**前端零身份逻辑**

- 前端**不读 cookie、不参与身份判定**；**但持有 `instance_id`**（`window.__ck.instanceId` 与服务端注入的 payload 字段），仅用于消息面携带
- 页面所需元信息（是否已认证 / 是否需登录 / 形态）由**入口注入**（同现有 `injectBootstrap`，§6.6）
- 服务端在**入口处**解析凭证 → 注入 `{instance_id, user, work_dir, data_dir}` 给后续各层
- **下行事件按「连接」过滤**，不依赖 payload

**兼容口径（61 零变更）**：payload 中的 `instance_id` **保留但语义降级**为「请求方自述、服务端不采信，**以入口绑定为准**」。

## 6. 认证（**阶段 2b · ✅ 已实施**）

> **已实施**：**2b-1**（`src/lib/data/auth` 库 + `Authenticator` 门面 + `login-*` 三主题 + bcrypt + 会话 / 免登录双令牌 + 入口承载）与 **2b-2**（claim 真实权限校验 + `requireAuth` / `authed` 真接线 + 前端登录 / 注册视图 + `auth.projectRoots`）。首屏 `requireAuth` / `authed` 已由**服务端按形态与凭证判定**（非客户端自称）。台账见 G-30 / G-31。

### 6.1 门面与 `login` 域（请求-响应）

- 认证走**门面** `Authenticator`（可替换实现：本期本地库 / OS 账号 / LDAP / OIDC）
- `login` 域：`login-register`（自助注册：用户名 + 密码）/ `login-in` / `login-out`；注册成功建议**自动登录**（[61 §4.6](../60-reference/61-消息一览.md)）

### 6.2 注册与 UID

- 注册生成 **UUID（UID）**，**一用户一 UUID**
- 建数据目录 `<用户数据根>/<uid>/`

### 6.3 密码与令牌

- 密码哈希 = **bcrypt**（**明确不用 MD5** —— 太快、无盐、跨用户可比）
- **令牌两类**：
  ① **会话令牌**（browser）= `Set-Cookie`，`HttpOnly`，**不设 `Max-Age`**（关浏览器即失效）；
  ② **免登录令牌**（gui，存 `~/chonkpilot`）= **自证型** —— `{用户名, UID, 密码哈希}` **加盐加密**成一个长串（建议 **AES-GCM**，不用 DES），服务端解密即得身份；含密码哈希使其天然支持「**改密即踢下线**」。

### 6.4 存储划分

| 库 | 位置 | 内容 |
|------|------|------|
| **auth 库** | **app-server 的 exe 旁**（本期 bbolt 单文件，如 `auth.db`；亦可用 CSV） | 用户 · 项目 · **用户-项目关联** · 令牌 → **属数据层**，且**与业务库分离** → 将来可整体换远程 DB 而业务库不动 |
| **业务数据** | `<用户数据根>/<uid>/`（**实例侧**） | **每用户一套库** → **天然隔离，无需在任何表加 user 字段** |

### 6.5 配置与硬前提

- 配置：`auth.allowRegister`（默认 `true`；**对外暴露必须关闭**）；登录会话**闲置失效建议 12h**
- **硬前提**：① **HTTPS**（否则密码明文过网，哈希再强也无用）——非 HTTPS 且非 localhost，建议**启动即拒 / 强告警**；② **同源部署**（`/publish` `/events` `/show` 依赖 cookie 自动携带）

### 6.6 首屏注入

- 扩展既有 `injectBootstrap` → `window.__ck = {form, requireAuth, authed, instanceId}`
- **`authed` 由服务端读凭证判定**（非客户端自称）→ 前端据此分派登录视图 / 主视图，**零额外往返**
- **不使用 UA 判形态**（§1）

### 6.7 阶段 2b 的未决前置

`user` / `work_dir` 的**权限校验**阻塞于 [19 §3.1(g)](19-多租户服务端形态.md) 的五项：① 用户注册 / 登录 / 会话（**全新模块**）② user-project 关系与角色存储 ③ prjusr 根加 **user 维度** ④ workdir 由**服务端下发** ⑤ **项目选择白名单**。

> **另注（必查）**：「项目」是**被登记的对象**（有项目表）→ 用户创建项目时**必须校验路径落在其允许根下**，否则可自登记任意目录**绕过权限**。

## 7. 与 `filesys` 的关系（G-21 根治点）

三层现状（**已实施**）：

| 层 | 现状 |
|------|------|
| httpapi（browser） | ✅ 已缓解（`bindFilesys` 强制覆盖 `work_dir`） |
| gui 桥（desktop / gui） | ✅ 统一注入 `instance_id`（`injectInstance`）；`work_dir` **无需覆盖**（组件层已按绑定解析） |
| **filesys 组件** | ✅ **根治**：订阅 `instance-register` / `instance-exit`，自持 `instance_id → work_dir`，**忽略 payload 的 `work_dir`**（未登记 / 未绑定 → `forbidden`，**不回落载荷**） |

- **未订阅 `instance-heartbeat`**：filesys 与发布方恒**同进程同总线**，绑定生命周期 = 进程生命周期 → 心跳在 filesys 侧**无消费方**（与 persist 的一处有意差异）。
- `/dirs` 的 `allowedDirs()` = 「服务端限定作用域、客户端不得自报路径」的**参考实现**。
- **关联缺口 [G-29]**：~~sweep 超时回收时不补发 `instance-exit`~~ → **✅ 已修**：llm 与 persist 的 sweep 回收时**补发 `instance-exit`**（主题与 payload 不变）→ filesys 等订阅方解绑。见 G-29。
