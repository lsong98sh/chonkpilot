## 1. 问题与目标

- **要解决的问题**：工具的「异步转后台 / 超时 / 取消」三件事目前**分散在三处**——gateway 的计时与执行池（`execPool`）、mcp-server 的 executor 硬上限、llm-server 的域工具；且**取消链路不达执行**：gateway 的取消最终落到各 provider 的 `Invalidate`，对 in-memory 与内嵌 executor 节点是 **no-op**，只有 stdio/http/sse 的代理连接可被真终止。结论：**除 `tool_stop` 用 `process_id` 做 OS kill 外，无法真正终止已在执行的工具**，且**⑤「超时自动取消」当前完全不存在**。
- **目标（可验收）**：
  1. **单次 `tools/call` 的执行层控制统一在 gateway**（唯一裁决点：模式裁决 + 阈值/超时计时 + 裁决事件 + 取消编排）；**执行按四条线分别实现**（in-memory / http / spawn(stdio) / sse）。**任务编排（任务树/父子/级联/批量/任务事件）不在 gateway，而在 llm-server**——gateway 只做**单次调用的执行层**异步/裁决/取消，**不得表述为「所有控制都在 gateway」**；完整分层见 §3.6 A
  2. 五种配置全部可用（§3.2），其中 **⑤ 超时自动取消为新增**；**默认 `0` = 不取消**，不配置时行为逐字节不变。
  3. 「**10 类 × 5 配置 = 50 种组合**」中**硬约束剔除后有效 34**（其中 类⑧/⑩ 的 ⑤ 按「**尽力**」降级计入；按「不支持」剔除则为 **32**）、**目前可用 28**，缺口 6 项全部集中在 ⑤（§3.2）。（**旧 6 类口径**「6 类 × 5 = 30 / 需覆盖 28 / 可用 22」已改按「执行线」定为 **10 类**，见 §3.1 / §3.2）

- **非目标**：**零新增 MQ 主题**；**`tools/list` 的 `_meta` 不新增字段**（= 静态能力描述 `hot`/`category`/`async`/`async-threshold`/`timeout`）；**`tools/call` 的 `params._meta.chonkpilot` 允许增字段**（= **逐调用上下文**，用户已放行，如 `task_id`；见 §3.6 D 与 [16 §8.4](16-路径解析规范.md)）；**61 消息面零变更**；不改沙箱归属（[14-安全域-agentbox](14-安全域-agentbox.md)）。

## 2. 总体方案

**gateway 独占「单次 `tools/call` 执行层」控制面，执行面按四条线分实现。**（**任务编排**——任务树/父子/级联/批量/任务事件——**在 llm-server**，见 §3.6 A）

```text
控制面（gateway，唯一裁决点；**范围 = 单次 `tools/call` 的执行层**，任务编排在 llm-server）
  模式裁决（async 契约 meta → Params.AsyncMode → 调用级覆盖）
  + 阈值/超时计时（doCall 的 timer）
  + 裁决事件（mcp-tasks-report / 用户裁决回执）
  + 取消编排（onTaskCancel → 按 provider 类型分派终止动作）
        │
        ├─ in-memory 线（类① self 闭包 / 类②③④ llm 域工具 / 类⑤ 内嵌 mcp-server 执行器）
        │      只能「协作式取消」：ctx 取消 + 目标侧消费（无 OS 级 kill）
        ├─ spawned 线（类⑥ stdio；类⑦/⑨ 自持 proc）
        │      Invalidate → kill + respawn（隔离池按 workdir 保留）
        └─ proxied 线（类⑧/⑩ 纯远程）
               ctx 断请求（「尽力」语义，不能杀对端进程）
```

**统一小接口**：把各 provider 现有的 `Provider.Invalidate` 升级为统一小接口 **`Start` / `Status` / `Cancel` / `Terminate`**；`Invalidate` 降为 **`Terminate` 的 proxy 实现**（保留现有调用点语义）。

**关键设计取舍**：控制面**全部复用既有机制**——零新增 MQ 主题、**`tools/list` 的 `_meta` 零新字段**（`tools/call` 的 `params._meta.chonkpilot` 属逐调用上下文、可扩，见 §3.6 D）、零新配置域（仅 usr `tool_async.<tool>.cancel_on_timeout`）。

**三条必须一并记住的已知事实**：

1. **`onTaskCancel` 目前是「恒 `Invalidate`」、无按线分派**（`mcpgateway.go:845`）。
2. **⑤「超时自动取消」当前完全不存在**——超时点只发裁决事件或转后台，**永不自动取消**。
3. **executor 侧「取消不达执行」**——gateway 的 `execCtx` 也是 `context.Background()` 派生（`mcpgateway.go:726`），`callTool` 亦然（`executor.go:56,107`）→ **两层都「不继承请求 ctx」**。

### 3.4 四线终止语义

| 线 | 覆盖类（新口径） | 终止动作 | 语义强度 |
|----|------|---------|---------|
| in-memory | ① / ②③④ / ⑤ | **协作式**：ctx 取消 + 目标侧消费（无 OS 级 kill） | **我方执行体 = 可终止**（实测取消后 **0s 退出**）；**第三方不消费 ctx = 不可终止**（取消后**仍跑满**）——**不能整体读作"恒不可终止"** |
| http / sse **自持 proc** | ⑦ / ⑨ | 断请求 **+ `Terminate`（kill + respawn）** | 强（可真终止） |
| http / sse **纯远程（proxied）** | ⑧ / ⑩ | **仅断请求** | **声明「尽力」** |
| spawned（stdio + http/sse 自持） | ⑥ / ⑦ / ⑨ | **`Terminate`**：kill + respawn；**隔离池按 workdir 保留**（`provider.go:396-439`） | 强 |

> **四线终止语义实测（PoC `TECH-POC/cancelprop`）**：
> - `L1 in-memory · 协作式`（**我方**执行体，如 `llm_run` / DSL 运行器）：取消后 **0s 退出 → 能终止**；
> - `L2 in-memory · 不协作`（**第三方**忽略 ctx）：取消后**仍跑满 620ms → 不可终止**；
> - `L3 spawned`：**强终止**（kill 耗时 **2ms**、心跳停止增长）；
> - `L4 proxied`（**纯远程**）：**只能尽力**（断请求后对端 `finished=true` 仍在跑）。
>
> → **判据 = 我方 vs 第三方**，而非"in-memory 一律不可终止"。**我方执行体「能终止但落不了地」的链路缺口**（子 turn 未继承父 ctx + 阻塞等待不可打断）。

> **类③（task 型域工具 `tool_stop`/`tool_result`）的取消通知链（已落地，B6）**：域工具远程回调经 mq 内存总线 **`Emit` 同步派发**——执行体（`execTaskTool`）跑在 gateway 执行 goroutine 里，`t.cancel()` 只取消发送方等待、**无法中断同步 handler**。故取消经**回报通道反向通知**：gateway `tm.cancel` 补发 `mcp-tasks-report{state:cancelled, tool_call_id}` → llm `onGatewayTaskDone` 按 `tool_call_id` 查**工具执行取消表**（`taskExecCancels`：`domainExecute` task 分支登记执行 ctx cancelFunc、结束注销）→ cancel 真停执行体（`tool_result` 轮询感知退出、不空耗到 timeout）；被取消的调用不在此标 done/error——终态由回报链推进（`tasks.done` 幂等）。**残余偏差（声明）**：已 detached 的任务再取消时回报随执行 goroutine 结束才发出 → 执行体不即时停（轮询本身有 timeout 自限，默认 30s），终态一致。

### 3.5 最小改造路径

1. **`onTaskCancel` 由「恒 `Invalidate`」改为按 provider 类型分派**（统一接口加 `Terminate`，`Invalidate` 降为其 proxy 实现）。
2. **⑤ 落地** = `doCall` 的 `timer.C` 分支（`mcpgateway.go:777`）按 `cancelOnTimeout > 0` **直接 `tm.cancel`**（**不等用户裁决**）；判别值来自 usr **`tool_async.<tool>.cancel_on_timeout`**（配置面，见 [64-配置项一览](../60-reference/64-配置项一览.md)）。
3. **零新增 MQ 主题**：复用 `mcp-tasks-report` / `mcp-gateway-changed`（原列的 `mcp-tasks-cancel` / `mcp-tasks-status` / `mcp-tasks-result` **已移除** —— 取消 / 转后台改经**进程内 sink**（`ExecSink.CancelExec` / `DetachExec`）、状态以层为准；**前端入口映射**（`src/lib/gui/bridge/bridge.go:298-316`）中 `mcp-tasks-cancel` 白名单项待清理（不改前端））；**`tools/list` 的 `_meta` 不新增字段**（`tools/call` 的 `params._meta.chonkpilot` 可扩，见 ④ 与 §3.6 D）。

> 本节把「**任务编排**」与「**单次调用的执行层控制**」分开，并据此刻定四组口径；事实均按代码逐行核实。

#### A. 任务编排分层（**纠正「所有控制都在 gateway」**）

#### B. task 类（`tool_stop` / `tool_result`）归 llm（用户已拍板）

- **用户口径**：「taskManager 在 llm 里面是吗？如果是，那就放在 llm 里面吧」。

#### C. 类②（`llm_run`）的「⑤ 超时自动取消」**不纳入** → 组合数口径维持 **34 / 32**

- **事实**：`llm_run` 的**执行实体在 llm-server** —— `domainmcp.go:161-164`：`isLLMTool` → **`go s.runSubJob(tc, callID, node, args)`** 后**立即返回**「已提交子会话执行，结果稍后回填」；任务节点 `kind=llm` 由 llm 建/广播（`tasks.go`）。gateway 看到的是一次**已立即返回**的调用 → **无进程可杀、无可取消的上游调用**（对 `llm_run` 的 gateway 任务包装是**空洞的**）。
- **结论**：类② **不纳入 ⑤** → §3.2 的有效组合口径**维持 34 有效 / 32（「不支持」口径）**。
- **正确机制** = **llm 任务树 `cancelSubtree` + `tool_stop`/`onTaskStop` 级联（`tool_task.go:39-67` / `server.go:1071-1085`）+ 子作业自身 turn ctx**。附带澄清：代码里确有 `jobEnv.watchCancel`（`src/lib/llm/server/jobdsl.go:484-485`，`jobdsl.go:326` 挂载，200ms 轮询作业根节点 → `eng.Cancel()`），但它是**子作业消费「级联取消」**的实现细节（[21 §4.4](../20-modules/21-llm-server.md) 描述的 200ms 轮询即此，该条描述本身无误、保留），**不是**类②「自管取消」的依据。

#### D. `_meta` **允许增字段**（用户口径：「`_meta` 内可以增加任何需要的」）

- **两种 meta 必须分清**：
  1. **`tools/list` 的 `_meta`** = **静态能力描述**（`hot`/`category`/`async`/`async-threshold`/`timeout`）→ **不新增字段**（§1 非目标）；
  2. **`tools/call` 的 `params._meta`** = **逐调用上下文**，**本来每次都不同**：现已在传 `_meta["chonkpilot"] = {instance_id, work_dir, data_dir, ...}`（[16 §8.4](16-路径解析规范.md)）→ **`task_id` 属后者**，与既有用法一致（**不是**「把每次不同的值放进静态描述」）。

- **用途**：若 go-sdk in-memory 传输**不传递** client ctx cancel（`memnode.go:61-63`），则由 `params._meta.chonkpilot.task_id` + mcp-server 侧 **in-flight 注册表**（`task_id` → executor 调用）承接终止（§3.5 ④ · §7 B3）。**探针证「能传递」→ 本兜底不触发、不实施（仅登记）**，见 §3.7。

### 3.7 探针结论与类①「只能同步」落地方案（**探针结论仅记录；类①「只能同步」✅ 已落地（方案 B）；域工具 `_meta` 透出同批落地**）

> 依据：用户任务「I-83 剩余 2 项」（探针 + 类①落地方式）；事实按代码逐行核实 + 探针单测实跑。

**A. in-memory ctx 取消传递（探针结论 = 能传递）**

- **探针**：`src/lib/gateway/gateway/memnode_cancel_probe_test.go` → `TestInMemoryCtxCancelReachesHandler`（与 `newMemNode` 同建连顺序；handler 阻塞等 `ctx.Done()`；client 侧 `CallTool` 后取消调用 ctx）。**实跑**：`go test ./gateway/ -run TestInMemoryCtxCancelReachesHandler -count=1 -v` → **PASS**，日志 `结论=能传递：server handler 观察到取消 err=context canceled`。
- **机制（代码链）**：MCP client `call()` 在 `ctx.Err() != nil` 时发 `notifications/cancelled`（`mcp/transport.go:call → cancelCall`）→ server 侧 `canceller.Preempter` 收通知后 `go conn.Cancel(reqID)`（`mcp/transport.go`）→ `jsonrpc2.Connection.Cancel` → `incomingRequest.cancel()`（`internal/jsonrpc2/conn.go`）→ handler 的请求 ctx（`context.WithCancel(readIncoming ctx)`，`acceptRequest`）取消。
- **重要区分**：in-memory 传输**不传 client ctx 的 value**（故 `memnode.go` 仍以协议 `_meta` 往返调用上下文，`memnode.go:179-180` 的注释针对 **value**）；**取消信号**走 MCP 协议层显式通知，与 ctx value 是两条不同通路。另注：连接根 ctx 取消**不**自动传导（`PropagateCancellation=false`，`jsonrpc2` `notDone` 包裹）——影响的是「连接级」而非「单调用级」。
- **对后续设计的含义（仅记录，不实施）**：`Terminate` 对 in-memory 线（类① self 闭包 / 类②③④ llm 域工具 / 类⑤ 内嵌 executor）**可经 ctx 下沉 cancel 且到达 handler** → **`_meta.chonkpilot.task_id` + in-flight 注册表**（§3.5 ④ / §3.6 D / §7 B3）**非必需**；后续若实施 B2/B3，可**优先只做 ctx 下沉**（B3 的 `callTool` 继承 ctx + `CommandContext`；类② `runSubJob` ctx 感知），**不需**新增 `_meta` 字段。**降级不达的仍是 in-memory 的「非协作」目标侧**（§3.4：目标侧不消费 ctx 即无效）—— 但**传递本身已被证伪为阻碍**。

**B. 类①（`mcp_find`/`mcp_load`/`mcp_invoke`）「只能同步」的落地方式（✅ 已落地 = 方案 B）**

- **落地（方案 B）**：`registerMetaTools` 注入 self 节点的三个工具 `Meta` 由 `{hot:true, category:"meta"}` 改为 **`{hot:true, category:"meta", async:"never", timeout:0}`**（`src/lib/gateway/gateway/meta_tools.go:74`）—— `async:"never"` → `toolAsyncMeta(route)` 返回 `never` → `explicitNever` 锁死（**不可被调用级 `async=true` / 全局 `AsyncMode` 覆盖**，`mcpgateway.go:754`/`:785` 既有语义）→ **类① 恒同步**，与 §4「类①③④ 仅同步」硬约束**一致**；`timeout:0` = **无上限**（与 `tool_stop`/`tool_result`/`ask_user` 同口径，见 §3.8「绝对优先」）→ gateway **不设裁决点**（永远等，用户可取消）。
  - **零新字段 / 零消息面**：`async` / `timeout` 属既有静态能力集（§1 非目标），**不涉 MQ 主题 / payload 变更、不改 61**；代价 = 这 3 个工具的 `tools/list` 会多出 `async:"never"` 与 `timeout:0`（无上限）键（前端 / `_meta` 消费点按既有 `async`/`timeout` 语义处理）。
  - **与其它工具一处语义**：`async` 统一走工具 `_meta`（类① 注入时硬编码；类②③④ 由契约 `[meta]` 经 `tools/register` 透出，见下），不再需要 `doCall` 内的工具名名单。
- **校验**：类① 在调用级 `async=true` / 全局 `AsyncMode=auto|always` 下**仍同步**（`explicitNever` 锁死）；L1 用例见 §7「需新增测试清单」。
- **域工具 `_meta` 透出 `async` / 系统工具 `timeout=0`**：`loadDomainTools` 现**解析并携带契约 `[meta]`**（`category`/`async`/`async-threshold`/`timeout`，`domainmd.go:47-59`）→ `tools/register` 载荷透出 `category`/`async`/`async_threshold`/`timeout`（`hot` 保留，`domainmcp.go:170-190`）→ gateway `registerTool` 据此写入工具 `_meta`（**`async` 为 `auto`/空不显式透出**；**`async-threshold` 仅 `>0` 透出**；**`timeout` 键显式声明即透出（含 `0`/`-1`）**，`mcpgateway.go:1265-1299`）。故四域工具 `_meta` 现状：
  - `tool_stop` / `tool_result` / `ask_user` = **`async=never`**（**仅同步**，类③/④）；`tool_stop`/`ask_user` 另 `hot=true`；
  - `llm_run` = **`async=always`**（**仅异步**，类②，**不属「仅同步」类**）；
  - `tool_stop` / `tool_result` / `ask_user` 契约显式 **`timeout=0`** → **`_meta.timeout=0`（显式透出，非缺失）** → **无上限**（gateway `limit<=0` **不设裁决点**、executor `noLimit` **不设执行硬上限**，永远等待、用户可取消）= 「**系统工具（`category=server` / `meta`）不单独设执行硬上限**」；**元工具 `mcp_find`/`mcp_load`/`mcp_invoke`**（无契约 md）由 `registerMetaTools` 注入时**显式声明 `timeout=0`**（`meta_tools.go:74`）→ 同样 **`_meta.timeout=0`（无上限，绝对优先、可取消）**。`llm_run` **无 `timeout` 键** → **`_meta.timeout` 缺失** → 执行侧回落全局默认（`async=always`，无裁决意义）。`tool_result` 的 `timeout` **入参**是轮询等待秒数、与执行硬上限无关。
  - **超时/阈值透出口径**：`timeout` 键显式声明即透出（含 `0`/`-1`）、语义为无上限（**未设置 = 回落**）；`async-threshold` 仍仅 `>0` 透出。见 **§3.8**。

### 3.8 超时 / 阈值取值语义（**权威**）

> 用户口径：**「未设置」与「`0` / `-1`」必须区分** —— **未设置**（键缺失 / `null` / 空串 / 非数字）= **回落下一优先级**；**显式 `0` / `-1` = 无上限**（永不超时、不设裁决点，**永远等待、由用户取消**）；**正数** = 该值（秒）。本节为超时 / 阈值取值的**唯一权威口径**，覆盖「契约解析 → `_meta` 透出 → usr 覆盖 → executor 硬上限 → gateway 裁决点 → 前端字段」全链路。
> 代码落点：`contract.go parseToolDoc`（`TimeoutSet`）· `config.go ToolAsyncOverride`（`ThresholdSet`/`HardTimeoutSet`/`optIntField`）· `executor.go resolveExecTimeout` · `gateway/mcpgateway.go`（`asyncDefaults` 的 `timeoutSet`/`thrSet` · `doCall` 的 `limit`）· `gateway/tooloverride.go` · `llm/server/{domainmd.go,domainmcp.go,gwclient.go,server.go}`。

**三态判定（通用）**：

| 取值 | 含义 | 与「未设置」的区分点 |
|:--:|------|------|
| **未设置** | 回落下一优先级 / 全局默认 | 键缺失 · `null` · 空串 `""` · 非数字 |
| **`0` / `-1`** | **无上限**：永不超时 / 不设裁决点，永远等待、用户可取消 | 键**显式声明**且 `<= 0`；靠 `TimeoutSet` / `ThresholdSet` / `HardTimeoutSet` / `regMsg.Timeout`（`*float64`）/ `metaKeySet` 与「未设置」**显式区分** |
| **正数** | 硬上限 / 阈值点 = 该值（秒） | 键显式声明且 `> 0` |

**逐链路落点与最终行为**：

| 链路 | 未设置 | 显式 `0` / `-1` | 正数 |
|------|--------|----------------|------|
| **契约解析**（`[meta] timeout`，`contract.go parseToolDoc`） | 键缺失 / 空串 → `TimeoutSet=false`、`Timeout=0` | `TimeoutSet=true`、`Timeout=0/-1` | `TimeoutSet=true`、`Timeout=v`；**非整数 → `loadTools` 直接报错 `bad timeout %q`**（无回落） |
| **`_meta.timeout` 透出**（`buildTool`；gateway `registerTool` 同口径） | **不写**（下游按未设置回落） | **写 `0/-1`**（供 gateway / 前端区分「未设置」与「无上限」） | 写 `v` |
| **usr 覆盖**（`ToolAsyncOverride` 的 `threshold` / `hard_timeout`） | 键缺失 / `null` / 空串 / 非数字 → `Set=false`，**不覆盖**该字段 | `Set=true`，值 `0/-1` 保留（`NormalizeToolAsync` 保留显式 0/-1） | `Set=true`，值 `v`。**`threshold` 仅 `>0` 写 `_meta.async-threshold`**（显式 0/-1 不写 `_meta`，但 gateway 从覆盖表直读、仍生效）；**`hard_timeout` 永不进 `_meta`** |
| **executor 执行硬上限**（`resolveExecTimeout` → `(timeout, noLimit)`） | 逐级回落：usr `hard_timeout` → 契约 `timeout` → `cfg.execTimeout()`（prj `timeout_sec` / 内置 300s） | **`noLimit=true` → 不设 `WithTimeout`**（`ctx2 = 请求 ctx`，不设超时点），子进程永不超时、**仍可取消**（B3：`exec.CommandContext` 绑定请求 ctx） | `context.WithTimeout(v)`，到点杀子进程 → `tool %s timeout after %ds` |
| **gateway 裁决点**（`doCall` 的 `limit`） | 超时：**工具 `_meta.timeout` 显式 `0`/`-1`（无上限）绝对优先**；否则 调用级 `args.timeout`（仅 `>0`）→ server 级 `TimeoutSec(>0)` → 工具 `_meta.timeout`（`>0`）→ 全局 `CallTimeout`（默认 60s）；阈值未声明 → 回落有效超时。**注**：`_meta.timeout` 显式为**正数**时，调用级 / server 级仍可覆盖（保持既有链）；self 节点 / dir 节点 `entry.TimeoutSec` 恒 0（不 override），仅第三方 server（`mcp_server.timeout`）可能设之 | **`limit<=0` → 不设点**（工具 `_meta.timeout` 显式 `0`/`-1` 时**绝对优先，调用级 / server 级 / 全局均不得覆盖**）：`select{done / detach}` 只等「完成」或「用户转后台 / 取消」，**不发 `mcp-tools-timeout`、不进 awaiting、不自动转后台**（never/manual 无裁决条；auto 无阈值则阻塞等待） | `limit=v`：auto 到点自动转后台（不重跑）；manual 到点发 `mcp-tools-timeout{options:[detach,cancel]}`；never 发 `{options:[wait,cancel]}` |
| **前端**（`SettingsToolAsyncPage`「异步阈值」/「执行硬上限」两列） | 输入框留空 → 占位「契约默认 / 回落全局」、**不写库**（显示契约现值） | 输入 `0` / `-1` → **无上限**（tooltip「永远等待，用户可取消」）→ 写库 | 输入正数 → 该值 → 写库；**非法值**（如 `-5`；`isLimitValue` 仅受 `>=0` 或 `-1`）→ 失焦回落显示值、不写库 |

> **三处例外（如实记录）**：
> 1. **调用级 `args.timeout`**（gateway `doCall`）**仅 `> 0` 生效**（`if callTimeout > 0`）→ 调用级写 `0` / 负数 = **不覆盖**（回落），**不构成「无上限」**（`args.async` 无此例外）。
> 2. **dir 节点工具的 usr `hard_timeout` 未接线**（mcp-server 按契约名查、gateway 下发暴露名）→ 前端对该类行禁用「执行硬上限」列并标注「不适用」。
> 3. **工具 `_meta.timeout` 显式 `0` / `-1`（无上限）绝对优先、不可被覆盖**（「无上限」必须是绝对的；第三方工具若声明了也「覆盖改不了」）—— `doCall` 代码落点 = `if !(def.timeoutSet && def.timeout <= 0) { …调用级 / server 级 / 全局链… }`（`mcpgateway.go:801-812`）：即便调用级 `args.timeout` 为**正值**、server 级 `entry.TimeoutSec>0`、全局 `CallTimeout>0`，该调用**仍 `limit<=0`（不设裁决点）**，阻塞至完成或用户取消。仅当工具 `_meta.timeout` 为**正数**时才保留「调用级 > server 级 > 工具 > 全局」链。

## 4. 规则与约定

| 项 | 结论 | 理由 |
|----|------|------|
| 执行层控制面归属 | **gateway 独占**（模式裁决 + 计时 + 裁决事件 + 取消编排） | 工具唯一入口，已持执行池（`execPool`）与计时器。此为**单次调用执行层**的控制面；**任务编排（任务树/父子/级联/事件）在 llm-server**，**不得表述为「所有控制都在 gateway」** —— 见 §3.6 A |
| **池按 instance 分区（硬约束）** | **执行池（gateway `execPool`）与任务视图（llm `taskManager`）必须按 instance 分区**（gateway `tasks` · llm `nodes`，以及全部 instance 状态单池）；**`tasks/cancel` / `tasks/status` / `tasks/list` 必须做 instance 归属校验或过滤** | 单进程可服务多 instance（split 服务端 exe / browser）时，单池会导致**跨 instance 取消 / 查询 / 打断**；standalone 因「进程 = instance」天然规避 —— 见 [20-实例隔离与后端分离](20-实例隔离与后端分离.md) §4 缺口 2/3/5/8。`tasks/cancel\|status\|list` 方法面**已移除**（连同 `checkTaskScope` 归属校验）→ 控制为**进程内调用**（层 + sink，无跨实例消息面暴露）。 |
| 执行面 | **四条线分别实现**（in-memory / http / spawn(stdio) / sse） | 终止能力由传输形态决定，无法归一 |
| 接口统一 | `Provider` 新增 **`Terminate(ctx, instanceID, workdir)`**（取消的**执行线入口**）；`Invalidate` 保留（proxy 实现，`Terminate` 内部走 `InvalidateScoped` → kill + respawn）；in-memory（`memNode` / `registered`）的 `Terminate` = **协作式 no-op** | 取消语义需按类型分派（`onTaskCancel` 调 `Terminate`）；保持既有 `Invalidate` 调用点兼容 |
| ⑤ 默认值 | **`0` = 不取消；`> 0` 生效**（秒） | 不配置时行为**逐字节不变**。**注**：此处 `0` = **不做取消动作**，与超时/阈值取值的 `0` = **无上限**同旨（均「不做该动作」；见 §3.8） |
| ⑤ 触发 | 超时点**直接 `tm.cancelRef`**（→ `onTaskCancel` 按执行线终止），**不等用户裁决**、**不发 `mcp-tools-timeout`** | 「自动取消」的定义即无人工介入 |
| ⑤ 覆盖范围 | 仅 **spawned / 自持线**强语义；in-memory 协作式；纯 proxied「尽力」 | 见 §3.4 |
| **分类维度** | **按「执行线」分 10 类**（§3.1）：**归属按提供方、处理按执行线** | 档位与终止能力由**执行线**决定；注册/透传面仍由**提供方**决定（`registeredProvider` vs gateway 本地闭包照旧） |
| **模式硬约束**（**已真实生效**） | **类①③④ 仅同步**；**类② 仅异步**；**类⑤–⑩ 四档全支持**（配置①–④） | 由执行线决定可用模式（§3.1 / §3.2）；`never` 不可被调用级覆盖的既有语义保留（`mcpgateway.go:754`/`:785`）。**落地口径**：**类①** 经 `registerMetaTools` 注入时显式 `_meta.async="never"`（方案 B，§3.7 B）；**类③④** 经契约 `[meta] async=never` 由 `tools/register` 透出至 `_meta`；**类② `llm_run` = `async=always`**（**仅异步，不属「仅同步」类**） |
| **⑤ 适用性（按类）** | **类① 不定义**（无执行硬上限）· **类③ 不定义**（`tool_stop`/`tool_result` 本身即「停止/查询」工具，自我取消无意义）· **类④ 不定义**（等人语义）· **类⑤⑥⑦⑨ 支持**（executor 硬上限 / stdio·http·spawned·sse·spawned 的 kill + respawn）· **类⑧/⑩ 降级为「尽力」**（只能断请求，不能杀远端进程） | 见 §3.4；类② 亦**不纳入 ⑤**（其**执行实体在 llm-server**：`domainmcp.go:161-164` 起 goroutine 后**立即返回** → gateway 侧任务包装**空洞**、无进程可杀；取消由 llm 任务树 `cancelSubtree` + `tool_stop`/`onTaskStop` 级联承接，见 §3.6 C） |
| **`ask_user` 结论**（**我方建议，待用户确认**） | **仅同步 + 无超时 + 不纳入 ⑤** | ① 现状契约即 `async=never` + `timeout=0`（本无超时裁决点）；② 语义 = **人在环等回答**，「超时自动异步 / 自动取消」等于**替用户取消掉提问**，属错误语义；③ 若将来要解决「长等待让 UI 无响应」，属**交互层 / 前端呈现**问题，不应借「转后台」解决 |
| 消息面 | **零新增主题**；**`tools/list` 的 `_meta` 不新增字段**（`tools/call` 的 `params._meta.chonkpilot` 属逐调用上下文、可扩；**61 消息面零变更**，见 §3.6 D） | 复用既有的 `mcp-tasks-report` 通知面（**`tasks/*` 方法面已移除**）与前端映射 |
| 配置面 | 仅 usr `tool_async.<tool>.cancel_on_timeout` | 与既有工具异步档位同页同域 |
| 硬上限 | mcp-server 侧 `resolveExecTimeout` **保留**；优先级链 = **usr `hard_timeout` > 契约 `timeout` > 全局**（prj `timeout_sec` / 内置 300s）；**每级「未设置」才回落下一级，显式 `0`/`-1` = 无上限（`noLimit`，不设 `WithTimeout`，永远等、可取消）** | 见 **§3.8** · [25-mcp-server §9](../20-modules/25-mcp-server.md) |

## 6. 边界与异常

- **双轨超时（类⑤）**：gateway 裁决点与 mcp-server 硬上限并存。二者同时到达时，**以先到者为准**；硬上限触发后 gateway 侧任务只能收到执行错误，无法再终止。任一侧**显式 `0`/`-1`（无上限）→ 该侧不设点**（gateway `limit<=0` **不发 `mcp-tools-timeout`**；executor `noLimit` **不设 `WithTimeout`**）→ 调用仅由「另一侧到点」或「用户取消」结束；见 **§3.8**。
- **取消达执行（B2/B3 已落地）**：取消链 = 执行池 `t.cancel()` 取消执行 ctx → 经 in-memory 传输的 `notifications/cancelled` 送达 handler 请求 ctx（§3.7 探针证「能传递」）→ 执行体侧真停（mcp-server `callTool` 的 `exec.CommandContext` 携请求 ctx → kill 子进程；llm 域 `runSubJob` 的 `watchCancel` 感知父 ctx）。gateway 侧 `onTaskCancel` 按执行线分派：spawned/自持 = `Terminate`（kill + respawn）、in-memory = 协作式 no-op、纯远程 = 仅断请求。**遗留协作式失败面**：in-memory 的**第三方**目标侧不消费 ctx 时取消无效（§3.4 判据 = 我方 vs 第三方）；类⑤ 另仍可经 `tool_stop` 用 `process_id` 做 OS kill（`tool_task.go:48-57`）。
- **纯远程（类⑧/⑩）**：仅能断本端请求，**对端进程可能继续运行** → 语义明确为「**尽力**」；不得宣称「已终止」。
- **`Invalidate` 的全池语义**：kill + respawn 覆盖**全池**（`provider.go:528-539`）→ 会影响同 server 其它 workdir 的**在飞调用**；改造时须保持既有行为或显式收窄（不得静默变更）。
- **隔离池默认值**：`isolate` 缺省 stdio=true / http·sse=false → 类⑨/⑩ **默认无实例池**，`Terminate` 退化为断常连。
- **协作式取消的失败面**：目标侧不消费 ctx → 任务状态可标记 `cancelled`，但**实际执行仍在继续**（须在 UI/报告语义上与「已终止」区分）。
