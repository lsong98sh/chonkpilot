## 1. 问题与目标

- **要解决的问题**：工具的「异步转后台 / 超时 / 取消」三件事目前**分散在三处**——gateway 的计时与 TaskManager、mcp-server 的 executor 硬上限、llm-server 的域工具；且**取消链路不达执行**：gateway 的取消最终落到各 provider 的 `Invalidate`，对 in-memory 与内嵌 executor 节点是 **no-op**，只有 stdio/http/sse 的代理连接可被真终止。结论：**除 `tool_stop` 用 `process_id` 做 OS kill 外，无法真正终止已在执行的工具**，且**⑤「超时自动取消」当前完全不存在**。
- **目标（可验收）**：
  1. **单次 `tools/call` 的执行层控制统一在 gateway**（唯一裁决点：模式裁决 + 阈值/超时计时 + 裁决事件 + 取消编排）；**执行按四条线分别实现**（in-memory / http / spawn(stdio) / sse）。〔**订正（2026-09-17，[42 §2 (90)](../40-roadmap/42-决策记录.md)）**：**任务编排（任务树/父子/级联/批量/任务事件）不在 gateway，而在 llm-server**——gateway 只做**单次调用的执行层**异步/裁决/取消，**不得表述为「所有控制都在 gateway」**；完整分层见 §3.6 A〕
  2. 五种配置全部可用（§3.2），其中 **⑤ 超时自动取消为新增**；**默认 `0` = 不取消**，不配置时行为逐字节不变。
  3. 「**10 类 × 5 配置 = 50 种组合**」中**硬约束剔除后有效 34**（其中 类⑧/⑩ 的 ⑤ 按「**尽力**」降级计入；按「不支持」剔除则为 **32**）、**目前可用 28**，缺口 6 项全部集中在 ⑤（§3.2）。〔**订正（2026-09-17）**：原「6 类 × 5 = 30 / 需覆盖 28 / 可用 22」为**旧 6 类口径**，分类已改按「执行线」定为 **10 类**，见 §3.1 / §3.2 与 [42 §2 (88)](../40-roadmap/42-决策记录.md)〕

- **非目标**：**零新增 MQ 主题**；**`tools/list` 的 `_meta` 不新增字段**（= 静态能力描述 `hot`/`category`/`async`/`async-threshold`/`timeout`）；**`tools/call` 的 `params._meta.chonkpilot` 允许增字段**（= **逐调用上下文**，用户已放行，如 `task_id`；见 §3.6 D 与 [16 §8.4](16-路径解析规范.md)）；**61 消息面零变更**；不改沙箱归属（[14-安全域-agentbox](14-安全域-agentbox.md)）。

## 2. 总体方案

**gateway 独占「单次 `tools/call` 执行层」控制面，执行面按四条线分实现。**（**任务编排**——任务树/父子/级联/批量/任务事件——**在 llm-server**，见 §3.6 A）

```text
控制面（gateway，唯一裁决点；**范围 = 单次 `tools/call` 的执行层**，任务编排在 llm-server）
  模式裁决（async 契约 meta → Params.AsyncMode → 调用级覆盖）
  + 阈值/超时计时（doCall 的 timer）
  + 裁决事件（mcp-tasks-report / 用户裁决回执）
  + 取消编排（onTaskCancel → 按 provider 类型分派终止动作）
        │
        ├─ in-memory 线（类① self 闭包 / 类②③④ llm 域工具 / 类⑤ 内嵌 mcp-server 执行器）
        │      只能「协作式取消」：ctx 取消 + 目标侧消费（无 OS 级 kill）
        ├─ spawned 线（类⑥ stdio；类⑦/⑨ 自持 proc）
        │      Invalidate → kill + respawn（隔离池按 workdir 保留）
        └─ proxied 线（类⑧/⑩ 纯远程）
               ctx 断请求（「尽力」语义，不能杀对端进程）
```

**统一小接口**：把各 provider 现有的 `Provider.Invalidate` 升级为统一小接口 **`Start` / `Status` / `Cancel` / `Terminate`**；`Invalidate` 降为 **`Terminate` 的 proxy 实现**（保留现有调用点语义）。

**关键设计取舍**：控制面**全部复用既有机制**——零新增 MQ 主题、**`tools/list` 的 `_meta` 零新字段**（`tools/call` 的 `params._meta.chonkpilot` 属逐调用上下文、可扩，见 §3.6 D）、零新配置域（仅 usr `tool_async.<tool>.cancel_on_timeout`）。

**三条必须一并记住的已知事实**：

1. **`onTaskCancel` 目前是「恒 `Invalidate`」、无按线分派**（`mcpgateway.go:845`）。
2. **⑤「超时自动取消」当前完全不存在**——超时点只发裁决事件或转后台，**永不自动取消**。
3. **executor 侧「取消不达执行」**——gateway 的 `execCtx` 也是 `context.Background()` 派生（`mcpgateway.go:726`），`callTool` 亦然（`executor.go:56,107`）→ **两层都「不继承请求 ctx」**。

### 3.4 四线终止语义

| 线 | 覆盖类（新口径） | 终止动作 | 语义强度 |
|----|------|---------|---------|
| in-memory | ① / ②③④ / ⑤ | **协作式**：ctx 取消 + 目标侧消费（无 OS 级 kill） | **我方执行体 = 可终止**（实测取消后 **0s 退出**）；**第三方不消费 ctx = 不可终止**（取消后**仍跑满**）——**不能整体读作"恒不可终止"** |
| http / sse **自持 proc** | ⑦ / ⑨ | 断请求 **+ `Terminate`（kill + respawn）** | 强（可真终止） |
| http / sse **纯远程（proxied）** | ⑧ / ⑩ | **仅断请求** | **声明「尽力」** |
| spawned（stdio + http/sse 自持） | ⑥ / ⑦ / ⑨ | **`Terminate`**：kill + respawn；**隔离池按 workdir 保留**（`provider.go:396-439`） | 强 |

> **〔订正（2026-09-20，[41 I-118](../40-roadmap/41-未决项登记.md)）〕四线终止语义实测（PoC `TECH-POC/cancelprop`，2026-09-19）**：
> - `L1 in-memory · 协作式`（**我方**执行体，如 `llm_run` / DSL 运行器）：取消后 **0s 退出 → 能终止**；
> - `L2 in-memory · 不协作`（**第三方**忽略 ctx）：取消后**仍跑满 620ms → 不可终止**；
> - `L3 spawned`：**强终止**（kill 耗时 **2ms**、心跳停止增长）；
> - `L4 proxied`（**纯远程**）：**只能尽力**（断请求后对端 `finished=true` 仍在跑）。
>
> → **判据 = 我方 vs 第三方**，而非"in-memory 一律不可终止"。**我方执行体「能终止但落不了地」的链路缺口 = [G-18](../40-roadmap/41-未决项登记.md)**（子 turn 未继承父 ctx + 阻塞等待不可打断）。

### 3.7 探针结论与类①「只能同步」落地方案（**2026-09-19 登记；本批不实施**）

> 依据：用户任务「I-83 剩余 2 项」（探针 + 类①落地方式）；事实按代码逐行核实 + 探针单测实跑。

**A. in-memory ctx 取消传递（探针结论 = 能传递）**

- **探针**：`src/gateway/gateway/memnode_cancel_probe_test.go` → `TestInMemoryCtxCancelReachesHandler`（与 `newMemNode` 同建连顺序；handler 阻塞等 `ctx.Done()`；client 侧 `CallTool` 后取消调用 ctx）。**实跑**：`go test ./gateway/ -run TestInMemoryCtxCancelReachesHandler -count=1 -v` → **PASS**，日志 `结论=能传递：server handler 观察到取消 err=context canceled`。
- **机制（代码链）**：MCP client `call()` 在 `ctx.Err() != nil` 时发 `notifications/cancelled`（`mcp/transport.go:call → cancelCall`）→ server 侧 `canceller.Preempter` 收通知后 `go conn.Cancel(reqID)`（`mcp/transport.go`）→ `jsonrpc2.Connection.Cancel` → `incomingRequest.cancel()`（`internal/jsonrpc2/conn.go`）→ handler 的请求 ctx（`context.WithCancel(readIncoming ctx)`，`acceptRequest`）取消。
- **重要区分**：in-memory 传输**不传 client ctx 的 value**（故 `memnode.go` 仍以协议 `_meta` 往返调用上下文，`memnode.go:179-180` 的注释针对 **value**）；**取消信号**走 MCP 协议层显式通知，与 ctx value 是两条不同通路。另注：连接根 ctx 取消**不**自动传导（`PropagateCancellation=false`，`jsonrpc2` `notDone` 包裹）——影响的是「连接级」而非「单调用级」。
- **对后续设计的含义（仅记录，不实施）**：`Terminate` 对 in-memory 线（类① self 闭包 / 类②③④ llm 域工具 / 类⑤ 内嵌 executor）**可经 ctx 下沉 cancel 且到达 handler** → **`_meta.chonkpilot.task_id` + in-flight 注册表**（§3.5 ④ / §3.6 D / §7 B3）**非必需**；后续若实施 B2/B3，可**优先只做 ctx 下沉**（B3 的 `callTool` 继承 ctx + `CommandContext`；类② `runSubJob` ctx 感知），**不需**新增 `_meta` 字段。**降级不达的仍是 in-memory 的「非协作」目标侧**（§3.4：目标侧不消费 ctx 即无效）—— 但**传递本身已被证伪为阻碍**。

**B. 类①（`mcp_find`/`mcp_load`/`mcp_invoke`）「只能同步」的落地方式（**现状核实 + 最小方案登记**）**

- **现状核实（2026-09-19，逐行）**：**当前无任何「只能同步」强制**。① 三个 meta 工具经 `registerMetaTools` 注入 self 节点，`Meta` **仅** `{hot:true, category:"meta"}`（`meta_tools.go:63-68`）——**无 `async`/`timeout`**；② `doCall` 的档位解析纯由 `toolAsyncMeta(route)`（读 `_meta.async`，缺省 **`auto`**）+ `Args`/`Params.AsyncMode` 覆盖决定（`mcpgateway.go:728-755` / `:960-976`）；③ `softNeverDefault`（第三方软缺省）对 **builtin**（self 节点）**不适用**（`mcpgateway.go:946-957`）。→ 结论：类① 现状被判为 **`auto`**（可自动转后台 + 阈值），**与 §4「类① 仅同步」硬约束不符**（`_meta` 无载体 + 无名单强制）。
- **最小落地方案（登记；**本批不实施**）**：
  - **方案 A（推荐，零 `tools/list` 变更）**：**gateway 内部硬编码名单** —— 在 `doCall` 档位解析后按**归一工具名**（剥离 `self_` 前缀后 ∈ `{mcp_find, mcp_load, mcp_invoke}`）**强制 `mode="never"`**（与 `explicitNever` 同语义、且**不参与四档**：调用级/全局覆盖均不得改写）；落点 = `mcpgateway.go:doCall` 档位段（`:748-755` 附近）或 `registerMetaTools` 注入后在 `registry` 标注。**理由**：类① 无契约 md/无 meta 载体（§3.1 / §5），名单是唯一不触碰消息面与 `_meta` 的显式约束。
  - **方案 B（备选）**：**注入时设 meta** —— `meta_tools.go` 注入的 `mcp.Tool.Meta` 增 `"async":"never"` → `toolAsyncMeta` 返回 `never` → `explicitNever` 锁死（`_meta` 字段名 `async` 属既有静态能力集，非「新增字段」）；代价 = 这 3 个工具的 `tools/list` 会多出 `async:"never"` 键（**不改消息面**，但改 tools/list 输出）。
  - **共同验收（实施时）**：L1 断言类① 在 调用级 `async=true` / 全局 `AsyncMode=auto|always` 下**仍同步**；组合口径维护 §3.2 的 **34 / 32**（类① 恒剔 4 档）。**当前批次仅登记，未改任何代码。**
- **注意**：上述方案**不涉 MQ 主题/payload 变更**，亦**不改 61**；方案 B 若实施需评估 `tools/list` 输出变更对前端/`_meta` 消费点的影响。

| 项 | 结论 | 理由 |

## 6. 边界与异常

- **双轨超时（类⑤）**：gateway 裁决点与 mcp-server 硬上限并存。二者同时到达时，**以先到者为准**；硬上限触发后 gateway 侧任务只能收到执行错误，无法再终止。
- **取消不达执行**：两层 ctx 均自 `context.Background()` 派生 → in-memory 线（类①②③④）与内嵌 executor（类⑤）**收不到取消**；类⑤ 只能等硬超时，或由 `tool_stop` 用 `process_id` 做 OS kill（`tool_task.go:48-57`）。
- **纯远程（类⑧/⑩）**：仅能断本端请求，**对端进程可能继续运行** → 语义明确为「**尽力**」；不得宣称「已终止」。
- **`Invalidate` 的全池语义**：kill + respawn 覆盖**全池**（`provider.go:528-539`）→ 会影响同 server 其它 workdir 的**在飞调用**；改造时须保持既有行为或显式收窄（不得静默变更）。
- **隔离池默认值**：`isolate` 缺省 stdio=true / http·sse=false → 类⑨/⑩ **默认无实例池**，`Terminate` 退化为断常连。
- **协作式取消的失败面**：目标侧不消费 ctx → 任务状态可标记 `cancelled`，但**实际执行仍在继续**（须在 UI/报告语义上与「已终止」区分）。
