## 1. 定位

**MQ 是组件间唯一的跨组件通道**（单体形态亦然）：

- 抽象掉物理边界——同一份业务代码在"同进程内存总线"与将来"跨进程/多机"下语义一致。
- 所有交互 = 事件（fire-and-forget）+ 请求-响应（publish + promise 收集），**无独立 RPC**。
- 唯一豁免：GUI↔server 的 `/show` 字节流、测试端口端点白名单。

当前实现 = **进程内内存总线**（**去掉 NATS**；去中心化 MQ 留待自研，见 §7）。

> 目标形态：**客户端 = 前端 + GUI**；**服务端 = llm + gateway + filesys + data 等合并为一个 exe（服务）**；**消息经 HTTP 在 GUI 与 llm server 之间直接路由**。
> 落地原则 =「**内部采用内存，外部用 bridge**」：**进程内用内存总线**（沿用本文门面），**跨端（GUI↔服务端）用 bridge(HTTP) 路由**。**当前实现仍为单体合并（同进程内存总线）**，上述分离为**演进方向**；消息面（主题/payload）不变。见 [40 T-24](../40-roadmap/40-演进计划.md)。

## 2. 门面接口（Go）

包：`src/lib/mq`。核心是两个方法 + 一个共享值 + 一个 promise：

```go
type Bus interface {
    Prefix() string
    Emit(ctx context.Context, subject string, payload any) *Future // 唯一发送入口
    On(subject string, order int, h VHandler) (Sub, error)         // 唯一订阅入口
    // v1 兼容（迁移期兼容面；生产/测试已全迁，暂保留，仅 v1 自身测试使用）
    Publish(subject string, payload []byte) error
    Subscribe(subject string, h Handler) (Sub, error)
    Close() error
}

type Value struct { Subject string; Payload []byte; Result any; Errors []error }
type VHandler func(ctx context.Context, subject string, v *Value) error
```

语义要点：

| 要点 | 说明 |
|------|------|
| **不 Await = 事件**；**Await = 请求-响应** | `Emit` 同步派发全部订阅者后 resolve；订阅者把结果写进 `v.Result`，发起方 `f.Wait()` 取回 |
| **errors 恒收集、不 reject** | handler 返回 error / panic → 追加 `v.Errors`，**不中断后续订阅者**；发送端自查 `v.Err()` |
| **order 升序** | `On(subject, order, h)`；同 order 按注册序（`(order, id)` 稳定排序） |
| **通配** | `*` 匹配单段、`>` 匹配剩余多段（NATS 约定，按 `.` 分段） |
| **payload** | `[]byte` / `string` 原样；其他类型 `json.Marshal` |
| **并发** | `sync.RWMutex` 保护订阅表；派发在锁外执行 |

> v1 `Publish/Subscribe` 为迁移期兼容（等价 `Emit` 不 await / `On(subject,0,包装)`），**不写回、order=0**。

## 3. 主题命名

### 3.1 前缀注入（业务不写 `chonk.`）

- 宿主在 `mq.New(Options{Prefix: "chonk."})` **注入一次**；业务一律写**相对主题**。
- 总线内部 `fullSubject` 补前缀用于注册/匹配；**下发给 handler 的 subject 统一去前缀**（相对形式）。
- 兼容保护：主题**已带**该前缀则原样透传、不重复加（遗留全主题调用方可继续工作）。

### 3.2 相对主题形态

| 形态 | 示例 | 分段 |
|------|------|------|
| 域-动作（kebab，单段） | `session-start`、`task-done`、`instance-register`、`data-prj-security-list` | 1 段 |
| 点分主题（多段，供通配） | `filesys.changed`、`mcp-tools-list`（域前缀 `mcp-`） | ≥2 段 |

- 全主题示例：`chonk.session-start`、`chonk.filesys.changed`。
- 通配按 `.` 分段：桥订阅 `>`（→ `chonk.>`）即可收到全部业务事件。

### 3.3 主题空间归属

| 主题空间 | 交互方 | 承载 |
|---------|--------|------|
| `data-<domain>-*` | 前端 ⇄ persist | 数据面（list/load/save/delete/restore + `refresh` 广播） |
| `filesys.*` | 前端/桥 ⇄ filesys | 文件查询/写/声明 + `filesys.changed` |
| `gui.*` | 前端 ⇄ gui 桥 | 本地面（窗口/布局/系统能力/截图/上传） |
| `session-*` / `task-*` / `instance-*` / `tool-retry` / `prompt-optimise` | 前端 ⇄ server | 会话方法面与事件 |
| `mcp-*`（组前缀） | server ⇄ gateway | 工具方法面（`tools/list·call` ↔ `mcp-tools-list·call`）+ `mcp-tasks-report` / `mcp-gateway-changed` |

> 全部主题与 payload 的**权威定义 = [61-消息一览](../60-reference/61-消息一览.md)**（测试唯一准则，冻结）。

## 4. 前端对称实现（`src/frontend/src/utils/mq.js`）

前后端**同一套 publish/on promise 语义**：

### 4.1 后端 → 前端（唯一入口）

Go 侧经 WebView2 `Eval` 直调 `window.mq.emitRemote(envelope)`，信封：

```json
{ "type": "<前端事件 type>", "payload": "<JSON 字符串>", "src": "mq|gui" }
```

- `emitRemote` 解析 payload（字符串 → JSON 对象）后按 `type` **本地 dispatch**（同 order 有序）；
- **只做本地分发，不回发后端（防环）**；
- 特殊：`llm-receive` 主主题分发后，再按 `payload.type` 二次分发子主题 `llm-receive.<type>`。

### 4.2 前端 → 后端（唯一发送）

```js
mq.emit(topic, payload)   // 本地按 order 分发 pre/on/post|error/final + fetch POST /publish
```

- HTTP 响应信封 `{ ok, result, errors }`（errors 收集、恒 accept，发送端自查）；
- `await mq.emit(...)` → `{ payload, results, backend }`（**收集**）；不 await → **事件**；
- 无 `request/RPC` 方法。

### 4.3 本地操作生命周期

`pre → on(main) → post | error → final`（本地请求-响应；`on` 支持 `order`）。Vue 指令：

```text
v-mq:[topic].[phase].[domEvent].[stop].[prevent].[once]="handler"
  · 订阅模式：v-mq:topic.on="fn"（挂载注册 / 卸载取消）
  · 触发模式：v-mq:topic.click="payload"（DOM 事件 → mq.emit(topic, payload)）
```

> 业务交互一律 `v-mq` / `mq.emit`；`@click` 仅限组件内部纯本地动作。

## 5. 桥的分派与事件映射（`src/lib/gui/bridge`）

`POST /publish` 的 `type` 决定处理面（`Bridge.PublishEvent`）：

| type 形态 | 处理 |
|-----------|------|
| `llm-start` | 拆两步：`session-start`（session/turn/llm/think/effort/scenario_id）+ `session-send{type:text-user,content}` |
| `gui.*` | 桥本地（`guiDo`，复用原 `/call` 内部实现） |
| `data-*` | 经总线 persist 数据服务（`dataViaPersist`，注入 `instance_id`+`req_id`） |
| 含 `.` 的点分主题（`filesys.*`） | 直通总线服务（订阅方写回 Result/Errors） |
| 单字方法（`llm-send`/`llm-cancel`/`ask-user-reply`/`task-stop`/`tool-retry`/`prompt-optimise`） | 映射为相对域主题（`frontMethodSubjects`），注入 `instance_id` |

**总线 → 前端**：桥订阅 `>`（相对全通配），`forwardEvent` 把相对主题映射为**稳定前端字符串**（`mqTypeMap`），未命中则原名直通：

```text
session-receive → llm-receive   session-complete → llm-complete   session-ask → ask-user
task-started → tasks.started    task-updated → tasks.updated      task-done → tasks.done
tool-changed → tools.list_changed   （data-* / filesys.* 原名直通）
```

**src 防环**：桥记录本实例近期发布的主题（1s 窗口、一次性消耗），命中则跳过转发，避免自己 `/publish` 的事件被二次 dispatch 回前端。

## 6. 设计约束与边界

1. **payload 一律携带 `instance_id`**（含 register；单实例也带）——多实例/多项目隔离的依据。
2. **跨端 payload 为 JSON 字符串**（信封约定），接收端自行解析。
3. **无 `/call` RPC、无 `/events`、无 `req_id`（v2）**：请求-响应靠 promise 结果写回，回执 = 同一次派发的 `v.Result`。
4. **errors 恒 accept**：不因订阅者报错而 reject；发送端必须自查。
5. **订阅方可多答**（一疑问多答）：多个订阅者各自写回 `Result`，前端 `results` 为数组。
6. **消息冻结**：主题/payload 的增删改须用户确认（见 [50-测试体系 §1](../50-testing/50-测试体系.md)）。
