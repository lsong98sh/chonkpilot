## 1. 问题与决策

### 1.1 用户已拍板（原话）

> 严重问题啊。要改文档。**必须按照 instance 管理**。我觉得需要考虑是否重新考虑后端。按照 instance 进行分离。感觉 **data, filesys 可以统一 gateway**，**llm 可能需要按照 instance 分离**。**split 下 gui 和 instance 是绑定的，无需分割**。**browser 下，用 browser 替代 gui 层**是这样的吧。

### 1.2 决策口径

| # | 决策 | 含义 |
|:--:|------|------|
| D1 | **执行池（gateway `execPool`）与任务视图（llm `taskManager`）必须按 instance 管理** | 「取消 / 状态 / 额度」三类操作**均带 instance 维度**：池按 instance 分区，`tasks/cancel` / `tasks/status` / `tasks/list` 必须做 **instance 归属校验或过滤**（现状见 §3 · §4 缺口 1/2/3/5/8）。**上述三个方法面已移除**（控制改进程内调用），归属校验随之取消；**「池按 instance 分区」的其余要求不变**。 |
| D2 | **后端分离方向**（用户倾向的混合方案，见 §5 C） | **`data` / `filesys` 统一到 gateway**（两者**本身无 instance 状态、纯参数化**，合并**无额外状态风险**）+ **`llm` 按 instance 分离** |
| D3 | **split 下 gui 与 instance 绑定，无需分割** | gui 侧 instance 与前端 **1:1**（`src/lib/gui/main.go:533,586,609`），**不存在**「gui 侧多 instance 同进程」问题；需要分离的是**服务端**（`chonkpilot-server.exe` 内的 llm） |
| D4 | **browser 下用 browser 替代 gui 层** | browser 形态**替代 gui 层职责**（前端承载 + 会话托管 + 作用域裁决），**native 能力需替换或禁用**（[19 §3.3](19-多租户服务端形态.md)）；instance 与用户/项目绑定，**同进程多 instance 更为严重** |

> **决策口径更新**：**① instance 隔离 = 当前优先实施**；**② `data` / `filesys` 不纳入 instance 隔离**——二者**以 `workdir` 为管理单位、维持现状**（故 D2 中「`data` / `filesys` 统一到 gateway」**不再作为本次前置**）；**③ 安全责任** = 「**instance 绑定 `work_dir`**」（[19 §3.4](19-多租户服务端形态.md)）+「**agentbox 执行层限制**」（`security-*` = 可读 / 可写目录、递归，见 [14](14-安全域-agentbox.md)）；**④ 缺口 6（filesys 采信请求 `work_dir`）按用户口径不纳入本次**。

## 5. 候选方案与倾向

| 方案 | 内容 | 代价 / 前置 |
|:--:|------|------|
| **A · 逻辑隔离** | **池按 instance 分区**（gateway `tasks` + llm `nodes`/`turns`/`busy`/`continuePending`/`asks`）+ **`tasks/cancel\|status\|list` 归属校验/过滤**（**三面已移除；此项不再适用**）+ **连接池 key 加 instance** + **`tempRoot` 分桶** + filesys 归属校验（缺口 6） | **改动最小**（不跨进程、不动拓扑）；**只消隐患、不达「按 instance 分离」目标** |
| **B · 进程隔离** | **每 instance 一套 llm**（每 instance 一进程） | 需**先解决跨进程传输**（§6 未确认项：split 下 gui↔server 真实传输口径不一致）；instance 数增长 → 进程数增长 |
| **C · 混合（用户倾向，D2）** | **`data` / `filesys` 统一到 gateway**（二者**本身无 instance 状态**：filesys 结构无实例状态 `filesys.go:22-26`、watcher 按 work_dir 分桶；data 每 instance 绑一份、请求参数化 `session.go:25-27` → **合并无额外状态风险**）+ **`llm` 按 instance 分离**（llm 侧**确有 instance 状态单池**：§3.2） | 依赖 B 的跨进程面（§6）；**data/filesys 合并 = 收敛服务端进程数**，但需明确「谁启动 filesys」口径（§6） |

**推进建议**：**先 A（消隐患，等效于把 §4 缺口 1–5、8 变成「按 instance 分区」的硬约束）→ 再评估 C**。理由：A 是 C 的前置（C 的 llm 分离后，各进程内仍是单 instance，但**合并到 gateway 的 data/filesys 仍需 A 的归属校验与池分区口径**），且 A 的改动面最小、可独立验证。

**任务侧统一按 [21-任务层设计方案](21-任务层设计方案.md)（Task 层独立化）** —— Task 层与 **LLM / Data / Filesys 平级**（D1）· `task_id` **由调用层分配**（D2）· **全同步落库**（D3）· 表结构自由（D4）。故本条 **A/B/C 中「任务侧」的表述让位于 21 篇**：不再以「把 llm/gateway 的任务池按 instance 分区」（A）作为任务侧主路径（+ 缺口 2/3/5/8 的任务侧收敛见 §4 补注）；**A 中非任务侧项**（`tempRoot` 分桶、filesys 归属校验、连接池 key 加 instance）**仍然有效**。

**与既有登记的关系**：[40 G-14](../40-roadmap/40-演进计划.md)（**gateway 为全局单份、非 per-instance**，user 建议「每 instance 一个 gateway 实例与对应 cache」）与本篇 **C 的方向一致**，属同一演进线的两个入口。

## 10. 无 `instance_id` 消息清单与入站校验（G-41-c）

> **背景**：§8 的 **MW-11** 结论「多实例下 `View.Resolve` 唯一实例回退失效 → 不带 `instance_id` 的数据入口须逐条审计」的**清单化落地**。本节 = 扫描 [61-消息一览](../60-reference/61-消息一览.md) + [61-messages.schema.json](../60-reference/61-messages.schema.json) 后，对 **payload/event 未声明 `instance_id`** 的主题**逐个判定**：①「按设计无需 instance」/ ②「应有但缺失」。
> **判据（§0 硬规则）**：`61 §0` 明载「业务 payload **一律必带 `instance_id`**（单实例同样携带），经桥业务消息由桥自动注入」；**唯一豁免 = `server-starting`**。故「文档 payload 未列 `instance_id`」**不等于**线上缺失 —— **前端 → 后端**的消息由桥 `injectInstance`（`src/lib/gui/bridge/bridge.go`）自动注入。本节 ② 特指**旁路发送方**（插件/脚本/内部直发）可能缺 `instance_id` 而落到实例数据面的主题。
> **实现（G-41-c）**：data 面入站 `persist.handle`（`src/lib/data/persist/persist.go`）按**主题白名单**校验 —— 白名单（全局级域 `user-config` / `scenario` / `mcp` / `knowledge`）内**允许无 instance**；**白名单外缺 `instance_id` → 明确失败**（`{ok:false, error:<缺 instance_id>}`，不再静默走"唯一实例回退"）。**未改 `61`**：本校验依赖 §0 既有硬规则，未新增/改/删任何主题与 payload 字段。

| 主题（家族） | 应含 `instance_id` | 判定理由 |
|------|:--:|------|

| `filesys.list/content/create/mkdir/remove/rename/copy/watch/unwatch` | 否① | **以 `work_dir` 定位**（61 §2：payload 携带 `work_dir` 做越界校验）；点分主题经桥 `injectInstance` 幂等注入 `instance_id`（§1.1 点分直通），服务端按 work_dir 分桶 |
