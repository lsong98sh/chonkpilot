## 1. 总原则：层 ≠ 工程

> **层 = 职责角色；工程 / exe = 宿主（打包方式）。** 层的定义**不随部署形态变化**。

**推论**

1. 新增一个能力 = **加包 + 装配处注册一行**，而不是"新增 module + 新增 exe + 新增消息面"。
2. "搬迁"（目录归位）= **零行为变更、零消息面变更**。
3. **层间仍走 MQ**（现状保留）—— 工程位置的改变不动通信方式；见 §7。

## 2. 工程构成

| 工程 | 角色 | 产物 |
|------|------|------|
| `lib` | **库**：`core/` 底座 + 服务层（`data` / `filesys` / `task` / `llm` / `gateway` / `mcp-server`）+ `mcp-tools`（executor） | — |
| `desktop` | 外壳·宿主（**桌面单体**：薄壳 → `lib/gui.Main`；`cli/` = CLI 单体） | `dist/desktop`：`chonkpilot.exe` / `chonkpilot-cli.exe` |
| `gui` | 外壳·宿主（**GUI 客户端**：薄壳 → `lib/gui.Main`，`-tags split`） | `dist/gui`：`chonkpilot-gui-client.exe` / `chonkpilot-cli-client.exe` |
| `server` | 外壳·宿主（独立 server；gui 与 browser **共用**） | `dist/server`：`chonkpilot-server.exe`（+ 静态页 `www/`、引擎、`capability/`） |
| `others` | 外壳·协议（对外 MCP 出口 + 第三方 MCP 接入） | `dist/other`：`chonkpilot-mcp-server.exe` / `chonkpilot-mcp-gateway.exe` |
| `plugins` | 独立能力体 / 引擎 / 插件（`codegraph` / `vfts` 引擎 + `plugin*`） | 引擎 exe → `dist/plugins/*`（发行时并入 `dist/desktop`、`dist/server` 根）+ executor ×3 |
| `frontend` | 前端工程（Vue3，双入口） | embed → `src/{desktop,gui}/frontend/dist`；browser → `dist/server/www` |
| `test` | 测试工程（`unittest` / `systest` / `llmproxy`） | — |

**目录约定**（`src/` 下不带 `chonkpilot-` 前缀；产物入 `dist/*`）

```text
src/
├── frontend/                  # 前端工程（Vue3，仓库级；双入口 embed.html / index.html）
├── lib/                       # 库：core 底座 + data/filesys/task/llm/router/assembly/gateway/mcp-server(+server/) + mcp-tools
├── desktop/                   # 外壳·宿主：桌面单体（main.go 薄壳 + cli/ = CLI 单体）
├── gui/                       # 外壳·宿主：GUI 客户端（main.go 薄壳；frontend/dist = 客户端 embed 落点）
├── server/                    # 外壳·宿主：独立 server（gui / browser 共用）
├── others/                    # 外壳·协议：mcp-server / mcp-gateway 两个 exe 外壳
├── plugins/                   # 插件与引擎：plugin{, -memory, -history, -compress, -codegraph, -vfts} + codegraph / vfts 引擎
└── test/                      # 测试工程（unittest / systest / llmproxy）
dist/
├── desktop/  gui/  server/  other/  plugins/
```

> 🆕 **D-28**：上文 `src/` / `dist/` 分区即落地形态。**两个宿主壳共用同一份宿主实现**（`lib/gui` 的 `Main(distFS, Options{Form})`，方案 B：**零重复**）：`src/desktop` = `//go:embed all:frontend/dist` + `FormDesktop`；`src/gui` = 同壳 + `FormGui`。`-tags split` **不再决定宿主分支**（仅保留对 `instance` 心跳与 `llm`/`persist`/`plugin-*` 的 `sweep_split.go` 的作用）。

**Lib 内部分层与隔离**

- 依赖方向：`core/`（**零仓库依赖**）← 服务层（`data` / `filesys` / `gateway` / `task` / `llm`）+ `assembly/`（装配实现）；**`router/` 亦零仓库依赖**（纯 lib：LLM 出网协议适配，见 [10 §3](10-分层与依赖.md)）
- **隔离**：非门面的一切下沉 `<组件>/internal/` —— **编译器强制**（`internal` 之外不可 import），取代"靠人查"的文档纪律
- 门面 = **翻译层**（存储模型 → 领域模型），**不是管道**：不交解析器、不交路径规则
- 详见 §7

## 3. 外壳边界（7 类职责）

**外壳只应有**

1. 进程入口与生命周期（`main` / 参数 / 退出 / `instance-claim`·`instance-exit`）
2. 宿主环境适配（读 env、定 `work_dir`/`data_dir`、注入；`instance-claim` 的 `work_dir` 取值见 [22 §3.1](22-实例与会话标识.md)）
3. **传输装配**（in-process / HTTP bridge / SSE / stdio）
4. 承载层（WebView2 窗口 / 静态资源 / console）
5. **装配选择**（装哪些层、注册哪些契约、开哪些插件）—— **只"选"，不"装"**
6. 协议适配（对外 MCP ↔ 内部 MQ）
7. **身份与作用域**（实例认领 `instance-claim` + 作用域裁决下发；**用户注册 / 登录 / 鉴权属阶段 2b，见 §8**）

**外壳不该有**：业务规则 · 领域判断（名字 / 类型 / 树）· 状态机 · 持久化 · 层间协调逻辑。

**判据**

- **换宿主测试**：换成另一个外壳还成立吗？成立 → 归 Lib
- **去 I/O 测试**：把 stdin/stdout/网络/窗口/文件/时钟都 mock 掉还能跑吗？能 → 归 Lib

> **独立能力体例外**：`mcp-tools`（executor）与引擎（codegraph/vfts）**不是外壳**，是"被 spawn 的执行体 / 独立部署" → **不得依赖 Lib 服务层**（executor 现状仅依赖 `paths`）。

## 4. 形态矩阵（**三形态**）

| 形态 | 组成 | **认证提供方** | 用户模型 | 产物 |
|------|------|---------------|:---:|------|
| **desktop** | desktop（内嵌 server） | **无**（本机单用户、免鉴权） | 单用户 | `dist/desktop`（`chonkpilot.exe` + `chonkpilot-cli.exe`） |
| **gui** | gui 客户端 + 独立 server（**server 可异地**） | **门面 `Authenticator`** | 多用户 | 客户端 `dist/gui`（`chonkpilot-gui-client.exe` + `chonkpilot-cli-client.exe`）· 服务端 `dist/server`（`chonkpilot-server.exe`） |
| **browser** | 浏览器 + server | **门面 `Authenticator`**（浏览器登录） | 多用户 | `dist/server`（`chonkpilot-server.exe` + 静态页 `www/`，**与 gui 同一份 exe**） |

> 🆕 **命名（含第二刀）**：**产物目录**已按形态重整（`dist/standalone/` → **`dist/desktop/`**、`dist/split/` → **`dist/gui/`**，脚本 `build-standalone-gui.ps1` → `build-desktop.ps1`、`build-split.ps1` → `build-gui.ps1`）；**本表第一列的形态标识亦已重整（语义翻转）** —— 原 `standalone` → **`desktop`**（桌面单体）、原 `desktop`（≡ team）→ **`gui`**（GUI 客户端 + 独立 server），`browser` 不变（与 [22 §2](22-实例与会话标识.md) · [61 §4.6](../60-reference/61-消息一览.md) `window.__ck.form` 一致）。**产物名同步**：桌面单体宿主 `chonkpilot-gui.exe` → `chonkpilot.exe`；gui 形态客户端 → `chonkpilot-gui-client.exe` / `chonkpilot-cli-client.exe`；`chonkpilot-server.exe` 名不变（gui 与 browser 共用）。

**要点**

- **形态 = 装配组合**（传输 + **令牌承载** + 数据根前缀），**不是三个工程**；构建脚本名即形态名。
- **三者差异只在客户端形态与令牌承载**：GUI（desktop / gui）= **桥注入**；browser = **`Set-Cookie`**。见 [22 §5](22-实例与会话标识.md)。
- **`gui` 与 `browser` 都用同一 `server` 工程，且同等要求认证**：独立 server **可运行在异地** → 客户端断言不可信，一律**以连接层凭证为准**（[22 §6](22-实例与会话标识.md) · [61 §4.6](../60-reference/61-消息一览.md)）。
- **desktop** = 本机单用户、**免鉴权**；`work_dir` 取**服务端启动参数** `--work-dir`（缺省 cwd）。
- **形态不由 UA 判定**（UA 可伪造，仅可作日志诊断）；`window.__ck.form` 由**服务端注入**。
- **认证未实施**：`requireAuth` / `authed` 当前恒由服务端注入为 `false` / `true`（2a 口径）。

## 5. 三区部署拓扑

```text
前端（薄桥）  →  app-server（无状态）  →  存储区（有状态）
```

| 区 | 组件 | 状态 |
|------|------|------|
| **前端** | browser ／ gui-bridge | 无状态 |
| **app-server** | llm · gateway · mcp-server · mcp-tools | **无状态**（会话/轮次/消息/任务树均落库），**可水平扩展** |
| **存储区** | **data（单实例·无状态）** · filesys | 有状态（DB 文件） |

**要点**

1. **`data` = 单实例 + 无状态**：状态全在 DB 文件 → **可任意重启 / 主备切换**；单实例 → 满足 bbolt 独占写，**无分片、无亲和**。
2. **nginx 只需 app-server 一层**（按 `user` 哈希）——且**仅为「在飞 turn 的后续控制面消息」亲和**（`ask-user-reply` / `tool-stop` / `tool-retry`）。
3. **扩展路径**（若将来需要）：按 **`project-id`（UUID）** 分片 + 实例注册表（复用现成 `instance-*`），**不用 nginx 手写规则** —— workdir 物理路径会随部署漂移，不能作分片键。
4. **文件如何到应用区**：app-server **挂载**存储区的 workdir，executor **直接读写**；filesys 服务负责**监听 / 变更通知 / 前端文件树**（不承担全部文件 IO —— 网络往返性能不可接受）。

## 6. 路径映射

同一份 workdir 在两区路径不同：

```text
存储区视图   /projects
应用区视图   /home/chonkpilot/projects      ← 挂载点
```

**规则**

1. **应用区全链路用挂载后路径**（executor / DSL `@"file"` / 工具入参）
2. 边界（调 `data` / `filesys`）按**部署级映射表**解析 —— 映射表属**部署配置**，不落 DB
3. **DB 只存逻辑路径**（相对 workdir），**不存物理绝对路径** —— 否则换挂载布局即失效（**当前未实现**，见 §9 · G-24）
4. 路径前缀体系见 [16-路径解析规范 §8](16-路径解析规范.md)：`~/` · `!/`（临时）· 绝对；**相对路径一律拒绝**
5. **`~/` 按模式求值**：standalone = OS 用户目录（`C:\Users\…` / `/home/…`）；**多用户 = 指定用户信息目录**（系统认证下 = 同上；其他可指定，缺省为 exe 同级 `data`）—— 多用户口径见 [22 §6.4](22-实例与会话标识.md)（auth 库 + 每用户一套业务库）

## 7. 通信：门面（替代"必须走 MQ"的表述）

- **一律经门面**；绑定 = `inline` / `http` / `mq`
- **Lib 内包间仍走 MQ**（现状保留）；门面**收编** MQ，**不并列**（否则同一件事出现三种写法）
- 门面 = **翻译层**，不是管道：**不交解析器、不交路径规则**（格式与路径都是服务端事实）
- **请求面 + 订阅面成对**：广播/多订阅**塞不进**请求-响应门面，须独立定义（inline = 回调注册；http = SSE / 长连接）
- **绑定选择**：编译期决定"编入哪些绑定"，**装配期决定"用哪个"**（外壳职责 5）
- **事件 = 提示，不是状态**：可丢、可乱序 → 订阅方收到后**去读当前状态**；重连后**全量重读**一次
- ⚠️ **inline 同步派发**（总线同步逐订阅者执行）→ **订阅回调必须轻量**，**禁止在回调内反向调用**同一门面（否则自死锁）；http 绑定不暴露此问题 → **契约须按最差绑定设计**
- ⚠️ **契约类型分层**：**wire 形状（61 绑定）与门面领域 DTO 是两件事，不合并**——内核契约类型（`data.ChatMsg` / `ToolCall` / `Snapshot`）**即**消息面/存储形状（`_meta`、`tool_calls[].function{name,arguments}`、`history`/`snapshot_turn`），被跨模块 MQ 消费方直接解析；门面 DTO 一律用**领域字段**（`meta`、平铺 `name`/`arguments`、`messages`/`turn`）。**门面已进面的域，消费方只认 DTO**（不得翻回内核类型往返），两者的翻译只留在门面实现侧。合并成单一家族只剩两条路且都有代价：统一到门面写法 = 改 MQ payload 键名（**61 变更**）；统一到内核写法 = 门面退化为 wire 形状（违本节）

**PoC 背书**（`TECH-POC/`）

| PoC | 结果 |
|------|------|
| `facade`（一份定义 → 自动生成 http 绑定；编译 tag 选绑定） | inline **17/17**、http **15/17**、跨进程 ✅ |
| `cancelprop`（取消传播 + 4 线终止 + 重试边界） | **10/10** |
| `webview2-cookie`（虚拟源 cookie） | **5/5** |
