## 1. 决策（用户已拍板）

### 1.1 用户原话

> Task 是一个完完全全独立的东西，它和 LLM、Data 以及 Filesys 是同一层的。Task ID 是由**调用层**来决定的，因为它可以决定它的 Parent ID 是什么。一致性的话，我建议**全部使用同步**。至于库的话，只要**表结构合理**就行了，无所谓使用一张表还是两张表（例如一张表控制 session 下的工具以及工具的层级，一张表控制 session 和 session 的关系）。

### 1.2 决策口径（D1–D10）

| # | 决策 | 口径 |
|:--:|------|------|
| **D1** | **层级** | Task 层是**完全独立的一层**，与 **LLM / Data / Filesys 平级**——**不是** data 的一个域、**不是** gateway 的子模块、**也不是**「与 data 同侧」。建议 module 名 **`chonkpilot-task`**。层以 **DB 为权威**、由事件驱动（详见 §3/§4）。 |
| **D2** | **task_id 归属** | `task_id` **由调用层（发起方）分配**——因为**只有调用层才能决定它的 `parent_id` 是什么**。**层不分配 id**，只做 **upsert / 唯一性校验**（撞号处理见 §6-6）。 |
| **D3** | **一致性** | **全部同步**——「**事件 → 层 → 落库 → 返回 ack**」；**发起方等 ack 后才继续**（不采用异步落库 / 最终一致）。 |
| **D4** | **表结构** | **一张表或两张表皆可**，只要**结构合理**；用户举例：「一张表控制 session 下的工具以及工具的层级 / 一张表控制 session 与 session 的关系」。本方案给出 **α 单表自引用（推荐）** 与 **β 双表** 两个选项（§5）。 |
| **D5** | **同步口径（不节流不合并不合并）** | **每个事件同步落库，不节流、不合并**。依据（用户口径）：**llm 场景不存在高频**、一个 workdir 也不太会很多人同时工作 → 原「发起端节流 + 同 `task_id` coalesce」建议**作废**；「写延迟实测 / 并发上限」**降级为非阻塞项**（可留作观测，**不作为门槛**）。见 §6-2 / §6-3。 |
| **D6** | **管理单位分工** | **data / filesys / taskManager = 以 `workdir` 为管理单位**；**gui / browser / llm / gateway = 以 `instance` 为管理单位**。推论：**Task 层隔离键 = `workdir`**（非 instance）→ `task_id` 唯一域 = **`(workdir, task_id)`**；事件里的 `instance_id` **仅作来源标注**（**视图过滤维度见 D7 = 按 `top_session`**；「前端按 instance 过滤视图」旧表述已订正），**不作隔离键**。库归属自动落定 = prj 库 `<workDir>/.chonkpilot/chonkpilot.db`（`src/data/shared.go:76`、`db.go:138`）→ 原「prj 库 vs usr 库」待确认**关闭**（**无需 usr 级 task 库**）；与 gateway 下游连接池**按 workdir** 分池（`src/gateway/gateway/provider.go:170-172,396-407`）**口径一致**（三处同为 workdir）。风险项见 §6-7。 |
| **D7** | **树按主会话（`top_session`）过滤** | **树以 `top_session`（主会话）为组织 / 过滤维度**；`workdir` 为**隔离键**（数据单位，D6）、`instance_id` **仅来源标注** → **同一 workdir 下多 instance 的任务汇入同一数据域（同一棵树），但视图按 `top_session` 切分**（= 多 instance 并发写同一树的可见性策略：**各自主会话互不混视**）。由此**消解 §6-7 / §8-①**（~~原「视图按 instance 过滤」~~ → **按 `top_session` 过滤**）。配套：唯一域仍 = **`(workdir, task_id)`**；**撞号 → 拒绝并记错误日志**（层不覆盖）。 |
| **D8** | **exec 明细长期可读（2026-09-18 P3 批次）** | gateway 执行态明细（`workdir` / `provider_key` / `phase` / `state` / `message` / `detail{trigger/threshold_s/mode/timeout_s/options}` / `at`）写入权威行 **`exec_json`** 并**随行长期保留**（可经 `data-tasktree-tasks` 读；**不只存内存**）→ 与「内存逐出、库保留历史」（§6-5）同向。配套口径：**`exec_json` 只增不减（深合并）**、状态优先级 **终态 > 执行态(detached/awaiting) > 粗粒度(pending/running)**（见 §9.3）。 |
| **D9** | **异步 status/result 落 message 表 content 三段（2026-09-18 收尾，[42 §2 (99)](../40-roadmap/42-决策记录.md) · [42 §2 (100)](../40-roadmap/42-决策记录.md)）** | 异步工具的**状态与结果不再由 gateway 提供**（`mcp-tasks-status` / `mcp-tasks-result` 已移除）→ 落 **message 表** role=tool 消息 `content` 的 **`{call,result,async}` 三段**：`call`（工具名/参数/tool_call_id）· `result`（`content` + `status`）· `async`（`pending` / `task_id`（= gateway 执行 id）/ `moved_at`）。写入 `src/llm/server/turn.go:699 persistToolResult`；结构 `src/data/persist/view.go:50-74`（`ParseToolContent` 兼容旧 `ToolPairPayload`）。**读取** = `data-session-content` 的 key 前缀 **`tool_result:<tool_call_id>`**（既有方法扩参，payload/返回形状不变）；取不到 → **明确文案**「异步结果已不可用（任务已终态，但 message 表无该调用的结果行）」（`server/tool_task.go:169`），**不静默返空**。**状态**以层 `State(task_id)` 为准。 |
| **D10** | **控制面 = 层 authoritative + sink 执行（2026-09-18 收尾，[42 §2 (99)](../40-roadmap/42-决策记录.md) · [42 §2 (100)](../40-roadmap/42-决策记录.md)）** | **控制（取消 / 转后台）的唯一入口 = `task-stop` / `task-background`（mq 方法面）**；MQ 传输面不再有 `tasks/cancel` / `tools/background`（已移除）。执行链 = `onTaskStop`/`onTaskBackground` → **层为权威**（`CancelSubtree` 标终态 / `ExecOf` 取 exec 句柄）→ 层对持句柄节点回调 `OnCancelExec` → **进程内 sink** `ExecSink.CancelExec(gw_task_id)` / `DetachExec` → gateway `(*Gateway).CancelExec` / `DetachExec` → `provider.Invalidate` **真打断**（取消）/ 解绑返回 pending（转后台）。**sink 未注入 / 执行池不可用 → 明确错误、不动作**。`task-stop` 载荷 **`{task_id?, tool_call_id?, cascade?}`**：工具行只持 LLM tool_call_id → 服务端 `tm.findByToolCall` **反归一**为 server 节点 `task_id`（`server/server.go:1157`）。 |

## 3. 事件契约（最小集，**全部同步**）

> D3 口径：**事件 → 层 → 落库 → 返回 ack**；发起方**等 ack 后才继续**（层内 upsert 幂等）。
> **层是唯一接收方 / 唯一落库方**；其他模块**只发事件、不再自行拼树**（§4）。

| 事件 | 关键载荷 | 说明 |
|------|---------|------|
| `task-created` | `{instance_id, task_id, parent_id, kind(tool/llm/ask), top_session, session_id, tool, tool_call_id, args摘要}` | 节点首次登记（**id 由调用层给**，见 D2）；`kind` = `tool` / `llm` / `ask` |
| `task-started` | `{instance_id, task_id}`（+ 可选 `started_at`） | 进入 running |
| `task-detached` | `{instance_id, task_id, mode(自动/手工), threshold_s?}` | 转后台（自动按阈值 / 手工经**进程内 sink**：`ExecSink.DetachExec`，[42 §2 (99)](../40-roadmap/42-决策记录.md)） |
| `task-awaiting` | `{instance_id, task_id}` | 裁决中（等待超时裁决 / 等人表单） |
| `task-done` | `{instance_id, task_id, result摘要}` | 终态（成功） |
| `task-error` | `{instance_id, task_id, error摘要}` | 终态（失败；`cancelled` / `interrupted` 均按**终态**处理，见 §8.1-3） |
| `turn-started`（llm 额外） | `{session, top_session, parent}` | turn = llm 节点（§4） |
| `turn-ended`（llm 额外） | `{session, top_session, parent}` | turn 终态 |

> **消息面口径（⚠️ 必须用户确认后才落地）**：`task-done` / `task-started` 与前端 `task-*` 主题**已在 [61](../60-reference/61-消息一览.md) 存在**；`task-created` / `task-detached` / `task-awaiting` / `task-error` / `turn-started` / `turn-ended` 属**新增**。**若这些事件走 MQ 主题**，则构成 [61](../60-reference/61-消息一览.md) **消息面冻结变更**——**必须先经用户确认**；**本轮只登记设计，不改 61**。若实现为**进程内层 API（不经 MQ）**，则 61 **零变更**（实现形态待定，见 §6）。

## 4. 树规则（**层为唯一权威**）

1. **`top_session` 归拢根 + 视图过滤维度（D7）** —— 每个节点必带 `top_session`，同 `top_session` 的节点构成一棵树（根 = 主会话派生物）。**数据单位 = `workdir`（D6，隔离键），视图 / 查询按 `top_session` 切分（D7）**：同一 `workdir` 下多 instance 的任务**汇入同一数据域**，但**各自主会话互不混视**；`instance_id` **仅来源标注、不作过滤键**。
2. **`parent_id` 显式优先** —— 父节点由**调用层给出**（D2：调用层才知道 parent 是谁），层**不猜、不重排**。
3. **turn = llm 节点** —— 沿用既有口径 `node_type=session`（[61 §data-tasktree-list](../60-reference/61-消息一览.md)），会话身份在独立字段 `session_id`。
4. **工具 / ask 节点挂到发起它的 turn 节点下** —— 即 `parent_id` = 该 turn 的 llm 节点 `task_id`。
5. **其他模块不得自行拼树** —— llm / gateway **只发事件**（§3），**由层统一建树 + 落库**；这正是 D2「id 由调用层分配」与 D3「全同步」的前提（见 §6-1）。

**顺序依赖（D3 的必要性）**：turn 节点必须**先同步登记并拿到 `task_id`**，后续工具节点才能以其为 `parent_id` —— 若异步落库，则父 id 尚不存在 → 子节点无法正确挂载。
