## 一、问题定义：为什么需要这一段

### 1.1 三条失败模式

| 失败模式 | 表现 |
|---|---|
| 需求是**散点**，设计是**槽位** | 两者之间没有落位动作，导致"符合需求"无判据 |
| 规模一上来就靠**通读** | 需求上千条时，任何"靠理解"的方式必然退化为抽样 |
| 交付粒度 ≠ 验收粒度 | 一个任务里塞多个功能点，AI 收尾时无法自证"做完了" |

补充一条（2026-10-12 讨论确认）：

| 失败模式 | 表现 |
|---|---|
| **记录不是结构化的** | 用户中途改主意/补充/纠正，散落在对话里；没有台账，变更无法不重跑地归并 |

### 1.2 这一段的三个目标（也是验收判据）

1. **完全满足用户需求** —— 每条需求都能追溯到落地位置；
2. **AI 开发/测试不遗漏** —— 覆盖度可机械校验，不靠人肉通读；
3. **数据流转符合用户期待** —— 每个动作都是一次"输入对象 → 输出对象"的变换，全链路可核对。

### 1.3 一句话结论

> **设计不是"再想一遍"，而是"换轴重投影"：把需求，沿一组固定的轴各投影一次。**

## 二、总原则（六条，贯穿全程）

| # | 原则 | 含义 |
|---|---|---|
| 1 | **换轴不换文** | 同一段需求读 N 遍，每遍只带一个轴。禁止"读一遍想所有事"（那是自由思考 = 抽样） |
| 2 | **先薄后厚，上游冻结** | 先横向把所有对象薄薄过一遍，冻结后才纵向逐个做厚 |
| 3 | **业务语言** | 全程只装业务对象、业务动作、业务参数。技术词（类型/长度/索引/缓存/日志）一律不进 |
| 4 | **单一事实源 + 派生视图** | 字典是唯一事实源；页面/菜单/权限/报表/任务卡/Excel 都是它的派生视图 |
| 5 | **门控 = 计数归零** | 门控不是"你觉得对吗"，是"某个计数必须为 0" |
| 6 | **缺口驱动提问** | 提问不靠"想还该问什么"，靠**校验报出的缺口**。缺口在哪，下一个问题就在哪 |

**原则 3 的战略意义**：只有业务语言，业务人员才能逐格点头；技术语言一进来，业务人员失去确认权，"符合需求"就再也无法验证。

## 三、两阶段划分（需求沉淀 vs 设计细化）

### 3.1 边界

| | **需求阶段**（`se` 00–12） | **设计阶段**（本方法） |
|---|---|---|
| 干什么 | **沉淀** | **细化 + 编号** |
| 产出 | 属性、动作、术语（口语化） | 对象/状态/动作（编号）+ 处理过程、参数、元数据、接口、报表、权限 |
| 编号 | **无** | 全部补齐 |
| 元数据 | 不涉及 | 完整元数据（码表 / 编号规则 / 单位） |

### 3.2 由"需求阶段不编号"推出的关键结论

**名字就是主键。**

没有 `OBJ-001` 可引用，一切引用只能靠名字。于是：

> **需求阶段的命名守门，比设计阶段重要得多。** 一旦"两个名字指同一物"或"一个名字指两物"，沉淀从根上就乱了，后面补编号也救不回来（不知道该给谁编号）。

这条必须在**用户说出口的那一刻**处理，不能等收尾——因为名字会立刻扩散到多处。

### 3.3 交接：唯一一次"改号"机会

设计阶段开工第一件事，是建一张 **`名字 → 编号` 映射表**：

```
客户     → OBJ-001
申请单   → OBJ-002
集采     → ACT-001
```

**这是唯一一次"改名换号"的机会**，之后名字随便改，编号不动。映射表必须**显式产出、显式确认**，不能隐式完成。

## 四、第一层思考：怎么切批，从哪进

### 4.1 工具：依赖图 + 拓扑分层

切批依据**不是**需求文档的章节顺序（那是业务域顺序，给人读的），而是**产物之间的依赖关系**：

> 给所有设计产物画一张"谁引用谁"的图，**从没有入边的节点开始切批**。

**口子（入口）**：不在第一章，在**被引用最多、自己却不引用别人**的三样东西——全局开关、名词表、骨架。

### 4.2 六批

| 批 | 内容 | 从需求文档哪里取 | 冻结后供谁用 |
|---|---|---|---|
| **B0** | 全局开关（多组织/多语言/审计范围/移动端…） | 企业画像 + 通用维度 + 非功能性 | 决定后面所有表结构 |
| **B1** | 名词表：对象清单 + 关系 + 主/从/引用分类 + 主键 | 管理对象 + 生命周期 | 后面所有批次 |
| **B2** | 骨架：角色 + 菜单 + 页面名单（只有名字，不含内容） | 角色/流程 + 管理对象 | B3 的容器 |
| **B3** | 逐对象深化：属性 → 状态机 → 动作表 → 页面内容 → 权限格 → 用例 | 各对象的诉求/可管理项/接口 | **重复 N 次，一批一个对象集群** |
| **B4** | 横切：能力基线、业务处理过程、报表、业务参数、定期/批量处理 | 通用维度 + 对外接口 | — |
| **收口** | 数据字典 + 追溯 + 任务卡 | — | 交 AI 执行 |

**B3 是主体工作量**，也是唯一需要重复的批次。

### 4.3 三条切批纪律

1. **先薄后厚** —— B0–B2 坚决不写内容（B2 的页面只写名字）。三批走完你还不知道任何页面长什么样，这是对的。
2. **上游冻结，下游才开工** —— 批与批之间有冻结门。问题走**变更流程**，不许就地改。
3. **一批 = 一个对象集群（3~6 个实体）** —— 这是"一次上下文装得下、且能完整验收"的最大单元。批内再拆任务，控制在 3~5 个。

### 4.4 数千条需求怎么摊

**按归属做，不按顺序做。**

1. B1/B2 建立**挂载点**（对象、页面）；
2. B3 之前，把需求条目逐条**归并挂到对象和页面**上（这一遍很薄，只归并挂载，不做设计）；
3. 于是上千条被摊到十几个对象批次里 → 每批只有几十条；
4. 归并不掉的（跨对象、全局性）自动落到 B4。

**关键认知：需求条数 ≠ 设计条数。** 需求条数 ∝ 业务表述的冗余度；设计量 ∝ 实体数 + 页面数 + 动作数 + 字段数。设计只写一次，需求条目靠**挂载关系**复用设计。

## 五、第二层思考：批内怎么做

### 5.1 单对象六步（顺序不可换）

```
定位 → 标识与关系 → 属性 → 状态机 → 管理项 → 物理化
```

| 步 | 做什么 | 为什么在这个位置 |
|---|---|---|
| 1 定位 | 主对象 / 从属对象 / 引用对象 | 决定后面花多少力气（差 5 倍） |
| 2 标识与关系 | 主键、编码规则、外键（指向谁、被谁指） | 外键决定"谁能先做"；被引用的先做 |
| 3 **属性** | 业务属性 × 四问（见 5.2） | 一切的下游 |
| 4 状态机 | 状态清单 → 进入/退出条件 → 迁移权限 → **超时行为** | 状态是属性之一，属性没定无从谈 |
| 5 管理项 | 状态 × 动作 | 状态不明无从展开 |
| 6 物理化 | 属性 → 字段（类型/长度/索引/脱敏）属**技术实现**，业务字典里只留"取值范围" | 属性全定后是一次翻译 |

**对象类型 vs 投入量**

| 类型 | 例 | 生命周期 | 独立页面 | 独立权限 | 设计量 |
|---|---|---|---|---|---|
| 主对象 | 客户、合同 | 有 | 有 | 有 | 满配（六步全走） |
| 从属对象 | 联系人、拜访记录、回款单、订单明细 | 跟随主对象（可有简单状态） | 无独立菜单（嵌在主对象页或从其进入） | 通常继承，必要时单定 | 只走属性 + 简化状态 |
| 引用对象 | 产品、地区、字典 | 无 | 无（只被选） | 无 | 只走属性 |

> **从属对象 ≠ 没有状态、没有权限**，它只是**没有独立菜单**。反例：回款单有"已到账 / 已核销"状态、财务能看所有回款——它仍是合同下面的从属对象。

> **对象 / 从属对象 / 属性 的判据**（易混，务必分清）
> | 判据 | 属性（字段） | 从属对象 |
> |---|---|---|
> | 数量关系 | **一对一**（客户只有一个"行业"） | **一对多**（一个客户 N 条拜访记录） |
> | 自己带不带字段 | 不带（属性就是一个值） | **带**（时间/方式/人/内容/计划） |
> | 要不要独立增删改查 | 不要 | **要** |
>
> **只要用户说"要能记录…"，先默认那是对象，不是字段。** 高危词：记录、明细、历史、条目、流水、清单。
> 降格为属性的唯一边界：**永远一对一 + 字段很少（1~3 个）+ 永不独立管理**。安全默认是一律按从属对象处理。

### 5.2 属性：六类来源 + 四问

**六类来源**（属性不止来自对象自身）

| 来源 | 例 |
|---|---|
| 对象固有 | 客户名称、合同金额 |
| 状态 | `status` |
| 对象级公共标准 | 创建人/时间、修改人/时间、软删除（**全项目定一次，所有对象套用**） |
| **动作带出** | 来源去向（血缘）、提交人/时间、撤销相关 |
| 权限带出 | 负责人、部门、组织 |
| 集成带出 | 外部单号、同步状态、最后同步时间 |

> **"动作带出的属性"不可事后回填**：其他属性可以补、可以回填，来源关系不行——动作发生那天没记，就永久丢失。所以它是"第一天就必须决定"的属性。

**四问**（每个业务属性都要过）

| 问 | 影响 |
|---|---|
| 谁看得见？ | 字段级权限（敏感字段打标） |
| 要不要留痕？ | 是否进变更历史 |
| 会不会被外部系统带进来？ | 幂等 / 同步字段 |
| 取值是否固定？ | 硬枚举 or 可配置码表 |

### 5.3 业务动作表（所有东西的上游）

**动作的定义（可多对多）**

> 动作 = {输入对象（可多个）} → {输出对象（可多个，新产生）} + {原对象的状态变更} + {副作用}

**四类变更**（拆开才能各推各的）

| 变更类型 | 问 | 导出什么 |
|---|---|---|
| 字段变更 | 写了哪几个字段？ | 表单字段、校验、必填 |
| 状态变更 | 从哪个状态到哪个？ | **状态机 + 业务流程环节** |
| 对象变更 | 牵动了哪些别的对象？ | **一起成功（事务）+ 跨对象流程** |
| 副作用 | 通知谁？写什么日志？编什么号？同步给谁？ | 通知、留痕、编号规则、接口 |

**对象间动作**（一等的独立类别）

| 形态 | 形状 | 例 |
|---|---|---|
| 聚合 | N → 1 | 多张申请单 → 集采单 |
| 分解 | 1 → N | 集采单 → 多条分发记录；BOM 展开（分解 + 规则表） |
| 转移 | N → N（改归属不改数量） | 调拨、批量转派 |

判断标准：**它的输出对象，是不是"这个对象自身的表里查不到"的东西。** 是，就是对象间动作。

**对象间动作的四个必答**

1. **来源去向（血缘）** —— 集采单记来源单号、分发记录记父单号。**逆操作 = 沿血缘反向拆解**；无血缘则无法回溯、无法撤销、无法审计。
2. **守恒规则** —— ①数量守恒（可自动校验）②规则映射（按比例）③**不守恒**（有议价/损耗，必须写明差额去哪）。
3. **一起成功** —— 一次动作写多张表，部分失败怎么办（边界 + 补偿）。
4. **可撤销性** —— 三条件：血缘完整 ∧ 下游未消费 ∧ 非终态。三种实现：物理撤销 / 红冲（生成反向单据，**会长出新对象**）/ 禁止撤销（改走变更流程）。

> **撤销本身是一个普通动作**，同构：输入 = 原输出对象；输出 = 无 或 一张反向单据；副作用 = 通知、审计。

### 5.4 动作的来源（防漏）

动作只来自三个地方，缺任一处必漏：

| 来源 | 例 |
|---|---|
| 状态迁移 | 每个状态的进入/离开通常对应一个动作 |
| 需求里的动词 | "要能查重 / 要能转派 / 要能导出" |
| **能力基线** | 每个对象默认都有：查看历史、导出、导入、批量操作、附件 |

**能力基线带来的动作最容易被漏**，因为它不出现在任何需求里，也不属于任何对象专有。

### 5.5 动作 → 页面 → 菜单（两个桥，跳不过）

| 桥 | 为什么必须 | 不做的后果 |
|---|---|---|
| **桥1：动作 → 页面（归组）** | 一屏能放多个动作（列表页同时有查/筛/批量/导出） | 20 个动作 = 20 个菜单项，**菜单爆炸** |
| **桥2：页面 → 菜单树（组织）** | 页面要按对象归属 + 工作流顺序排 | 菜单变成无结构平铺 |

硬规则：**菜单项 ≈ 每对象的"列表页"一个**，详情/新建/编辑是列表页的**下级路由**，不占菜单位。
**菜单有两个来源**：业务菜单（动作表派生）+ 基线菜单（系统管理/报表/工作台，来自能力基线）。

### 5.6 角色：先问岗位，再算最小角色数

角色来自**组织岗位**，不要从权限点聚类（会聚出技术上合理、业务上不存在的角色）。但动作表能算**最小角色数**：

```
权限点集合 = { 角色 → 该角色可执行的动作ID集合 }
最小角色数 = 这些集合去重后的个数
```

- 两个岗位集合完全相同 → 同一角色，可合并（常查出冗余岗位）；
- 某岗位集合 ⊂ 另一岗位 → 可能是子角色或受限视图，需业务确认。

## 六、需求阶段的沉淀规范

### 6.1 三个沉淀文件

| 文件 | 存什么 | 标识 |
|---|---|---|
| `属性.md` | 口语化的字段（"客户有行业、规模"） | 名字 |
| `动作.md` | 谁要对什么做什么（"销售要能把客户转成商机"） | 名字 |
| `术语.md` | 名词定义 + 别名 + **冲突裁决** | 名字 |

**"口语化"是特性不是缺点**：需求阶段的属性就该是"客户有行业、规模"这种粒度；设计阶段才细化成"取值/必填/谁能看/是否留痕/是不是算出来的"。

### 6.2 对象清单必须标类型

对象清单（`se` step_01）里每个对象都要标 **主对象 / 从属对象 / 引用对象**，从属对象要写明**挂在谁下面**。

> 现有 `se` step_01 门禁只写「核心对象清单是否确认（至少3个）」，**没要求区分类型** —— 这是从属对象被漏掉、或被误给了不该有的菜单项的根源。

### 6.3 命名守门（需求阶段最关键的约束）

**三条规则：**

| 情况 | 处理 |
|---|---|
| 新名词与已有名词**近义** | 强制问用户：是同一个东西（合并，留主名+别名）还是两个（必须改一个名） |
| 新名词与已有名词**同名** | 必须改一个名（否则后面永远说不清） |
| 用户用了**两个名**指同一物 | 合并，定主名与别名 |

**时机**：在用户**说出口的那一刻**，分类之后、写入之前。不能等收尾。

**门控**：`未裁决的命名冲突 = 0`。

## 七、设计阶段的字典规范

### 7.1 九组产物目录

| 组 | 产物 |
|---|---|
| 基座 | 对象清单 · 关系 · 主/从/引用分类 · 全局开关 |
| 结构 | 对象属性 · 状态与流转（含超时）· 业务动作表（含来源去向·数量守恒·一起成功·可否撤销·谁发起） |
| 数字 | 数字口径表 · 同时要东西怎么分 |
| 派生 | 页面清单（录入/查看/集中处理）· 菜单 · 角色 · 权限 |
| 计算 | 业务处理过程（怎么算的，逐个标"可调"或"写死"） |
| 呈现 | 报表清单（看什么维度 · 数字怎么来 · 谁能看 · 能不能导） |
| 自动化 | 定期/批量业务处理 · 业务参数（含改了要留痕） |
| 兜底 | 单据打印 · 数据迁移 |
| 收口 | 来源去向对照表 · 任务卡 |

### 7.2 文件清单（按类型切，不按对象切）

**为什么按类型**：①跨对象动作零问题（动作全在一处，谁都能当输入输出）②校验天然按类型 ③一个类型一个编号序列 ④引用完整性只读两文件。

**两个维度分开**：文件按**类型**切（存储维度）；批次按**集群**切（工作维度）。不冲突。

| 文件 | 卡片类型 | 编号 |
|---|---|---|
| `01-对象.md` | 对象 + 属性（属性不编号，用 `OBJ-001.金额`） | `OBJ-` |
| `02-状态.md` | 状态 + 状态迁移 | `STA-` |
| `03-动作.md` | 动作（对象内 + 对象间） | `ACT-` |
| `04-处理过程.md` | 复杂的业务处理过程（简单的写在动作卡里） | `PRC-` |
| `05-参数.md` | 业务参数（标量） | `CFG-` |
| `06-元数据.md` | 码表/枚举 + 编号规则 + 单位 | `DIC-` `NUM-` |
| `07-接口.md` | 对外接口 | `API-` |
| `08-报表.md` | 报表 | `RPT-` |
| `09-权限.md` | 权限矩阵（**表格**） | — |
| `_索引.md` | 对象 → 关联 ID（**派生**，由脚本生成） | — |
| `_台账/` | 反馈 / 变更 / 待定 / 决策 / 门控 | `FB-` `CHG-` |

九个主文件 + 派生索引 + 台账目录。

### 7.3 编号与引用约定

1. **编号格式**：`<前缀>-<3位序号>`，如 `OBJ-001`。永不复用；删除只做归档标记（🗄），不物理删。
2. **引用写法**：首次出现写全 `OBJ-001 客户`，之后可只写 `OBJ-001`。
3. **只给会被引用的东西编号**：对象 / 状态 / 动作 / 参数 / 接口 / 报表 / 场景 / 功能点 / 用例。**属性不编号**（用限定名 `OBJ-001.金额`）。
4. **需求条目不编号**，按"章节+序号"粗引用（如 `五-2.3`）—— 因为它不被引用（功能点不从它来）。

### 7.4 载体形态：卡片/块 为主，表格为辅

| 内容 | 形态 |
|---|---|
| 对象 / 状态 / 动作 / 接口 / 报表 / 参数 / 处理过程 | **块（卡片）** |
| 权限矩阵等**真正的二维矩阵** | **表格** |
| 主存 | **Markdown 块 + 表格**（人机共用、git 友好） |
| 交付视图 | Excel / HTML 宽表（给业务人员逐格确认） |

**为什么用块而不是表格**：

| | 表格 | 块 |
|---|---|---|
| 多值 | 拆边表 + 要 join | **卡片自包含**，一个动作的信息全在一处 |
| 带理由/备注 | 塞不进 | 自然，想写几句写几句 |
| AI 生成出错 | 一格错，**整表废** | **坏一块，只坏一块** |
| 内容量不均 | 一列被最长的撑爆 | 每块各自伸缩 |

**卡片四条约定**：

1. **标题带 ID**：`### ACT-001 · 集采` —— 既是给人看的，也是**解析锚点**（脚本按标题切块）；
2. **字段用列表**：`- 字段名：值` —— 固定字段名，不换说法；
3. **多值分行**：不用逗号挤一行，直接子列表；
4. **必填字段不许缺**：缺了脚本要报。

**一条硬规矩**：**表里只放标量；一对多、多对多一律拆行/分行。** 禁止把多值塞进一个单元格（Markdown 表格不支持单元格内换行，`<br>` 各渲染器表现不一，AI 常把表格结构打断）。

**为什么不用 JSON 作主存**：JSON 是"全有或全无"（少个逗号整个文件失效），Markdown 表/块是"局部可坏"，对 AI 生成物更安全；且 JSON 的 git diff 有噪音。JSON 只在需要喂给程序时按需生成。

**为什么不用 Excel 作主存**：它是二进制，**git 看不了变更、合不了冲突** —— 而变更历史正是本方法的核心。Excel 只做交付件。

示例（一个动作卡）：

```markdown
### ACT-001 · 集采

- 所属对象：OBJ-010 集采单
- 前置状态：已提交
- 输入对象：
  - OBJ-001 申请单
  - OBJ-002 采购申请
  - OBJ-003 补货申请
- 输出对象：
  - OBJ-010 集采单
- 数量守恒：三张输入的数量之和 = 集采单数量（可自动校验）
- 一起成功：集采单 + 明细
- 可否撤销：仅红冲（下游已分发时）
- 来源去向：集采单.source_ids → 上面三张单
- 业务理由：多张申请合并采购，拿批量价
```

### 7.5 对象 ≠ 表

一个对象可能要 2~3 张表（主表 + 变更留痕 + 快照）；两个对象可能并进一张表；动作产生的新对象（集采单、红冲单）也要独立成表；枚举/字典是码表，不是业务表。

### 7.6 不进字典的东西

| 不进 | 原因 |
|---|---|
| 页面 / 菜单 / 权限视图 / 报表 / 任务卡 | **由字典派生**（改了字典要重新生成） |
| 数据类型 / 字段长度 / 索引 / 缓存 | **不是业务**，属技术实现 |

## 八、台账体系（智能体的档案系统）

### 8.1 六个台账

| 台账 | 何时写 | 回答什么 |
|---|---|---|
| **进度** | 每步/每批结束 | 断在哪、下一步做什么（`se` 已有，太粗） |
| **反馈** | **每次用户发言** | 用户到底说了什么 —— **逐字原话** |
| **变更** | 反馈判定为变更时 | 相对上一版改了什么（增量，不重跑） |
| **待定** | 发现没定的东西 | 哪些没定、谁认领、阻塞了谁 |
| **决策** | 做了非显然的判断时 | **为什么这么定**（最容易丢） |
| **门控** | 每道门 | 验了什么、**没验什么** |

### 8.2 反馈：七类 × 七字段

**先分类**（决定处理方式）：

| 类型 | 例 | 处理 |
|---|---|---|
| 补充 | "还要能按行业筛选" | 增量 ADD |
| 纠正 | "不是 3 天，是 5 天" | 增量 MODIFY |
| 撤销 | "那个折扣审批不要了" | 增量 REMOVE |
| 澄清 | "我说的客户指签约客户" | 写术语表 + 可能修正既有产物 |
| 改主意 | "先不做了，第二期再说" | 延后 + 优先级调整 |
| 疑问 | "能对接钉钉吗" | 转待定台账 |
| 确认 | "对，就是这样" | 门控确认记录 |

**再落表**，统一七字段：

```
编号 | 类型 | 原话 | 我的理解 | 落点 | 影响面 | 状态
```

| 字段 | 说明 |
|---|---|
| 编号 | `FB-0001`，永不复用 |
| 类型 | 上面七类之一 |
| **原话** | **用户逐字原话，不许改写** |
| 我的理解 | AI 翻译成设计语言的结果 |
| 落点 | B3 某对象.某属性 / B2 页面 / B1 对象清单 / B0 开关 |
| 影响面 | 作废哪些下游产物 |
| 状态 | 待归并 / 已归并 / 待确认 / 已确认 |

### 8.3 一条最关键的规矩

> **原话必须逐字保留，不许只记"我的理解"。**

理由：**AI 的理解会错**。只记理解后的版本，错了永远查不出来，且业务人员**没有东西可以校验**。留了原话，业务人员就能一行一行对着看。这是"业务人员确认权"在工具层面的落地。

**产物也要行级溯源**：字典里每一行记 `来源: FB-0012`。这样任何一格都能回答"你因为哪句话才存在"——包括它是不是 AI 自己加的。

### 8.4 与门控的接口

每道门加两条检查：

1. **待归并池已清空**（反馈不得带着未归并过门）；
2. **待定台账里没有未认领项**。

### 8.5 变更回流（非瀑布的两条回边）

| 回边 | 何时走 | 代价 | 记账 |
|---|---|---|---|
| **回边1：门禁 → 本批** | 产物不合格 | 小 | 不用 |
| **回边2：门禁 → 上游** | **上游本身错了**（不是产物错） | 大 | **必须记账** |

走回边2 时三件事一个都不能少：**①记**（谁/为什么/什么条件触发）**②算**（哪些下游产物作废）**③重跑**（受影响批次重新过门）。

> **非瀑布 ≠ 大循环**，而是**两条受控回边 + 回边记账**。自由度靠台账兜底；没有台账的放任回流 = 状态混乱。

**变更窗口**：回流要有强制力，靠门控那条"待归并池必须清空"——窗口开着可以提，窗口关了必须归并干净才能过门。

## 九、门控与校验（重点）

### 9.1 三条原则

1. **可机械判定** —— 门控条件必须是"某个计数为 0"或"某个引用必须存在"，**不能是"你觉得完整吗"**。
2. **卡在批边界** —— 每批一道门；门不过，下一批不许开工。
3. **不卡死，但必须显性化** —— 没定的允许过门，但必须**登记成 TBD 并指派认领人**。

### 9.2 三层门

| 层 | 判什么 | 谁判 |
|---|---|---|
| **产出物门** | 这一批的产物齐不齐（空格 / 空值 / 空表） | 脚本查空 |
| **一致性门** | 产物之间对不对得上（引用完整性、校验计数） | 脚本查计数 |
| **确认门** | 业务人员逐格点头了没有（业务可述性） | **人** |

三层全过才算批完成。**产出物门 + 一致性门是硬门，确认门是软门。**

### 9.3 每道门的四要素

1. **门在哪** —— 哪个批边界；
2. **判什么** —— 用哪条计数 / 哪条引用规则；
3. **谁来判** —— 脚本 / 人 / 二者都要；
4. **不过怎么办** —— 退回哪一步；TBD 怎么登记。

### 9.4 硬门 vs 软门

| | 硬门 | 软门 |
|---|---|---|
| 内容 | 计数归零、引用完整、必填非空 | 业务人员确认 |
| 判定 | 脚本，**不许人工豁免** | 人，必须留痕（谁 / 何时 / 确认了哪一版） |
| 不过 | 直接退回 | 补问，或登记 TBD |

### 9.5 TBD 挂起机制

允许带 TBD 过门，但每个 TBD 必须四件齐备：

1. 登记（写进 TBD 清单）2. 有认领人 3. 写清**什么条件下必须关掉** 4. 列出**它阻塞了哪些下游**

> **TBD 不得跨过收口门。** 收口门前必须全部关闭或明确豁免。

### 9.6 校验清单（硬门的核心）

**分四类：形（结构图算）/ 义（AI 逐边给理由）/ 结构（字段与引用）/ 命名。**

**形 —— 四条图校验**（对象流转图 + 每对象状态图）

| 校验 | 判据 | 查出什么 |
|---|---|---|
| **幽灵对象 = 0** | 每个对象至少一条入边（创建它的动作，含四类来源之一） | 凭空出现的对象 |
| **断头状态 = 0** | 每个对象有明确初始态，且只能由创建动作进入 | 不知道从哪开始 |
| **死路状态 = 0** | 每个非终态至少一条出边 | 卡死、走不下去 |
| **不可达状态 = 0** | 从初始态出发能走到每个状态 | 设计了但永远到不了 |

> 例外要显式声明：**允许永久存在的对象**（如客户）无终态不是错，但必须写"允许永久存在"，不能靠默认。
> 注意：**动作数量本身不是校验目标**（多一个少一个无所谓），校验针对**结构**。要求按对象类型区分：主对象必须有创建动作 + 至少一个管理动作；从属/引用对象放宽。

**义 —— 每条边必须有业务理由**

> 图查"形"，查不了"义"。**"跳过中间环节直接进下一轮，业务上能不能衔接"只有 AI 能判。**
> 做法：**每一条边（每次状态迁移 / 每次对象流转）都必须带一句"为什么它可以这样"。空着 = 未确认。**
> → 于是"义"也变成可计数的：`无业务理由的边 = 0`。

**结构**

| 校验 | 计数为 0 的含义 |
|---|---|
| **孤儿字段 = 0** | 有字段不属于任何对象 |
| **悬空动作 = 0** | 有动作没挂到任何页面（= 没有入口） |
| **无状态对象 = 0** | 有对象没有状态（= 没人管得了它） |
| **无公式的派生字段 = 0** | 有数字字段没人说清楚怎么算（= 报表与单据各算各的） |
| **悬空引用 = 0** | 有 ID 引用了不存在的对象/状态/参数 |
| **重号 = 0** | 有编号重复 |
| **缺必填字段的卡片 = 0** | 卡片字段不齐 |

**命名**

| 校验 | 计数为 0 的含义 |
|---|---|
| **未裁决的命名冲突 = 0** | 有近义/同名未处理 |

**收口门专属**

- 每条需求至少挂到一个动作（追溯无孤儿）
- 每个动作至少一条任务卡
- 每个页面至少一个入口
- 悬空 TBD = 0

> **这就是"数千条需求下完整无缺"的实现方式**：不靠谁读完，靠这些计数归零。

### 9.7 缺口驱动提问（原则 6 的落地）

**校验报出的缺口，直接变成下一个问题。**

- 报"对账单是幽灵对象" → 下一个问题："对账单是怎么产生的？"
- 报"集采单的死路状态" → "集采单建成之后如果不分发，会怎样？"
- 报"这条边没有业务理由" → "为什么可以直接跳到这一步？"

**缺口驱动提问，而不是自觉驱动提问。** 这条一旦成立，"AI 漏问"就从原理上被堵住——因为它不需要"知道该问什么"，只需要去看缺口。

### 9.8 逐批门控清单

**门 1 · B0 → B1：全局开关门**
- 判：每个开关项都有结论（做 / 不做 / 沿用默认），无空值 ｜ 硬门：脚本查空 ｜ 软门：业务确认
- 冻结：全局开关，后续影响面走变更

**门 2 · B1 → B2：对象名词门**
- 判：①每个对象有主键 ②每条关系两端都是已登记对象 ③每个对象有主/从/引用分类 ④无孤儿对象 ⑤**未裁决命名冲突 = 0**
- 硬门：引用完整性 ｜ 冻结：**对象名与主键冻结**

**门 3 · B2 → B3：骨架门**
- 判：①每个角色至少关联一个页面 ②每个页面至少挂一个对象 ③菜单无孤岛
- 硬门：脚本 ｜ 软门：业务确认 ｜ 冻结：**菜单树与角色清单**

**门 4 · B3 每个对象集群后：对象深化门**
- 判：孤儿字段 = 0 · 悬空动作 = 0 · 无状态对象 = 0 · 无公式的派生字段 = 0 · 幽灵对象 = 0 · 断头/死路/不可达 = 0 · 无业务理由的边 = 0
- 判（必填）：每个字段有"谁能看 / 是否留痕 / 取值范围"；每个动作有来源去向；对象间动作有守恒结论；每个动作有可撤销性结论
- 硬门：计数 + 必填 ｜ 软门：业务确认 ｜ 冻结：**该集群的字典冻结**

**门 5 · B4 → 收口：横切门**
- 判：①能力基线每项有三态结论 ②数字口径表每个数字有公式 ③"同时要东西怎么分"有结论 ④定期/批量处理有触发条件与失败清单 ⑤业务参数有**生效时机**
- 硬门：脚本查空 ｜ 软门：业务确认

**门 6 · 收口门**
- 判：①全库校验归零 ②追溯无孤儿 ③每个动作至少一条任务卡 ④每个页面至少一个入口 ⑤TBD 清空或已豁免 ⑥业务可述性抽样
- 硬门：1–5 ｜ 软门：6 ｜ 输出：字典定稿 + 任务卡清单

## 十、业务语言对照

**全程使用左列说话；右列是技术说法，不进设计文档。**

| 说这个（业务） | 别说这个（技术） |
|---|---|
| 业务处理过程：这事怎么算 | 算法 / 规则引擎 |
| 业务参数：规矩里可以调的那几个数 | 配置项 |
| 定期/批量业务处理 | 批处理 / 定时任务 |
| 同一样东西被几个人同时要，怎么分 | 并发抢占 / 锁 |
| 同一件事重复处理一次，会不会出乱子 | 幂等 / 可重跑 |
| 这几件事必须一起成功 | 事务边界 |
| 这张单子从哪来、又变成了什么 | 血缘 from / to |
| 谁发起、什么时候系统自己发起 | 触发源 |
| 处理不了的那些怎么报给你 | 失败清单 / 异常处理 |
| 这个数字是怎么算出来的 | 报表口径 |
| 谁能看、谁能改、谁不能 | 权限矩阵 / RBAC |
| 状态与流转 | 状态机 |
| 这个单子有哪几种状态、什么时候变 | 状态机 |
| 这一屏是录入用、查看用、还是集中处理用 | 页面类型 |
| 业务对象 / 属性 / 从属对象 | 实体 / 字段 / 子表 |
| 定期业务处理跑错了怎么办 | 批处理重试 / 幂等键 |

> **质量门**：每一格，必须能用业务话讲给业务人员听。讲不通的那一格，要么没设计到位，要么掺了技术杂质。

## 十一、与现有 `se` 流程的接口

### 11.1 输入映射（`se` 产物 → 设计步骤）

| 设计步 / 产物 | 从 `se` 哪一步取 |
|---|---|
| 对象清单 / 关系 / 分类 | step_01 管理对象（**需补主/从/引用标注**） |
| 全局开关 | step_00 企业画像 + step_09 通用维度 + step_11 非功能性 |
| 属性 × 四问 | step_10 核心字段（**仅字段名**）+ step_05 可管理项 + step_06 权限矩阵 |
| 状态机 | step_04 生命周期 |
| 动作表 | step_05 可管理项（**现按"状态"组织，需重组成"动作"视角**） |
| 业务参数 | step_07 配置项 |
| 对外接口 / 集成字段 | step_08 对外接口 |
| 权限（角色 × 动作） | step_06 权限矩阵（**升级粒度**：从"角色×对象×状态"→"角色×动作"） |
| 能力基线 | step_09 通用维度（**需补一份基线清单**） |
| 验收用例 | step_10 验收标准（**需补编号与场景枚举**） |
| 追溯 | step_12 追溯矩阵（**需扩成完整四列**） |

### 11.2 输出

- **数据字典**（业务口径定稿，业务人员逐格确认）
- **任务卡清单**（一卡一动作 + 验收点）
- **TBD 清单**（收口门时须清空）

### 11.3 `se` 现状实测（2026-10-12 核实）

| 我们讨论的 | `se` 里的位置 | 到哪个粒度 |
|---|---|---|
| 管理对象 | step_01 | 清单 + 诉求 + 边界 ✓（**缺类型标注**） |
| 状态 / 生命周期 | step_04 | 状态 + 进出条件 + 迁移 ✓ |
| 动作 | step_05 可管理项 | 按**状态**组织（含权限/输入/输出/规则/通知）✓ |
| 权限 | step_06 | 角色×对象×状态 + 行级 + 字段级 ✓ |
| 配置 / 参数 | step_07 | 四类配置 + 层级/默认值/边界 ✓ |
| 接口 | step_02 + 08 | 契约 + 字段 + 幂等 ✓ |
| **属性 / 字段** | **step_10** | **只有字段名清单**（无规格）⚠️ |
| 报表 / 元数据 / 批量 / 审批流 / 审计 / 附件 | **step_09** | **只到"要不要"** ⚠️ |
| 完备性检查（MECE） | step_09 | **软检查**（LLM 自问自答）⚠️ |

**四项完全缺失**：

| 缺的 | 说明 |
|---|---|
| **术语 / 命名** | 全流程没有术语表，命名守门从零开始 |
| **血缘（来源去向）** | step_10 的"关系"是**实体关系**（客户→联系人），不是**血缘**（这张单从哪些单来）——两回事 |
| **数字口径** | 没有任何一步说"可用库存 = 在库 − 预占 − 冻结" |
| **撤销 / 抢占** | 都没有 |

**两条观察**：
1. step_09 的 MECE 检查已是"完备性检查"雏形（问的正是"有没有状态没被功能覆盖"），但**靠 LLM 自问自答，输出"遗漏 0 处"** —— 形状对了，判定方式不可靠。
2. **step_10 是唯一摸到设计的一步**，却混装了两样：数据模型（ER/索引/事务边界，技术味重）+ 验收标准。这一步**跨线了**。

### 11.4 需要补的东西

1. **对象类型标注**（step_01）—— 补主/从/引用。
2. **稳定 ID** —— 为"会被引用的条目"补编号（对象/状态/动作/参数/接口/用例）；叙述型步骤（企业画像、干系人）不编号；**需求条目仍不编号**。
3. **能力基线清单** —— 新建（默认全有的平台能力，逐项标三态）。
4. **校验的载体** —— 依托字典实现，配一个校验脚本。
5. **门控升级** —— 从"有没有遗漏？"（软）升级为计数归零（硬）。
6. **术语表 + 命名守门** —— 新建。
7. **需求阶段沉淀三文件** —— 属性/动作/术语。

## 十二、外部可借（2026-10-12 调研）

### 12.1 行业格局

主流工具已收敛到同一个形状 `spec → plan → tasks → implement`：**GitHub Spec Kit**（可移植性最好）、**AWS Kiro**（requirements 用 EARS）、**BMAD-METHOD**（多智能体人格）、**OpenSpec**（brownfield 用 ADDED/MODIFIED/REMOVED 增量）、**Project Loop**（验证层）、**Tessl**（规格注册表）。

三条共识：四阶段形状、**阶段之间有人工门控**、有一份**最高层不变量**（Spec Kit 叫 constitution）。

行业自己承认的两个最大痛点：「**SDD 是不是加了 token 的瀑布？**」「**建造者自己批改自己的作业**（builder marks its own homework）」。

### 12.2 我们与行业的差异

| 维度 | 我们的 `se` | 行业共识 | 判断 |
|---|---|---|---|
| **起点** | 从零引导不懂 IT 的业务人员 | 从 prompt / 已有 user story 开始 | **我们在上游，是空白区** |
| **颗粒度** | 12 步，每步一份 skill | 1 个 feature 一份 spec（1–3 页） | 我们更细，也更重 |
| **门控判定** | LLM 自查 | 脚本判定，并声明"验了什么、没验什么" | **我们落后** |
| **验收标准** | 自由文本 | **EARS**：`WHEN [条件] THE SYSTEM SHALL [行为]` | **可直接借** |
| **最高层不变量** | 无 | Spec Kit 的 `constitution.md` | **缺，可补** |
| **变更通道** | 线性不跳步 | 增量标记 + spec 长期存活 | **缺轻量通道** |
| **双标签（业务/技术）** | 有 | 无对等物 | **我们独有** |

### 12.3 可借清单（六条）

1. **EARS 验收句** —— 把验收标准从自由文本改成固定句式，可解析、可断言、可转测试；
2. **constitution** —— 把全局开关 + 业务语言纪律 + 不做的边界合并成一份跨批次不变量；
3. **增量变更标记** —— 走完首轮后，变更走 `ADDED / MODIFIED / REMOVED`，不动原文档；
4. **门控脚本化** —— 硬门用脚本判定，并输出"验了什么、没验什么"；
5. **两条回边 + 记账** —— 见 8.5；
6. **一条自查尺**：Project Loop 的原则「**每一个角色必须能改变某个门的裁决，否则它就是仪式**」—— 可直接用来体检 `se` 的 12 步：**哪一步不能改变任何门的裁决，那一步就是仪式。**

## 十三、agent 工作循环

```
用户说一句
  ↓ ① 分类（七类反馈，多标签；置信度低就反问）
  ↓ ② 命名守门（查术语表：近义/同名 → 强制区分）
  ↓ ③ 读对应 skill（先查它的前置产物在不在）
  ↓ ④ 深挖澄清 → 写回卡片/台账（原文逐字入反馈台账）
  ↓ ⑤ 每轮跑一次校验（形 / 义 / 结构 / 命名）
  ↓ ⑥ 校验报出的缺口 → 直接变成下一个问题
轮次结束
  ↓ 覆盖门：12 类意图都有终态（已澄清 / 不适用 / 待定），未处理 = 0
  ↓ 深度门：每类必填字段无空
  ↓ 完备性门：对象≥1 · 每对象有动作 · 校验计数归零
```

**12 个 skill 从"步骤"改为"参考文件"**：按**意图**路由，不按顺序执行。用户中途跳回第一章、加一个新需求，都属正常。

## 十四、如何转成提示词

### 14.1 骨架

沿用现有 skill 的格式：`[meta]`（`roletag`）+ `[description]` + `[content]`。

### 14.2 门控在提示词里怎么表达

三条要求：

1. **写成可执行的检查清单**，不写成描述。例：
   - ❌「确保设计完整，没有遗漏」
   - ✅「逐条核对：幽灵对象 = 0；断头状态 = 0；死路状态 = 0；不可达状态 = 0；无业务理由的边 = 0。任一不为 0 → 标注本批未完成，不许开工下一批」
2. **门控必须给出"不过怎么办"** —— 退回哪一步、TBD 怎么登记。只写"不许过"会卡死。
3. **区分硬门与软门** —— 硬门写"脚本/清单判定，不许豁免"；软门写"须业务人员确认并留痕"。

### 14.3 三条注意

1. **不许在提示词里出现技术词**（见第十节对照表），否则业务人员的确认权丢失。
2. **门控规则要能逐条"计数"**，提示词里必须写明"计数为 0"这个形式。
3. **台账要落盘**（进度 / 反馈 / 变更 / 待定 / 决策 / 门控），支持中断续跑。

### 14.4 形态落地建议

**先不要造新工具。** 零新工具就能跑：

| 步 | 做什么 | 用什么 |
|---|---|---|
| 1 | 定死卡片/表格的**表头与字段约定** | 约定文档 |
| 2 | 写**一个校验脚本**：读文件 → 建图 → 输出计数 + 缺口清单 | `script_run` |
| 3 | 在 skill 里写死循环：**每轮跑校验，缺口变问题** | skill 文本 |
| 4 | 三类门按计数判定 | 校验脚本输出 |
| 5 | 需要业务确认时导出 Excel/HTML | 导出脚本 |

工具化（`ledger_run` 台账域）留到**两个场景跑通、字段约定不再变**之后再做——否则固化的是一份还会变的东西。

## 十五、边界（明确不做）

| 不做 | 原因 |
|---|---|
| 页面布局、组件、样式 | 业务设计不需要 |
| 数据类型 / 长度 / 索引 | 技术实现阶段 |
| 性能、技术选型、部署拓扑 | 技术实现阶段 |
| 缓存、日志、监控等非业务项 | 不是业务视角 |
| 行业知识库（会计准则、税务、社保政策） | 不属于本方法；需由专家或知识库提供 |

> **本方法的定位**：解决"怎么建"（业务全貌 → 可校验的设计），不解决"建什么才算对"（行业知识）。
