## 一、顶层模式选择：先分流，再细化

> **状态标注（2026-11-04 核对）**：✅ = 已由场景向导实现；⚠️ = 有控件/部分实现，但未完全映射到编排或缺少细分；🔵 = 规划项/未实现（无控件或字段）。实现位置：前端 `src/frontend/src/views/scenario/ScenarioWizardDialog.vue`（选项常量 L645-770、状态 L794-819、`deriveTeam` L1003），后端 `src/lib/llm/server/wizard_compose.go`。A/B/C 三模式 + 自定义已实现；本稿保留原文，仅在条目末尾追加标记。

ChatDev 提供了 Default / Art / Human / **Incremental** 四种预置配置，其中 Incremental 专为既有项目的增量开发设计。你的产品可以借鉴这个“预置配置 + 自定义”的思路，但顶层分流应更明确。

**顶层选项应分为三类：**

- **模式 A：从0构建（Greenfield）** — 无既有代码库，从需求到可运行产品。✅
- **模式 B：持续迭代（Iterate）** — 已有代码库，在现有架构和代码风格上增加功能或修改行为。✅
- **模式 C：重构/现代化（Refactor/Modernize）** — 已有代码库，目标不是增加功能，而是改善结构、迁移技术栈或偿还技术债。✅

每个模式进入后，再展开各自的选项菜单。多智能体协作群的**角色构成、工具集、评审强度、执行节奏**都随模式不同而重新编排。

## 二、模式 A：从0构建 — 选项菜单

这一模式的菜单承担“项目脚手架”的功能，同时决定需要拉起哪些子智能体。

### 1. 目标平台（决定“构建什么”）

参考现有 CLI 工具的交互式向导，平台选项应覆盖：

- **纯前端**（Web SPA / 静态站点）✅
- **纯后端**（API 服务 / 微服务）✅
- **全栈**（前后端一体）⚠️（由 `frontend + backend` 多选组合表达，无独立“全栈”项）
- **移动端**（原生 / 跨平台）✅
- **小程序**（微信 / 支付宝 / 抖音等）✅
- **全平台**（Web + 移动 + 小程序，多端复用）⚠️（由 `web + mobile + miniapp` 多选组合表达，无独立项）

选中某个平台后，才解锁对应的技术栈子菜单。这与 ai-coding-starter 的逻辑一致：只有选择 Frontend Agent 后，才提供 Design System 选项。⚠️（现行按向导步骤 2/3 解锁；技术栈项未按平台动态隐藏）

### 2. 技术栈（前端）

选项应覆盖主流框架，同时允许“由智能体推荐”：⚠️（有“其他/自定义”输入；无 LLM 推荐控件）

- **框架**：React / Vue / Svelte / Next.js / Nuxt / 原生 HTML+JS ✅
- **UI 体系**：Tailwind CSS / shadcn / Ant Design / Element Plus / 无 ✅
- **状态管理**：Zustand / Redux / Pinia / 内置 🔵（无对应字段/控件）
- **构建工具**：Vite / Webpack / Turbopack 🔵（无对应字段/控件）

### 3. 技术栈（后端）

参考 aiagentflow 和 create-axiom-forge 的选项设计：

- **语言/框架**：Node.js（Express/NestJS/Fastify）/ Python（FastAPI/Django/Flask）/ Go（Gin/Fiber）/ Java（Spring Boot）/ Rust（Axum）⚠️（语言与 `gin/fiber/nestjs/fastapi/spring/axum` 已实现；Express / Fastify / Django / Flask 无独立选项）
- **API 风格**：REST / GraphQL / tRPC / gRPC 🔵（无对应字段/控件）
- **认证方案**：JWT / Session / OAuth2 / 无 🔵（无对应字段/控件）

### 4. 数据层

- **数据库**：PostgreSQL / MySQL / MongoDB / SQLite / 无 ✅
- **ORM/ODM**：Prisma / Drizzle / TypeORM / Mongoose / 原生驱动 ⚠️（`prisma/drizzle/typeorm/gorm/native`；无 Mongoose）
- **缓存/消息**：Redis / 消息队列 / 无 🔵（无对应字段/控件）

### 5. 架构形态（决定智能体群的组织结构）

- **两层结构**：前端 ←→ 后端 API ✅
- **三层结构**：表现层 / 业务逻辑层 / 数据访问层 ✅
- **微服务**：多个独立服务 + API Gateway ✅
- **Serverless**：函数即服务 + BaaS ✅

架构形态直接影响子智能体的**拆分粒度**。两层结构可能只需要 1 个前端 Agent + 1 个后端 Agent；微服务架构则需要按服务边界拆分多个后端 Agent，并额外配置一个“集成协调者”角色。

### 6. 协作群规模与自治程度

这是“自动配置智能体群”的核心参数，参考 dsh-agent-forge 的“每个工作区决定启用哪些 agent、谁当 lead、工作如何路由”的设计：⚠️（团队规模与自治级别两组核心参数未实现；仅“成员列表 + 自动推导”）

- **最小团队**（3-4 个角色）：Architect + Coder + Reviewer + Tester 🔵（无团队规模控件；`deriveTeam()` 按模式/平台/架构自动推导成员，可在摘要页增删成员）
- **标准团队**（5-6 个角色）：+ Product Analyst + DevOps 🔵（同上，无规模选择）
- **完整团队**（7+ 个角色）：+ UI 设计师 + 安全审查者 + 文档撰写者 🔵（无规模选择）
- **自治级别**：每步确认（Human-in-the-loop）/ 关键节点确认 / 全自动 🔵（无对应字段/控件）

## 三、模式 B：持续迭代 — 选项菜单

这一模式的关键区别在于：**智能体群必须先“理解”既有代码库，再动手**。菜单的重点从“选择技术栈”转向“采集代码库上下文”。

### 1. 代码库接入方式

- **本地目录**（直接指向工作区）✅
- **Git 仓库 URL**（克隆后分析）✅
- **已有 IDE 工作区** ✅

### 2. 智能体自动侦察的内容（无需用户逐项配置，但可预览和修正）

参考 Step Code 的 explore agent（只读仓库侦察）和 aiagentflow 的“智能检测”能力：

- 编程语言与框架 ✅
- 包管理器与构建工具 ✅（`package_manager` / `build_tool` 由 probe 返回并被 compose 消费）
- 测试框架与运行方式 ⚠️（仅 `test_tool`；无“运行方式”字段）
- 代码风格与格式化规则 ⚠️（仅 `lint_tool`；无格式化规则字段）
- 目录结构与架构模式 ⚠️（`top_dirs` / `structure`；无架构模式判定）
- 现有文档（README、ADR、API 文档）🔵（probe 无文档字段）

### 3. 迭代任务类型（决定拉起哪些子智能体）

- **功能增量**（在现有模块上添加新功能）→ 需要 Coder + Reviewer + 对应的 Tester 🔵（无任务类型选择器）
- **行为修改**（修改现有逻辑）→ 需要 Coder + Reviewer + 回归测试 🔵
- **Bug 修复** → 需要 Debugger + Tester + 回归验证 🔵
- **性能优化** → 需要 Performance Analyst + Coder + Benchmarker 🔵
- **依赖升级** → 需要 Dependency Auditor + Coder + 兼容性测试 🔵

### 4. 影响范围与风险控制

- **允许修改的文件范围**：仅当前模块 / 跨模块 / 全仓库 ✅
- **是否允许修改依赖**：是 / 否 / 仅安全补丁 ✅
- **是否自动运行测试**：修改后自动 / 手动触发 ✅
- **是否自动创建分支/PR**：是 / 否 ⚠️（仅 `bBranch=yes/no`；无 PR 创建）

### 5. 迭代节奏模式

参考华为云码道的两种开发模式：

- **氛围模式（Vibe）** ：边聊边做，即时验证，适合探索性迭代 ✅
- **规范模式（Spec-Driven）**：先写规范/计划，再执行，适合有明确验收标准的迭代 ✅

## 四、模式 C：重构/现代化 — 选项菜单

重构场景的智能体群需要比迭代场景**更强的分析和验证能力**，因为“不改变外部行为”是核心约束。

### 1. 重构目标类型

- **代码结构重构**（提取函数/类、消除重复、改善命名）✅
- **架构重构**（单体拆微服务、分层重组、模块解耦）✅
- **技术栈迁移**（框架升级、语言迁移、数据库更换）✅
- **技术债偿还**（移除死代码、修复已知设计缺陷）✅
- **安全加固**（修复已知漏洞、加强输入验证）✅

### 2. 行为保持策略（核心约束）

- **严格行为保持**：所有现有测试必须通过，公共 API 签名不变 ✅
- **兼容性优先**：允许内部行为微调，但外部接口保持兼容 ✅
- **允许破坏性变更**：有明确的迁移路径和版本策略 ✅

### 3. 重构范围与验证方式

- **文件级 / 模块级 / 系统级** ✅
- **验证方式**：现有测试套件 / 新增特征测试 / 人工验收清单 / 智能体自验证（生成验证脚本）✅

### 4. 智能体群的特殊角色

重构场景通常需要额外拉起以下角色之一或多个：

- **Legacy Analyzer**：理解既有代码的“隐性契约”和依赖关系 ⚠️（`deriveTeam()` 恒推送“遗留分析员”，不读取 `sel.cRoles`）
- **Compatibility Guardian**：监控重构是否意外改变了外部行为 ⚠️（恒推送“兼容守护”，不读取 `sel.cRoles`）
- **Migration Planner**：生成分步迁移计划，确保每一步都可回滚 ⚠️（仅 `cTarget=stack` 时推导，不读取 `sel.cRoles`）

## 五、多智能体协作群的自动配置逻辑（贯穿三个模式）

菜单的每一项选择都应映射到智能体群的**编排参数**。参考 dsh-agent-forge 的 agent 定义维度——模型、推理强度、人格、可见工具集、插件集、委派深度——以及 AgentScope 的 Leader/成员角色模型。

**建议的映射规则：**

| 用户选项 | 影响的智能体配置 |
|---|---|
| 目标平台 | 决定启用哪些技术栈专属子智能体（前端 Agent / 移动端 Agent / 后端 Agent）✅（`deriveTeam` 读取 `platforms`） |
| 架构形态 | 决定子智能体的拆分粒度与协调角色数量 ✅（`archMap`：two/three/micro/serverless） |
| 自治级别 | 决定是否启用 Planner oversight 及审批节点 🔵（无自治级别字段） |
| 任务类型（迭代/重构） | 决定是否拉起 Debugger / Legacy Analyzer / Compatibility Guardian 等特殊角色 ⚠️（B 模式无任务类型；C 模式仅按 `cTarget` 部分映射） |
| 技术栈 | 决定每个子智能体的工具集（构建命令、测试命令、lint 规则）⚠️（语言/框架进入提示词合成，但未映射为每角色工具集） |

**协作策略参数应暴露给高级用户：**

- **Leader 选择**：哪个 Agent 统一接收任务并协调分工（参考 AgentScope 的 Leader 机制）🔵（无 UI/字段）
- **委派深度限制**：Agent 可以向下委派几层 🔵（无 UI/字段）
- **并行/串行路由**：哪些阶段可以并行执行 🔵（无 UI/字段）
- **模型分配**：每个角色使用哪个 LLM（参考 aiagentflow 的“按角色分配模型”）🔵（无 UI/字段）

## 六、菜单交互设计的核心原则

1. **渐进式披露**：顶层只展示模式选择和目标平台，技术栈等细节在进入子流程后再展开。aiagentflow 的初始化向导是很好的参照：先自动检测，再让用户确认或修正。✅（5 步向导 + `agent-wizard-probe` 预填）
2. **默认值优先**：每个选项提供“智能体推荐”默认值，用户只需在偏离默认时手动选择。⚠️（有静态默认值与“全部默认”一键生成；无 LLM 推荐，probe 只影响 mode 默认）
3. **选项即编排信号**：用户的每一项选择都应实时反映在“即将拉起的智能体群预览”中，让用户看到自己的选择如何转化为具体的 Agent 团队构成。⚠️（有团队预览；自治级别、任务类型、多数技术栈选项不参与 `deriveTeam`）
4. **可保存为预设**：允许用户将一组选项保存为项目级预设（类似 ChatDev 的 CompanyConfig 目录），下次进入同一项目时自动加载。✅（`savePreset` / `loadPreset`，localStorage 按 `workDir` 存储，打开向导时自动预填）

**总结：三个模式的菜单设计核心差异——从0构建的菜单重点是“脚手架选择”（平台、技术栈、架构），迭代的菜单重点是“上下文采集”（代码库接入、侦察预览、任务类型），重构的菜单重点是“约束定义”（行为保持策略、验证方式、特殊角色需求）。三者共享同一套“选项→智能体编排”的映射机制，但每个模式触发的智能体群构成不同。**
