# ChonkPilot 工程架构评审（2026-11-16）

> 范围：主仓 `chonkpilot` + 同级仓 `chonkpilot-agent` / `chonkpilot-framework` / `chonkpilot-plugins` / `chonkpilot-webview2`（`chonkpilot-proxy` / `chonkpilot-service` / `chonkpilot-util` 仅作旁证）。
> 方法：规格文档通读 + 源码静态核验（关键路径逐行复核）+ 代码度量。
> 性质：只读分析，未修改任何产品代码。本文为讨论基线，后续逐题深化。

---

## 一、一页速览

| 维度 | 事实 |
|---|---|
| 产品 | Windows 桌面 AI 助手 / IDE 工具，单文件 `chonkpilot.exe`，WebView2 宿主 + 常驻后端 |
| 技术栈 | Go 1.26（后端）· Vue 3 + Vite（前端，实际为纯 JS，无 TS 源码）· bbolt · MCP SDK |
| 规模 | 主仓 1,526 文件 / **10.3 万行 Go**（非测试 6.0 万）+ 4.7 万行前端 + 2.1 万行规格文档 + 5.5 万行 Python E2E |
| 同级仓 | agent 4.1 万 · framework 3.3 万 · plugins 6.9 万 · webview2 0.5 万 → 合计 **约 25 万行 Go** |
| 模块数 | **53 个 Go module**，分布在 6 个仓，全部靠本地 `replace` + 硬编码 `GOROOT` 串联 |
| 消息面 | 241 个主题（由 `61-messages.schema.json` 生成键常量），payload **无生成类型** |
| 插件 | 12 个业务插件 + 2 个引擎，全部进程外 exe，UDS 桥 + 各自 MCP HTTP |
| 工程设施 | **无 CI、无 lint、无 go.work、无 race 门禁**；单作者 139 次提交（2026-07 ~ 11） |
| 产物 | `dist/` 262 MB；codegraph 单插件 32 MB；前端 17 MB / 165 个 chunk |

一句话判断：**产品完成度和设计意图都明显高于平均水平，但"用字符串消息总线当内部 API + 把工程拆成 53 个模块"这两个基础选择，把复杂度推到了难以维护、难以验证、难以复现构建的区间。**

## 三、架构拆解

### 3.1 运行时拓扑

```
┌──────────────────── chonkpilot.exe（windowsgui，单文件）────────────────────┐
│  Win32 消息环 / 托盘 / 日志窗                                                │
│  WebView2 多窗口  ← go:embed Vue dist                                       │
│    │ POST /publish · /show · /plugin-ui · /plugins/<id>/api                 │
│    ▼                                                                        │
│  bridge(src/lib/gui) ── MQ Hub（单订阅 ">" + WorkDirPolicy）                 │
│    ├── llm/server：turnCtx 状态机 → chat.Engine → router(SSE)               │
│    ├── data/persist：data-<domain>-* 应答 → bbolt 三级库 + dialog 库         │
│    ├── filesys：fsnotify → filesys.changed                                  │
│    └── gateway：MCP 执行池 ─┬─ 进程内 mcp-server（.tool.md, runtime=builtin）│
│                              └─ 插件 MCP HTTP（127.0.0.1 随机端口 + token）    │
│  插件 supervisor(mgr) ──UDS 帧桥──► 12 插件 exe ──► 引擎 exe                 │
└─────────────────────────────────────────────────────────────────────────────┘
        remote 插件 ──WSS──► chonkpilot-remote-server.exe（SQLite / H5 / Admin）
```

### 3.2 分层与依赖

| 层 | 代码 | 行数 | 职责 |
|---|---|---:|---|
| 0 总线 | framework `core/mq` + `runtime/bus` | ~1k | 进程内同步 pub/sub + Future 结果收集 |
| 1 数据 | `src/lib/data` | 27.4k | 权威状态唯一持有者；bbolt；三级库 + 一树一库 |
| 2 网关 | agent `gateway` | 7.4k | 工具唯一入口：注册/池/异步/熔断/取消 |
| 3 会话 | `src/lib/llm` + agent `chat/session/router` | 50k + 14.9k | 回合执行、上下文、tool_pair、压缩、子会话/群聊 |
| 4 文件 | `src/lib/filesys` | 2.1k | 监听 + 列目录 + 文件操作 |
| 5 插件 | plugins 仓 | 42.4k（非测试） | 进程外能力 |
| 6 UI | `src/lib/gui` + frontend | 8.3k + 46.7k | 纯消费者 |

依赖方向总体单向；唯一的回环「工具完成 → 回合继续」通过 MQ 事件解耦——这个决策是合理的。

### 3.3 消息面

- **进程内**：`bus.Emit(ctx, topic, payload) *Future` 同步派发；订阅者写 `v.Result` / `v.Errors`；`Wait()` 收集。没有独立 RPC。
- **跨进程**：UDS 帧（`{k,id,name,payload,ok,result,errors}`）+ 插件自己的 Streamable HTTP MCP。
- **数据面**：`data-*` 请求带 `req_id`，persist 把 `{req_id, ok, result}` **重发回同一主题**，调用方挂临时 order=100 订阅收敛（`src/lib/data/persist/envelope.go:5`）。
- **前端**：`mq.emit` = 本地分发 + 无条件 `POST /publish`；后端经 `Eval("window.mq.emitRemote(...)")` 把事件注入页面。

### 3.4 回合引擎（心脏）

`turnCtx`（`src/lib/llm/server/turn.go:116`）是单轮状态机：输入队列 → `chat.Engine.runFrame` → `router.Call`（SSE）→ tool-call → `gateway.doCall` → 结果回填 `engineInbox` → 续轮 → `llm-complete`。

值得肯定的细节：
- 异步工具四模式与「成功优先」判定（`gateway/src/mcpgateway.go:808`）。
- 取消阶梯 L0（cancel 通知）→ L1 grace → L2 关连接 → L3 杀进程树。
- `reported` 标志保证终态回报「恰好一次」。
- 插话帧栈（LIFO）与 `awaitPendingResult` 的轮内等待（无超时）。
- 实例维度分桶（`instKey(instance, id)`），同进程多项目不互相取消。

### 3.5 数据层

- `usr`（`~/.chonkpilot/chonkpilot.db`）、`prj`（`<workDir>/.chonkpilot/chonkpilot.db`）、`prjusr`（`~/.chonkpilot/data/<project-id>/` 或 `users/<user>/`）。
- 会话树 = 一个 `dialog-<hex>.db`，目录表 `dialogs` 可重建。
- 配置读取 `prjusr → prj → usr → 系统资源` 逐 key 回退。
- **明确写着「无版本迁移：库结构 = bucketsFor 直建（缺失即建，幂等）」**（`src/lib/data/db.go:50`）。

### 3.6 插件体系

- 发现：`<id>/plugin.ini`（启动命令）→ spawn → `plugin.hello`（manifest 随 exe 内嵌上报）→ `plugin.register` → 自建 loopback MCP HTTP → `plugin.mcp.register{url, token, hot_tools}`。
- 工具描述由 gateway 作为 MCP 客户端从插件 HTTP 拉取，`_meta.chonkpilot` 注入调用上下文。
- 监控：15s ping / 3 次失败 Kill / 指数退避重启 / 5s 优雅停止。
- 工具契约：`.tool.md`（YAML front matter + schema），可 `runtime=builtin` 进程内执行。

### 3.7 工程化现状

- 53 个 module，无 `go.work`；所有跨仓依赖是 `replace ../../../chonkpilot-*`。
- `build-desktop.ps1` 固定 `$env:GOROOT = "e:\GoDev\go1.26"`（`build-desktop.ps1:50`）。
- 无 `.github/`、无 golangci、无 eslint、无 editorconfig。
- `msgkeys` 由 schema 生成且有 `-check`（这点做得好）；但事件名 `event-names.js` 仍是手写并靠注释要求两端同步。

## 四、设计评审

### 4.1 评分

| 维度 | 分 | 理由 |
|---|---:|---|
| 产品完整度 | 8.5 | 功能面覆盖了本地 Agent 平台几乎所有环节 |
| 架构意图 | 8 | 分层、权威状态、单一入口、插件隔离的思路清晰 |
| 模块边界 | 4 | 53 module、重复类型、4 套协议、God package |
| 正确性/并发 | 4 | 核心链路存在 ctx 断链、幂等 TOCTOU、状态竞态 |
| 安全 | 3 | fail-open 身份、默认弱口令、同源 iframe、全局输入注入 |
| 可维护性 | 3.5 | 20% 注释是"历史叙事"，文档/代码漂移，巨型文件 |
| 可复现构建 | 2 | 本地 replace + 硬编码 GOROOT + 无 CI |
| 可测试性 | 4.5 | 测试量很大，但测不到 P0 竞态；E2E 过重 |

### 4.2 根本性设计错误

**E1. 用字符串主题总线当"内部 API"，而不是编译期接口。**

- 每一层之间都靠 `Emit(topic, map[string]any)`；payload 没有类型、没有 schema、没有编译检查。241 个主题、97 处裸状态字符串。
- 主题常量存在 **4 份事实源**：生成的 `msgkeys_gen.go`、framework 的 `runtime/topics`、`bridgebus` 的 25 条裸字符串路由、`mgr` 的 13 个本地常量。
- 进程内 `Emit` 是**同步串行**的：handler 里的任何慢操作都会阻塞发布方；`bus` 只在派发前检查一次 `ctx`，长 handler 无法取消。
- 没有投递保证：队列满静默丢帧（`protocol/frame.go:428`），序列化失败 payload 变 `nil` 且不报错（`bus/internal.go:149`）。
- 可观测性差：无法静态追踪消费者，也没有 trace/span。

> 正确做法：**进程内用 Go 接口/方法调用，进程边界才用协议**。MQ 作为 UI/插件/远端的对外通道保留，但不该是 `session → data`、`llm → gateway` 的传输方式。

**E2. 请求-响应实现了两套语义，超时值互相矛盾。**

- 进程内：订阅者写 `v.Result`，`Future.Wait()`。
- 数据面：`req_id` + 同主题重发应答（`data/persist/envelope.go`），调用方临时订阅 + 硬超时。
- 超时值：dataclient 5s、bridgebus 5s、ui action 30s、`EmitData` 30s、插件命令 60s、工具 11 分钟、SDK 默认 15s。

> 正确做法：**只有一种请求-响应**（`id + deadline + cancel`），超时预算按能力定义在一张表里，客户端与服务端共享。

**E3. 53 个 module / 6 个仓 / 本地 replace / 无 CI。**

- 主仓 23 个 module，插件仓 20 个，agent 6 个，framework 2 个。
- 每个 module 的 `go.mod` 都写 `replace ../../../chonkpilot-*`；离开作者机器的目录布局就无法构建。
- `go 1.26.0` + 硬编码 GOROOT + 私有 WebView2 fork。
- 无 CI：`gofmt -l` 有 32 个文件不通过；Win32 文件缺 `//go:build windows`；仓库里残留 `.exe`、`node_modules`、`dist`。
- 类型在边界重复：至少 5 份 `Context`、2 份 `Message`、2 套 `TurnStore` 签名。

> 正确做法：**一个仓 + `go.work` + 少量 module（api / core / plugins-sdk / tools）**，版本依赖而非路径依赖，CI 三件套：`build + test -race + lint`。

**E4. 数据层：无迁移、无 schema 版本、一树一库。**

- `data/db.go` 明确"无版本迁移"，只做"桶缺失即建"。加字段可以，改语义、改索引、回滚、修复损坏都不行。
- 一树一库解决了写隔离，但代价是跨树查询、跨库事务、删除/分叉一致性都要应用层兜。
- bbolt 单文件排他锁 + 3s 超时；进程级单例被删掉后，全靠这个超时兜底。
- 所有列表查询都在 Go 里扫表。

> 正确做法：**SQLite（WAL）+ `PRAGMA user_version` + 迁移脚本 + 单库多表**；`dialog_id` 做索引而不是分库。

**E5. 插件信任模型 fail-open，传输栈三套。**

- `plugin.hello` 只校验"id 非空"；`DataGuard` 对未登记插件直接放行（`mgr/api.go:443`）。
- browser/desktop 的 engine UDS 无认证；context 未绑定实例时 `ownedBy` 返回 true。
- 插件 UI 与主 UI 同源，`/publish` 与 `/show` 没有来源校验。
- gateway spawn 的 MCP server 走 `sandbox.Prepare`（只挂 Low IL，**不建 Job Object**），`exec.Command` 不带 ctx。
- crontab 沙箱把整个 `work_dir` 加进可写白名单，拿不到策略时 fail-open。

> 正确做法：**deny-by-default**；一次性 token；能力授权按 manifest 裁剪；插件 UI 独立 origin；Job Object；沙箱策略缺失 = 拒绝。

**E6. 事件契约只有"名字"共享，没有"类型"共享，且兼容层成了主路径。**

- schema 只生成 `Topic*` / `Field*` 常量；payload 形状靠文档和人工同步。
- `event-names.js` 手写，注释要求"两端同步添加"。
- 最典型后果：前端 `handleReceive` 读 `data.text`，服务端发 `{type, payload:{text}}`（`sessionMessages.js:207` vs `handler_task.go:359`）。文本显示**依赖桥兼发的旧事件 `llm-token`**；**推理内容没有兼容事件，所以永远为空**。**（2026-11-16 已修复：前端改读 `payload.text`，`llm-token` 整体删除。）**
- 新协议路径实际是死的，产品跑在 legacy compat 上。

> 正确做法：一份 schema 同时生成 Go struct + TS interface + 校验器；契约测试覆盖每个 topic；兼容层要么删，要么被测试覆盖。

**E7. "文档即权威"变成"文档即负担"。**

- 21k 行 spec，代码里 20% 是注释，大量是 `2026-10-22（BATCH-X）`、`D-45`、`G-107` 式历史叙事。
- 文档与代码已漂移：file 工具契约写 `runtime: builtin` + CLI 参数，实际是插件 MCP；session 契约宣称 semantic/hybrid + HNSW + cosine，vfts 代码明确"阶段 1 只做 FTS"。
- 41-未决项被整体清空，但代码注释仍引用已不存在的编号。

> 正确做法：**契约文档由代码生成/校验**；设计决策用一页 ADR；代码注释只解释"为什么"。

### 4.4 安全缺陷

1. **remote 首启自动创建 `admin/admin`，默认无 TLS，`CheckOrigin: true`**。
2. **插件身份自证 + DataGuard fail-open**。
3. **engine UDS 无认证 + context 归属 fail-open**。
4. **插件 iframe 与宿主同源**，`/publish` 无 frame 校验，`/show` 可读项目数据根。
5. **desktop 插件全局输入注入**，无白名单/确认。
6. **crontab 沙箱 fail-open + 整个 work_dir 可写**。
7. `/show` 白名单包含项目数据根（`window.go:565`）。

### 4.5 工程化缺陷

| 项 | 现状 | 后果 |
|---|---|---|
| 构建复现 | 本地 replace + 绝对 GOROOT + 私有 fork | 换机器/CI 无法构建 |
| CI | 无 | 回归靠人；race 从未跑 |
| 格式/静态检查 | 32 文件 gofmt 不通过；无 lint | 风格漂移、死代码增长 |
| 编码 | 部分 `go.mod` 中文注释 mojibake；CRLF/LF 混用 | 工具链/评审噪音 |
| 测试 | 55k 行 Python E2E 驱动 GUI；无 `-race`；无契约测试 | 测不到 P0 竞态 |
| 测试目录 | 大量测试与源文件不 1:1（自身文档要求 1:1） | 规范失效 |
| 死代码 | `timeout_arbiter`（2026-11-16 已删）、`awaiting`、空 `sandbox/`、`internal/testbus/`、本地 `winproc` 副本、`wailsjs/`、`dist-browser/` | 误导维护者 |
| 产物 | 262MB；codegraph 32MB；前端 165 chunk / 17MB | 安装/启动成本 |
| 可观测性 | 前端错误只进 console；每请求一行 audit；无 metrics/trace | 线上不可诊断 |

### 4.6 前端专项

- 无 TypeScript（装了 `typescript@7`、`tsconfig` 只 include `.js`、无 `vue-tsc`）。
- 14 个 SFC 超过 800 行，`MessageList.vue` 1,820 行。
- 状态双轨：1 个 Pinia + 12 个模块级单例；项目切换只 reset Pinia。
- 轮询过多：会话列表 4s、running 节点 1s、群聊 500ms+1500ms 猜刷新。
- 性能反模式：`computed` 里 `setTimeout`；`CodeView` 串行递归拉整个工作区；20MB 附件 base64；每消息订阅 MQ。

### 4.7 架构复杂度账本

| 当前机制 | 是否可以去掉/替换 | 理由 |
|---|---|---|
| 自研进程内 MQ | **可以，改为 Go 接口** | 单进程内无投递/序列化需求 |
| `req_id` 同主题应答 | **可以** | 与 Future 语义重复 |
| 自定义帧协议 ×2（各 480 行） | **可以合并** | diff 仅包名/注释；readFrame 3 份 |
| 插件 bridge + MCP HTTP + engine UDS | **可收敛为一种** | stdio JSON-RPC 一种就够 |
| 53 module | **可收敛到 ~8** | 单团队、单产品 |
| 三级 DB + 一树一库 | **可合并为 SQLite 单库** | 隔离收益 < 一致性成本 |
| 兼容事件层（llm-token） | **已删除**（2026-11-16） | 曾是主路径，负资产 |
| 21k 行规格 | **保留契约 + ADR，删叙事** | 文档应可执行/可校验 |

## 五、如果重做：目标架构

### 5.1 必须保留的产品不变量

1. 单文件、双击即用的桌面体验。
2. 每项目隔离（配置/会话/文件边界）。
3. 插件进程外隔离。
4. Agent/场景/工具契约的产品模型。
5. 工具取消/异步/后台/记忆/检索能力面。
6. 离线优先、本地数据可迁移。

**不保留的偶然复杂度**：进程内字符串 MQ、53 module、三套传输、兼容层、三级库分库、无类型 payload、自研帧协议。

### 5.2 目标拓扑

```
chonkpilot/                      ← 单仓 + go.work
  apps/desktop/                  ← 唯一壳：WebView2 + 托盘 + 单实例（~1k 行）
  core/                          ← 单一 module（~8 万行）
    api/                         ← 唯一边界协议：typed commands/events（生成）
    engine/                      ← turn 状态机 / 上下文 / 压缩（Go 接口）
    store/                       ← SQLite（WAL）+ 迁移 + 查询
    tools/                       ← MCP client + builtin
    pluginhost/                  ← 进程监管 + 一种 JSON-RPC
  plugins/                       ← 每插件独立 module，manifest 共享
  web/                           ← Vue3 + TS，客户端由 schema 生成
  contracts/                     ← JSON Schema：消息/工具/manifest/配置
  docs/adr/                      ← 一页决策记录
```

内部调用：

```go
// 现在： bus.Emit(ctx, "data-session-history", map[string]any{...}).Wait()
// 重做： store.SessionHistory(ctx, SessionHistoryQuery{...}) (History, error)
```

边界只保留两种协议：
- **UI ↔ core**：`POST /rpc`（JSON-RPC 2.0，`id/method/params/deadline_ms`）+ SSE 事件流（带 `seq`，可 resume）。
- **core ↔ plugin**：MCP over stdio（或同一 JSON-RPC 走 UDS），manifest 提供工具 schema，宿主下发 capability token。

### 5.3 关键决策对照

| 主题 | 现设计 | 重做方案 | 为什么 |
|---|---|---|---|
| 内部通信 | 字符串主题 + 同步派发 | Go 接口/方法调用 | 编译期检查、可 mock、无序列化、天然 ctx |
| 边界协议 | MQ + 3 套帧 + HTTP | 1 套 JSON-RPC + 1 套 MCP | 减少实现与超时表 |
| 请求-响应 | Future / req_id 两套 | `id + deadline + cancel` 一套 | 语义统一，取消可传播 |
| 事件 | `Eval(JS)` 注入 | SSE + `seq` + resume | 可重连、可测试、可观测 |
| 存储 | bbolt 三级 + 一树一库 | SQLite 单库/作用域 + 迁移 + FTS5 | 事务、索引、查询、升级 |
| Schema | 只生成键名 | 生成 Go/TS 类型 + 校验 + 契约测试 | 消灭 E6 类 bug |
| 模块 | 53 module + replace | 1 work + ~8 module + 版本依赖 | 可复现构建 |
| 插件监管 | UDS 桥 + 自建 MCP HTTP | supervisor + Job + token + 单协议 | 生命周期/安全/简单 |
| 前端 | JS + 手写协议 | TS + 生成客户端 + 虚拟列表 | 类型安全、性能 |
| 测试 | 55k 行 GUI E2E | 契约 + 核心集成 + 少量 E2E | 更快、更准 |
| 构建 | PS 脚本 + 硬编码 GOROOT | Taskfile/Make + go.work + CI | 一键、可复现 |

### 5.4 回合引擎重做要点

```
Idle → Accepting → Streaming → AwaitingTool(s) → Streaming → ... → Final
                      ↑             │
                      └── Inbox ────┘（插话在 tool 等待期插入，流式期排队）
```

- 每个 turn 一个 `ctx`，从 UI 贯穿到 provider/gateway/插件/子进程。
- 所有副作用先落库再前行；重启后 `interrupted` 可恢复。
- 终态不可变（`complete/error/cancelled` 只进入一次）。
- 幂等键在 API 边界（`client_msg_id` 唯一索引，查重/开轮/插入同事务）。
- 异步 = detach 语义：同步返回与 `mcp-tasks-report` **二选一**。

### 5.5 插件体系重做要点

- 一次性 `plugin_token`，`hello` 必须携带且在清单内。
- 一个 manifest schema（宿主与 SDK 共用类型）。
- 只暴露 MCP server（stdio/UDS）；工具 schema 启动时校验。
- `exec.CommandContext` + Job Object + 进程树 Kill。
- 权限 deny-by-default；按项目/实例裁剪。
- 插件 UI 独立 origin / sandbox iframe，唯一通道 `postMessage`。

### 5.6 前端重做要点

- TS + `vue-tsc --noEmit` 门禁；协议类型由 schema 生成。
- 领域 composable；SFC ≤ 600 行。
- 事件委托替代每消息订阅；一次性 child index；共享 1s 时钟。
- 大附件二进制分片上传。
- 共享单例统一 `reset()`。

### 5.7 迁移路径

1. **先修 P0**（2 周）。
2. **协议收敛**（4-6 周）：高频内部路径改接口直调；MQ 只留边界；删兼容层。
3. **存储迁移**（4 周）：bbolt → SQLite，双写/回放校验，迁移框架。
4. **模块收敛**（3 周）：go.work 下 8 module；去 replace；CI。
5. **插件安全**（3 周）：token + deny-by-default + Job + 独立 origin。
6. **前端类型化**（4 周）。
7. 可选：codegraph/vfts 独立服务化。

## 七、结论

最值得肯定的是"产品思维"：回合状态机、工具网关、异步/取消、插件隔离、记忆、检索、远程接入都做出来了，很多边界（取消阶梯、恰好一次回报、实例分桶、owner 不变式）是想清楚了的。

最大的问题不是某个 bug，而是三个基础选择带来的复利成本：

1. **用字符串消息总线做进程内 API**——让编译器、类型系统、IDE、trace 全部失效。
2. **过早、过度地拆模块/拆仓**——53 个 module 换来不可复现构建、重复类型和跨仓漂移。
3. **用"文档 + 注释叙事"替代可执行契约**——21k 行 spec 没阻止字段漂移。

如果重做：保留产品模型与分层意图，内部改普通 Go 接口，边界只留一套带 deadline 的 JSON-RPC/MCP，存储换带迁移的 SQLite，模块收敛到一个 work，契约由 schema 生成并进 CI。

如果只演进：先做第六节的 12 件事；前 5 项属于"不做就会持续产生错误数据"的级别。
