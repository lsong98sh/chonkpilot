## 1. 问题与目标

**需求（原始）**：主 agent 发现是 **e2e 测试**这类任务时 → 打开一个群聊窗口 → 布置任务 → 相关 agent **自动处理、彼此交互** → 直到任务完成。

**与单聊的本质差异**：

| 维度 | 单聊 | 群聊 |
|---|---|---|
| 参与者 | 人 + 1 个子 agent | **N 个 agent**（主 agent 布置 + 成员） |
| 人的角色 | **对话者**（要发言） | **旁观者**（只读，插不上话） |
| 窗口性质 | 聊天窗口 | **展示板**（机器人之间的窗口，人只是看） |
| 工具交互 | 窗口内可发生 | **窗口内不发生**，全在各自子会话里 |

---

## 2. 总体结构（三层）

```
群聊会话（只走文本 · 不跑工具 · 人只读）
   ├── 主 agent 布置任务（第一条消息）
   ├── 参与者 1 的「干活子会话」（工具交互）→ 回填结论
   ├── 参与者 2 的「干活子会话」（工具交互）→ 回填结论
   └── …
```

- **群聊会话**：**展示板** —— 只承载**结论**与 `ask_user` 卡片，**自身不跑 LLM、不碰工具**（D11）
- **参与者的会话**（`work_session`）：每个参与者（**含主 agent**，D46）有一个自己的会话、**继承群聊上下文**；每轮被叫到 → **一次 LLM 调用**完成**判定 + 执行**（可多轮工具）（D12 / D20）
- **回流**：干完 → **只把结论扔回群聊**（不是过程）；判"**无关**"则**不上屏、不入下一轮**（D13 / D21）

---

## 3. 一轮流程（依次认领）

1. **发起**：主 agent 布置任务 → 群聊首条消息（D18）
2. **叫号**：系统按**参与者名单顺序**依次交给每个参与者（D3）；**带 `@某人` 的发言只投给被 @ 的人**（其余人收不到 → 也就不会被触发）；**公开发言投给所有人**（D27 / D33）
3. **各自判定 + 执行（同一次 LLM 调用）**：轮到者在**自己的会话**里（继承群聊上下文），**一次 LLM 调用**同时完成"跟我有关吗"的判定与执行（D20）
   - **有关** → 干活（可多轮工具）→ 回**结论** → **上屏** + **进下一轮**
   - **无关** → 回"**无关**" → **不上屏**、**不传入下一轮**（但**落库**）（D13 / D21）
4. **上屏与下一轮**：**结论随时上屏**（**谁结束谁上屏**，D31）；**下一轮必须等本轮全部走完才启动**（屏障**只挡下一轮**，不挡上屏）→ 启动时把**本轮所有发言合并成一条信息**喂给**各参与者会话**（**按 `@` 过滤**，D32 / D33）
5. **终止**：**主 agent 判定目标达成** 或 **用户停止**（§7）

> **一轮可多人发言**（串行、非并行）：依次走完后，本轮各人的结论按顺序留在群聊里（D4）。

## 4. 群聊窗口 UI

**结构**：顶部/侧边 = **参与者头像区**；主体 = **结论消息流**。

**头像状态**（一眼看出每个 agent 此刻在干什么）：

| 头像表现 | 含义 |
|---|---|
| 头像上**小图标旋转** | **正在思考**（本轮被叫到，正在判断/干活） |
| **转停 + 无发言** | **无关**（不接，不产生群聊消息） |
| **有发言** | **产出了结论** |

**交互**：
- 点某条**发言**（或点**头像**）→ 在群聊窗口**右侧分栏**显示该 agent 的**自己的聊天记录**（D17 / D29）
- **随时可点**：会话**运行中 → 实时显示**；**已结束 → 只读**（D48）
- 分栏**不占窗口数**（**不另开独立窗口**）（D29）
- 人**不能发言**（只读旁观）；记录**可回看**（D14）
- **主 agent ≡ "用户"**：它的话**靠左侧显示**（同真人用户消息位置）；布置任务 = 开场发言（D47）

**窗口布局**：**左**（参与者头像区 + 结论消息流）｜**右**（选中 agent 的子会话内容，只读）

**入口 / 挂载 = 与单聊完全统一**（✅ D41）—— 群聊同样是**主 agent 为完成某个特定任务而启动的子聊天**，所以**挂在同一处**：

| 入口 | 与单聊的关系 |
|---|---|
| **会话列表下挂**（主会话行下挂子聊天，含 `finished`） | 同单聊 **D32**（含 finished，点击打开） |
| **启动时「未结束子聊天」提醒对话框** | 同单聊 **D38**（列出 purpose + 父会话 + 状态） |
| **输入框上方状态条** | 同单聊 **D21**（「正在 <purpose>」+ 继续） |
| **唯一区别** | **图标** —— 下挂时用图标区分**单聊 / 群聊** |

**人机唯一例外**：`ask_user` —— **形态同主窗口现状**（弹窗问答）；**按 instance 投递到本群聊窗口**（见 §13 · D42）。

## 5. 会话与数据模型（含待定）

**已知需要**（字段细节待定）：
- 群聊会话**类型标识** = **`kind = group_chat`**（✅ D25）—— 与单聊的 `sub_chat` / `dsl_run` 的 `sub_session` 并列
- 干活子会话命名 = **`work_session`**（✅ D23）
- 每条群聊消息需要**发送者标识**（哪个 agent 说的）—— 现架构**没有**（消息只有 `role ∈ system/user/assistant/tool`）
- **参与者名单** = 由**主 agent 选取**（**可动态加人**）；也支持**全体参与（全体会议）**（✅ D26）
- **入口 / 消息族 = 复用单聊「子聊天」那套**（✅ D39）：父窗口**状态条** / **会话列表**统一挂"子聊天"条目，条目带 **`purpose`**（= display name）+ **agent(s)** —— **1 个 agent = 单聊，N 个 = 群聊**
  → 由此 **群聊可复用单聊已定的 4 条 `subchat-*` 消息**（可能只需**扩字段**，而非新增消息族）
- **落库新表**（✅ **D44**，**外键关联到 `kind = group_chat` 的会话**）：
  - **① 参与者名单 + 角色** → 一张表
  - **② 每【大轮次】的投递对象** → 一张表（**"大轮次" = 群聊依次叫号的那一轮**，**不是**子会话内部的轮次）
  - → 两张表**合并或分开**均可（用户无强偏好）；字段细节待定

> **注意**：这是**消息面 / 落库变更**，按项目准则须**单独经用户确认**（§10）。
>
> **⚠️ 术语提示（防混）**：本档凡称"**子会话**"，均指**参与者的会话 `work_session`**（D23）—— **不是**单聊的 `sub_session`（`dsl_run` 的 `LLM` 步骤派生物）。两者**不同物、不同视图**。

## 6. 上下文继承（已定）

- **群聊本体**：只有**结论** → 体量小，**"全量"很便宜**
- **上下文（含按人压缩）落点 = 子会话**（✅ D22）—— 就是**背后那个隐藏的会话**里
  - 参与者**会话**（`work_session`）**继承群聊上下文**，**"按人压缩"发生在这里**（D6 / D7 / D8）

## 7. 终止条件

| # | 触发 | 说明 |
|---|---|---|
| ① | **用户可随时停** | 防"喋喋不休" |
| ② | **主 agent 判定目标达成** | 必须由**主进程（主 agent）**判断 |
| ③ | **硬上限：最大轮次**（✅ D49 / D50） | **项目级配置**（**非系统级**），**默认 20 轮**（可选区间 ~20–40）；**到顶强制停** + **主 agent 终审表态**；**用户可点「继续」在原线程上续跑** —— 兜底"防跑飞"（业界标配，见 §17） |

**口径（D10，沿用单聊）**：主 agent 判定达成 → **点亮"可以结束了"** → **用户拍板结束**（若给主 agent 自动结束权限，需另裁）。

> **注**：③ 是**唯一的硬闸**——①②都是"判断"，只有它**不依赖任何 LLM 判断**，纯计数兜底。

## 11. 与既有机制的关系

| 既有机制 | 关系 |
|---|---|
| `dsl_run` 的 `LLM "agent" "prompt" "目的"` | **同构**：子会话干活 → 结论回填父轮。群聊 = 它的**多 agent、多轮版** |
| 单聊 `sub_chat` | **不同物**：单聊是**人机一对一子聊天**；群聊的"干活子会话"是**agent 的私有工作区**（命名已区分：`work_session`，D23） |
| 任务树（tasktree） | **不建"会话型"节点**（同单聊 D19 / D39）—— 群聊是否结束**存会话行**（`lifecycle`）；`work_session` 干活产生的**工具调用节点**本就属 tasktree（tasktree 只记工具调用），**不产生会话实体节点** |

## 14. instance 父子链与跨窗口消息投递（要害 · 2026-10-15）

> 用户口径：**弹新窗口聊天 / 单聊 / 群聊，每个窗口都是一个 instance** —— 因为**消息按 instance 定向投递**（"没有 instance 的投递不成立"）。

## 15. 群聊窗口关闭后的续聊（⚠️ 新增要害 · 2026-10-15）

> 用户提出："**群聊的窗口关闭以后的续聊**" 是**很重要的问题**。

### 15.1 与单聊的关键差异（不能照抄）

| | 单聊 | 群聊 |
|---|---|---|
| 驱动 | **输入驱动**（用户不说话就不跑） | **自动长跑**（依次认领 → 结论 → 下一轮，**无人也在转**） |
| 关窗 | 用户暂离，会话状态不变（单聊 D3） | **？** —— 关掉后它**还在转吗**？ |

→ 单聊"关窗 = 暂离"**不能直接套**：群聊若无人看还在跑，就是 **烧 token + 无人应答 `ask_user`**。

### 15.2 必须先定的 4 件事（**已全部裁决 → 见 §15.4**）

| # | 问题 | 选项 | 我的建议 | 裁决 |
|---|---|---|---|---|
| **P1** | 关群聊窗口后，群聊**还跑吗** | ① **暂停**（不结束）② 继续跑（后台跑完） | ① 暂停 | ✅ ①（并给"终止"选项，N22） |
| **P2** | 群聊的**驱动挂在哪**（决定 P1 能否实现） | ① **群聊窗口的 instance** ② 主窗口的 instance ③ **server**（与窗口无关，需新机制 ≈ job 管理） | ① | ✅ ①（N23） |
| **P3** | **重开入口**在哪 | ① 主会话窗口挂一条状态（像单聊状态条）② 会话列表里打开 ③ 启动时提醒 | ① + ③ | ✅ **复用单聊「打开子聊天」**（N24） |
| **P4** | 与 §14 的关系 | —— | ~~补"子→父"：走 §14 方案 A~~ | ✅ **定向投递**（§14.2；**方案 A 已放弃**） |

### 15.3 风险与依赖

- **暂停 / 重启的 turn 状态**：现有 `data-session-cleanup-stale` 会把 `running` 的 turn 标 `interrupted`，**无 `paused` / `awaiting` 概念** → 群聊"暂停"若**跨进程重启**，轮次会被**误标中断**（与 §13 的 `awaiting` 缺口**同源**）
- **依赖 §14**：主窗口感知"群聊正在跑 / 已结束" = **跨窗口投递**（`parent_instance` 链）

### 15.4 裁决方向与结果（用户 2026-10-15）

**关窗给选项**：关群聊窗口时提供 —— **① 暂停** / **② 终止**。

**强关应用（进程退出）= 必然中断**（无法避免；被中断的多是**工具调用**）：群聊的 `work_session` **一并 `interrupt`** —— **复用现有 interrupt 态，不引入 `paused`**。

**恢复 = 打开群聊窗口 → 点「继续」**：

| 情形 | 处置 |
|---|---|
| 子会话**已有结论** | **保留**，不重跑 |
| 子会话**无结论**（被中断） | **继续用**（续跑 / 重跑） |
| 本轮走向 | **等本轮全部结束**（屏障走完）→ 再进下一轮 |

→ "**继续**" = **只补跑本轮"没结论"的子会话**，补齐后本轮收口、继续循环。

| # | 事项 | 裁决 |
|---|---|---|
| **N22** | 关窗后 | ✅ **给选项：暂停 / 终止** |
| **N23** | 群聊驱动归属 instance | ✅ **群聊窗口的 instance**（"关窗即停"的前提；无异议即定） |
| **N24** | 重开入口 | ✅ **复用单聊「打开子聊天」入口**（同一套 `subchat-*` 消息族）；条目带 **`purpose`**（= display name）+ **agent(s)** —— **1 个 agent = 单聊，N 个 = 群聊** |
| **N25** | "暂停"是否跨进程重启保持 | ✅ **不引入 `paused`**：强关 = `interrupt`（复用现有），靠「继续」补跑无结论者 |

> **🟢 落地（SUBCHAT-3 阶段 F-2，2026-10-16）**：N22–N25 的后端/调度侧已落地 —— **暂停** = 进程内停机（`sc.ctx` 取消；**不落库、无 `paused`**，`lifecycle` 保持原值）；**终止** = 既有 `subchat-finish` → `finished`（并停掉在跑调度器）；**强关应用** = 复用既有 `interrupt`（**未新增态**）；**驱动归属 = 群聊窗口的 instance**（N23）：`instance-register.session_id` → `InstanceForSession` 反查，`instance-exit` 即停机（**关窗即停**）。**「继续」= 断点补跑**（D45 甲案）：只补本轮无结论者；**第 2 道防线（工具幂等）不属本阶段**。**关窗选择弹窗（暂停/终止二选一 UI）属阶段 G**。

> **⚠️ 副作用重复 → 处置（✅ D45，2026-10-15）**
>
> **问题**：补跑"无结论"的子会话时，若中断发生在**工具已执行之后**，重跑可能**重复副作用**（例：文件被改两次）。
>
> **处置 = 两道防线**：
> 1. **续法 = (甲) 从断点续** —— **保留**已发生的对话 / 工具记录，补一条"**该工具被中断**"的结果 → **LLM 接着跑**（它**看得见自己干过什么**，可自行判断要不要重调）。**注意**：这只让 LLM **有机会**判断，**不保证**它不重调 → 所以还要第 2 道。
> 2. **工具侧尽量幂等**（用户建议）—— **工具重跑时自动识别"前面更新到哪"再接着来**：
>    - **写文件类大多可行**：`patch` / 整体 `write` **天然幂等**（重复应用同样的 diff/内容结果一致）；`append` 类可**加标记**，重跑时见到标记即跳过
>    - **外部副作用识别不了**：发消息 / 调第三方 API / 有副作用的 shell 命令
>
> **残余风险（已知、接受）**：**外部不可识别类无法 100% 保证** —— 其中**最要命的是"写数据库表 / 改表数据"**（用户 2026-10-15 点出）：这类**没有办法解决**，**不予处理**。

## 16. ⛔ 硬约束：非主会话一律**同步**（不得异步）（2026-10-15）

> **用户口径**："**凡不是主聊天都不能做异步，做异步就惨了**" —— **单聊 / 群聊（及一切非主会话）的轮次必须同步跑完**。

### 16.1 确切含义

- "异步" = **工具调用转后台、脱离当前轮次**（`tasks/*` 四态、`DetachExec`）
- 工具 async 模式**四档**：`always` / `never` / `auto` / `manual`（`src/lib/mcp-server/server/config.go:120-121`）
- **全局覆盖** `Params.AsyncMode`：`""` = 默认 `auto`；**`"never"` = 强制同步**（`src/lib/gateway/gateway/mcpgateway.go:921-922`）
- **既有先例**：CLI 单体就传 `AsyncMode: "never"`（`src/desktop/cli/main.go:174`，注释"强制同步，不允许转异步"）

### 16.2 为什么"惨"

- 这些会话的**状态推进全靠"轮次跑完"**：单聊的**收口点亮**、群聊的"**本轮屏障**"（等本轮全部走完才进下一轮）—— **一旦工具转后台、轮次提前结束 → 判定全乱**
- 且后台工具脱离轮次后，**结果回流 / 中断恢复**（§15）都会失序

### 16.3 落地要求

- **非主会话的会话启动参数**强制 **`AsyncMode = "never"`** → 记为 §10 · **C7**
- **适用范围 = 非主会话里的每一次工具调用**（用户 2026-10-15 补充）—— **不做区分**：无论工具自身 async 档是 `always` / `auto` / `manual`，在非主会话里**一律同步执行**
- 与既有一致：单聊 **D6**（`subchat_open` = `async: never`）
- **代价（接受）**：长耗时工具会**阻塞轮次**（不会转后台）；但这正是要的 —— 轮次状态推进必须可控

## 17. 业界对照（2026-10-15 调研 · 供评审参考）

> 起因（用户）："看看现在外面的群聊，它的调度做法是不是和我讲的一样？"

### 17.1 四条主干（"谁定下一个发言者"）

| 流派 | 代表 | 定人方式 | 每轮 LLM 调用（估） |
|---|---|---|---|
| **固定顺序 / SOP** | MetaGPT、ChatDev、CrewAI `sequential`、Dify/Coze 工作流 | **写死流程** | 1 |
| **中心调度者 supervisor** ⭐**最主流** | LangGraph `supervisor`、CrewAI `hierarchical`、AutoGen `GroupChatManager`、Copilot Studio、Anthropic Research | **一个 LLM 决定派谁** | 2（选人 + 干活） |
| **群聊选人 selector** | AutoGen `SelectorGroupChat`（`speaker_selection_method` 四档：`auto`/`round_robin`/`random`/`manual`） | **LLM 在共享上下文里挑人**，或轮换/随机/人工 | 1–2 |
| **定向交接 handoff** ⭐第二主流 | OpenAI Agents SDK、AutoGen `Swarm`、LangGraph handoff | **当前 agent 把控制权交给下一个** | 1 |
| 专项 · 双人角色扮演 | CAMEL | 严格二人交替 | 2 |
| 专项 · 辩论/投票 | multi-agent debate | **每轮全体并行发言 + 聚合** | ≈ N·R+1 |

### 17.2 我们 vs 业界

| 我们的设计 | 对应业界 |
|---|---|
| **依次认领**（全员轮着看） | AutoGen **`round_robin`** |
| **`@某人` 定向** | **handoff**（定向交接）+ selector 点名 |
| **主 agent 兜底 / 判定达成** | **supervisor**（业界最主流那条） |
| **群聊 = 展示板**（只上屏结论，干活在各自会话） | **业界无此形态** —— 最接近是 Anthropic 的 "worker 隔离 + 主 agent 综合"，但它**没有展示板**。**这是我们的独有设计** |
| **全量 + 按人压缩** | MetaGPT 的**发布/订阅按类别过滤**、Anthropic 的 **worker 上下文隔离** —— 我们属**偏先进一档** |

### 17.3 三条可借鉴

1. **硬上限**（已采纳 → §7 ③ / D49）：业界**标配** `max_round` / `max_turns`（AutoGen `MaxMessageTermination`、LangGraph 递归上限）；我们原先只有"判断"没有"计数兜底"。
2. **主 agent"怎么判达成"可借 Magentic-One 的"双账本"**：**Task Ledger**（总计划 + 事实 + 猜测）+ **Progress Ledger**（每步自省进度、判断是否完成）。→ 补 D10"主 agent 判定"的具体做法（**待评估是否采纳**）。
3. **公共经验**：Anthropic / AutoGen / LangGraph 均明确"**能单 agent 就别上多 agent**"；多 agent token 常为 chat 的 **10 倍以上**，且**不适合强共享上下文的任务** → **反证我们"只上屏结论 + 上下文压缩"方向正确**。

### 17.4 一处更正

调研任务描述里把 **Stanford Generative Agents** 概括为"自主认领 + 投票" —— **不准确**：原论文**没有把"投票"作为调度原语**（它是"无中心编排的自治仿真"，市长竞选属**涌现**行为）。"投票/辩论"那条线对应的是 **multi-agent debate**。

### 17.6 创新性评估（2026-10-15 二次调研 · 用户问"咱们算创新还算啥？"）

| 我们这条 | 业界成熟度 | 结论 |
|---|---|---|
| **到顶 = 硬停 + 主 agent 终审 + 用户点「继续」原线程续跑** | **成熟** | AutoGen `MaxMessageTermination` 到顶**直接终止**，且**再 `run()` 即从断点续跑**（官方把 `max_turns` 称作 "pause the team for user input"）；LangGraph **checkpointer + `Command(resume=…)`**；OpenAI Agents SDK `RunState` 序列化；Claude SDK 明确提示 "Resume session to continue"；产品级 **Cosmic Agents 到 15 轮弹 "Paused" 卡片 + Continue 按钮**（连 tool call 都保留可展开）→ **我们这条 = 业界标配组合，不是创新** |
| **agent 自评"无关" → 静默弃权** | **最少见** ⭐ | 主流框架（AutoGen `SelectorGroupChat` / LangGraph supervisor / OpenAI SDK）**一律是"外部 selector/supervisor 选人"**，agent **没有**"被叫到后自己弃权"的身份（`allow_repeated_speaker` 也只是外部约束）。工程先例仅见 **swarms `GroupChat` 的出价制**（每 agent 私评 0–1 分，最高且过阈值者发言，"Everyone else stays silent"）；学界有 EARS / ProACT / *Speak or Stay Silent* 等**较新且少数派**论文 → **我们属"少数派设计"，但非首创** |
| **群聊只上屏结论、过程在各自会话** | **机制成熟 / 产品形态少见** | 底层机制**有明文**：Claude Code subagents（"intermediate steps … stay isolated and **never clutter your main conversation**"）、AutoGen `SocietyOfMindAgent`（整场群聊当 inner monologue，对外只出一个 agent）、AG2 nested chats。但"**多 agent 在同一面板里只留结论**"的产品形态**较少见** → **机制有先例、形态较少见** |
| **判定与执行 = 同一次 LLM 调用** | —— | 业界 selector/supervisor 模式**要多花一次"选人"调用**（每轮 2 次）；我们折进执行调用，与 **handoff** 模式（1 次/轮）同量级 → **是省钱的取舍，不是创新** |
| **终止由用户拍板** | —— | 业界多为**自动终止条件**（`TERMINATION` / `FINISH` / 关键字）；我们"主 agent 点亮 + 用户拍板"比业界**多一道人** → 取舍，非创新 |

**结论**：**我们不是"创新"，是"组合优化"** —— 零件几乎都能在业界找到对应（多数还是标配）；**唯一较少见的是"agent 自评无关 → 静默弃权"**；真正可能的**组合差异**是「**静默弃权 + 展示板 + 按人压缩**」这三条**一起用**（业界未有人如此组合）。
→ **落地前务必原型验证，别把"新颖"当成"已证有效"。**

> **未证实项（存疑，不采信）**：① LangGraph"调大 `recursion_limit` 后从 checkpoint 恢复"**无官方明文**（属文档+社区综合）；② CrewAI `max_iter` 默认值 25 / 15 说法不一（疑版本差异）；③ Anthropic Research 博客**未明文**说明 UI 是否隐藏 subagent 中间过程（属架构推断）。

## 18. 「目标 / 剧本 / 收敛条件」放在哪（✅ 已裁决 2026-10-15）

> **起因（用户）**：像"**代码审查**"这种群聊 —— **主 agent + 程序员 + 测试员 + 审查员**四个角色 —— 他们的**顺序规则、判定条件、收敛与退出条件**，**放到各自 agent 的 system 里？还是别的地方？** 而且 **"群聊的整体目的"** 该放哪？

### 18.1 问题的实质 —— 这是当前设计的**真空**

已定 **D43**（注入**参与者名单 + 角色**），但**没有任何地方**承载：
- **本次群聊想达成什么**（目标）
- **怎么走**（顺序 / 剧本）
- **什么时候收敛、什么时候退出**

### 18.2 建议：**分三层放**（职责不同，别混）

| 放什么 | 放哪 | 理由 |
|---|---|---|
| **角色人格**（"我是代码审查员，我负责…"） | **各 agent 自己的定义**（场景 agent 文件） | 这是**这个 agent 固有**的，与"哪次群聊"无关 → **适合放各自 system** |
| **本次群聊的目标 + 剧本 + 收敛/退出条件** | **群聊注入层**（在 D43 之上扩展，**主 agent 开群聊时写入**，**每轮注入给所有参与者含主 agent**） | 这是**"这一次"的**，不是某个 agent 的；放各自 system 会**固化、且主 agent 无法按任务调整** |
| **下一个叫谁** | **`@` 定向**（handoff，D27 / D33） | 见 §18.3 —— **不需要全局"阶段机"** |

### 18.3 你的例子，用**现有机制**就能落地

```
1. 主 agent（= "用户"口吻）布置："审查这次改动，别引入回归"
2. 审查员 → 发现问题 → 发言末 @程序员
3. 程序员 → 修改 → @审查员
4. 审查员 → 复审 → 若"改动复杂 / 涉安全" → @测试员；否则**跳过测试**、直接判收敛
5. 测试员 → 回归测试（贵：2~3 小时）→ 报结果
6. …循环，直到 主 agent 判定收敛 / 用户停 / 撞硬上限（D49 / D50）
```

→ **"贵操作（回归测试）不能每轮做"这个节奏，由审查员自己在 `@` 时判断** —— **不需要系统层面的"阶段机"**。这正是 handoff 模式的用法。

### 18.4 裁决结果（N26–N29 · 2026-10-15）

| # | 问题 | 选项 | 裁决 |
|---|---|---|---|
| **N26** | **目标 / 剧本放哪** | ①（**建议**）**群聊注入层**（主 agent 写入 + **每轮注入**） ② 各自 agent 的 system ③ 群聊首条消息 | ✅ **① 群聊注入层** —— 用户："**每个参与人员都应该要知道**" |
| **N27** | **剧本从哪来** | ① 纯**主 agent 现写** ② 场景预置模板 + 主 agent 实例化 ③ 两者 | ✅ **① 主 agent 现写** —— 用户："**没有预置、不需要预置**"；但**必须给样板**（§18.5 · D51） |
| **N28** | **收敛 / 退出条件写谁** | ① 写进同一份"剧本" ② 主 agent 自己判（D10） ③ 都要 | ✅ **③ 都要**：剧本写"什么算收敛"的**判据** + **主 agent 按判据判**（D52） |
| **N29** | **收敛要"有耐心"** | 借 Magentic-One 的 Progress Ledger：**先看"有没有实质推进"**再判 | ✅ **采纳**（D52）—— 判收敛前**先看有无实质推进**，**不得草率收敛** |

### 18.5 剧本样板（→ 落进**开群聊工具的 `description`** · D51）

> **用户要求**：剧本**由主 agent 现写**是对的，但**必须给样板**，否则它不知道"写到什么程度"。样板要体现三种 `@` 写法：**不同人完成 → 指向不同目标** · **按情况指向不同目标** · **指向全员**。
> **不拆版**（用户 2026-10-15）：**不做"精简版 + 完整版"拆分** —— "**告诉他这里边应该怎么去写，然后给个小小的样例就可以了**"；**整段进 `description`**（会占每轮 token，**接受**）。

**样板（以"代码审查"为例，将写进工具契约 `description`）**：

```
【群聊目标】
审查 src/foo/ 本次改动：不引入回归、不新增安全漏洞。

【参与者与职责】
- 审查员：审 diff，列出问题（按严重度）
- 程序员：按审查意见修改
- 测试员：跑回归测试（很贵，仅在被点名时执行）
- 主 agent：判收敛

【推进规则（靠发言末行的 @ 决定下一个叫谁）】
- 审查员发现问题 → @程序员
- 程序员改完     → @审查员
- 审查员复审：
    · 改动复杂 / 涉安全 → @测试员
    · 只是小修         → 不 @，直接报"已收敛"
- 测试员跑完     → @审查员
- 需要全员同步   → @全体

【收敛条件（主 agent 判定，要有耐心）】
- 判定前**先看"有没有实质推进"**（如：问题数是否在下降 / 是否每轮都在改同一处 / 是否只是措辞变化）
- **不得草率收敛**
- 判据：连续 2 轮无新的实质问题，且（若调用过测试）测试通过 → 判"达成"，点亮「可以结束了」

【退出条件】
- 用户手动停
- 撞轮次上限 → 主 agent 终审 + 给进度摘要
```

### 18.6 落地补充（阶段 F-1，2026-10-16 · 实施记录）

> 阶段 F-1（发起 + 依次认领调度器 + `work_session` + 注入 + 上屏/屏障 + 收敛终止 + 到顶处置）**已落地**。
> 实施落点 = `src/lib/llm/server/groupchat_sched.go`（调度器 / 展示板 / 状态推送 / 发起 / 继续）+ `src/lib/llm/server/turn.go`（第五层群聊注入）。

**目标 / 剧本 / 收敛条件的落点 = `sessions` 的 3 个可选列 `goal` / `playbook` / `convergence`**（理由：与既有子聊天固定参数 `kind`/`lifecycle`/`agent`/`scenario_id`/`llm`/`purpose` 同层同法——建会话时写入、**仅非空才写键**（普通会话行形状零变化）、注入层**复用同一次会话行读取**（`sessionRow`）即得，无需新增表/新消息主题）。写入 = `subchat_open` 群聊分支的 `SessionEnsure`；读取 = 第五层注入。

**机读约定（**不得新增消息主题**；用既有 `data-session-append-message` 字段 + 结论文本约定）**：

| 语义 | 约定（可机读） |
|---|---|
| **「无关」**（D13/D21） | 该参与者本轮 `work_session` 的**最终 assistant 文本**，其**首个非空行**（去首尾空白）恰为「**无关**」→ 判无关：**不上屏、不入下一轮**（但已落在它自己的 `work_session` 历史里 = D21 的「落库」） |
| **「收敛」**（D10/D52） | **主 agent** 的结论文本中**单独一行**为「**已收敛**」（写作 `【已收敛】`）→ 判目标达成 → `lifecycle=ready`（点亮）+ 发既有 `subchat-state` |
| **到顶终审「未达成」**（D50） | 达上限后主 agent 终审：文本含「**已收敛**」→ 点亮；否则（含显式「【未达成】」或未表态）→ **强制 `finished`** + 展示板追加系统提示「因达轮次上限终止，可能本次群聊未完成。可点「继续」在原线程上续跑」 |
| **`@` 名单**（D27/D33/C6） | 发言**最后一行**的 `@xxx`（可多个）；`@全体` / `@所有人` / `@all` → **公开条**（投给全体）；不写 `@` = 公开条。落到消息的 `mentions`（归一到名册 `agent`）；**公开条投给全体、定向条只投被 @ 者** |

**阶段 F-1 落地口径（对 §3 的细化）**：
- **一轮的投递对象**：首轮 = 全体（按名册顺序）；此后 = 由**上一轮发言**按上表 `@` 语义算出的并集（公开条 ⇒ 全体；否则仅被 @ 者），写入 `group_round_targets`（每大轮次一条）；**无人认领（本轮无人发言）→ 主 agent 兜底**。
- **上屏 = 随时**（谁结束谁上屏，D31）：每条结论立即追加到群聊展示板（同一条「展示板 turn」下），带 `sender_agent`；**主 agent 发言按 `role=user` 落库**（D47 靠左显示）。
- **屏障只挡下一轮启动**（D31）：本轮全部参与者走完才由本轮发言算下一轮（串行执行下天然满足）。
- **`work_session`**：确定性 id = `work-<群聊会话id>-<净化后的 agent 名>-<agent 名哈希>`，**幂等建会话** → 跨大轮次复用；`kind=work_session`、`parent_id=群聊会话`、`Agent=参与者`；其轮次经 `runChildTurn` 在**每次被叫到时**跑一次（判定 + 执行同一次调用，D20），上下文继承 = 逐轮喂入「上一轮适用于该参与者的发言合并条」（D32）。**「按人压缩」落在这层** = 依赖既有按会话压缩机制（本阶段不做定制压缩器；`work_session` 未进子聊天清单，不影响单聊视图）。
- **到顶 + 继续**：`group_chat.max_rounds`（默认 20）由调度器现读；到顶走终审；用户 `subchat-continue`（**新增的 client→server 同名主题**，见 61 §4.2/§4.5）→ `lifecycle` 回 `chatting` + **从上次大轮次之后**续跑（另给一轮预算）。
- **`subchat-participant-state`**（阶段 E 已登记消息）= 本阶段的生产者：轮到 → `thinking`、判无关 → `idle`、产出结论 → `spoken`（广播，前端按 `parent_session_id` 归属过滤）。
