## 1. 问题与目标

### 1.1 要解决的问题

主 agent 在推进任务时，会识别出**需要一段独立对话才能完成的事**（典型：需求讨论、方案设计）。当前只能把用户拉到主会话里聊，导致：

- 主会话被长话题污染，上下文迅速膨胀；
- 无法给这段讨论**固定的角色与能力边界**；
- 讨论结束后没有收口与回切动作。

### 1.2 目标（可验收）

| # | 目标 |
|---|---|
| G1 | 主 agent 能用**一个工具**打开一个新的对话窗口，并把需求描述交接过去 |
| G2 | 该窗口是**固定参数会话**（角色 / 场景 / LLM 锁定，用户不可切换） |
| G3 | 该会话**跨多轮**进行，人格在**重启恢复后仍保持** |
| G4 | 讨论结束由**子 agent 自报**（建议）+ **用户点「结束」**（拍板）；窗口关闭、回切原会话 |
| G5 | 用户关窗**不等于结束**；之后可**在同一会话**续聊 |
| G6 | 单聊产出对用户可见（窗口内消息 + 落盘文件）；「是否完成」由**子 agent 建议、用户拍板** |

### 1.3 非目标

- **不含群聊模式**（多 agent 同窗交互）——另立文档。
- **不改**既有「LLM 委派」机制（现行走 **`dsl_run` 的 `LLM` 命令**：宿主执行独立子轮次 + 结果回传，语义是「派发 → 挂起等 → 自动回填」；本方案是「不挂起 + 用户主导」）。
- **不新增消息面 topic**（见 §5.2 冻结评估）。
- **不引入后台裁决器**（见 §3.5 为何取消）。
- **结果不回流主会话**（见 §3.4.3 的取舍）。
- **单聊不进任务树**——状态由子会话域（会话行）承载，见 §3.4.4。
- **不含 job 管理**——将来另立独立域（与「子会话域」并列，均不并入任务树）。

## 2. 总体方案

新增两个**域工具**（`category=server`、`async:never`）：

| 工具 | 作用 |
|---|---|
| `subchat_open` | 建固定参数子会话（`kind=sub_chat`，`lifecycle=chatting`）、写入交接内容、触发前端开窗，**立即返回 `{ok, session_id}`**（主轮不挂起） |
| `subchat_finish` | 子 agent 自报「我认为已完成」→ `lifecycle=ready` + **点亮**窗口内常驻的「结束」按钮（**建议态，不等于结束**） |

窗口与单聊的生命周期**解耦**：

```text
主 agent ──subchat_open──▶ 固定参数子会话（kind=sub_chat, lifecycle=chatting）──▶ 前端开窗（绑定该 session）
       ◀─ {ok, session_id} ──       │
                                    ├─ 多轮对话（人格由会话固定参数保持）
                                    │
                          子 agent 自报（subchat_finish）→ lifecycle=ready + 点亮「结束」按钮
                                    │
        用户点击「结束」 ──▶ lifecycle=finished + 关窗 + 回切原 session（主会话不新增消息）
```

**与既有「LLM 委派」的分工**：现行委派走 **`dsl_run` 的 `LLM` 命令**（`LLM "agent" "提示词" "目的"` → 宿主经 MQ 执行独立子轮次并回传），语义是「派发 → 挂起等 → 自动回填」，适合**黑盒子任务**；`subchat_open` 的语义是「开窗 → 交接 → 用户说完回来」，适合**需要用户参与的开放讨论**。两者并存，不互相替代。

## 3. 详细设计

### 3.1 链路三段

| 段 | 动作 | 落点 |
|---|---|---|
| **打开** | 主 agent 调 `subchat_open(agent, scenario_id, llm, prompt)` | 新工具契约 + server 域 handler |
| **轮转** | 用户 / 子 agent 交替；人格由会话固定参数保持 | 会话固定参数 + 提示词注入层 |
| **收口** | 子 agent 自报（建议）→ 用户点「结束」（拍板） | 第二个工具 + 前端 |

### 3.2 会话固定参数与两个标识

现状：`sessions` 行只有 `session_id / title / created_at / updated_at / parent_id`（写入点 `src/lib/data/internal/session/session_facade.go:312-322`），**没有 agent / 场景 / LLM**。这正是「恢复轮丢人格」的根因（见 §3.3）。

**「从哪来 / 自己是谁」两个标识——都已具备，零新增字段**：

| 标识 | 载体 | 说明 |
|---|---|---|
| **自己** | 窗口 URL 的 `session-id`（`src/lib/gui/registry.go:109-127`） | 窗口天然绑定自身会话 |
| **从哪来** | 会话行 `parent_id` | 建会话时即写入，且随 `session-new` 广播（`session_facade.go:295-322`） |

**新增字段（`sessions` 行）**：

| 字段 | 含义 |
|---|---|
| `kind` | **类型标识（三值）**：`""` = 普通顶层会话；**`sub_session` = 子会话**（**`dsl_run` 的 `LLM` 步骤**派生的子轮次会话，现行路径）；**`sub_chat` = 子聊天**（`subchat_open` 创建） |
| `agent` | 固定角色名（子 agent 定义引用；仅 `sub_chat` 有） |
| `scenario_id` | 固定场景（目录名 / key；仅 `sub_chat` 有） |
| `llm` | 固定 LLM（仅 `sub_chat` 有） |
| ~~`inject`~~ | **已删除**（D37）：注入层文本**代码内建**、按 `kind == sub_chat` 自动注入，**不落库**（§3.3） |
| `lifecycle` | 子聊天生命周期（**只有三态**）：`chatting`（进行中）/ `ready`（子 agent 判断该结束）/ `finished`（已结束）（**仅 `sub_chat` 有**，见 §3.4.4） |

**为何必须区分「子聊天 / 子会话」**：两类都是 `parent_id` 非空的子会话，**光看 `parent_id` 分不开**；而它们的通路完全不同——子会话（`dsl_run` 的 `LLM` 步骤派生）随**任务执行树**、由父轮次驱动；子聊天（`subchat_open`）不进任务树、由用户驱动、有独立生命周期（§3.4.4 / §3.4.5）。故 `kind` 是这两个域的分界标识。

**不变量**：

```text
kind ∈ {sub_session, sub_chat}  ⟺  parent_id != ""
kind == sub_chat                ⟹  才有 agent / scenario_id / llm / lifecycle
```

**写入方**（三条创建路径必须各自标对）：

| 创建路径 | 写入 `kind` |
|---|---|
| 普通会话（`llm-start` 首次落库，`session.go:33-47`） | `""` |
| `dsl_run` 的 `LLM` 步骤派生的子会话（`EnsureSessionWithParent`；`llm_run`/`jobdsl.go` 为**残余代码**，非现行路径） | `sub_session` |
| `subchat_open` handler | `sub_chat` |

**历史数据回退口径**：现有行无该字段 → 读侧 `parent_id != ""` 且 `kind` 缺失 ⇒ 视为 `sub_session`（保守，不影响新功能）。

> **不设**「裁决状态位」——没有后台裁决器（§3.5）。

### 3.3 提示词：会话注入层（**代码内建** · 按 `kind` 自动注入）

现状分层是四层：**全局 → 目录 → 场景 → agent**，拼在 `resolveTurnScenario`（`src/lib/llm/server/turn.go:379-418`，拼接点 `:412`）。

**新增第五层「会话注入层」**，承载单聊专属指令（如「完成时调用 `subchat_finish`」的收口协议）。

**注入条件（D37，2026-10-15 定）**：在 `resolveTurnScenario` 组装提示词时**判定会话 `kind ∈ {sub_chat, group_chat}`**（两者同属"子聊天"体系）→ 是则**自动追加**该层。**群聊在此基础上另加"参与者名单 + 角色"**（见 [群聊方案 §8 · D43](群聊会话设计方案.md)）。

| 约定 | 取值 | 理由 |
|---|---|---|
| 判定依据 | 会话行 **`kind`**（§3.2） | **确定的事实**——不依赖模型发挥、不需场景配置、不需工具入参 |
| 文本出处 | **必须代码内建**（llm-server 内固定文本） | 判定与文本都与代码绑定；**放到外部可改、被改错就失去意义**；改文案走代码评审 |
| 是否分化 | **所有子聊天（`sub_chat` / `group_chat`）统一一套**，不按 `purpose` / `agent` 分化 | 先一套够用，避免为假想差异增复杂度 |
| 工具入参 | **无 `inject`** | 不需要主 agent 传 |

**必须一并修的口子**——同文件注释明写（`src/lib/llm/server/turn.go:376-378`）：

> 恢复轮无 scenarioID / agent（**未持久化**）→ 仅注入全局层 + 目录层

即：**现阶段进程重启后，恢复轮会丢人格**。因此本方案要求：

1. 固定参数**持久化到会话**（§3.2）；
2. `resolveTurnScenario` 的**新轮与恢复轮同口径**读取：优先取会话固定参数，其次取请求参数。

> **第五层天然覆盖两条路径**：判定点在**唯一的提示词组装处** → 新轮与恢复轮都会自动带上收口协议，**无需单独处理恢复轮**。

### 3.4 工具契约与状态承载

#### 3.4.1 `subchat_open`

| 项 | 取值 |
|---|---|
| `category` | `server`（**必须**——只有 server 进程内的工具能发 MQ；executor 工具是子进程，够不着） |
| `_meta.async` | `never`（同轮同步返回；不挂起主轮） |
| 入参 | `agent`、`scenario_id`、`llm`、`prompt`（交接内容）——**无 `inject`**：注入层**代码内建**、按 `kind` 自动注入（§3.3 · D37） |
| 返回 | `{ok, session_id}`；失败（如撞窗口上限）→ `ok=false` + 原因，**必须明确回给 LLM** |

**handler 步骤**：建会话（`kind=sub_chat` + `parent_id` + 固定参数，`lifecycle=chatting`）→ **以用户口吻写入交接内容为「用户消息」首轮** → **异步发起子会话首轮**（D30，主轮不挂起）→ 触发前端开窗 → 返回。

> `subchat_open` 的结果**在返回那一刻定稿**（`completed`），此后**不再被改写**——工具结果是终态，且启动清理会把非终态 tool_pair 标 `interrupted`（`src/test/chonkpilot-data/unittest/persist/cleanup_stale_pairs_test.go:1-3`），故**不存在"延迟回填工具消息"这条路**。

**开窗触发方式（已定：按业务新增事件）**：`subchat_open` handler 在 server 进程内发**业务事件** `subchat-opened{instance_id, session_id, parent_session_id, title}`（server 进程可发 MQ，先例 `ask_user → session-ask`）→ 前端据此自动开窗。

**为何不借 `session-new`**（订正 2026-10-15）：`session-new` 是**通用会话事件**，payload 只有 `{instance_id, session_id}`（`61-消息一览.md:380`）——**既无 `kind`**，又会让"是否该开窗"的判定依赖"事件是否到达所有窗口"这种与业务无关的偶发事实。子聊天是业务概念，**该有自己的事件**（§5.2 消息族）。

**归属判定天然成立**：`subchat-opened` 自带 `parent_session_id` → 前端只需比较"本窗口绑定会话 == `parent_session_id`"，不匹配则忽略。**不再需要**任何针对通用事件的额外前置。

> 好处：① 不必给 `session-new` 加 `kind`（不欠 F-1/F-2 那笔债）；② 天然继承 I-1 判定与「主窗当前会话不得开窗」守卫（后端直开窗会绕过该守卫）；③ 现成先例：`DslStepsPanel.vue:154-160` 已实现「为子会话手动开窗」，本方案只是把「手点」变成「按事件自动」。

> **已知代价（已接受）**：自动开窗走 `gui.window.open-chat`，**同步建窗**会阻塞调用窗口（父会话窗口）的 UI 线程约 **0.7~1.4s**（`registry.go:80-86`）。**已裁决保留同步**（D27）——异步化需配套新增完成事件，收益不抵代价。

#### 3.4.2 `subchat_finish`

| 项 | 取值 |
|---|---|
| `category` | `server` |
| `_meta.async` | `never` |
| 入参 | 无（或仅 `note`，用于窗口内提示文案） |
| 返回 | `{ok}` |
| 副作用 | 会话 `lifecycle` 转 **`ready`** + 发 **`subchat-state`** + **点亮**该单聊窗口内**常驻**的「结束」按钮（**建议态**：不关窗、不回流、**不等于结束**） |

#### 3.4.3 结果回流：**不回流**（只切会话）

收口后**主会话完全不动**——不写消息、不起轮、不改任何历史。仅**回切窗口**。

**已知代价（认账）**：主 agent 派发了单聊，但**永远拿不到结果**，只能由用户在主会话里转述。本方案的定位是「**单聊产物给人看，不给主 agent 消费**」；若将来需要回流，须另立方案（见 §3.4.3 备注）。

> 备注（为何不采用「回填工具消息」）：
> ① `subchat_open` 是同步工具，结果返回即 `completed`，留成非终态会被启动清理标 `interrupted`；
> ② 已完成 turn 里的工具结果是**终态不可变**（`finishOnce` 保证），事后改写会破坏快照（`snapshot`）与预存 token（`turn_tokens`）的一致性。

#### 3.4.4 状态承载：会话行（**子会话域，不进任务树**）

单聊状态**由会话行自身承载**，**不建任务节点、不并入任务树**（用户口径 2026-10-15：*「它属于子会话」「和现在的任务不能重叠」*）。

**现状事实（据此说明为何不能复用任务树）**：

| 事实 | 出处 |
|---|---|
| **子会话现在恰恰寄生在任务树里**：llm 子会话落库时按 `kind` 派生 `node_type = llm → session`，任务树的 `session` 节点就是它 | `src/lib/task/task.go:43-49` |
| `subsession-changed` 不是独立子会话域的事件，而是**任务树视图**里"选中 session 节点"的本地事件 | `views/tasks/SessionTree.vue:123-131` |
| `data-session-list` **明确只返回顶层会话**（子会话拿不到） | `src/lib/data/facade/session.go:22,46` |

**结论**：做「独立子会话管理」必须**有子会话域自己的查询能力**——本方案以**业务消息 `subchat-list`** 落地（§5.2）。

**做法（最小路径）**：

1. 会话行扩展承载状态：`kind`（`sub_chat`；`sub_session` = 现行子会话，见 §3.2）、`lifecycle`（**三态**：`chatting / ready / finished`）——与 §3.2 固定参数同批；
2. 清单：发**业务消息 `subchat-list{parent_id}`**（§5.2）→ 返回该父会话的子聊天；**不改** `data-session-list`（它继续"只看顶层"）；
3. 状态变更通知：由 **`subchat-opened`**（新增）/ **`subchat-state`**（状态变化）推送，+ `gui.window.closed` 触发刷新。

**可见性判据**（驱动 §3.4.5 的状态条内容）：

```text
列出  ⟸ lifecycle ∈ {chatting, ready}
不列  ⟸ lifecycle == finished
```

> 边界（**已裁决** D39）：任务树现有的 llm 子会话节点（`sub_session`）**保持不动**；单聊（`sub_chat`）**不进任务树**。两类由 `kind` 分流，各走各的视图。

#### 3.4.5 入口形态：「进行中子聊天」状态条

**入口不是"原会话的子会话管理"，而是一条独立的状态提示**——用户口径 2026-10-15：*「这个是子聊天，和原来会话无关」*。

| 项 | 结论 |
|---|---|
| 位置 | **对话窗口的输入框上方**（主窗口与对话窗口同为 chat 面板），**常驻**（`ChatPanel.vue`） |
| 形态 | **默认折叠为一条**（占位条：「**N 个子聊天进行中**」，**淡色**〔淡粉/淡蓝，走主题 token〕以区别于常规 UI —— 用户至少能看出"有这么一条"）；**点击展开** → 列表**最多显示 15 条**，超出部分**可滚动**；展开后每条 = 「**正在** <`purpose`>」+「**继续**」+「**强制结束**」 |
| **范围** | **按父会话过滤**——`kind == sub_chat` **且** `parent_id == 当前窗口绑定的会话`，且 `lifecycle ∈ {chatting, ready}` |
| 自指 | 按 `parent_id` 过滤**天然排除自身**（当前窗口绑定的会话不可能是自己的父）——**无需额外排除逻辑** |
| 点击行为 | `gui.window.open-chat{session_id}`——**未打开则建窗、已打开则前置**（`bringTop`）。幂等与前置均为既有能力（`registry.go:86-153` · `window.go:395-400`） |
| 「**强制结束**」 | 发 `subchat-finish{session_id}`（与窗口内「结束」**同一条消息**）→ 该子聊天转 `finished`、状态条移除；**不打开窗口**（D31） |
| 数据来源 | **`subchat-list{parent_id}`**（业务消息，取代 `data-session-list` 加参），返回**全部**子聊天 `{session_id, purpose, title, lifecycle}`；状态条**自行过滤** `lifecycle ∈ {chatting, ready}`。**不需要 `gui.window.list` 预判"已开"**——`open-chat` 本身幂等（同 session → 激活） |
| 刷新 | **`subchat-opened`**（新增）/ **`subchat-state`**（状态变化）/ `gui.window.closed`（关窗）/ `data-session-title-changed`（标题变化） |
| 状态文案 | 三态映射：`chatting` = 「**正在** <`purpose`>」/ `ready` = 「<`purpose`> · 可以结束了」/ `finished` = 不显示——**自建轻量映射**，不复用任务 8 态。**文案来源 = `purpose`**（gateway 注入的 `tool_call_display_name`，§5.4），**不是**自动摘要标题（摘要会变、可能很长） |

**为何不复用任务层**：复用会让单聊与「**任务**」概念重叠（`node_type` 再塞一个值），而用户已明确「它属于子会话」「和任务不能重叠」，并预告将来还有独立的 **job 管理**——把不同执行物都塞进任务树只会让其语义继续膨胀。故子会话走**自己的域**。

> **视图边界（已定）**：单聊出现在**状态条**（未结束 · 本会话窗口内）与**会话列表**（挂在父会话行下 · **含已结束**，见 §3.4.6）；**不出现在任务面板**（任务面板继续只管既有任务与 llm 子会话节点）。
> **`parent_id` 保留**，承担两处技术关联：① 状态条**过滤依据**（本节）；② 关窗后**回切原会话**依据（§3.8 F5）。

#### 3.4.6 回看入口：会话列表里「挂在父会话下」

**入口（已定 2026-10-15）**：**会话列表**中，每个主会话行下挂它的**子聊天**（子节点）；点击子节点 → **打开对话窗口**（`gui.window.open-chat{session_id}`）查看历史。

> **只挂 `kind ∈ {sub_chat, group_chat}`**（子聊天 / 群聊）：`dsl_run` 的 `LLM` 步骤派生的**子会话**（`sub_session`）不进会话列表——它们仍在**任务执行树**里（T7 不动）。两者是不同业务物，走不同视图。

**三种生命周期的呈现**：

| `lifecycle` | 状态条（本会话窗口内） | 会话列表（父会话行下） | 点击打开后 |
|---|---|---|---|
| `chatting` / `ready` | **显示** | 显示 | **可继续**对话 |
| `finished` | 不显示 | **仍显示**（即回看入口） | **只读** —— **不显示输入框** |

**数据来源**：`subchat-list{parent_id}` 返回该父会话的**全部**子聊天（**含 `finished`**）——状态条与会话列表**各取所需、前端过滤**，服务端不必分两次查。会话列表**展开主会话时懒加载**。

**为何放会话列表**：

- 状态条是「**正在进行的**」视图，天然只装非终态；把已结束塞进去会让它的语义变浑；
- 工具卡片在消息流里、会滚出视口，回头翻历史很费劲；
- 会话列表本就是"**按会话找东西**"的地方，子聊天挂在父会话下最合直觉。

**与既有契约的关系**：`data-session-list` **仍是"只返回顶层会话"**（`src/lib/data/facade/session.go:22,46`）——本方案**不改它**，而是用新的 `subchat-list` 挂子节点。

**只读规则**：`finished` 的子聊天窗口**不显示输入框**（只能看历史）。理由：`finished` 是用户拍板的终态，若还能接着聊就等于"悄悄复活"（D25 已定不区分正常/强制 → 终态必须稳定）。

> **一个连带的窗口行为（已定）**：任何路径进入 `finished` 时，若该子聊天窗口**正开着** → 立即**变只读**。
> 差别仅在"离开"动作上：**窗口内**点「结束」= 变只读 **+ 自关 + 回切**（F5，用户本就要走）；**状态条**点「强制结束」= 只变只读（用户在主窗口，不打扰）。

#### 3.4.7 启动提醒：「未结束子聊天」对话框

**触发（D38，2026-10-15 定）**：**打开 exe、主窗口就绪后判断一次**——若存在未结束的子聊天（`lifecycle ∈ {chatting, ready}`）→ 弹对话框。

> **不做空闲提醒**（原 T3 备选，已废除）：启动对话框是"**一次性、让人当场做决定**"，优于挂在角落里没人看的常驻提示。

| 元素 | 内容 |
|---|---|
| 标题 | 「有 N 个子聊天未结束」 |
| 列表 | 每条 = `purpose` + **所属父会话**（标题）+ 状态（进行中 / 待确认结束） |
| **点击一条** | **打开该子聊天窗口**（`gui.window.open-chat`）→ 对话框关闭 |
| 底部提示文本 | 「其余可在**会话列表**中、对应会话下找到」→ 引导用户后续去导航 |

**范围是全局的**：启动时用户可能在任何会话，故此处列**所有会话下**的未结束子聊天（数据形态见 §3.4.4 的 `subchat-list` **不带 `parent_id`** 调用）。

**不提供**：

- ~~「全部打开」~~ → **一次只开一个**，天然**绕开 5 窗口上限**（无需为它定异常行为）
- ~~「终止」~~ → 用户想终止，就去**各自会话**里点「结束」

**每次启动都判断**（不记"已提醒过"状态 → **无需新增存储**）。

### 3.5 收口机制

**取消后台裁决器**。理由（用户口径 2026-10-15）：

> 主 agent 的判断没什么意义——**除非两个 agent 使用不同模型**。同模型下让主 agent 复核 = 自己复核自己。

于是收口没有任何后台 LLM 调用：

| 段 | 谁 | 做什么 |
|---|---|---|
| ① 建议 | **子 agent** | 轮末判断「我认为已完成」→ 调 `subchat_finish` → **点亮**常驻的「结束」按钮 |
| ② 拍板 | **用户** | 点击「结束」→ 关窗 + 回切原 session（§3.4.3 不回流） |

> **`ready` 可逆（写入方已定）**：`ready` 只是"最近一轮的建议"——**子会话新一轮开始处**，若 `lifecycle == ready` 则置回 `chatting`（写入方 = 轮次启动路径）。只有用户点「结束」才进 `finished`。

**「结束」按钮常驻可点**（非终态即可见），且**有两个入口**：

- **窗口内**：「结束」——人已在窗口里、看过产出
- **状态条上**：「**强制结束**」——人不在窗口里，直接收口（§3.4.5）

理由：

- 「一直不结束」必须有兜底入口——**用户随时可强制收口**。只放窗口内就做不到"随时"：窗口关着、或**撞满 5 个窗口上限打不开**时都够不着（见 E5）；
- 若"强制"要过 LLM（让子 agent 去调工具），**不可靠**（模型可能不调，或调了别的东西）。人已决定，就不必再绕一层模型；
- 于是：**两个入口写同一条 `subchat-finish`**；子 agent 的自报只是"建议"，不负责让按钮出现。

**可选档（保留条件）**：仅当**子会话 LLM ≠ 主 agent LLM** 时，才追加「主 agent 复核」一道——此时判断才有独立性。默认路径不含复核。

**兜底**：空闲超时只在状态条上加**提醒**（**不是状态**，不改 `lifecycle`），**不强制收口**，防用户忘了点。

### 3.6 产出与完成判定

**没有需要被喂料的裁决器**，所以「产出读取」问题**自然消解**：

| 项 | 结论 |
|---|---|
| 产出在哪 | ① 单聊窗口内的会话消息（用户直接看得到）；② 落盘文件（如 `docs/xx-设计.md`） |
| 谁判完成 | **子 agent 建议 + 用户拍板**（§3.5） |
| 大项目 / 长周期（如设计一周、文件多而大） | **不需要特殊机制**——用户看着产出自己决定何时点「结束」 |
| 失败重试 | **不适用**——没有后台裁决调用 |

> 代价要认账：**质量把关落在用户身上**。这是取消裁决器的真实成本，也是本方案接受它的前提（同模型复核无增益）。

### 3.7 生命周期与续聊

**关窗 ≠ 结束**。生命周期是**子会话域自己的状态机，只有三态**（**不复用任务 8 态**，见 §3.4.4）：

| `lifecycle` | 含义 | 触发 | 状态条 | 「结束」按钮 |
|---|---|---|---|---|
| **`chatting`** | 进行中 | `subchat_open` 建会话 | **显示**「正在 <标题>」 | 常驻可点 |
| **`ready`** | 子 agent 判断**该结束了**（建议态，**非终态**） | 子 agent 调 `subchat_finish` | 显示 + **点亮/高亮** | **点亮** |
| **`finished`** | 已结束 | **用户点「结束」** | 消失 | — |

> **`finished` 不是"消失"，是"转到会话列表"**：状态条不再列它，但会话列表里仍挂着它，点开可**只读回看**（§3.4.6）。

**只要三态的原因**：

- **窗口开/关不是状态** —— 「关窗暂离」不改变 `lifecycle`（仍是 `chatting`），故不需要 `open` / `detached`，也**不需要关窗上报**（窗口是否存在由前端自行感知）。
- **正常完成与强制中止不区分** —— 用户点「结束」即 `finished`，无论子 agent 报过没有。
- **进程退出/崩溃没有独立态** —— 重启后仍是 `chatting`，状态条照常显示、可继续，不存在"被中断"的诈尸态。

**`ready` 可逆**：它表示"最近一轮子 agent 认为可以结束"，**不是终态**；用户若继续聊了一轮，新一轮开始即回到 `chatting`。**只有用户点「结束」才进 `finished`**。

**续聊入口 = chat 窗口输入框上方的「正在 <子聊天>」状态条**（§3.4.5）：列出**当前会话的**未结束子聊天 → 点击「继续」= `gui.window.open-chat{session_id}`（**未开则建窗，已开则前置**）→ 回到**同一 session** 继续。

> 工具卡片**不再承载**状态化按钮：卡片在历史里、会滚出视口，且会造成「两处状态不一致」。状态统一由状态条这一个入口表达。

#### 3.9.1 一次完整旅程

| # | 用户做什么 | 用户看到什么 | 代码做什么 |

| 5 | （子 agent 自报） | 「**结束**」按钮**点亮**、状态条高亮，提示"可以结束了" | 子 agent 轮末调 **`subchat_finish`**（server 域）→ handler 写会话 `lifecycle = ready` + 发 **`subchat-state`** → 子聊天窗口按钮与父窗口状态条同步点亮 |
| 6 | 点「结束」 | 子聊天窗口关闭 → 主窗口**切回原会话** → 状态条消失 | 前端发 **`subchat-finish{session_id}`**（服务端写 `lifecycle = finished`）→ 本窗口自关（`gui.window.status{close}`，**执行对象恒为来源窗口**）→ 宿主广播 `gui.window.closed` → 主窗口按**状态条列表**判定归属后**回切**原 session → 状态条因 `finished` **不再列出**而消失 |
| 7 | 强砍（它没自报也点） | 与第 6 步**完全一样** | **同一个入口**，不经 LLM；`finished` **不区分**正常完成 / 强制中止（D25） |
| 8 | 忘了它 / 关了应用 | 重启后状态条**照常挂着**，点「继续」即可接着聊 | `lifecycle` 持久化在**会话行**，重启后仍 `chatting`（**无 `interrupted` 诈尸态**）；前端启动后发 `subchat-list` 重建状态条 |

#### 3.9.2 屏幕元素与数据来源

| 位置 | 元素 | 出现条件 | 数据来源 |
|---|---|---|---|
| 主会话窗口 · **输入框上方** | 「正在 <标题>」+「继续」+「强制结束」**状态条** | 该会话有 `lifecycle ∈ {chatting, ready}` 的子聊天 | `subchat-list{parent_id}` |
| 主会话窗口 · 消息流 | 「已开启子聊天 <标题>」 | `subchat_open` 调用后一条 | 工具结果（**终态**，不再改写） |
| 子聊天窗口 · 标题栏 | 子聊天名字 | — | 会话行 `title` |
| 子聊天窗口 · 头部 | 无场景切换入口 | `kind == sub_chat` | 前端 F1 |
| 子聊天窗口 · 底部 | 「**结束**」按钮 | **常驻**；`lifecycle == ready` 时点亮 | `subchat-state`（F7）/ 用户点击 |
| **会话列表 · 主会话行下** | 子聊天**子节点** | `kind == sub_chat` 的子聊天（**含 `finished`**）；展开时懒加载 | `subchat-list{parent_id}`（§3.4.6，F8） |

> **两个易漏点**：
> ① 状态条**按发起它的那个会话**显示——A 会话开的子聊天，切到 B 会话**看不到**（D21）；
> ② **「继续」是唯一回头入口**——窗口关掉后，主会话那条「已开启」只是历史记录、不是按钮；`finished` 后状态条消失，**该子聊天在 UI 上即无入口**（历史仍保留）。是否要给"已结束"留回看入口，见 **§10 Q4**。

## 4. 规则与约定

| 项 | 结论 | 理由 |
|---|---|---|
| 工具形态 | 必须是 `category=server` 域工具 | executor 是子进程，无法发 MQ；先例 `ask_user` → `session-ask` |
| 工具异步性 | 两个工具均 `async: never` | `subchat_open` 同步返回，主轮**不挂起**（与 `dsl_run` 的 `always` 相反） |
| 工具结果 | 返回即定稿（`completed`），**不再改写** | 工具结果属终态；启动清理会把非终态 pair 标 `interrupted` |
| 关窗语义 | = 用户**暂离**，**状态不变**（仍 `chatting`），非结束 | 用户明确口径（2026-10-15） |
| 收口裁决权 | **子 agent 建议 + 用户拍板** | 同模型下主 agent 复核无独立性（2026-10-15） |
| 强制收口 | **用户随时可点「结束」**，不经 LLM | 子 agent 可能永不报；过 LLM 不可靠 |
| 复核（可选档） | 仅当**子会话 LLM ≠ 主 agent LLM** 时启用 | 判错才有独立性 |
| **结果回流** | **不回流**，主会话完全不动 | 只回切窗口；单聊产物给人看（§3.4.3） |
| 状态标识 | **会话行 `lifecycle` 三态**（`chatting / ready / finished`，子会话域）；**不进任务树** | 「它属于子会话」「和任务不能重叠」；任务树语义不再膨胀 |
| 关窗定向 | 前端自关（session_id 作定向键） | 后端够不着宿主 hwnd |
| 回切原会话 | 宿主广播 `gui.window.closed` → 主窗口按状态条列表判定归属后切回 | 复用已有广播 |
| 固定参数存放 | **会话行**，非 URL | URL 可改、重启丢、后端读不到、其他消费者看不到 |
| 参数优先级 | 会话固定参数 > 请求参数 | 「固定参数」的语义落点 |

### 5.2 消息面：新增 `subchat-*` **业务消息族**（按业务，不借数据面）

**口径（2026-10-15 用户）**：消息设计有「**按业务**」与「**按数据**」两种模式，各有千秋；**本方案取「按业务」** → 子聊天是业务概念，**用业务消息表达**，不拿通用数据动词（`data-session-*`）去凑。

**消息族（新增 4 条；须按 `61-消息一览 §0` 确认 → §10 Q1）**：

| 消息 | 方向 | 载荷 | 用途 | 取代掉 |
|---|---|---|---|---|
| **`subchat-opened`** | 服务端 → 前端 | `{instance_id, session_id, parent_session_id, title}` | 父窗口自动开窗 | 原拟「`session-new` 加 `kind`」+ 父窗口守卫 |
| **`subchat-list`** | 前端 → 服务端 | `{parent_id?}`（**可选**） | `parent_id` 有值 → 该父会话的**全部**子聊天（**含 `finished`**，前端过滤）；**缺省 → 全局**未结束子聊天（启动提醒用，§3.4.7）。每条含 `session_id` / `purpose` / `title` / `lifecycle` / `parent_session_id` / 父会话标题 | 原拟「`data-session-list` 加参」 |
| **`subchat-finish`** | 前端 → 服务端 | `{session_id}` | 用户拍板 → `lifecycle=finished` | 原拟「`data-session-*` 加动作」 |
| **`subchat-state`** | 服务端 → 前端 | `{session_id, parent_session_id, lifecycle}` | 状态实时同步（`ready` 点亮 / `finished` 消失） | 原 T12「接受非实时」妥协 |

**为何优于借数据面**：

- `subchat-opened` **自带 `parent_session_id`** → 归属判定退化为"比较两个字段"，不再依赖"事件到达所有窗口"这种与业务无关的偶发事实（**不再欠 F-1/F-2 的债**）；
- 与既有业务消息（`llm-start` / `task-stop` / `ask-user`）同族，语义直白；
- **全部是"新增"而非"改既有契约"**，风险更低。

**落库字段（非消息面）**：`sessions` 行仍须加 `kind`（`""` / `sub_session` / `sub_chat`）/ `lifecycle` / `agent` / `scenario_id` / `llm`（**无 `inject`**：注入层代码内建，§3.3 · D37）。

**其余链路继续复用既有消息**：关窗自关与回切走 `gui.window.closed`；**关窗（暂离）不上报**（状态不变）。

### 5.4 `purpose` 的来源与流转

**来源**：**复用 gateway 注入的 `tool_call_display_name`**（[registry.go:65-67](file:///e:/BizWorks/chonkpilot/src/lib/gateway/gateway/registry.go#L65-L67)：给每个工具注入、设为**必填**、≤20 字符、仅 UI 展示）——**`subchat_open` 不自己声明任何展示参数**。

**三个名字指同一个值**（既有约定，沿用不发明）：

| 层面 | 名字 |
|---|---|
| 工具**参数**名（gateway 注入） | `tool_call_display_name` |
| **消息面字段**名（`tasks.*` 事件、`subchat-opened`） | `purpose` |
| 任务节点**字段**名 | `Purpose` |

**取法：走注入通道，不走 args** —— args 里的该键会被 `doCall` 统一剥离（[mcpgateway.go:856-858](file:///e:/BizWorks/chonkpilot/src/lib/gateway/gateway/mcpgateway.go#L856-L858)），**handler 永远读不到**；应经注入通道传给工具（进程内 `context.Context` / 域工具 `payload["context"]` / 进程外 `CHONKPILOT_*`）。

**流转**：`subchat_open` 处理逻辑读注入的 purpose → 落 `sessions.purpose` → 随 `subchat-opened` 下发 → 状态条 / 会话列表子节点 / 窗口标题显示。

> ⚠️ **前置依赖：C1**（该值**当前未进入任何注入通道**，需先补）——见 §11.2。

### 5.5 术语与命名对照（**防混**）

> 本项目里 **两个不同层次的东西都叫 "session"**，极易混——下表钉死。

| 名字 | 所属层次 | 含义 |
|---|---|---|
| `sessions.kind = ""` | **会话实体** | 普通顶层会话 |
| `sessions.kind = sub_session` | **会话实体** | `dsl_run` 的 `LLM` 步骤派生的**子会话**（现行路径） |
| `sessions.kind = sub_chat` | **会话实体** | **子聊天**（本方案，`subchat_open` 创建） |
| `tasktree.node_type = "session"` | **树节点**（由 `kind` 派生） | **LLM 步骤节点**——**不是"会话实体"**；其 `session_id` 字段只是**附属身份**（供切会话/开窗） |
| `tasktree.node_type = "tool"` | 树节点（派生） | 工具调用节点（`kind` ≠ llm） |
| `tasktree.shadow = true` | 树节点 | **不进树** ← **唯一真正的"筛选"标记** |
| `tasktree.top_session` | 树节点 | 树**按主会话切分**的组织/过滤维度 |

**写法约定**（各自遵守既有约定，不强行拉齐）：

| 层面 | 写法 | 例 |
|---|---|---|
| **消息族**（topic） | 连写 + **连字符** | `subchat-opened` / `subchat-list` |
| **工具名** | 连写 + **下划线** | `subchat_open` / `subchat_finish` |
| **数据值**（`kind`） | **下划线** | `sub_chat` / `sub_session` |
| 域概念（中文） | — | 「子聊天」「子会话」 |

### 11.3 C2 · 单聊不再需要「派发层分支」（因 C1 改法而撤销）
