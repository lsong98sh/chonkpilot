## 1. 问题与目标

### 1.1 要解决的问题

当前一轮对话（turn）是**单 goroutine 串行状态机**：`loop()` 与 `chatOnce()` 在同一协程内执行，`chatOnce` 通过递归完成"LLM → 工具 → 结果回填 → 再 LLM"的循环（`src/lib/llm/server/turn.go` 的 `loop` / `chatOnce`）。由此产生两个阻塞点：

1. **同步工具会真实阻塞 loop**（`gc.Call` 同步派发）；即使异步工具会让出，前端在忙碌时仍走本地发送队列（`useSendQueue.js`），`llm-complete` 后才 drain。
2. **递归链展开期间 loop 回不到 `select`**，`tc.in` 里的消息无法被消费。

结果：用户无法在"工具正在跑"时插入一段对话。

### 1.2 目标（可验收）

| # | 目标 |
|---|---|
| G1 | 工具执行期间（`toolPending`）允许用户插入对话，且插入内容**优先被处理** |
| G2 | reasoning / text / tool-call 流式输出期间**禁止插入**（消息入 inbox，不丢弃、不并发发请求） |
| G3 | 插入的对话自身可继续调用工具（嵌套），嵌套期间主轮保持挂起 |
| G4 | 插入结束后，若原工具**未完成** → 主轮进入等待；完成后再统一续轮 |
| G5 | 插入结束后，若原工具**已完成** → 主轮立即续轮 |
| G6 | 等待期间可**再次插入**，不阻塞、不乱序、不重复续轮 |
| G7 | 所有发送先落 **prjusr 级 inbox**，实际插入 / 下一轮时才写 `messages`；重启可拉回未消费项 |
| G8 | inbox 支持两种类型（`insert` / `next_turn`）并可互转；原前端发送队列并入 inbox |
| G9 | 消息面：inbox 的写 / 读 / 撤回 / 提升**需新增 `llm-inbox-add/list/discard/promote`**（**61 冻结，实施前须确认**）；其余主题复用 |

### 1.3 非目标

- **不默认**改消息面；但 inbox 的写 / 读 / 撤回 / 提升必须新增 `llm-inbox-*`（见 §5.1），除此之外不改任何既有主题与 payload。
- **不做**多客户端并发插话（v1 单窗口单用户）。
- **不做**"并行分支插入"（v1 为栈，非树；树结构见 §3.2 的升级路径）。
- **不改**同步工具的既有语义之外的执行结果（只改"是否转异步"的调度方式）。
- ~~**不含**子会话 / 群聊的插话（v1 仅主会话）。~~ **〔2026-10-17 裁决〕** 改为**全形态支持**（主会话 / 子会话 / 群聊）——插话是聊天基本能力；随之**必须废止**既有「非主会话强制工具同步」（A5，`turnCtx.forceSyncTools`），否则非主会话插话不成立（见 §6）。

## 2. 总体方案：帧栈（Frame Stack）

引入**帧（frame）**概念：一个 frame = 一次进行中的 LLM 轮次及其工具等待集合。

- 主轮 = `frames[0]`（main frame）；
- 用户在工具等待期插入 → **push** 一个新 frame（insert frame）；
- 插入帧自己调工具 → 在**该帧内**等待（不新开帧）；
- 插入帧结束 → **pop**；回到新栈顶，按"双条件 AND 门"决定是否恢复。

```
turnCtx
└── frames []*frame            // LIFO 栈；frames[0] = main
     ├── [2] insert B          ← 栈顶（唯一可发 LLM 请求）
     ├── [1] insert A
     └── [0] main（其工具 C1 可在任意时刻完成）
```

**为什么是 LIFO 而不是 FIFO**：插话天然是嵌套关系（A 运行中插入 B，B 处理完应回到 A，而不是回到主轮）。FIFO 会丢失"父帧"信息，无法表达场景 4/5 的归位。

**为什么 v1 不用树**：单窗口单用户下，插入序列退化为一条链。`frame.parent` 指针已预留；将来若需要"多窗口并发插话 / 用户选择性结束某一支"，只需把调度器从"只看栈顶"改为"择一个可运行叶子"，帧结构不变。

**执行模型（前提）**：工具必须**强制异步**——派发即返回 `task_id`，主循环立即让出、回到 `loop` 的 `select`。所谓"后端继续执行、完成后通知 LLM"与"强制异步"是**同一件事的两面**：执行在 gateway 执行池继续，**通知 = 回执驱动的一次续轮请求**，不是独立消息。

唯一需要单独决策的是"插入轮上下文是否包含这个未完成的 tool-call"——结论是**保留 + 占位，不剔除**（见 §3.8）。

## 3. 详细设计

### 3.1 六个场景的状态映射（S1 / S2 / S3 / S4 / S4.5 / S5）

| 场景 | 用户描述 | 栈状态判定 | 处理 | 是否发 LLM 请求 |
|---|---|---|---|---|
| **S1** | 工具执行时插入 | `top.phase == toolPending` | **push** 插入帧，立即跑插入轮 | 是（插入轮） |
| **S2** | reasoning / text / tool-call 输出时插入 | `top.phase == streaming` | **拒绝插入**，消息入 inbox（`type=next_turn`）；本轮结束再消费，或显式提升为 `insert` | 否（等当前流结束） |
| **S3** | 插入后 LLM 返回又调工具 | 插入帧 `phase → toolPending` | 在**插入帧内**派发工具（嵌套），主轮继续挂起 | 是（工具回执后续插入轮） |
| **S4** | 插入结束、原工具仍在跑 | pop 后 `outer.pending ≠ ∅` | 外层 `phase = awaitJoin`，**不触发 LLM**；等回执 | 否（直到回执） |
| **S4.5** | 插入结束、原工具仍未跑完，**又要插入** | `top == outer` ∧ `outer.phase == awaitJoin` ∧ `outer.pending ≠ ∅` | push 新插入帧；主帧**保持在 `awaitJoin`**（可重入稳定态，可循环 N 次） | 是（新插入轮） |
| **S5** | 插入结束、原工具已跑完 | pop 后 `outer.pending == ∅` | 外层**立即 resume**（喂工具结果续轮） | 是（主轮续轮） |

### 3.2 帧结构与栈不变式

```text
frame
├─ id
├─ kind      : main | insert
├─ phase     : streaming | toolPending | awaitJoin | done
├─ pending   : map[task_id]pendingTool     // 本帧的异步工具
├─ inflight  : map[tool_call_id]time.Time  // 本帧的 ask_user / 子作业
├─ inboxRef  : *inboxRef                  // 指向 prjusr inbox 中本帧待消费项（不持有消息本体）
├─ parent    : *frame                      // 预留：升级为树
├─ resuming  : bool                        // resume 幂等标志
└─ resumeNote: string                      // 恢复时临时注入（不落库）
```

**栈不变式（实现与测试的硬判据）**

| # | 不变式 |
|---|---|
| I1 | **只有栈顶帧可以发起 LLM 请求**（绝对串行，杜绝上下文竞争） |
| I2 | 只有 `top.phase == toolPending` 时允许 push |
| I3 | `top.phase == streaming` 时禁止 push，消息入 inbox（`next_turn`），**不丢** |
| I4 | 帧 `done` = 无 `pending` ∧ 无 `inflight` ∧ 最后一次 LLM 输出不含 tool_calls |
| I5 | 帧出栈后，由 `maybeResumeTop()` 统一判定是否恢复（唯一入口） |
| I6 | `resume` 幂等（`resuming` 标志 + pending 已清空的双重判定） |
| I7 | **所有 phase 迁移只在 loop goroutine 内发生**，不加锁；锁只保护"其他协程写入的登记表" |
| I8 | `session-complete` **只在整个栈清空（全部帧 done）时发一次**；插入帧运行 / 等待期间主帧不得终结 |

### 3.3 统一入口：inbox →（实际插入时）→ `messages`

**所有发送都先落 prjusr 级 inbox，再在"实际插入 / 下一轮开始"时写 `messages`。** 不再分"直接落库"与"内存缓冲"两条路径。

| 当前 phase | 收到用户发送（`llm-inbox-add`） | inbox 类型 | 后续 |
|---|---|---|---|
| `toolPending` / `awaitJoin` | 允许立即插入 | `insert` | 立刻消费 → 落 `messages` → push 插入帧 |
| `streaming` | **不打断当前流** | `next_turn` | 等本轮结束；期间若进入可插入相位，可**提升为 `insert`** |
| `done / 无 turn` | 非插话 | `next_turn` | **立即消费**：以 item 携带的参数起新一轮 |

**为什么"先 inbox 后 message"**

- 统一路径：消除"S1 直接落库 / S2 只能缓冲"的分裂；
- 落 `messages` 的时刻 = **位置已确定的时刻**（工具 `running` 行已落库，或新一轮已开始），天然不破坏 `assistant(tool_calls) → tool` 的相邻不变式；
- 崩溃时消息仍在 inbox，**不丢**（符合 [71 §3.3](../spec/70-conventions/71-编程规范.md)）。

**消费与合并（Q2：合并）**

- 同一批被消费的多条（同一 turn / 同一类型）**合并为一次 LLM 请求**（携带多条 `user` 消息）；落 `messages` 仍逐条保留，前端展示不合并；
- `insert` 项：在 `toolPending` / `awaitJoin` 时**逐条即时消费**（用户期望即时响应），不做微批延迟；
- `next_turn` 项：本轮结束后按到达顺序消费；若本轮被中断，则随重启流程处理（§6.2.3）。

**类型互转**

- `next_turn → insert`：当 turn 进入 `toolPending` / `awaitJoin`，允许**显式"立刻插入"**（转换属用户意图变更，默认不自动提升）；
- `insert → next_turn`：**目标 turn 在消费前已结束 / 中断**（竞态或重启）→ 自动降级，随后按 `next_turn` 规则消费。

**前端配套**

- 输入框不再因"忙碌"禁用；**发送（含空闲首条）即入 inbox**，由服务端按 phase 分类；无运行轮 → 立即消费起新一轮（turn id 由服务端分配，前端经既有 `turn-start` 回填）；
- 队列指示器展示 inbox 的 `pending` 项（含类型与目标轮），支持撤回 / 删除 / "立刻插入"。

### 3.4 插入帧内的工具调用（S3）

插入帧发起的 LLM 请求同样可以返回 tool_calls。处理方式：

1. 工具仍走 gateway 派发，但 `pending` 登记必须带 **frameID**（`frameOfTask[task_id] = frame`）；
2. 回执（`mcp-tasks-report` → `onGatewayTaskDone` → `onAsyncDone`）按 frameID **归帧**；
3. 该帧 `pending` 清空后走同一 `maybeResumeTop()`；
4. 主轮的 pending 不受影响（各帧 pending 独立）。

> 这是"递归"的正确落地形式：**递归语义保留，但递归由事件驱动、显式栈承载**，而不是 goroutine 栈。跨帧等待一律 `return` 回 `loop` 的 `select`，保证插话可消费。

### 3.5 汇合：双条件 AND 门（S4 / S5）

**核心结论：恢复不是"事件一到就触发"，而是两个条件的 AND。**

```text
resume(frame) 当且仅当：
  ① frame == top()                       // 所有插话都已出栈
  ② frame.pending == ∅ ∧ frame.inflight == ∅
```

两个触发点都调用同一个 `maybeResumeTop()`：

| 触发事件 | 来源 | 说明 |
|---|---|---|
| E1 插入帧出栈（pop） | 插入轮 `done` | S5 的分水岭：此时外层已空 → 立即续轮 |
| E2 外层工具回执 | `onAsyncDone` | S4 的分水岭：插入已结束 → 此刻才续轮 |
| E3 当前栈顶帧自身的工具回执 | `onAsyncDone` | S3：插入帧自己的 pending 清空 → 续该插入帧（不让位给外层） |

- **S4**：E1 先到 → 条件 ② 不满足 → 不恢复；E2 后到 → 两条件满足 → 恢复。
- **S5**：E2 先到（pending 已空，但帧不是栈顶）→ 不恢复；E1 后到 → 两条件满足 → 恢复。

这样"结果先到还是插话先结束"两种顺序都被同一条规则覆盖，**不需要两套分支**，也不会出现重复续轮。

#### S4.5：`awaitJoin` 是可重入的稳定态

`awaitJoin` 不是"一次性等待"，而是可以被插入**反复打断**的稳定状态：

```text
主帧 awaitJoin ──插入B──▶ 插入帧 B ──B 完成──▶ 主帧 awaitJoin（pending 仍非空）
      │                                              │
      │◀──────────── 再插入 C（可重复 N 次）───────────┘
      │
      └──────────── 工具回执（pending 清空）────────────▶ resume（转为 S5 结果）
```

三种到达顺序都必须正确：

| 顺序 | 事件序列 | 期望 |
|---|---|---|
| ① 回执晚于全部插入 | 插 B → B 完成 → 仍 `awaitJoin` → 插 C → C 完成 → C1 回执 | 主轮**只续一次**（在 C1 回执后） |
| ② 回执夹在插入中间 | 插 B → B 完成 → `awaitJoin` → 插 C → **C 运行中 C1 回执** → C 完成 | C1 回执时栈顶是 C → **不续主轮**；C 出栈后立即续主轮 |
| ③ 回执早于插入 | C1 回执已在 B 之前完成 | 主帧 pending 已空但非栈顶 → 等 B 出栈后立即续轮（即 S5） |

**关键约束**：回执只负责"清 `pending`"，**不直接触发续轮**；续轮永远由 `maybeResumeTop()` 在「栈顶 ∧ 无 pending」时发起。这条约束让 S4.5 的任意次重入都退化为同一个判定。

> 与 S3 的区别：**S3 是"插入帧自己还没跑完又插入"**（帧内嵌套，受 I2/I3 约束：插入帧在 `toolPending` 才可再插，`streaming` 期则入 inbox 等下一轮）；**S4.5 是"插入已结束、原工具还没跑完又插入"**（主帧在 `awaitJoin` 被重新打断）。


### 3.6 等待结束后"如何通知 LLM"

**先澄清一个语义**：这里的"通知"不是一条特殊 mq 消息，而是 **"把工具结果喂回 + 发起一次续轮请求"**。真正需要设计的是**触发时机**（§3.5）和**上下文语义**（本节）。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A 恢复即续轮 + 临时「续接说明」** | 工具结果按 `role=tool` 喂回；本次请求**前置一条不入库**的 system 说明，交代"等待期间发生过插话" | 语义清晰；不污染历史；可复用现有"指引只随请求携带、不落库"的做法（`msgs()` 已如此注入记忆/资产指引） | 每次恢复多一小段 system 文本 | **推荐** |
| B 把插话摘要塞进 tool result 附注 | 在工具结果里追加"期间用户插话…" | 无额外消息 | 污染工具结果载荷；前端工具卡片需解析；重放/压缩口径变复杂 | 不推荐 |
| C 纯靠历史自然顺序 | 不加任何说明 | 零改动 | 模型容易把插话的 assistant 回复误当成自己"未完成的输出"，出现重复回答/跑题 | 仅作兜底 |

**方案 A 的说明文案（示例，非最终定稿）**

```text
【插话续接】在你等待工具结果期间，用户插入了一段对话（见上方的 user/assistant 消息），
已按用户要求处理完毕。以下是该工具的真实结果，请继续完成原任务；不要重复调用该工具，
也不要重复回答已经回答过的插话内容。
```

实现要点：
- 说明只在该次请求的最前面注入，**不写入 `messages` 表、不进快照、不参与压缩**（与 `memoryGuide` / `assetGuide` 同口径）；
- 只要 `frame.hasInsertions == true` 就注入（**主帧与插入帧都适用**——嵌套插入同样会打断内层帧）；普通续轮零开销。

### 3.7 消息落库顺序不变式

既有机制：工具**发起即落 `running` 行**（`persistToolRunning`），终态**原地回填同一行**（`persistToolResult` 带 key）。由此得到线性历史：

```text
assistant(F, tool_calls=[C1])      ← F 的流结束时落库
tool(C1, running)                  ← F 派发 C1 时落库（位置固定）
user(M_A)                          ← 插入 A 落库
assistant(A, tool_calls=[C2])      ← 插入 A 落库
tool(C2, running)                  ← A 派发 C2 时落库
tool(C1, result)                   ← C1 回执：原地回填，位置仍在 assistant(F) 之后
tool(C2, result)                   ← C2 回执：原地回填
assistant(A, final)
```

**不变式**：`assistant(tool_calls)` 与其全部 `tool` 结果**始终相邻**（顺序不受插话影响），因此线性历史对 LLM 协议**始终合法**；插话内容自然落在两组工具交换之间。这是"不需要 fork/merge 上下文"的根本原因。

**`turn_id` 归属（硬约束）**：插入帧产生的全部消息（`user` / `assistant` / `tool`）一律写**主 turn 的 `turn_id`**，**不新建 turn**。`msgs()` 按 `turn_id` 读取，因此插入内容自然进入同一线性历史；`turns` 表仍只有一条记录，`session-complete` 仍只发一次。

### 3.8 上下文投影：运行中的工具不能是空串

现状：`ToolLLMContent` 在工具行**没有 `result` 段**时返回 `""`（`src/lib/data/internal/kernel/viewdata.go`）。这会让两类场景都给 LLM 一条**空 content 的 tool 消息**：

- 插入轮带上"运行中"的工具行（`running`，无 result）；
- 重启后「继续」带上"已中断"的工具行（`interrupted`，无 result —— `cleanupStaleToolPairs` 只改状态列，不补 result 段）。

**要求：投影必须按状态给出明确文案，不能是空串，也不能是裸 JSON。**

| `tool_call_status` | 投影给 LLM 的 content |
|---|---|
| `running` / `pending` | `（工具执行中，结果稍后返回）` |
| `interrupted` | `（工具已中断，未获得结果；如需重试请使用「重试」）` |
| `cancelled` | `（工具已取消）` |
| `failed` | 有结果用结果；无结果用 `（工具执行失败）` |
| `completed` | 有结果用结果；空结果用 `（工具执行完成，无文本输出）` |

落点：`MsgRowToChat` 把行级 `tool_call_status` 一并传给投影（`ToolLLMContent` 目前只接收 content 字符串，需扩参或改调用点）。**全局统一口径**优于仅对插入帧特判。

**是否干脆把未完成的 tool-call 从插入轮上下文中剔除？（结论：不剔除）**

| 方案 | 插入轮看到 | 优点 | 问题 |
|---|---|---|---|
| **保留 + 占位（推荐）** | `assistant(tool_calls)` + `tool("执行中…")` | 与落库历史一致；模型知道工具在跑，不会重复调用；两次请求前缀连续（KV cache 友好） | 需要 §3.8 的占位投影 |
| 剔除 | 只有插话前历史 + 插话 | 插入轮更"干净" | ① 同一 turn 出现两套上下文视图（插入轮看不到、恢复轮看得到）；② 模型不知道工具在跑 → 可能**重复调用**；③ 两次请求前缀不一致 → KV cache 失效；④ 与持久化历史不一致，不可复现 |

> 协议层面本来就不缺配对：`persistToolRunning` 在派发时就落了一条 `role=tool` 行（只是 `result` 段为空），所以不存在"assistant 有 tool_calls 但缺 tool 消息"的协议错误——只需要把**空投影**换成明确文案。

## 4. 规则与约定

| 项 | 结论 | 理由 |
|---|---|---|
| 插入准入 | 仅 `toolPending` / `awaitJoin` | 与 LLM 流式输出不并发，保证上下文串行 |
| streaming 期行为 | 消息入 inbox（`next_turn`），不丢、不并发发请求 | 对应场景 2「必须等待」 |
| 同一 turn 并发 LLM | **禁止**，只有栈顶帧可请求 | 避免 `hist` / `answer` / 落库顺序竞争 |
| 插入帧的工具归属 | 归插入帧，不归主帧 | 保证"谁的 pending 谁等" |
| 恢复判定 | 双条件 AND（栈顶 ∧ 本帧无 pending/inflight） | 一条规则同时覆盖场景 4 与场景 5 |
| `awaitJoin` 语义 | **可重入稳定态**，可被插入反复打断（S4.5） | 任意次重入都退化为同一判定 |
| 恢复幂等 | `resuming` 标志 + pending 复核 | 防"回执重复 / 两触发点同时命中"导致重复续轮 |
| 通知 LLM | 方案 A（续轮 + 临时续接说明） | 不污染历史，语义清晰 |
| 插入轮上下文 | **保留未完成 tool-call + "执行中"占位**，不剔除 | 避免重复调用 / 上下文双视图 / KV cache 失效 |
| **发送入口** | **先落 inbox，实际插入 / 下一轮时才写 `messages`**（含空闲首条） | 统一路径；落库位置确定，不破坏配对；崩溃不丢 |
| **inbox 类型** | `insert` / `next_turn`，可互转 | 覆盖"立即插入"与"等下一轮"两种用户意图 |
| **前端发送队列** | 并入 inbox（本地镜像 + prjusr 持久化） | 重启可拉回，不再依赖内存 |
| **插入消息 `turn_id`** | 一律写主 turn 的 `turn_id`，**不新建 turn** | `msgs()` 线性读取；`session-complete` 只发一次 |
| **inbox 上限** | 每会话 `pending` ≤ 50，超出拒绝并提示 | 防刷爆与背压 |
| **会话删除** | inbox 项**级联删除** | 不留孤儿 |
| **群聊插入归属** | 交给**该 turn 当前正在运行的 agent**，不重走群聊调度 | 避免插入被分给另一个 agent |
| 多条插入合并 | 同批消费的多条**合并为一轮**；`insert` 项即时消费 | 省 token 与即时响应的平衡 |
| 工具是否强制异步 | **全量强制**（含契约显式 `never`） | 这是插入能成立的前提 |
| 递归计数 | `maxToolIterations` 仍按 turn 累计；新增帧深上限 | 防止「插话 → 再插话」无限嵌套 |
| 崩溃恢复 | 帧栈**不重建**；inbox 拉回并显示「继续」；**不自动发送** | 状态收敛、输入不丢、不产生意外调用 |
| 取消语义 | `llm-cancel` = **全局终止**（所有帧 + 在飞工具），**不回到原任务** | 与现有语义一致；局部退出插话属新语义，见 §9 Q3-a |
| 作用域 | **全形态**（主会话 / 子会话 / 群聊） | 插话是聊天基本能力；需同步废止 A5（§6） |

## 5. 与既有机制的关系

### 5.1 消息面（冻结评估）

| 需求 | 结论 |
|---|---|
| 写入 inbox（发送） | **需新增** `llm-inbox-add`：承载完整发送参数（文本 / `llm` / think / effort / scenario），由 llm-server 按 phase 分类为 `insert` / `next_turn` |
| 插入轮流式输出 | **复用** `session-receive`（`type: reason/text/tool-call`） |
| 工具执行/完成 | **复用** `task-started` / `task-updated` / `task-done` 与 `mcp-tasks-report` |
| 终态 | **复用** `session-complete`（唯一终态） |
| **读回 inbox** | **需新增** `llm-inbox-list`（方法面）：取 `pending` 项，用于队列指示器与重启拉回 |
| **撤回 / 删除 / 提升** | **需新增** `llm-inbox-discard` / `llm-inbox-promote`（方法面） |
| 状态刷新 | **不加** `inbox-updated`：前端发送后本地镜像，收到首片 `session-receive` 即视为该 item 已消费；动作 / 重启 / 切会话时用 `llm-inbox-list` 对账 |

> **⚠️ 61 冻结**：本方案原"零新增 topic"的结论（旧 G7）**不再成立**。inbox 的写 / 读 / 操作必须新增上述方法面，**须经用户确认后**再登记到 `61-消息一览` + `61-messages.schema.json` + `msgkeys`。
> **为什么是 `llm-inbox-*` 而不是 `data-inbox-*`**：写 / 提升需要"当前 phase + 目标 turn"才能分类与调度，只有 llm-server 掌握；若交给 data 服务，就必须再加一条"写入后通知 llm-server"的事件。故**四条消息统一由 llm-server 处理**，持久化经 data facade 落到 prjusr。
> **为什么不复用 `llm-send`**：其 payload 不含 `llm` / think / effort / scenario，而 `next_turn` 需要以这些参数起新一轮；复用要么扩字段、要么丢参数，且"往已有 turn 塞消息"与"入队待下一轮"语义混淆。`llm-send` 继续承载 tool-result / notify / continue 等内部路径。
> 替代方案（不推荐）：只在重启时由后端把 inbox 直接注入 `llm-start` 响应 —— 会改变既有回执形状，且无法支撑队列指示器与撤回操作。

#### 5.1.1 新增消息契约（提案，待登记 61）

| 消息 | 方向 / 处理方 | 请求 | 响应 |
|---|---|---|---|
| `llm-inbox-add` | client→llm-server（方法面） | `{instance_id, session_id, turn?, llm, content, think_flag?, effort_level?, scenario_id?, idempotency_key?}` | `{ok, id, type:"insert"\|"next_turn"}` |
| `llm-inbox-list` | client→llm-server（方法面） | `{instance_id, session_id, status?="pending"}` | `{ok, items:[{id,type,turn_id,llm,content,created_at,status}]}` |
| `llm-inbox-discard` | client→llm-server（方法面） | `{instance_id, id}` | `{ok}` |
| `llm-inbox-promote` | client→llm-server（方法面） | `{instance_id, id}` | `{ok, type:"insert"\|"next_turn"}` |

- `instance_id` / `session_id` 必填（prjusr 归属）；`content` 沿用现有文本长度校验，纯空白拒绝；
- `turn` 可省略：由 llm-server 按 session 当前运行中的 turn 判定目标；无运行 turn 时 `type=next_turn`；
- llm-server 经 data 面 `data-inbox-append/list/update` 读写 prjusr（**内部面**，只由 llm-server 使用；客户端只经 `llm-inbox-*` 方法面）；
- 命名与字段以 `61-消息一览` 登记为准；登记时同步 `61-messages.schema.json` + `msgkeys`。

### 5.2 数据层

- **新增 prjusr 级表 `inbox_items`**（与 projects / users 同域），字段见 §6.2.3；
- 不新增 `turns.status` 取值；
- `messages` 表的**线性顺序不变式**见 §3.7；
- 工具 `tool_call_status` 语义不变（`running` → `completed/failed/cancelled/interrupted`）；
- 清理：`consumed` / `discarded` 按 TTL 清理（**7 天**；随启动/首次 llm-start 的 `TurnCleanupStale` 顺带执行，不新增消息/定时器；时间基准优先 `updated_at`、缺失回落 `created_at`，不可解析 → 保守保留）；`pending` 永不自动删；
- `inbox_items.turn_id` 仅 `insert` 使用；消费前目标 turn 已结束 → 降级为 `next_turn`；
- **会话删除时级联删除 `inbox_items`**，不留孤儿（`SessionDelete` 内执行；幂等删除不存在的会话时同样清理该 `session_id` 的历史孤儿行）。

### 5.3 前端

- 输入框**不再因忙碌禁用**；发送即入 inbox，由服务端按 phase 分类；
- `useSendQueue` 从"纯内存队列"改为 **inbox 的本地镜像**：展示、撤回、删除、提升都以服务端 `llm-inbox-*` 为准；
- 重启后：启动时 `llm-inbox-list` 拉回 `pending` 项，显示"有 N 条未发送消息"，由用户点「继续」重放（默认不自动发送）；
- 需要展示"工具执行中 / 插话处理中"的轻量状态（可复用 `task-*` 与 `session-receive` 推导，不新增消息）。

## 6. 边界、异常与重启恢复

> 依 [71-编程规范 §3.3](../spec/70-conventions/71-编程规范.md)：有状态功能必须同时给出「异常」与「重启恢复」，缺失视为设计未完成。

### 6.1 边界与异常

| 场景 | 处理 |
|---|---|
| 插入帧请求失败（LLM 错误） | 按现有 `LLM_REQUEST_FAILED` 终结**该插入帧**、取消其在本帧的在飞工具并出栈；随后走 `maybeResumeTop()`；主轮不受影响 |
| 插入帧超时未回执（工具） | 复用 `reapStalePending`，按 frameID 归帧兜底为 `failed` |
| 工具重复回执 | 幂等：`pending` 摘除后不再触发 `maybeResumeTop` 的实际恢复 |
| 用户取消（等待期） | `llm-cancel` = **全局终止**：级联取消所有帧的在飞工具 → `session-complete{status:"interrupted"}` 恰一次；**不会**回到原任务继续 |
| 用户想"退出插话、保留主任务" | **不要用 cancel**：让插话正常结束（或直接说"回到刚才的任务"）→ 插入帧 `done` → 按 S4/S5 自动 pop 回外层，主轮工具不受影响。cancel 只承载"全部停止" |
| 嵌套过深 | 帧深上限（建议 5）+ `maxToolIterations`（按 turn 累计）双保护 |
| 进程崩溃/重启 | 非终态工具由 `TurnCleanupStale` 标 `interrupted`；插入帧消息保留为普通历史；不尝试恢复栈 |
| 工具结果为空的成功 | 投影为 `（工具执行完成，无文本输出）`，避免与"执行中"混淆 |
| 插入内容为空 / 纯空白 | 准入前拒绝（沿用现有 trim 判定） |
| inbox 超限（每会话 > 50） | `llm-inbox-add` 返回拒绝（`ok:false`），前端提示，**不入库** |
| `insert` 目标 turn 已结束 | 消费时自动降级为 `next_turn`，消息不丢 |
| 会话被删除 | inbox 项**级联删除**；进行中的 turn 按现有取消流程终止 |
| 群聊插入 | 交给**该 turn 当前运行的 agent**；插入帧完成后回到同一 agent 的 turn，不重走点名 / 调度 |
| 多窗口同时插话 | v1 不支持；需升级为树调度（§2） |
| **非主会话的 A5 冲突** | 现有 `turnCtx.forceSyncTools()` 对 `sessionKind != ""` 一律附 `async=never`（SUBCHAT-2 阶段 A / 单聊 §12.5 B5 / 群聊 §16 D40）。**本方案全形态放开后必须废止/改写该规则**，否则子会话、群聊的工具永远同步，插话不成立。废止后需重新评估「收口点亮 / 本轮屏障靠轮次跑完」的判据（改用 `pending` 是否清空 + turn 终态，而非"工具必须同步"） |

### 6.2 重启恢复

**结论：v1 不重建帧栈，只保证「不丢输入 + 状态收敛 + 可继续」。**

#### 6.2.1 崩溃瞬间的状态盘点

| 状态 | 位置 | 崩溃后 |
|---|---|---|
| `frames` 栈 / `phase` / `pending` 映射 / `inflight` | **内存** | **丢失，不重建** |
| 用户 / 助手消息、工具 `running` 行 | `messages` 表 | 保留 |
| **inbox 未消费项** | **prjusr `inbox_items` 表** | **保留，重启拉回** |
| 轮次状态 `turns.status` | `turns` 表 | 保留（可能仍是 `running`） |
| 工具真实执行 | gateway 执行池（进程内） | **随进程终止** |

#### 6.2.2 恢复流程

1. 首次使用该 instance 时触发清理（`TurnCleanupStale`）：`tool_call_status ∈ {pending, running, provisional}` → `interrupted`；`turns.status=running` 收敛；
2. **帧栈不重建**：不尝试恢复"正在插话"的中间态，当前 turn 视为已中断；
3. 已落库的插话消息（user / assistant）作为**普通历史**保留；
4. **inbox 拉回**：查询 `status=pending` 的项 → 前端显示"有 N 条未发送消息 / 继续"；
5. 用户点「继续」→ 按类型重放（见 6.2.3）；**不点则不自动发送**。

#### 6.2.3 Inbox（prjusr 级统一入口）

**表 `inbox_items`（prjusr 库）**

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `instance_id` / `session_id` | 归属 |
| `turn_id` | `insert` 的目标轮；`next_turn` 可空 |
| `llm` | 发送时选中的 LLM（沿用原发送队列按 LLM 分桶的口径） |
| `type` | `insert` \| `next_turn` |
| `payload` | 文本 + 发送参数（`thinkFlag` / `effortLevel` / `scenarioId` …） |
| `status` | `pending` \| `consumed` \| `discarded` |
| `idempotency_key` | 客户端可选；消费去重（防"落库成功但未置 consumed"的重放） |
| `created_at` / `updated_at` | — |

索引：`(instance_id, session_id, status, created_at)`。

**生命周期**

1. **发送即入 inbox**（`status=pending`）——先持久化，再进内存；
2. **消费时落 `messages`**：
   - `insert`：在 `toolPending` / `awaitJoin` 消费 → 落 `messages` → push 插入帧；
   - `next_turn`：本轮结束 / 新一轮开始时消费 → 落 `messages`；
3. 消费成功 → `status=consumed`（按 TTL 清理）；
4. 用户撤回 / 删除 → `status=discarded`。

**幂等（关键）**：`消费 = 落 messages + 置 consumed` 必须**原子**（同一 data 请求 / 同一事务），或给 item 加 `idempotency_key` 去重；否则"落库成功但未来得及置 consumed"时，重启会**重复发送**。

**类型互转**

- `next_turn → insert`：turn 进入 `toolPending` / `awaitJoin` 时，允许**显式「立刻插入」**（默认不自动提升，避免改变用户原意）；
- `insert → next_turn`：**重启后目标轮已死 → 自动降级**。

**重启拉回与「继续」**

- 启动时 `llm-inbox-list` 拉回 `pending` 项；
- **默认不自动发送**（避免重启后自动产生 LLM 调用 / 计费），由用户点「继续」；
- 「继续」的语义分两种：
  - **原 turn 已中断**（进程重启）：以 `continue` 开新 turn，按到达顺序消费（`insert` 已降级为 `next_turn`）；
  - **原 turn 仍在运行**（仅窗口/前端重启）：`insert` 项继续插入，`next_turn` 项继续等待本轮结束。

**原前端发送队列并入**

- `useSendQueue` 的内存桶迁移为 inbox 的**本地镜像**；
- 入队 / 撤回 / 删除 / 提升全部经 `llm-inbox-*`，不再只存在前端内存；
- 队列指示器展示 `pending` 项的类型（插入 / 等下一轮）与目标轮。

#### 6.2.4 重启后「继续」时，之前工具如何处理

**结论：不自动重跑；统一收敛为 `interrupted`；LLM 看到明确的"已中断"占位；用户可显式重试。**

| 工具的落库状态 | 继续时的处理 |
|---|---|
| `completed` / `failed` / `cancelled`（已终态、结果已落库） | 原样使用，无变化 |
| `pending` / `running` / `provisional`（崩溃时非终态） | 启动清理标 `interrupted`；**不重跑** |
| 网关后台任务（`async.task_id`） | 执行池已随进程终止；同样标 `interrupted` |

**继续（`llm-start{continue:true}`）时的上下文**

- `turns.status`：`running → interrupted`（`TurnCleanupStale`）；继续时 `ReopenTurn` 复位；
- 工具行：`tool_call_status=interrupted`；`content.result` 若存在则同步改 status，**`result.Content` 原文不改**；
- 无 result 段的 running 行 → 投影为 `（工具已中断，未获得结果；如需重试请使用「重试」）`（§3.8），**不是空串**；
- 因此 LLM 能区分"工具中断"与"工具返回空"。

**需要重跑时：`tool-retry`（既有机制，跨重启可用）**

1. 定位：内存 tasktree 命中 → 直接用；否则从库 `tasktree` 找 `interrupted` 节点（`retryRecover`）；
2. 续轮上下文：该轮的 `user` + 末条 `assistant.tool_calls`（`lastToolCallPair`）；
3. 用**原参数**重跑 → 结果**就地回填同一 tool 行** → `FeedToolResult` 喂回续轮；
4. 若重跑又转后台（返回新 `task_id`）→ 节点置 `pending`，等 `mcp-tasks-report` 回报。

**约束**

- **不自动重跑**：崩溃时工具可能已产生副作用（写文件 / 发消息 / 下单），自动重跑会重复执行；
- 重跑前必须评估幂等性；高风险写操作需要幂等键或人工确认；
- 插入帧内调用的工具同样走上述规则（tasktree 已持久化，可定位）。

#### 6.2.5 副作用语义（必须明确）

- 工具结果回填是**至多一次**：崩溃时未回填的工具一律按 `interrupted` 收敛，**不自动重放**；
- 重试（`tool-retry`）会**再执行一次**：高风险写操作（发消息、下单、写文件）必须幂等或带去重键，否则重复副作用；
- 网关回执 `mcp-tasks-report` 丢失但实际已执行 → 收敛为 `interrupted`，前端显示「已中断 / 可重试」，**不假装成功**。

#### 6.2.6 明确不做（v1）

- 不持久化帧栈、不做「重启后从某个插入帧继续」；
- 不自动重放未完成工具；
- **不做**"重启后自动发送 inbox"（必须用户确认「继续」）。

| **Q1** | 契约显式 `never` 的工具是否允许被"强制异步"覆盖 | **允许**（执行层全量强制异步） | 需放开 gateway `explicitNever` 锁死；插入轮上下文**保留**未完成 tool-call + 占位（§3.8），不剔除 |
| **Q2** | inbox 中同批多条是逐条还是合并 | **合并为一轮** | §3.3；落 `messages` 仍逐条保留 |
| **Q3** | 是否支持"主动结束某一插入帧" | **不做**（用户确认） | `llm-cancel` 的作用域见 Q3-a（已定案） |
| **Q3-a** | `llm-cancel` 是全局终止还是"退出插话回原任务" | **A 全局终止（定案）** | 语义唯一、可预测；取消本身不新增消息（inbox 的 4 条另计，见 §5.1）；现有 `cancelByTurn` 天然覆盖所有帧。「退出插话」不靠 cancel——插话正常结束即自动 pop 回外层（见 §6） |
| **Q4** | 是否为"消息归属插入帧"新增 payload 字段 | **不加** | 前端靠顺序 + `task-*` 推导；不改既有 payload。inbox 自身的读回另见 Q7 |
| **Q5** | 子会话 / 群聊是否同样放开 | **全形态放开**（主 / 子 / 群聊） | **必须同步废止 A5「非主会话强制同步」**（`forceSyncTools`），并重估「收口点亮 / 本轮屏障」判据（§6） |
| **Q6** | 插话落库时机 | **所有发送先入 inbox，实际插入 / 下一轮时才写 `messages`** | 统一路径；落库位置确定，不破坏配对；崩溃不丢（§3.3 / §6.2.3） |
| **Q7** | inbox 的级别与重启行为 | **prjusr 级**；重启拉回并显示「继续」，**默认不自动发送** | 新增 `inbox_items` 表 + `llm-inbox-add` / `list` / `discard` / `promote`（**61 冻结，须确认**） |
| **Q8** | 原前端发送队列 | **并入 inbox**（`useSendQueue` 改为本地镜像） | 重启可拉回，不再依赖内存 |
| **Q9** | inbox 类型 | **`insert` / `next_turn` 两种，可互转**；`next_turn` 可显式「立刻插入」 | 覆盖两种用户意图；默认不自动提升 |
| **Q10** | 重启后「继续」时，之前的工具怎么处理 | **不自动重跑**；非终态统一收敛 `interrupted`；上下文给明确"已中断"占位；需要重跑走既有 `tool-retry` | 避免重复副作用；`tool-retry` 跨重启可用（`retryRecover`）；高风险写操作需幂等（§6.2.4） |
| **Q11** | inbox 状态刷新是否新增 `inbox-updated` 事件 | **不加** | 前端本地镜像 + 首片 `session-receive` 视为已消费；动作 / 重启 / 切会话用 `llm-inbox-list` 对账（§5.1） |
| **Q12** | 插入消息的 `turn_id` 归属 | **一律写主 turn 的 `turn_id`，不新建 turn** | `msgs()` 线性读取；`turns` 单条记录；`session-complete` 只发一次（§3.7） |
| **Q13** | 群聊插话归谁处理 | **该 turn 当前正在运行的 agent**，不重走点名 / 调度 | 插入结束后回到同一 agent 的 turn（§6.1） |
