### 0.1 架构总目标与边界（2026-10-17 用户口径）

> 用户原话要点：「把**所有的工具调用全部移到进程外**……进程内只做**文件变更监控、数据库读写、配置读写、LLM 调用、MCP 调用**……凡是可以由外部人工 / 外部插件 / 现有进程内工具实现的动作，**通通通过 TCP/IP 或 UDS 接口**实现。这样所有外部工具都可以操控我们的 **server 和 GUI**。」
>
> **〔口径订正（2026-10-17，用户）〕** 上引「进程内只做」的正确语义 = **server 进程对外提供这 5 类原子能力**（不是「进程内只剩这 5 项职责」）；工具调用全部在进程外，通过 TCP/UDS 消费这些原子能力。

- **server 对外提供的 5 类原子能力**（经 `transport`）：① 文件变更监控（filesys watcher）；② 数据库读写（data/persist）；③ 配置读写（config）；④ LLM 调用（llm/router）；⑤ MCP 调用（gateway / MCP server 连接）。
- **进程外（全部工具调用与外部动作）**：所有**工具实现/执行体**在进程外执行；外部工具 / 插件经上述 5 类原子能力组合实现 —— 任务（查询 / 终止 / 转后台 / 重试）· 会话（发起 / 取消 / 历史 / 内容）· 配置（读 / 写 / 删除）· 能力面（工具 / 资源 / 提示词）· 文件操作 · 记忆（激活提取 / 读取内容）· LLM（`llm.step` / 简单调用）· **GUI 控制（窗口 / 页面调整 / 预览页签 / 抽屉等）** · 插件运维动作 · 场景向导等。
- **边界澄清（2026-10-17，用户）**：**server 进程与 gateway 本体都不迁出进程**。gateway 仍是 server 内的**工具注册 / 路由中心**；迁出的只是 **LLM 可调用工具与 gateway 注册工具的 handler / executor**。工具调用请求仍由 server 内 gateway 受理，再路由到进程外执行体。
- **对外传输**：**UDS 为主（本机零配置）+ TCP 可选（跨机/容器）**（沿用 D3）；对外**独立方法面**，对内翻译为既有 MQ 主题（D2；默认复用，新增按 §11.10）。
- **已定（2026-10-17，用户；不再拍板）**：
  1. **所有工具全部外移，server 内零工具实现**：`mcp_find` / `mcp_load` / `mcp_invoke`、`subchat_open`/`subchat_finish`/`tool_stop`/`tool_result`、`llm_run`/`dsl_run`、filesys / web / browser / desktop 等全部作为外部插件 / 执行体；**gateway 只保留注册 / 路由 / 调度**，不含任何工具 handler。
  2. **GUI / Desktop 共享同一前台，全部控制开放**：窗口、页面、布局（含 `layout.free`）、抽屉、主题 / 语言 / 场景、预览页签、本机动作全部可调；`gui.native.*` 仅保留路径校验 + 审计（安全约束，不是范围限制）。
  3. **实例生命周期 = 纳入**（`instance-register` 等消息开放）；**认证 = 不做**（本机 UDS 信任；TCP 仅 loopback，跨机另议）。
  4. **迁移一次性切换**：不做半迁移、不留兼容别名。

## 1. 问题与目标

- **要解决的问题**：第三方工具（独立进程，Python / Node / Go 脚本、IDE 插件、批处理机器人）想**以平台为后端**——调 LLM、查配置、查聊天数据、操控平台内容。而这些能力**全是 61-消息一览里的内部契约**，第三方要接就只能照抄 GUI 桥或 `flash-cli`，且**没有任何授权与脱敏层**。
- **目标（可验收）**：
  1. 立起一个**与业务无关的通用传输层**（`transport`）：UDS / TCP 两后端，同一帧协议、同一会话语义；**包内不出现任何业务标识**（§3.6 纯净度验收）；
  2. server **通过该传输层对外提供能力**：能力以 **handler 注册**的方式**逐个叠加**，新增能力不动传输层；
  3. 插件以**平台级服务身份**接入，身份**由平台裁决**（插件不得自报作用域）；
  4. 对外是**独立方法面**（不暴露 `data-*` / `session-*` 等内部主题名），对内**翻译成既有 MQ 主题** → **默认复用既有 61；新增按 §11.10**；
  5. **默认关闭**、**fail-closed**；`apiKey` 等凭据**永不出平台**；每方法调用**审计可查**。
- **非目标**：
  - **不做**跨进程 MQ（`src/lib/core/mq` 内存实现不动）、**不做**去中心化总线；
  - **不做**协议翻译成第三方 LLM 协议（那是 `BRIDGE-1` 的 5669）；
  - **不把** `mq.Bus` 语义暴露给第三方（插件面不走裸主题）；
  - **不改造**既有实例前门 `udsapi` / 浏览器前门 `httpapi`（本期只新增，不重构）；
  - **GUI 控制全部纳入**（D7/§0.1）：窗口 / 页面 / 布局（含 `layout.free`）/ 预览页签 / 抽屉 / 主题语言场景 / `gui.reveal` / `console.open` / `pick-executable` / `capture` 等全部可调；`gui.native.*` 只保留路径校验 + 审计（安全约束，不是范围限制）。
  - **不把 server 进程 / gateway 本体拆出进程**（2026-10-17 用户口径）：gateway 仍是 server 内的工具注册 / 路由中心；只把**工具实现 / 执行体**迁到进程外插件。
  - **实例生命周期（`instance-*`）纳入目标**（用户 2026-10-17：`instance-register` 等消息也需要开放）；**认证域（`login-*`）不对外**；插件链路**不做安全认证**（用户 2026-10-17：本机 UDS 信任；TCP 仅 loopback，跨机另议）。

## 2. 总体架构

```text
第三方进程（Python / Node / Go …）
   │  ① 连接（UDS 默认 / TCP 可选）+ 认证
   ▼
┌──────────────────── src/lib/core/transport（业务无关） ────────────────────┐
│ Endpoint(listen) / Dialer / Conn（帧收发）/ Frame(req·res·evt·ctl)          │
│ 后端：uds | tcp   ·   认证钩子 Authenticator → Principal（不透明）          │
│ ✗ 不出现：主题名 / instance / 方法名 / 能力名 / 61 概念                      │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    ▼
┌──────────────────── src/lib/pluginbridge（机制层，仍无业务） ───────────────┐
│ Session    = 一条连接 + 身份 + 订阅表（事件下行过滤）                        │
│ Registry   = method → Handler 注册表（**能力叠加点**）                       │
│ 授权 / 审计 / 稳定错误码                                                    │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    ▼
        能力 handler（**逐个叠加**；每个 handler 内部走 MQ / 内部调用）
   llm.step → llm-simple · session.list → data-session-list · file.read → filesys.content …
                                    ▼
           平台内核：llm-server · persist(data) · filesys · gateway
```

**一句话**：**传输层只搬帧**；**注册层做身份、授权、路由**；**能力是挂在注册表上的 handler，一个一个加**。

**与既有两个前门的分工（并列，不重叠）**

| 前门 | 身份模型 | 服务对象 | 本期 |
|------|---------|---------|------|
| `udsapi`（`server.sock`） | 连接 = 一个**实例**（claim 后绑定 `work_dir`） | flash / 桌面薄壳 | **不动** |
| `httpapi`（`--http-addr`） | HTTP 会话 + 登录令牌 | 浏览器前端 | **不动** |
| **`pluginbridge`（`plugin.sock`）** | 连接 = 一个**插件**（平台级服务身份） | 第三方独立进程 | **本方案新增** |

## 3. 传输层 `transport`（业务无关 · D5 核心）

> 落点：**`src/lib/core/transport/`**（与 `uds`、`mq` 同属 module `chonkpilot-lib`，不新增 module）。

### 3.1 职责与非职责

| | 内容 |
|---|------|
| **做** | 监听 / 拨号 · 连接生命周期 · **帧**收发（req / res / evt / ctl）· 请求-应答关联（`id`）· 帧长上限 · 断连通知 · **认证钩子**（后端把连接换成不透明身份） · 多后端（uds / tcp） |
| **不做** | 不认识**方法名**（只当字符串搬） · 不认识**主题**（不做 subject 匹配） · 不认识 `instance` / `work_dir` / `project` · 不做授权判定 · 不做业务校验 · 不 import `llm` / `data` / `filesys` / `gateway` / `plugin*` |

### 3.2 接口草案（Go，示意）

```go
// Package transport 是**与业务无关**的进程间传输层：只搬帧，不管帧里装什么。
package transport

// Kind = 帧类型（沿用 uds 既有四种，语义仍是纯机制）。
type Kind string

const (
    KindReq Kind = "req" // 请求：{name, payload} → 期待同 id 的 res
    KindRes Kind = "res" // 应答：{id, ok, result, errors}
    KindEvt Kind = "evt" // 事件：{name, payload}（服务端 → 对端，单向）
    KindCtl Kind = "ctl" // 控制：{name, payload}（不投给业务，由宿主处理）
)

// Frame 是通用帧 —— transport 不解释 Name/Payload 的业务含义。
type Frame struct {
    Kind    Kind
    ID      int64           // req / res 关联
    Name    string          // req / ctl：方法名；evt：事件名
    Payload json.RawMessage
    OK      bool            // res
    Result  any             // res
    Errors  []string        // res
}

// Conn = 一条双向连接。
type Conn interface {
    Send(f Frame) error            // 并发安全
    Recv() (Frame, error)          // 单读者
    Call(ctx context.Context, name string, payload any) (Result, error) // 纯机制：req + 等 res
    Principal() Principal          // 认证后身份；未认证 = Nil
    Remote() string                // 对端标识（诊断用）
    Closed() <-chan struct{}
    Close() error
}

type Result struct { OK bool; Value any; Errors []string }

// Endpoint = 监听点；Dialer = 连接方。两接口均**后端无关**。
type Endpoint interface { Addr() string; Accept() (Conn, error); Close() error }
type Dialer   interface { Dial(ctx context.Context) (Conn, error) }

type Options struct {
    Backend       Backend         // uds | tcp（§3.4）
    Addr          string          // uds: 路径；tcp: host:port
    Authenticator Authenticator   // 认证钩子；nil = 不认证（仅限后端自带信任保证时）
    MaxFrameBytes int             // 缺省 64 MiB（对齐 uds.MaxFrameBytes）
    MaxConns      int             // 服务端缺省 64（对齐 uds.MaxConns）
    Logf          func(string, ...any)
}

func Listen(o Options) (Endpoint, error)
func Dial(ctx context.Context, o Options) (Conn, error)
```

### 3.3 帧协议

- **行分隔 JSON**（一帧一行、`\n` 结尾）—— **与现有 `uds` 逐字节同一套**（便于复用、统一排障）；`k` 字段 = 帧类型。
- 单帧上限 `MaxFrameBytes`（缺省 **64 MiB**，同 `uds`）；超限 → 断连 + 留痕（不返回半帧）。
- **请求-应答关联**：`id`（int64，连接内单调递增）；`Call` 内部维护 `pend` 表 —— **纯机制**，仍在业务无关范围内。
- **未识别字段一律透传**（向前兼容：后端/对端可加元数据）。

### 3.4 传输后端

| 后端 | 地址形态 | 信任来源 | 认证 | 状态 |
|------|---------|---------|------|:---:|
| **uds** | 文件路径 | **连接层**（socket 在 `%LOCALAPPDATA%`，OS 目录 ACL 限当前用户） | 内置「本机用户」验证器（不要求 token） | 🔵 首选 |
| **tcp** | `host:port` | 无 | **本期仅 loopback、不做认证**；跨机 token/TLS 后续另议 | 🔵 可选 |
| 预留 | stdio / 命名管道 / WebSocket | — | — | ⏳ 不在本期 |

> 约定：UDS 路径 `%LOCALAPPDATA%\chonkpilot\plugin.sock`（与 `server.sock` **同目录、各自独立**；env `CHONK_PLUGIN_UDS` 可覆盖以隔离）。TCP 由 `--plugin-addr` 显式开启（**默认空 = 关闭**；仅 `127.0.0.1:<port>`；跨机 token/TLS 另议）。

### 3.5 认证钩子

- `Authenticator` 是**唯一**允许 transport 触碰「身份」的地方，且它只回一个**不透明 `Principal`**（`{ID, Kind, Meta}`）—— 字段含义由注册层解释，transport 不解释。
- **本期不做认证**：UDS 本机信任；TCP 仅 loopback。`Authenticator` 仅作为后续跨机 token/TLS 的预留钩子，nil 即可运行。

### 3.6 纯净度验收（"和业务无关"要可验证）

1. `transport` 包内**不出现**以下标识符：`instance` / `work_dir` / `project` / `session_id` / `subject` / `topic` / `chonk.` / `data-` / `llm-` / `mcp-`；
2. `transport` 的 `import` 图**不含** `chonkpilot-llm` / `chonkpilot-data` / `chonkpilot-filesys` / `chonkpilot-gateway` / `chonkpilot-plugin*`（可加一条 L1 单测断言 import 白名单）；
3. `transport` 的**单测只谈帧与连接**（收发 / 上限 / 断连 / 并发 / 关联 / 两后端同一用例矩阵），**零业务断言**。

> 这三条 = 架构评审的硬门槛；评审时先跑这三条，再看功能。

### 3.7 与现有 `uds` 包的关系（**本期不动它**）

- `uds`（`src/lib/core/uds`）**包文档已自述「本包只做传输」**，但实际掺了业务：`instanceIDOf`（认 `instance_id`）· `matchSubject`（MQ 主题匹配）· `Server.SendEvent(instanceID, …)` / `IsCurrent`（实例路由）· `ctl` 帧专供 `instance-goto-top`。
- **本期策略**：**新增 `transport` 并只给插件前门用；`uds` 与 `udsapi` 原样不动**（实例前门零风险）。
- **后续（可选，⏳ 不入本期）**：待 `transport` 稳定后，再评估把实例前门的传输部分收敛到 `transport` 之上（把 §3.7 列出的四类实例语义**上移到 `udsapi`**）。若做，须单独拍板 —— **不为"通用"而重构正在跑的实例链路**。

## 4. 注册层 `pluginbridge`（server 侧：能力叠加点）

> 落点：**`src/lib/pluginbridge/`**（module `chonkpilot-llm`，与 `httpapi`、`udsapi` 同侧、并列）。机制层 —— 仍**不含具体能力**。

### 4.1 三个构件

| 构件 | 职责 |
|------|------|
| **Session** | 一条 `transport.Conn` + `Principal` → 授权快照、订阅表、断连清理；对外暴露 `Emit(name, payload)`（→ `evt` 帧） |
| **Registry** | `method → Handler` 注册表（**唯一的能力叠加点**）；`Handler = func(ctx, *Session, json.RawMessage) (any, error)` |
| **Gate** | 授权判定（§5.2 清单）+ 审计（§5.3）+ **稳定错误码**（比照 httpapi 的 `publishError.*`，如 `method_not_allowed` / `plugin_unauthorized` / `plugin_disabled` / `args_invalid`） |

### 4.2 叠加一个能力的固定步骤（这就是"能力一个个叠加"）

```go
// src/lib/pluginbridge/capabilities/llm_step.go（新增一个文件 = 新增一个能力）
func init() { Register("llm.step", handleLLMStep) }

func handleLLMStep(ctx context.Context, s *Session, args json.RawMessage) (any, error) {
    var in struct{ Prompt string; System string; LLM string }
    if err := json.Unmarshal(args, &in); err != nil { return nil, ErrArgsInvalid }

    // 对内：翻译到既有 MQ 主题（优先复用，不新造主题）
    v, err := s.Bus().Emit(ctx, "llm-simple", map[string]any{
        "prompt": in.Prompt, "system": in.System, "llm": in.LLM,
    }).Wait()
    if err != nil { return nil, err }
    return v.Result, nil          // 对外：{ok, result}
}
```

**固定四步**：① 写一个 handler 文件（含对内翻译）② `Register("<method>", h)` ③ 在授权清单族里登记该方法名 ④ 加一个帧驱动的用例。**传输层一行不改。**

### 4.3 方法命名与版本

- 独立命名空间 **`plugin/v1/<族>.<动作>`**（如 `plugin/v1/llm.step`、`plugin/v1/session.history`）——**不暴露**内部主题名（`data-*` / `session-*` 可随时重构，对外契约不变）。
- **控制帧**统一为 `plugin.hello` / `plugin.register` / `plugin.ready` / `plugin.exit` / `plugin.subscribe` / `plugin.unsubscribe` / `plugin.sys.*`；能力方法统一为 `plugin/v1/<族>.<动作>`。表格中的短名（`task.list`）仅为阅读别名，线上统一带 `plugin/v1/`。
- 版本段 `v1` 出现在方法名里 → 破坏性变更可并存 `v2`，不需要传输层配合。
- **已定**：**不沿用** gateway 的 MCP 方法名；插件能力面统一 `plugin/v1/<族>.<动作>`，MCP 工具面仍走标准 `tools/call`，两者边界清晰。

## 5. 身份、开放清单与审计（**本期不做认证**）

> **2026-10-17 用户口径**：插件链路**不做安全认证**。UDS 本机信任、TCP 仅 loopback；以下“授权清单”降级为“**开放清单 + 审计**”，不阻塞建连；仅“未注册插件 / 未知方法”拒绝。

### 5.1 身份模型

- 一条连接 = **一个插件身份**（`plugin_id`，如 `com.example.mybot`），由 `plugin.hello` 自报，平台记录并审计。
- **不做 token / 登录 / 授权校验**；UDS 依赖同用户 ACL，TCP 仅 loopback。
- 作用域**由平台注入**：handler 一律不接受调用方自报的 `work_dir` / `instance_id` / `user`（对齐 httpapi 的 `bindFilesys` 口径）；插件如需实例，走服务端分配的 `instance_id`。

### 5.2 开放清单（不做认证）

拟落 **`capability/plugins/<plugin_id>.json`**（与 `capability/mcps/<server>.json` 同构、同级）：

```json
{
  "id": "com.example.mybot",
  "enabled": true,
  "transport": { "uds": true, "tcp_token": "…" },
  "scope": { "projects": ["*"] },
  "methods": ["plugin/v1/llm.step", "plugin/v1/session.list", "plugin/v1/config.user.get"],
  "audit": true
}
```

- **未注册插件 / 未知方法 = 拒绝**；清单仅用于声明开放面与审计，**不做认证拦截**。
- 高危族（§6 第 4 批）**必须显式列出**，不在任何默认集里。
- 载体：先按 `capability/plugins/<plugin_id>.json` 提供；本期可不阻塞，缺失时按“默认开放清单”运行（仍审计）。

### 5.3 审计

- 每次调用落一行：`{ts, plugin_id, method, target(project/session), ok, ms, err_code}`。
- **不记**：`apiKey`、消息正文、文件内容、工具参数原文。
- 落点拟 `<dataDir>/logs/plugin-audit.log`（滚动，不入库）；审计不可写只 WARN，**不阻断服务**。

## 8. 边界与异常

### 8.1 事件订阅（**最大的未决技术点**）

- 现有下行事件（`session-receive` / `-complete` / `-ask` / `task-*` / `tool-notify` / `filesys.changed` / `data-*-refresh` / `mcp-gateway-changed`）**统一以 `instance_id` 过滤**。
- **插件没有 `instance_id`** → 直接订阅 `>` 会收到**全平台所有实例**的事件（噪声 + 越权）。
- 拟：由 **Session** 承担过滤（**传输层不参与**）——插件显式声明 `plugin.subscribe {topics:[{pattern, mode, filter:{projects?, sessions?, kinds?, instance_id?, direction?}}]}`，未声明 = 不投递任何事件。
- **已定**：过滤键 = `projects / sessions / kinds` + `instance_id` / `direction`；**不需要 attach 到某个会话**（订阅 ≠ 加入会话）。

### 8.2 其他

- **未注册插件 / 未知方法** → 拒绝，错误码明确，**不静默降级**；**不做认证拒绝**（用户 2026-10-17）。
- **默认关闭**：不带 `--plugin-addr` 且无插件清单时，前门不监听（同 httpapi 口径）。
- **凭据**：`apiKey` 只随请求内存流转，**不落日志、不进审计、不回第三方**。
- **连接数上限 / 慢消费者**：超限拒绝新连接；慢消费者丢帧（对齐 `uds` 与 httpapi `broadcast` 口径）。
- **平台级身份的固有代价**：授权为平台级 = 该插件可读**所有项目**的会话与配置。须在授权 UI 上**明示**（"此插件可读取你全部项目的数据"）。
- **跨机 TCP**：默认仅 loopback；非 loopback 须显式写全 + token；**TLS 待定**。

## 10. 已定口径（原“待拍板”项全部关闭）

1. **授权载体**：不做认证；`capability/plugins/<id>.json` 只作开放清单 + 审计，不做授权拦截；不建设置页授权 UI。
2. **方法命名**：统一 `plugin/v1/<族>.<动作>`；控制帧 `plugin.*`。
3. **事件订阅过滤键**：`projects / sessions / kinds` 够用；另支持 `instance_id` / `direction`。
4. **客户端 SDK**：先出 Go 包 + 自描述 `sys.info`；Python 壳后续再加。
5. **能力批次顺序**：按 §13.4 的 B0–B5 执行。
6. **工具边界**：**所有工具全部外移，server 零工具**（含 `mcp_find`/`mcp_load`/`mcp_invoke`、`subchat_*`、`tool_stop`/`tool_result`、`llm_run`/`dsl_run`、filesys/web/browser/desktop）；gateway 只保留注册/路由/调度。
7. **GUI 控制**：**GUI / Desktop 共享同一前台，全部动作开放（含 `layout.free`）**；`gui.native.*` 保留路径校验 + 审计。
8. **插件 instance**：不进用户实例菜单 / 托盘；可被 `instance.list` 查到；`client_type=plugin`，服务端生成 id。
9. **迁移顺序**：一次性切换，不做半迁移 / 兼容别名。
10. **查询 / 关联**：**两次 publish 原则**——跨进程请求 = request publish + result/error publish；传输层不等待、不持有 Future；查询用 `request_id` + `client_seq`；命令可选 `request_id`；**不使用 Request/Future**。
11. **前端**：响应式 store；action 发请求，store 订阅 `result/error`，组件只读 store；`dataClient` 仅作底层关联工具。
12. **配置 / 元数据缓存**：每个 `(scope, work_dir, exe_id)` 启动 load 一次；**system/user/prj/executor 四层全部 snapshot**；之后只靠 `config-saved/deleted` 增量更新；`revision` 检测漏事件；密钥脱敏；页面只读 `configStore`。
13. **大数据集**：目录树 / 知识库 / 任务树 / 会话列表不常驻；**LOD / 分页 + 事件失效**；保存只更新受影响节点，不整树 reload。

## 11. 插件注册协议（草案，2026-10-17）

> 目标：MCP server / 外部工具进程在 **spawn 后经同一 TCP/UDS 通道**注册自身特性、订阅回调、按需调用 server 能力。**server / gateway 本体不动**；本协议只描述「插件 ↔ server」的接入面。

### 11.1 握手流程

```text
server spawn 插件
  → 插件 dial plugin 入口（UDS 默认 / TCP 可选）
  → plugin.hello   {protocol, plugin:{id,name,version,kind,pid}}
  → plugin.register{features, subscriptions, tools?}
  → server 校验（沙箱/限制/订阅白名单）→ plugin.ready
  → 正常：`plugin/v1/<method>` 请求 / 事件下行 / 工具回调
  → 退出：plugin.exit（或断连）→ server 清理订阅与实例
```

- `kind`：`mcp-server`（VFTSS / Codebase 等）· `tool-provider` · `resident-indexer`（常驻索引器）· `observer` · `ui`。
- spawn 时由 server 注入 `CHONKPILOT_PLUGIN_ADDR`（UDS 路径或 `127.0.0.1:<port>`）与 `CHONKPILOT_PLUGIN_ID`；插件据此 dial。
- **无认证**（用户 2026-10-17）：本机 UDS 信任；TCP 仅 loopback，跨机另议。
- **两层身份**：`plugin_id` = 连接级平台身份；`instance_id` = 可选路由锚点。`kind=mcp-server` / `tool-provider` 需要实例时由**服务端分配**；`kind=resident-indexer` / `observer` 只用 `plugin_id`，**不注册实例**。
- 插件不得自报 / 覆盖 GUI `instance_id`；`instance-claim` 由服务端生成并校验，重复 id 直接拒绝。

### 11.2 可注册特性（features）

```json
{
  "features": {
    "mcp":   {"tools": true, "resources": true, "prompts": false},
    "sandbox": {"mode": "required|preferred|disabled", "reason": "needs-native"},
    "fs":    {"access": "none|read|write|read-write", "roots": ["${workDir}/.chonkpilot"], "follow_symlinks": false},
    "net":   {"access": "none|loopback|any", "hosts": ["api.example.com"]},
    "exec":  {"allowed": false},
    "env":   {"required": ["CHONKPILOT_WORKDIR"], "passthrough": []},
    "gui":   {"can_control": false},
    "limits":{"max_concurrency": 4, "max_frame_bytes": 67108864, "heartbeat_ms": 15000}
  }
}
```

| 组 | 字段 | 语义 |
|---|---|---|
| 身份 | `plugin.id/name/version/kind/pid` | 注册标识；`kind=mcp-server` 时 `id` = `servers/register` 的 server 名 |
| MCP 能力 | `mcp.tools/resources/prompts` | 声明是否提供对应 MCP 面 |
| 沙箱 | `sandbox.mode` | `required` 必须沙箱；`preferred` 有则用；`disabled` 请求禁用（server 策略可拒绝并记录） |
| 文件 | `fs.access` / `roots` / `follow_symlinks` | 自报读写需求与根；**声明 `none` = 约定不读**（无认证下为契约+审计，非强制） |
| 网络 | `net.access` / `hosts` | `none` / 仅 loopback / 任意；可给域名白名单 |
| 进程 | `exec.allowed` | 是否需要 spawn 子进程 |
| 环境 | `env.required/passthrough` | 需要的 env；server 只注入白名单 |
| GUI | `gui.can_control` | 是否允许调用 GUI 控制面（窗口/页面/抽屉/主题语言场景） |
| 限制 | `limits.*` | 并发、帧上限、心跳；server 可下调，不可上调 |

> **默认保守**：未注册 = `sandbox.required`、`fs.none`、`net.none`、`exec.false`、`gui.can_control=false`、无订阅。
> **校验**：`sandbox.disabled` 与 server 策略冲突 → 拒绝启动/注册（或降级并审计）；`fs.roots` 超出允许目录 → 拒绝；未知字段忽略（向前兼容）。

### 11.3 回调订阅（subscriptions）

```json
{
  "subscriptions": [
    {"id":"obs-1","pattern":"session-complete","mode":"async","filter":{"instance_id":"*","project_id":"*"}}
  ]
}
```

| mode | 语义 | 返回 |
|---|---|---|
| `async`（唯一模式） | 只投递，不等待 | 不返回 |

> **插件订阅只有 `async` 观察**；需要回执/结果时，用 `request_id` + `result` / `error` 事件（§11.14），**不引入 `Request` / Future 作为插件协议**。`filter` 不是订阅模式，而是 §11.13 的显式 before-hook 链（`plugin.filter.register`），只由 server handler 在 4 个 P0 阶段调用。

- **过滤器**：`pattern`（MQ 通配）+ `filter.instance_id/project_id/session_id/direction(server|gui)`。
- **filter 的限制**（必须由 server 硬校验）：
  - 禁止 `filter` 用于高频主题（`session-receive` / `llm-receive` / `tool-notify` / `filesys.changed` 等）；
  - 禁止 `>` / 多主题通配的 `filter`；
  - 每插件 `filter` 订阅数上限、超时上限、优先级范围；
  - 处理在**每插件独立队列 + 有界 worker** 中执行，**不得在 `mq.Emit` 同步 handler 内直调**；
  - 防环：插件不得拦截自己发出的同主题事件。
- **GUI 事件**：GUI 桥把原本丢弃的纯前端主题（`preview-tab-open` / `lf-*` 等）以 `gui-event {type,payload,instance_id}` 信封镜像给插件；**不新增 MQ 主题**。

### 11.4 server 能力调用（plugin → server）

```json
{"request_id":"r1","method":"plugin/v1/task.list","params":{"instance_id":"..."}}
→ event: plugin/v1/task.list-result {"request_id":"r1","ok":true,"result":{...}}
→ event: plugin/v1/task.list-error  {"request_id":"r1","ok":false,"error":{...}}
```

- **所有调用都是消息**：插件发请求事件，server 回 `result` / `error` 事件；`request_id` 关联，`instance_id` 防跨实例冲突。
- **不引入 `Request` / Future 作为协议**；SDK 可以提供 `await` 语法糖，但底层仍是 publish + 事件。
- 命令可选带 `request_id`：带 = 要完成/错误回执；不带 = 纯 fire-and-forget。
- 查询必须带 `request_id`；结果走 `<method>-result` / `<method>-error`。
- `filter` 是 server 侧 before-hook，不是 request；失败中止（§11.13）。
- 方法族（对内翻译既有 MQ / 门面，**优先复用；新增按 §11.10**）：
  - `sys.*` / `instance.*` / `task.*` / `session.*` / `config.*`
  - `llm.simple`（一次来回）
  - `memory.activate` / `memory.read`
  - `mcp.tools.list/call` / `filesys.*`
  - `gui.window.*` / `gui.page.*` / `gui.dialog.*` / `gui.pref.*`（需 `features.gui.can_control=true`；GUI 动作需目标 `instance_id`）

### 11.5 MCP server 作为插件

- VFTSS / Codebase 等由 gateway `servers/register` spawn 的 MCP server：spawn 后**可选**打开 plugin 通道注册 `features/subscriptions`；`plugin.id` = server 名。
- 工具/资源/提示词仍走标准 MCP 协议；plugin 通道只承载**特性、订阅、server 能力调用**。
- **resident-indexer 不是 MCP server**：它由 `pluginhost` 启动、不进 gateway、不注册工具；只订阅事件并写索引库（见 §11.8）。
- 未打开 plugin 通道的第三方 MCP server = 普通 MCP server（默认特性，无订阅），行为不变。

### 11.6 与既有实现的关系

- 复用：`uds` 帧 + `mq.Bus` + `instance-claim/register` + `tools/register`/`handler_subject` + `servers/register`。
- 新增：`plugin.hello/register/ready` 帧、`features` 校验、订阅表、每插件队列、server 能力方法面、GUI 事件镜像。
- **默认复用既有 MQ 主题**；本专题实现期允许新增（§11.10），命名暂定。

#### I. filter 策略（仅 4 个 P0 stage）

- **v1 不做通用拦截**；只允许 4 个 stage：`llm.before_start` / `llm.before_send` / `llm.before_simple` / `tool.before_call`。
- 每个 stage 可注册多个 filter，`priority` 升序；同优先级按 `plugin_id`。
- 高频主题只 `OBS`，禁止 filter：`session-receive`、`tool-notify`、`filesys.changed`、`task-updated`、`data-*-changed`。
- 禁止 `>` / 多主题通配；只允许显式 stage。
- 每插件 filter 数量、超时、优先级上限；超时 **fail-closed**。
- 不允许拦截自身发出的事件；不允许递归 emit。
- `replace` 只允许改 payload，不允许改 topic；`drop` 需审计。
- 其他主题只 `OBS`，不做 filter。

### 11.8 常驻插件（resident plugin）与 MCP server 的分工（2026-10-17 简化方案）

> 用户口径：不要给 MCP server 加复杂的 lifecycle / 池回收。把「插件」和「MCP server」拆成两个概念：
> - **resident plugin** = 随 server 启动/结束、永不主动杀、处理所有 instance 的常驻进程；
> - **MCP server** = 工具提供方，读 resident plugin 产出的索引/数据。
> 这样 indexing 进程不进 gateway 连接池，不需要 pool / idle / Invalidate 那套。

#### 11.8.1 两个概念

| 概念 | 形态 | 生命周期 | 职责 |
|---|---|---|---|
| resident plugin | 独立 exe，由 server 的 `pluginhost` 启动 | 随 server 启动/结束；崩溃才重启；**不被用户取消杀** | 监听所有 instance / filesys，维护索引，写库 |
| MCP server | 工具进程 | gateway 管理；可常驻或按需 | 读索引 / DB，提供工具；**不持有索引状态** |

- resident plugin **不注册成 MCP server**，不进 gateway；不需要 `ServerEntry.lifecycle`，也不需要改 `sweepIdle` / `Invalidate`。
- 它只走 plugin transport，复用 MQ / instance / filesys 事件。
- MCP server 被 kill / respawn 不影响索引；重启后直接读库。

#### 11.8.2 进程与启停

- server 启动 → `pluginhost` 拉起 resident plugin（eager）。
- server 关闭 → 发 `plugin.shutdown` → flush 索引 → 退出；超时才 kill。
- 崩溃 → 按退避重启（1s / 2s / … / 60s，最多 N 次）→ 重新订阅 → 重新对账；超过上限标 `degraded`。
- **没有 idle TTL、没有 per-instance 池、没有 cancel-kill**。
- 一个 resident plugin 进程服务所有 instance / work_dir；内部按 `work_dir` 分索引。
- `pluginhost` 保证**单例**（文件锁 / 进程锁），避免多 server 实例重复启动 indexer、重复写索引。
- 订阅：`instance-register` / `instance-exit` / `filesys.changed` / `data-prj-config-refresh`；用 `filesys.watch` 声明根目录。

#### 11.8.3 VTF / Codebase 拆两个 exe

| exe | 角色 | 职责 |
|---|---|---|
| `vfts-indexer.exe` / `codegraph-indexer.exe` | resident plugin | 监听文件变化、维护索引、写索引库 |
| `vfts-mcp.exe` / `codegraph-mcp.exe` | MCP server | 读索引库，暴露工具；可常驻或按需 |

- 索引库位置固定（`<data_dir>/index/<plugin-id>/<work_dir-hash>/` 或引擎现有索引目录），由 `pluginhost` 通过 env / argv 注入 `CHONKPILOT_INDEX_DIR`；MCP 工具以只读方式打开。
- **工具只查索引，不判断状态**：查到 → 返回结果；查不到 / 索引缺失 / 打不开 → **工具调用失败**（错误信息带 `index missing/unavailable`）。
- 不做 `index_status` 表、不做 `indexing` / `retry_after` 协议；工具不读配置、不扫描文件、不判断“文件是否已打开”。
- 索引完整性、文件变化、打开状态由 indexer 自己维护；工具只认查询结果。
- 并发：工具只读连接；indexer 写侧用 WAL / 原子替换；读失败按普通工具失败返回。

#### 11.8.4 为什么更简单

- 不需要给 MCP server 加 resident 字段；gateway 现有 pool / idle / reap / kill+respawn **完全不动**。
- resident plugin 是 server 的“常驻订阅者”，类似现有 `plugin.Hook` 的外部进程版；只增加 `pluginhost` 与 transport。
- **工具侧零状态**：不读配置、不查索引状态、不重启 indexer；只读索引库，查不到就失败。
- MCP server 无状态，杀 / 重启成本低；索引只在 resident plugin 里维护。
- 后续把所有外移工具集中到一个工程时，仍按「indexer 常驻 + MCP 工具」拆分；随系统分发。**落点（2026-10-17 定）**：沿用现有模块 **`chonkpilot-mcp-tools`**（`github.com/chonkpilot/chonkpilot-mcp-tools`），目录保持 **`src/lib/mcp-tools/`**（不使用 `src/tools/`，那里是构建工具 `genmsg`）；内部按域落 `cmd/`，共享 `internal/pluginclient`（插件桥客户端 SDK）；产物投放 `dist/desktop/tools/`、`dist/server/tools/`；`src/plugin-cli/` 仅为第三方接入样例，不是工具工程。实施登记见 [49 BRIDGE-2](../spec/40-roadmap/49-待实现项.md)。

#### 11.8.5 与现有实现的关系

- 复用：`plugins/plugin.Hook` 的启动顺序 / Stop 逆序、`mq.Bus`、`filesys` watcher、`instance.Manager`、`pluginbridge` transport。
- 新增：`pluginhost`（server 与 desktop 两处装配）负责 resident plugin 的 spawn / stop / restart；resident plugin **不经过** `gateway.connectServer`。
- `gateway` 不改：MCP server 仍按现有 `connectServer` + pool 管理；工具侧只读索引。
- 现有 codegraph / vfts 内部插件可先继续进程内；后续拆成 `*-indexer.exe` + `*-mcp.exe` 时再迁移。

#### 11.8.6 验收

- resident plugin 随 server 启停；空闲不退出；用户取消不影响它。
- 索引缺失 / 未建好时，MCP 工具调用**直接失败**（不等待、不重试协议）。
- 崩溃重启后索引可恢复；MCP server 被 kill / respawn 后工具仍可读索引。
- 多 `work_dir` 索引隔离，`instance-exit` 不误删其他项目索引。

### 11.9 调用上下文（`_meta` / `context`）

现有机制（决策 R-11）：调用上下文**不走 tool arguments**，由 gateway 在 `tools/call` 的 `_meta.chonkpilot` 注入。字段：

| 字段 | 含义 |
|---|---|
| `instance_id` | 实例 |
| `work_dir` / `data_dir` | 项目目录 / 数据目录 |
| `session` / `turn` | 会话 / 轮次 |
| `tool_call_id` | 本次工具调用 |
| `top_session` / `parent` | 任务树归属 |
| `purpose` | 本次调用目的 |

注入规则：

- `Origin=builtin`（self / dir / 本仓工具）→ gateway 注入完整 `_meta`；第三方 `Origin=user` 默认**不注入**。
- 我们的 `*-mcp.exe` 在 `servers/register` 标 `Origin=builtin`（或显式 `context:"meta"`）即可拿到上下文。
- `mcp-server` lib 的 `CallContext` 目前只解析 `instance_id/work_dir/data_dir/purpose`；要支持 `session/turn/tool_call_id/top_session/parent`，需扩展 `callContextFromMeta`（原始 `_meta` 对工具 handler 仍可见）。
- 插件 transport 的 `plugin/v1/<method>` 请求 / 工具回调统一带 `context` 对象（字段同上）；MCP 工具仍用 `_meta.chonkpilot`，两者语义一致。
- 第三方 MCP 若需要上下文：在工具 schema 显式声明 `work_dir` / `instance_id` 参数，或由用户配置 `context:"meta"` 信任开关；默认不注入。

索引工具用法：`*-mcp.exe` 从 `_meta.chonkpilot.work_dir` 定位 `CHONKPILOT_INDEX_DIR/<work_dir-hash>`，用 `session/turn` 做查询过滤；索引缺失或查不到 → 工具调用失败。

### 11.11 GUI 动作反向通道（plugin → GUI）

现状：`gui.*` 由 GUI 桥本地 `guiDo` 处理；纯前端主题（`preview-tab-open` / `lf-*`）只在 WebView JS 内分发，后端 `/publish` 丢弃。插件 → GUI 需要一条反向通道。

- 统一方法：`plugin/v1/gui.apply {target_instance_id, action, payload}`。
- **桌面单体 / GUI 宿主（同进程）**：pluginbridge 直接调用 GUI 的 `appHandler` / `guiDo`，或 `Eval("window.mq.emitRemote(...)")`。
- **server + browser / gui 分体**：server 通过目标 instance 的 UDS / SSE 下发 `gui-event` 信封，由 GUI 桥 `emitRemote` 到 WebView。
- 目标实例必须存在；无目标 = 失败；**不允许默认广播到所有窗口**（仅显式 `target="*"` 的窗口类动作）。
- 纯前端主题走 `gui-event`，**不新增 MQ 主题**；`gui.*` 本地面走 `gui.apply` 的 action 映射。
- 安全：`features.gui.can_control=true`；`gui.native.*` 仅同机 + 路径校验 + 审计；默认关闭。

### 11.12 消息元数据（61 扩展，2026-10-17）

> 目的：每个 topic 不只定义 payload，还要定义“它是什么消息、能不能被插件改”。落地时作为 61 schema 的扩展元数据（`x-chonk`）与 msgkeys 生成源；当前先在设计稿定义，实施时同步进 61。

| 字段 | 取值 | 说明 |
|---|---|---|
| `kind` | `event` / `query` / `command` / `response` / `control` / `local` | `event` = 通知；`query` = 请求-应答；`command` = 改状态的单向；`response` = `data-*` 应答；`control` = 实例 / 插件控制；`local` = GUI / 前端本地 |
| `direction` | `c2s` / `s2c` / `s2s` / `plugin` / `gui-local` / `fe-local` | 方向 |
| `scope` | `instance-required` / `instance-optional` / `global` / `local` | 是否需要实例 |
| `frequency` | `low` / `medium` / `high` / `stream` | `high` / `stream` 禁止 `filter` |
| `visibility` | `call` / `observe` / `filter` / `internal` | 与 §11.7 级别对应 |
| `mutable` | `none` / `payload` | 是否允许改 payload |
| `mutable_fields` / `immutable_fields` | `string[]` | `replace` 时校验；不可改字段变化 → 直接拒绝 |
| `drop` | `bool` | 是否允许丢弃；默认 false |
| `schema` | `$ref` | 原 payload / 修改后 payload 的校验 schema |
| `version` | `int` | 配合后续全量改名 / 契约版本 |

**首批允许修改（P0，4 个）**

| topic | kind | 可改字段 | 不可改 | 代码依据 |
|---|---|---|---|---|
| `session-start` | command | `llm` / `scenario_id` / `think` / `effort` | `instance_id` / `session` / `turn` / `parents` / `agent` / `continue` | `StartReq` → `newTurnCtx` / `resolveTurnScenario` |
| `session-send` | command | `content` | `type` / `tool_call_id` / `instance_id` / `session` / `turn` | `onLLMSend` → `FeedText(req.Content)` |
| `llm-simple` | query | `prompt` / `system` / `llm` | `instance_id` | `onLLMSimple` 直接拼 messages |
| `mcp-tools-call` | command | `arguments` | `name` / `tool_call_id` / `instance_id` | gateway `CallToolParams.Arguments` |

> `session-start` **不携带 `q` / `system`**；用户正文在 `session-send.content`。所以“before LLM send”的正文修改点是 `session-send`，`session-start` 改的是本轮 LLM/场景参数。

**候选（P1，默认不开）**

| topic | 可改字段 | 风险 |
|---|---|---|
| `prompt-optimise` | `content` | 只影响提示词优化结果 |
| `filesys.create` | `content` | 文件内容；`name` / `dir` 不建议改 |
| `filesys.rename` / `filesys.copy` | `new_name` | 路径移动；需根内校验 |
| `agent-wizard-compose` / `agent-wizard-generate` | `description` / prompts | 会写场景 / agent 文件，风险高 |

**其余全部 `mutable=none`**：`session-receive`、`tool-notify`、`filesys.changed`、`task-*`、`data-*`、`instance-*`、`gui.*`、`login-*` 等。

**规则**

- 只有 `mutable=payload` 且绑定到**显式 filter stage**（§11.13）的主题才允许改；`observe` 一律不能改。
- `replace` 必须保留 `immutable_fields`，并通过修改后 schema 校验；失败 → 中止并审计。
- `drop` 仅在 `drop=true` 时允许；`drop` 记审计。
- filter 仅 `frequency=low/medium`；`high/stream` 强制只读；禁止 `>` 通配。
- `kind=query` 的 **response 不 filter**（v1 只做请求侧 before-hook）；`control` 永不 filter。
- **v1 不做通用拦截**；改用 §11.13 的显式 filter chain。
- 本元数据是 §11.7 级别的**单一来源**；实现时用同一份表生成订阅 / filter 白名单，不在代码里另写一套判断。

### 11.13 Before-Hook / Filter Chain（替代通用拦截）

只对 4 个 P0 阶段开 filter：

| stage | 对应 topic | 执行点 |
|---|---|---|
| `llm.before_start` | `session-start` | `newTurnCtx` / 落库之前 |
| `llm.before_send` | `session-send` | `FeedText` 之前 |
| `llm.before_simple` | `llm-simple` | `llmOnceSpec` 之前 |
| `tool.before_call` | `mcp-tools-call` | `CallTool` 之前 |

- 注册：`plugin.filter.register {stage, priority, fields}`；服务端维护有序链。
- 执行：server 在副作用前调用 `filter.run(stage, payload, ctx)`；每个 filter 返回 `{action:"pass|replace|drop", payload?}`。
- 失败：任一 filter error / 超时 → **中止整条链**，返回错误；**不 publish、不调用 LLM、不执行工具**；记审计。
- 校验：每步 `replace` 后校验 schema + `immutable_fields`；不合法 → 中止。
- 顺序：`priority` 升序，同优先级按 `plugin_id`；每 stage 单链，禁止通配。
- 超时：单 filter 200ms、整链 1s（可配）；默认 **fail-closed**。
- **服务端强制执行**：filter 在 server handler 内执行，不依赖调用方先发 `before`，客户端无法绕过。
- **唯一允许的阻塞例外**：阻塞仅限当前请求 + 挂载的 filter + 有界超时；不影响 MQ 总线和其他请求。响应侧 `after` filter（`llm.after_receive` / `tool.after_result`）不在 P0，等请求侧稳定后按 §11.17 的表再盘点。

```text
sender --session-send--> server
  server: filter.run("llm.before_send", payload)
    filter A -> replace content
    filter B -> pass
  error -> return {accepted:false}; 不调用 LLM
  ok    -> FeedText(filtered content)
```

> 可选的两阶段写法（`sender → llm-before-send(request) → filters → sender → llm-send`）也能工作，但要求所有发送方改造、且可被绕过；**不建议**作为主路径。
> 其他 publish 保持 fire-and-forget；查询类用 `request_id` + `result/error` 事件；不再做通用拦截。

### 11.14 查询与关联：`request_id` + `result/error`（不引入 Request/Future）

- 请求：`{request_id, client_seq, instance_id?, ...}`。
- 结果：`{request_id, client_seq, instance_id, ok:true, result}`。
- 错误：`{request_id, client_seq, instance_id, ok:false, error:{code,message}}`。
- `request_id` 在实例内唯一；服务端以 `(instance_id, request_id)` 关联，避免多实例冲突。
- `client_seq` 由前端 / 调用方单调递增；服务端只原样回显，不解释。
- **查询**（list/get/status）必须带 `request_id` + `client_seq`；结果走 `<topic>-result` / `<topic>-error`。
- **命令**可选带 `request_id`：带 = 要完成/错误回执（`<topic>-done` / `<topic>-error`）；不带 = 纯 fire-and-forget。
- **事件**不带 `request_id`；订阅者只观察。
- **filter** 是 server 侧 before-hook，不是 request；失败中止（§11.13）。
- SDK 可以提供 `await` 语法糖，实现 = 注册一次性监听 + `request_id` 匹配；**线协议没有 Future**。

**查询竞态：latest-request-wins**

- 每次查询带 `request_id` + `client_seq`；服务端原样回显。
- 前端保存 `latest_client_seq`；`result/error` 到达时，若 `client_seq < latest_client_seq` 或 `request_id` 不匹配 → **直接丢弃**。
- 例：全文搜索输入 5 次 → 5 个请求；即使第 3 个最后返回，也不显示第 3 个结果。
- 输入侧可加 100–150ms debounce；可选按 `request_id` 取消旧查询；不依赖 Future。
- **latest-wins 只用于查询结果展示**；`save` 等命令的副作用不能因为“有更新的请求”而丢弃。

```text
filesys.list {request_id:"r1", client_seq:1}  → 丢弃（latest=5）
filesys.list {request_id:"r3", client_seq:3}  → 丢弃（晚到）
filesys.list {request_id:"r5", client_seq:5}  → 显示
```

```text
filesys.list {request_id:"r1", client_seq:1}  → filesys.list-result {request_id:"r1", client_seq:1, result:{items}}
save {request_id:"r2", client_seq:2}          → saved {request_id:"r2"} / save-error {request_id:"r2"}
session-receive {...}                        → 无 request_id
```

**前端响应式约定**：

- 组件不直接 `await` 查询；由 store 发请求、订阅 `result/error`、更新响应式状态，组件只读 store。
- 例：`files` store 的 `list()` 发 `filesys.list`，收 `filesys.list-result` 后写 `files.items`；UI 只渲染 `files.items`。
- `loading` / `error` 也进 store；不做组件级请求状态。
- `dataClient` 保留为底层关联工具（`request_id` + 一次性监听），不再作为组件主要数据源。

### 11.15 Load once + 事件增量缓存（配置 / 元数据快照）

**目标**：每个 `work_dir` / 执行体至少持有一份配置/元数据快照；启动或首次进入时 **load 一次**，之后只监听 `saved` / `deleted` 增量更新；前端用响应式 store，不再每个页面先 GET 一遍。

**Scope 与 key**：

| scope | work_dir | exe_id | 内容 |
|---|---|---|---|
| `system` | 无 | 无 | 系统配置 |
| `user` | 无 | 无 | 用户配置 |
| `prj` | 有 | 无 | 项目配置 |
| `executor` | 有 | 有 | 执行体专属配置 |

缓存 key = `(scope, work_dir?, exe_id?)`。

**消息**（新增，按 §11.10 暂定名）：

```text
config-load     {request_id, scope, work_dir?, exe_id?}
config-snapshot {request_id, scope, work_dir?, exe_id?, revision, items}
config-saved    {scope, work_dir?, exe_id?, key, value, revision, updated_at}
config-deleted  {scope, work_dir?, exe_id?, key, revision}
```

**初始加载同样是两次 publish**：`config-load` 请求 → `config-snapshot` 结果；之后才是 `config-saved/deleted` 增量。`config-snapshot` 带 `request_id` 关联。

**规则**：

- `snapshot`：整表替换，记录 `revision`。
- `saved`：`revision == local+1` → upsert；`revision <= local` → 丢弃；`revision > local+1` → **触发一次 resync**（可能漏事件）。
- `deleted`：同规则，按 `key` 删除。
- `revision` 由 server 按 scope/key 单调递增；多窗口并发 save 由 server 定序。
- 重连、切换 `work_dir`、进入新项目 → 只做一次 snapshot resync。
- **密钥脱敏**：`saved` 里的 value 不含真实 `apiKey` / token；用 `hasApiKey:true` / `masked:"sk-***"` 表示；前端永不缓存明文密钥。
- 默认不做乐观更新：先标 `pending`，收到 `saved` 再落 store；需要时再开乐观 + 回滚。
- 适用范围：用户/项目/系统配置、LLM、MCP servers、场景、提示词、能力清单、执行体配置。会话/任务这类大数据仍用查询 + `latest-request-wins`，不做全量常驻。

**现状与改动**：

- 现有 `data-user-config-refresh` / `data-prj-config-refresh` **只是失效信号，不带 key/value**。
- 新增 `config-snapshot/saved/deleted` 承载增量；旧 refresh 在迁移期保留，一次性切换后移除。
- 前端新增 `configStore`（按 `work_dir` 分区）；`load()` 只调一次，之后订阅 `config-saved/deleted`。
- 页面只读 store，不再各自 `get`。

**判定**：配置类数据量小（模型/MCP/场景/提示词通常几十到几百条），全量常驻可行；超过阈值的数据集不做常驻，仍走分页查询。

**四个层级全部 snapshot**：

- `system` / `user` / `prj` / `executor` 各持一份快照；
- 前端计算 `effective = merge(system, user, prj, executor)`；任一层 `saved/deleted` 只重算 effective，**不触发页面重新 get**；
- 写路径统一：`config.save` / `config.delete`（带 `scope` + `work_dir` + `exe_id` + `key` + `value` + `request_id`）→ server 落库 → `config-saved` / `config-deleted` → store upsert/remove；
- 页面不需要逐层保存、逐层刷新。

### 11.16 大数据集：LOD / 分页 / 节点失效

`snapshot` 只用于配置和元数据；**目录树、知识库、任务树、会话列表、搜索结果**数据量大，走 **load on demand（LOD）**。LOD 只是**加载策略**，不是协议；传输仍然是 **两次 publish**：`load` 请求 + `loaded` / `load-error` 结果，靠 `request_id` 关联，**不使用 Request/Future**。

**LOD 的传输形状**：

```text
tree-load {request_id, work_dir, path}
  → tree-loaded {request_id, work_dir, path, children, revision}
  → tree-load-error {request_id, error}

展开节点同理：tree-load {path: child} → tree-loaded {children}
```

| 数据 | 策略 |
|---|---|
| 目录树 | 先 load 根，展开时 load children；缓存 key = `(work_dir, path)`；`filesys.changed` 只失效父节点 / 前缀；虚拟滚动 |
| 知识库 | 先 load 根 / 当前层；展开时 load children；`data-kb-*` 或节点 `revision` 失效对应子树；不整树常驻 |
| 任务树 | 分页 + `tasktree-load` → `tasktree-loaded`（两次 publish） | 不常驻 |
| 会话列表 / 消息 | 分页 + `session-list-load` → `session-list-loaded`；消息流用事件增量 | 不整库常驻 |
| 搜索结果 | `request_id` + `client_seq` latest-wins；只保留最后一页结果 |

**保存大对象**：

- 仍用 `command + saved/deleted`，但事件带 `path` / `parent` / `op`；
- 前端只更新受影响节点，**不整树 reload**；
- 事件缺少路径信息时，退化为失效父节点或根前缀，不做全量刷新。

**分页 / 阈值**：children 超过一页或虚拟窗口大小就分页；缓存按 LRU 限制节点数。

### 11.17 两次 publish 原则（架构不变量）

**任何跨进程 / 跨端请求都必须拆成两次 publish**：

```text
第一次：request publish   （发起）
第二次：result / error publish（回报）
```

- 传输层**不等待、不持有 Future**；调用方不阻塞总线。
- 关联键 = `(instance_id, request_id)`；结果可以来自任意节点 / 连接。
- 这不是“为了异步而异步”，而是为了：
  - **去中心化**：请求方和结果方不必同进程、同连接、同节点；
  - **多端接入**：GUI、CLI、插件、远程 MCP 都能发请求 / 收结果；
  - **无队头阻塞**：慢请求不会卡住整条 MQ；
  - **慢消费者隔离**：慢插件只影响自己的队列；
  - **可回放 / 审计**：请求与结果都是消息；
  - **可水平扩展**：结果可以由另一个节点产出。
- 超时 = 调用方本地定时器；超时后按 `request_id` 丢弃晚到结果。
- 幂等：`request_id` 去重；结果可能重复，消费方必须幂等。
- SDK 的 `await` 只是本地语法糖（一次性监听 + `request_id` 匹配），**不是线协议**。

**唯一例外：server 内部 filter chain（§11.13）**。它允许在 handler 内等待，但阻塞范围仅限：

- 当前请求；
- 挂载的 filter；
- 有界超时；
- 不影响 MQ 总线和其他请求。

这是“用户自己挂的 filter 处理不当”，不是系统级阻塞。

**用 request/result 对找 filter 点**：

| 请求 → 结果 | 结果是否被二次加工 / 用于副作用 | filter |
|---|---|---|
| `session-start` → `session-accepted` | 否（只确认） | `before_start`（请求侧） |
| `session-send` → `session-complete` | 是（正文进入 LLM） | `before_send`（请求侧） |
| `llm-simple` → `llm-simple-result` | 是（prompt/system 进入 LLM） | `before_simple`（请求侧） |
| `mcp-tools-call` → `tool-result` | 是（arguments 进入工具） | `before_call`（请求侧） |
| `filesys.list` → `filesys.list-result` | 否（只展示） | 不需要 |
| `task-list` → `task-list-result` | 否（只展示） | 不需要 |

结论：**只有“结果还会被继续加工/消费”的请求-结果对才值得挂 filter**；纯展示/纯存储不需要。P0 先做 4 个请求侧 before；响应侧 after（如 `llm.after_receive` / `tool.after_result`）等这批稳定后再按同一张表盘点，不在 P0 开。

## 13. 两级实施计划（L1 任务清单 / L2 逐任务调研）

| **T7** | `tools/register` 在 `MCPServer == nil` 时失败；`handler_subject` 依赖进程内 `bus.Emit + Wait`；`CancelExec/DetachExec` 是进程内 sink | 保留 gateway 作为注册/路由中心；**所有工具外移，server 零工具**；外部 tool provider 走 pluginbridge 的 `tool.invoke` 请求 + `request_id` + `result/error` 事件；补 `cancel/detach/wait`；`_meta` 扩展 6 字段 | 已定：server 零工具；补外部取消/转后台语义与回调超时 | 外部工具注册/调用/取消/转后台/回调 |
| **T1** | `uds.Server` 无订阅协议；`uds.Client.On` 本地过滤；`udsapi` 只 `On(">")` 全量转发并绑定单实例 | 新建 `core/transport` + `pluginbridge`；`sub/unsub` 帧；每会话订阅表；有界队列；不复用 `udsapi` | 已定：复用现有帧格式；UDS 优先、TCP 仅 loopback；连接上限为实现细节 | 订阅过滤、背压、断线清理 |
| **T5** | `gui.*` 由桥 `guiDo` 本地处理；纯前端主题被桥丢弃 | `gui.apply` + `gui-event`；desktop 直调 / server 按 instance 下发 | 已定：全部开放（含 `layout.free`）；GUI/Desktop 共享同一前台；`gui.native.*` 保留路径校验+审计 | 目标窗口可达；无目标失败；纯前端镜像 |
| **T8** | `instance-claim` 接受客户端 id；`Manager.HandleRegister` 同 id 覆盖；`uds.bind` 同 id 顶旧连接 | 服务端生成 `plugin:<id>:<uuid>`；重复拒绝；GUI id 保护；resident 不注册实例 | 已定：64 上限内；插件实例不进用户实例列表 | 劫持/覆盖/清理/上限 |
| **T9** | `filesys` 只在 `httpapi.Start` / desktop host / CLI 启动；desktop 无 `udsapi/httpapi` | pluginbridge/pluginhost 双装配；filesys 解耦为总线能力宿主；启动顺序 listener → bridge → host → resident | 已定：desktop 默认开插件入口；CLI 默认不开 | desktop/server 双形态冒烟 |
| **T10** | 61 只有业务消息表；无 kind/mutable 元数据 | 增 `x-chonk`；生成订阅/filter 白名单；新主题落 planned；维护暂定名映射 | 已定：元数据进 schema；改名独立批次 | schema/msgkeys/前端一致 |
| **T13** | `dataClient` 是 publish + promise，组件直接 `await`；多请求会互相覆盖 | store 发请求 + 订阅 `result/error`；`request_id` + `client_seq` 做 latest-wins；晚到结果丢弃；`loading/error` 进 store | 组件改造范围；debounce 可选；命令副作用不能丢 | 连续 5 次搜索只显示最后一次；乱序返回不覆盖 |
| **T14** | 现 `data-*-config-refresh` 只发失效信号；页面各自 `get` | 新增 `config-snapshot/saved/deleted`；`revision` 增量；`configStore` 按 `work_dir` 分区；启动只 load 一次；密钥脱敏 | 全量常驻阈值；旧 refresh 迁移；多窗口并发定序 | 只 load 一次；save/delete 增量更新；漏事件 resync |
| **T15** | 目录树 / 知识库可能整树拉取；数据量大 | 根 + 展开时加载 children；**`load` + `loaded` 两次 publish**；节点缓存 LRU；`filesys.changed` / `data-kb-*` 失效父 / 前缀；分页 / 虚拟滚动；保存事件带 `path` | 事件粒度；缓存上限；失效策略 | 不整树常驻；展开加载；局部刷新 |

### 13.5 开工前确认

**无待拍板项。** 全部按已定口径执行：

- **所有工具外移，server 零工具**；gateway 只保留注册 / 路由 / 调度。
- **GUI / Desktop 共享同一前台，全部控制开放（含 `layout.free`）**；`gui.native.*` 保留路径校验 + 审计。
- 能纯 publish 的都纯 publish；命令用完成/错误事件收尾；查询用 `request_id` + `result/error` 事件；**不使用 Request/Future**。
- Filter 是 server 内部 before-hook，失败/超时 **fail-closed**（不发送）。
- 前端用响应式 store：action 发请求，store 订阅 `result/error`，组件只读 store。
- **每个 work_dir 一个索引库**，固定路径，不做分区。
- 50 测试体系登记「帧驱动 + 帧断言」豁免。
- 一次性切换，不做半迁移 / 兼容别名。

> 开工后不再逐项打断；新需求进 backlog，只有阻塞性未知才停。

### 13.6 变更控制

- 编码期发现新问题：先判断是否阻塞当前批次；不阻塞 → 记 backlog，继续；阻塞 → 停下来问，不猜。
- 每个批次结束必须过验收；未过不进入下一批。
- 不做半迁移、不留兼容别名；61 改名按独立批次全量替换。
