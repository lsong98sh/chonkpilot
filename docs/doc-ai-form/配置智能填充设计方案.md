## 1. 问题与目标

### 1.1 要解决的问题

配置页（LLM / MCP）与工具（原语）编辑页目前**全部手填**：用户要配一个模型，必须自己知道 `model` / `baseUrl` / 上下文窗口 / 协议 / 能力标志等一整套参数；要新建一个工具，必须自己写契约 md（基本信息 / 摘要 / 参数 JSON / 正文）。

结果是：
- 门槛高——用户只想要「用 GLM 的某个模型」，却被迫先成为 provider 参数专家；
- 易错——`baseUrl` / `protocol` / 上下文窗口填错，要到用报错才发现；
- 重复劳动——已经能一句话说清的需求（"做一个 Excel 转 CSV 的工具"），却要手写成契约。

### 1.2 目标（可验收）

| # | 目标 |
|---|---|
| G1 | 在 LLM 配置弹窗、MCP 配置弹窗、工具原语编辑页各提供**一个「AI 填充」入口**：用户用自然语言描述需求 → LLM 产出**结构化字段建议** |
| G2 | 建议**只回填表单待保存态**（高亮「AI 建议」），**不自动落库**；是否采纳、是否保存由用户决定 |
| G3 | 回填后**复用既有校验**（LLM→【测试连接】；工具→保存后契约生效）后再由用户点【保存】 |
| G4 | 工具原语支持**按需求生成整份契约**（标题 / 摘要 / 参数 JSON / 正文），沿用 `data-knowledge-save` 落盘 |
| G5 | 复用既有 LLM 调用与 provider 选择机制（子系统默认 LLM `llm.promptOptimise`），**不引入第二套 LLM 配置** |

### 1.3 非目标（本版不做）

- **不代填 `apiKey`**（任何形态、任何来源）。
- **不自动落库 / 不自动保存**（建议态 ≠ 落库态）。
- **不联网检索**（V1 仅靠模型自身知识；"查最新参数"的联网版见 §10）。
- **不新增表单字段 / 不改现有配置键语义**（如尚无「计费模式」键 → 见 §10 V2）。
- **不处理** [36-配置 §3.2](../spec/30-function-points/36-配置.md) 的"只写不读"死键（不为其生成配置）。
- **不改** 新建原语的既有流程（先建文件再编辑）；本版只增强**编辑页**的填充能力。

## 2. 总体方案

统一一条三段式链路，三处表单共用：

```text
用户：自然语言（"我要用 GLM 的 X 模型" / "连一个 GitHub MCP" / "做一个 Excel→CSV 工具"）
   │
   ▼  ① 建议（LLM）
「配置助手」一次性调用 → 结构化 JSON（仅该表单白名单字段）
   │
   ▼  ② 回填（只改待保存态，不落库）
表单字段填充 + 标「AI 建议」；禁用/禁填字段（apiKey 等）保持不动
   │
   ▼  ③ 校验（复用既有能力）
LLM：点【测试连接】探活；工具：保存后契约生效 / 列表可见
   │
   ▼  ④ 用户点【保存】才落库
```

**为什么可行（现状已具备）**：

- 已有 LLM 调用管道：`gui.prompt-optimise` / `chonk.prompt-optimise`（流式生成/优化；provider = 子系统默认 LLM `llm.promptOptimise`；稳定错误码 `optimizeError.<code>`）——见 [optimize.go](../src/lib/gui/bridge/optimize.go)、[prompt.go](../src/lib/llm/server/prompt.go)。
- 已有「点分主题直通总线 + 同步请求-应答」范式：`llm.test-connection`（`chonk.llm.test-connection{...}` → 同步应答 `{ok, latency_ms, model_echo?, error{kind,message}}`）——见 [llm_testconn.go](../src/lib/llm/server/llm_testconn.go)。
- 已有「新增 LLM 消息」先例：`zprompt-summarize` / `zprompt-summarized`（2026-10-14，D-55，用于原语描述提取）。
- 已有原语「AI 生成正文」先例：`PrimitivePanel.vue` 的 `handleGenerate` 已复用 `prompt-optimise`（`useCase` = 契约类型 + 大纲）生成**正文**。
- 已有原语文件树写盘通道：knowledge 域 `KnowledgeDoc`（name/title/meta/description/parameters/content）+ `data-knowledge-save`，序列化由 `contractmd.Build` 承担——见 [knowledge.go](../src/lib/data/facade/knowledge.go)。

### 3.2 R1 · 后端调用面（建议形态）

```text
主题（点分相对主题，直通总线）：config.suggest
请求 payload：{ instance_id?, kind, text, current? }
   kind    = "llm" | "mcp" | "tool"     （目标表单种类；决定白名单与指令）
   text    = 用户自然语言
   current = 当前表单值（可选；供增量补全 / 保持已填项）
应答 result：{ ok, fields: {<字段>: <值>}, notes?, error?: {kind, message} }
   fields 只含该 kind 的**白名单字段**（见 §4）
```

要点：
- **provider 选择口径统一**：与 `prompt-optimise` 一致，读 `llm.promptOptimise`（缺失/空串由数据层读侧回落 `defaultLLM`）；**现读配置、热生效**，不缓存到进程级。
- **一次性、非流式**：结构化 JSON 用一次性返回最简单（流式半截 JSON 无展示价值）。超时按 §6 处理。
- **指令模板**：按 `kind` 选择"字段清单 + 输出 JSON schema + 禁止项（apiKey）"的固定指令（对齐 `optimiseInstruction` 的写法：只输出结果、无解释）。
- **输出解析**：严格 `json.Unmarshal`；解析失败 → 明确错误（复用 `optimizeError` 风格的稳定错误码）。
- **复用**：`llmOnceSpec`（一次性无上下文会话入口）/ `specFor` + `providerFromConfig` 的 provider 解析链；失败恒走 result 信封（恒返回 nil，不抛总线错误，前端据 `result.ok` 分流）——与 `llm.test-connection` 同形。

### 3.3 R2 · 消息面（**须用户确认**）

两个候选（**择一**，均触碰 `61-消息一览` 冻结）：

| 方案 | 内容 | 代价 | 评价 |
|---|---|---|---|
| **A（推荐）新增点分主题 `config.suggest`** | 与 `llm.test-connection` 同范式：新增主题 + payload/result 字段 | 新增 1 个主题 + 字段；browser 形态需在 `allowedDottedPrefixes` 放行（[publish.go](../src/lib/llm/httpapi/publish.go)） | 语义独立、请求-应答清爽、便于对账测试 |
| B 复用 `prompt-optimise` 加 `type=config_suggest` | 不改主题，仅加 `type` 枚举值；前端把返回文本当 JSON 解析 | payload 语义漂移（"优化提示词"被挪作"配置建议"）；流式返回需前端拼完再解析 | 不推荐 |

> **冻结要求**：无论 A/B，须先按 [50-测试体系 §1](../spec/50-testing/50-测试体系.md) 经用户确认，并在 `61-消息一览.md`（§1 点分直通 / payload / result）登记；同步 `61-messages.schema.json`、`msgkeys`。

### 3.4 R3–R5 · 前端落点

**共同约定**：
- 入口形态 = 一个「AI 填充」输入框（自然语言）+【生成】按钮（不新造组件体系，复用 `Input`/`Textarea`/`Button`）。
- 回填 = **只改待保存态**（`localData` / `form`），并对被 AI 改动的字段加**「AI 建议」标记**；用户改动手填即清除标记。
- **禁填字段**（§4 标 🚫）与 `apiKey` 一律不动。
- 失败 = 人话文案（复用 `optimizeError.<code>` 的本地化风格）。

**R3 · LLM 配置（`EditLLMDialog.vue`）**：回填 `name/model/protocol/baseUrl/maxContextToken/maxOutputToken/thinking/reasoningEffort/capabilities`（`temperature`/`maxToolIterations` 仅给建议值）。回填后用户点既有【测试连接】（**只读探活**，不入库）验证。

**R4 · MCP 配置（`EditMCPDialog.vue`）**：回填 `name/transport/description` 及连接字段（`url` 或 `runtime+args+env`）、`namespace/timeout`。transport 变更须**联动显隐**（复用现有 `showUrl`/`showSpawn` 逻辑）。
> ⚠️ **校验边界**：「工具」页签的【加载工具】依赖该 server **已被网关注册**（按别名过滤 `tools-list`），AI 填充的草稿**未保存前无法加载工具**。故 MCP 侧 V1 **不做保存前预校验**，靠"保存后接入结果 / 再次编辑"体现（见 §6）。

**R5 · 工具原语（`PrimitivePanel.vue`）**：把既有「AI 生成」（现仅 `form.content` 正文，`useCase` = 类型 + 大纲）**升级为按需求生成整份契约字段**（`title/description/parameters/content`，`meta` 的 runtime/args 等按类型补）。仍走**既有保存通道** `data-knowledge-save`（`KnowledgeDoc` 领域形态，序列化 = `contractmd.Build`）。

### 3.5 复用 / 不新增

| 复用 | 不新增 |
|---|---|
| provider 解析（`llm.promptOptimise`）、一次性会话入口 | 不引入第二套 LLM 配置 |
| 稳定错误码风格（`optimizeError.<code>`） | 不新增错误码体系 |
| 【测试连接】探活、`tools-list` 加载 | 不新增预校验链路 |
| `data-knowledge-save` + `contractmd` 序列化 | 不新增写盘通道 |

## 4. 字段映射（AI 可填 / 禁填）

> 图例：✅ 可填 · ⚠️ 仅给建议值/需确认 · 🚫 禁填（安全/运行语义/密钥/归属）。

| 表单 | 字段 | 可填性 | 说明 |
|---|---|---|---|
| **LLM** | `name` | ✅ | provider 展示名（可推导） |
| | `model` | ✅ | 模型名 ← 用户描述 |
| | `protocol` | ✅ | `openai` / `responses`（按 provider 惯例） |
| | `baseUrl` | ⚠️ | 端点可能过时 → 必须由【测试连接】验证 |
| | `maxContextToken` / `maxOutputToken` | ⚠️ | 模型规格，可能过时；建议值 + 用户确认 |
| | `thinking` / `reasoningEffort` | ✅ | 推理开关/档位 |
| | `capabilities`（reasoning/vision） | ✅ | 能力标志 |
| | `temperature` / `maxToolIterations` | ⚠️ | 仅给默认建议值 |
| | `apiKey` | 🚫 | **绝不代填** |
| **MCP** | `name` / `transport` / `description` | ✅ | — |
| | `url`（http/sse） | ✅ | 公开 MCP 端点 |
| | `runtime` / `args` / `env`（stdio） | ⚠️ | 依赖本机已安装相应运行时 |
| | `namespace` / `timeout` | ⚠️ | 可给默认 |
| | `level`（App/User/Project） | 🚫 | 归属由用户定，不代选 |
| | `enabled` / `isolate` / `sandbox` | 🚫 | 安全 / 运行语义 |
| | `hot_tools` | 🚫 | 需已连接才可枚举 |
| **工具原语** | `title` / `description` / `parameters` / `content` | ✅ | 整份契约主体 |
| | `meta`（runtime/args/output/category/async/hot） | ✅/⚠️ | 部分恒为默认（如 `category`） |
| | `refs` / `delegate`（agent） | ⚠️ | 需已知名称，谨慎 |

**不适合智能化（C 类）**：`apiKey`、层级归属（level）、沙箱/隔离开关、窗口几何/布局、主题/语言、纯文件/目录选择（用系统选择器）。

## 5. 规则与约定

| 项 | 结论 | 理由 |
|---|---|---|
| 落库时机 | 建议**只回填待保存态**，落库仍由【保存】触发 | 列表类即落盘、表单类手动保存的既有口径（[CFG-015](../spec/30-function-points/36-配置.md)） |
| 幻觉防护 | 「建议 → 用户确认 → 校验」三段式；`baseUrl` 等必须过探活 | 模型名/端点/窗口可能编错 |
| 密钥 | `apiKey` 全程不参与 | 安全 |
| provider | 统一读 `llm.promptOptimise`（现读、热生效） | 与 `prompt-optimise` 一致，不另立配置 |
| 输出 | 严格结构化 JSON，仅白名单字段 | 便于回填 + 防越权字段 |
| 并发 | 建议比照 `prompt-optimise` 每实例在飞上限（B-24）限流 | 防无界 goroutine |
| 死配置 | 不为 [36 §3.2](../spec/30-function-points/36-配置.md) 死键生成配置 | 避免制造更多无效配置 |

## 6. 边界与异常

| 场景 | 处理 |
|---|---|
| LLM 返回非 JSON / 缺字段 | 明确错误（稳定错误码），不部分回填；用户可重试 |
| `kind` 未知 / `text` 为空 | 入参校验失败（对齐 `llm.test-connection` 的 `invalid`） |
| 生成耗时较长 | 一次性应答需设超时（建议 ≥ 前端 30s 口径，必要时延长）；超时 → 明确错误 |
| browser 形态 | 点分主题须在 `allowedDottedPrefixes` 放行，否则 `topic not allowed` |
| MCP 草稿未保存 | 无法【加载工具】→ V1 不预校验（§3.4 R4 说明） |
| 上游回显密钥 | 应答/日志强制脱敏（复用 `maskLLMSecrets` 思路） |
| 用户已手填部分字段 | `current` 随请求上传，指令要求"仅在需要时覆盖"；回填后仍可手改 |

## 8. 与既有机制的关系（消息面冻结评估）

- **是否改动数据层**：**否**（复用 `data-knowledge-save`；无新表/新键）。
- **是否新增配置键**：**否**（V1）。
- **CLI / 其它形态**：无 UI 形态自然不涉及；browser 形态仅需白名单放行。
