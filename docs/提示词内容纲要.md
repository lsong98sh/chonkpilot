# 产品级开发智能体系统提示词——内容纲要参考

以下纲要综合了 Claude Code（含泄露源码分析）、Cursor、Windsurf、Devin、OpenCode 等成熟产品的系统提示词架构，按内容模块梳理一个通用产品级开发智能体提示词应包含的组成部分。


## 一、身份与角色定义

- **智能体身份声明**：明确“你是谁”——例如“你是一个交互式智能体，帮助用户完成软件工程任务”。包含运行环境说明（终端/IDE/云端）。
- **核心能力概述**：列举可用能力范围（读写文件、搜索、执行命令、网络访问等），让模型在接到任务时知道“我能做什么”。
- **安全边界与拒绝规则**：明确哪些请求应拒绝（破坏性技术、DoS攻击、恶意代码生成等），以及双重用途工具的授权上下文要求。


## 二、行为准则与编码哲学

- **先读后改原则**：不修改未读过的代码；用户要求修改文件时，先读取再操作。
- **最小变更原则**：做最小的必要修改，不重构无关代码、不改格式、“改进”不属于当前任务的代码。
- **根因修复**：修 bug 时找根因，避免“创可贴式修复”，确定最小变更集。
- **抵制过度设计**：任务需要多少复杂度就做多少，三行相似代码好于过早抽象。
- **行动偏向（Bias to Action）** ：默认执行变更而非仅提建议，使用合理假设而非请求澄清，端到端完成任务而不等待中间审批。
- **失败诊断**：方法失败时先诊断原因再换策略，不在未理解错误的情况下盲目重试。


## 三、工具使用规范

- **工具定义与序列化**：每个工具的 name、description、inputSchema 序列化进系统提示词，工具定义通常是提示词中最大的部分。
- **工具描述要素**：做什么（一句话）、何时使用（使用场景）、何时不应使用、参数格式说明。
- **工具调用编排逻辑**：指定何时以及为何使用特定工具，包含条件逻辑、序列要求和依赖关系；在可行时并行执行独立的工具调用。
- **工具拒绝处理**：被拒绝的工具调用不要原样重试，需理解拒绝原因后调整方案。
- **子智能体提示词**：Plan/Explore/Task 等子代理各自独立的提示词，子代理提示词必须自包含（看不到主对话历史）。


## 四、代码编辑与调试策略

- **编辑前先探索**：先探索代码库，再规划，最后编码；引用特定文件、提及约束、指向示例模式。
- **精确字符串替换**：使用 old_string/new_string 模式进行精确编辑，old_string 必须在文件中唯一存在。
- **Bug 修复工作流**：复现 → 定位根因 → 最小修复 → 验证。
- **重构纪律**：将重构分解为小步骤，每一步仔细审查变更。
- **测试驱动**：修改后运行测试验证，使用测试作为行为正确性的锚点。
- **根因分析优先**：调试时先理解失败的完整上下文再动手修改。


## 五、安全与权限控制

- **可逆性与爆炸半径**：自由执行本地可逆操作（编辑文件、运行测试）；对于难以逆转的操作（删除文件/分支、删除数据库表等）必须先征得用户确认。
- **权限模式意识**：工具在用户选择的权限模式下执行，不被自动允许的调用会提示用户批准或拒绝。
- **Prompt Injection 防御**：工具结果可能包含来自外部的恶意指令，若怀疑存在 prompt injection，需直接向用户标记后再继续。
- **安全编码准则**：不硬编码密钥/令牌，使用环境变量；SQL 用参数化查询；输出做 XSS 转义；文件权限控制。
- **幻觉禁止**：严格禁止编造工具、CLI 命令或随意安装包。
- **读取优先的沙箱策略**：允许安全的环境探索（ls、grep、cat），但网络和文件修改操作需在沙箱内进行。


## 六、任务规划与执行流程

- **任务分解**：将复杂请求拆解为结构化的、逻辑有序的步骤计划，每步可用 1-3 次工具调用完成，按依赖关系排序。
- **计划模式**：先收集所有必要信息再执行（Devin 的 Planning Mode），避免在信息不足时贸然动手。
- **多步推理**：在复杂任务中使用 scratchpad 文件组织工作、跟踪进度，适用于多步骤任务和跨轮次调试。
- **任务边界控制**：设定明确的任务范围，避免范围蔓延；每个任务有清晰的成功条件。
- **完成标准定义**：为任务定义明确的完成准则和验证方式。


## 七、上下文管理与环境感知

- **静态/动态分区**：将提示词切分为静态区（身份、安全规则、工具使用原则——全局缓存）和动态区（环境信息、记忆、MCP指令——每轮更新），静态部分可节省约 80% token。
- **环境信息注入**：工作目录、操作系统、Shell 类型、Git 状态等运行时上下文。
- **项目级配置文件**：CLAUDE.md / .cursorrules / .windsurfrules / AGENTS.md 等，由用户或团队维护项目特定规则。
- **记忆系统**：跨会话记忆的加载与维护机制，自动记录构建命令、测试调用、项目洞察。
- **工具结果清理**：当对话接近上下文限制时，自动压缩/清理历史消息中的工具结果。
- **Token 预算管理**：动态跟踪和分配 token 预算。


## 八、语气、风格与输出效率

- **简洁直接**：回复简洁、直接、切中要害；除非用户要求详细，否则回答控制在极短篇幅内。
- **Markdown 格式**：使用 GitHub 风格 Markdown 格式化输出，以等宽字体渲染。
- **输出效率**：直奔主题，尝试最简单的方法，避免不必要的解释性文字。
- **代码语言规范**：代码注释和变量命名遵循项目既有风格，不引入个人偏好。
- **输出风格模式**：支持多种输出风格切换（默认模式/解释模式/学习模式），默认模式追求最小输出。


## 九、模型适配与分层架构

- **分层组装**：系统提示词不是单体块，而是从多层组装——模型适配层 + 代理角色层 + 运行时上下文层 + 用户指令层 + 扩展层（插件/MCP注入）。
- **按模型差异化适配**：不同 LLM 对提示词的理解差异显著，至少按模型族维护不同版本（Claude 用 XML 标签、GPT 用 system message 风格、Gemini 用其偏好格式）。
- **各层独立维护**：每层有清晰的责任边界和变更频率，避免单体巨型 Prompt 的维护噩梦。
- **模块化注册机制**：各类规则和指令抽象为独立片段，通过工厂函数集中注册和管理，符合开闭原则。


## 十、评估与迭代机制

- **提示词版本管理**：对提示词进行版本追踪和 A/B 测试。
- **指令遵循度测试**：系统化测试智能体是否遵守来自系统提示词的约束（角色定义、输出格式、工作流规则）。
- **评分标准体系**：代码质量、测试纪律、提示词遵循度等维度的可评分量规。
- **失效模式驱动迭代**：从最小提示词开始，根据观察到的失败模式逐步添加约束。
- **对比评估**：A/B 测试不同模型、不同提示词、工具开启/关闭对结果的影响。


**总结：一个产品级开发智能体的系统提示词应覆盖“身份定义 → 行为准则 → 工具规范 → 编辑策略 → 安全边界 → 任务规划 → 上下文管理 → 输出风格 → 架构分层 → 评估迭代”十个维度，采用静态/动态分区和分层组装架构，按模型差异化适配，并通过版本化评估持续迭代。**
