# Agent 角色提示词的维度框架

角色提示词不是散文，而是**结构化字段的集合**。按「由内到外、由稳定到易变」分层组织：前六层描述「这个角色是什么」（可在角色原型中预置复用），第七层描述「在这个项目里怎么表现」（实例化时注入），第八层是「不能越的线」，第九层是「让程序能管理它」。把角色当结构化数据而非散文来设计，才能被装配器实例化、被编排器流转、被测试验证、被版本化管理。

## 一、身份层（我是谁、我不是谁）
- 角色标识与名称：稳定的角色原型标识 + 面向用户展示的名称。
- 一句话职责：须含**边界声明**（例：「我只负责实现，不做架构决策」）。
- 资深程度与语气风格：影响措辞与决策风格。
> 关键：身份层要让模型清楚「我是谁、我不是谁」。

## 二、职责与边界层（最易被忽略、也最关键）
- 核心职责（1–3 条）与次要职责（可裁剪）。
- **明确不做什么**（`out_of_scope`，比做什么更重要）。
- 上报条件（何时必须上报主控/用户）、完成后交接对象。
- **完成的可验证定义**（`success_criteria`）。
> 关键：缺 `out_of_scope` 会越界；缺 `success_criteria`，编排器无法判定是否该流转。

## 三、方法论层（怎么想、怎么做）
- 标准工作流（如：先探索 → 再规划 → 再实现 → 自验证）。
- 决策启发式（如「最小变更优先」「根因优先于补丁」）、推理模式、冲突时的优先级（正确性 > 简洁性 > 性能 > 风格）。
- 明确要避免的常见错误做法与质量门槛，并给出样例。
> 关键：同一角色原型在不同技术栈下可沿用同一方法论，只微调细节。

## 四、工具与能力层（权限必须白名单化）
- 必需工具白名单 / 可选工具池 / 明确禁止的工具（安全边界）。
- 工具使用规范（何时用、何时不用、并发规则）、模型档位、可委派层数、是否允许创建子角色。
> 关键：实例化只从可选工具池中筛选，**不允许自由增删权限**。

## 五、输入/输出契约层（可被编排器解析）
- 输入：接收什么、前置条件（如「必须有已确认的架构文档」）。
- 输出：结构定义（diff / 报告 / 测试用例 / 计划）、格式约定（Markdown / JSON / 代码块 / 结构化文本）、正例与反例、是否幂等。
> 关键：没有结构化输出，主控无法解析子角色结果并决定下一步。**契约必须可解析**。

## 六、协作层（决定多角色拓扑）
- 向谁汇报、与谁平级协作、可委派给谁。
- 冲突解决机制、跨角色通信风格、可访问的共享上下文（项目规格、历史决策、代码索引）。
> 关键：角色须声明协作意图，装配器才能正确连线。

## 七、上下文感知层（通用角色 → 本项目角色的关键）
- 需要注入的项目上下文（技术栈、架构、目录结构）。
- 必须遵守的项目约定（命名、目录、提交信息、测试框架）。
- 引用的工程规格章节、运行时动态上下文来源、长期记忆的读写方式。
> 关键：同一个角色原型注入不同项目上下文后，行为差异巨大——本层决定「在这个项目里怎么表现」。

## 八、约束与纪律层（不能越的线，含 `hard_constraints`）
- 不可协商的**硬约束**（安全、合规、性能底线）、可协商的软约束、输出风格规则。
- 明确禁止的行为清单、触发上报/暂停的条件、完成前的自验证清单。
> 关键：与技术栈强相关的强制纪律属于硬约束子集，按项目注入。

## 九、元信息层（让程序能检索与组装）
- 版本号、变更记录、维护者、分类标签。
- 适用模式（从零构建 / 迭代 / 重构）、适用技术栈、依赖的其他角色。
> 关键：装配器通过标签与适用条件做规则匹配，通过依赖关系做完整性校验。

**总结**：角色提示词 = 身份 + 职责边界 + 方法论 + 工具能力 + I/O 契约 + 协作关系 + 上下文注入 + 约束纪律 + 元信息。前六层是「这个角色是什么」，第七层是「在这个项目里怎么表现」，第八层是「不能越的线」，第九层是「让程序能管理它」。
