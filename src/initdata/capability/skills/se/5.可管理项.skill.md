# 第05步 Skill：可管理项

[meta]

[description]
第05步：可管理项——按对象×状态列出权限/输入/输出/规则/通知，并标注双标签

[content]

## 一、理论

第04步确定了每个对象的状态机。第05步要回答：

**在每个状态下，具体要管什么？**

可管理项包含五个维度：

| 维度 | 含义 | 示例 |
|---|---|---|
| **权限** | 谁能操作 | 销售可编辑报价，经理可审批 |
| **输入** | 需要填什么 | 报价金额、折扣率、交付日期 |
| **输出** | 系统展示什么 | 报价单预览、历史报价对比 |
| **规则** | 有什么约束 | 折扣>10%需经理审批 |
| **通知** | 谁需要被通知 | 提交报价时通知经理 |

**为什么需要这一步：**

第04步只确定了"状态是什么"，没确定"每个状态下做什么"。没有可管理项，第10步的数据模型就不知道要设计哪些字段，第06步的权限矩阵也不知道要控制哪些操作。

**这一步的目标：**

对每个对象的每个状态，逐一明确权限、输入、输出、规则、通知。

## 二、LLM的思考框架

### 预判（问之前）

**根据第01步管理诉求和第04步状态机预判：**

| 输入 | 预判 |
|---|---|
| 商机有"方案报价"状态 | 需要管理：报价金额、折扣率、审批规则 |
| 合同有"审批中"状态 | 需要管理：审批人、审批意见、审批时限 |
| 回款有"已到账"状态 | 需要管理：到账金额、到账日期、核销状态 |
| 有折扣审批诉求 | 规则：折扣>10%需经理审批 |
| 有跟进记录诉求 | 输入：跟进方式、跟进内容、下次跟进时间 |
| 有消息通知诉求 | 通知：提交报价通知经理、审批通过通知销售 |

**预判的目的：** 准备好"如果用户说要管商机，我该提哪些可管理项"。

### 识别（问之中）

| 信号 | 用户说 | LLM判断 |
|---|---|---|
| 提到审批 | "报价要经理批" | 规则+权限+通知 |
| 提到字段 | "要记录竞争对手" | 输入：竞争对手字段 |
| 提到通知 | "审批完要告诉我" | 通知：审批通过通知销售 |
| 提到权限 | "只有经理能改折扣" | 权限：字段级权限 |
| 提到约束 | "报价不能低于成本" | 规则：报价金额>=成本价 |
| 提到展示 | "要看历史报价" | 输出：历史报价对比 |
| 提到自动化 | "金额自动算" | 规则：自动计算 |

### 兜底（用户答不出来时）

**场景1：用户说"不知道要管什么"**

> "没关系，我按标准可管理项给你列一遍。以商机'方案报价'状态为例：
>
> **权限：**
> - 销售可编辑报价，经理可审批，要吗？
> - 成本字段仅经理可见，要吗？
>
> **输入：**
> - 报价金额、折扣率，要吗？
> - 交付日期、付款条件，要吗？
> - 竞争对手信息，要吗？
>
> **输出：**
> - 报价单预览，要吗？
> - 历史报价对比，要吗？
>
> **规则：**
> - 折扣>10%需经理审批，要吗？
> - 报价金额不能低于成本价，要吗？
>
> **通知：**
> - 提交报价时通知经理，要吗？
> - 审批通过时通知销售，要吗？
>
> 你逐个看，哪些要？"

**用逐条确认的方式，代替开放式提问。**

**场景2：用户说"你觉得呢"**

> "以你们的业务（卖标准产品、有折扣审批），我建议商机'方案报价'状态下：
>
> **必做：**
> - 权限：销售可编辑，经理可审批
> - 输入：报价金额、折扣率
> - 规则：折扣>10%需经理审批
> - 通知：提交报价通知经理
>
> **建议做：**
> - 输入：交付日期、付款条件
> - 输出：报价单预览
> - 通知：审批通过通知销售
>
> **可以后做：**
> - 输出：历史报价对比
> - 输入：竞争对手信息
>
> 你觉得呢？"

### 纠偏（用户答得不对时）

**场景1：用户说"什么都要管"**

> "每个状态都管太多，会导致：
> - 销售录入负担重，不愿意用
> - 界面复杂，找不到重点
> - 开发量大，上线慢
>
> 建议分优先级：
> - 必做：不做系统不成立
> - 建议做：不做效率低，但能忍
> - 可以后做：有了更好，没有也行
>
> 你看哪些是必做的？"

**场景2：用户说"不需要通知"**

> "不需要通知的话，审批完销售怎么知道？"
> - 如果答"销售自己看" → 销售可能几天都不看
> - 如果答"经理口头说" → 系统里没有留痕
>
> 建议：至少做站内信通知，成本低，效果好。你觉得呢？"

**场景3：用户说"规则硬编码就行"**

> "硬编码的话，以后规则变了怎么办？"
> - 如果答"找开发改" → 每次改都要开发，周期长
> - 如果答"那就配置" → 进入第07步配置项
>
> 建议：经常变的规则做配置，不常变的硬编码。你觉得哪些规则会经常变？"

### 映射（回答之后）

| 本步骤产出 | 映射到 |
|---|---|
| 权限 | 第06步权限矩阵 |
| 输入字段 | 第10步数据模型 |
| 输出展示 | 第10步数据模型、第11步界面设计 |
| 业务规则 | 第07步配置项（哪些规则可配置） |
| 通知 | 第09步通知渠道、第11步消息可靠性 |
